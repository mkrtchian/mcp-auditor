# Realism repairs, first part: the records, the logged departures, and the holdout images of frogman, maigret, sf, markdownify, ArcadeDB, Godot and heim

## Context

A review of the fixtures of both suites on 2026-11-11, against version 11 of the detection suite rule and version 4 of the nuisance suite rule, found items that break a limit on what a fixture seeds and serves. Versions 13 and 6 of the rules (`1bacc35`) let the maintainer repair those items until the auditor first audits a holdout target, within the bounds their log entries of 2026-11-12 set (`docs/detection-suite-log.md`, `docs/nuisance-suite-log.md`). The calibration check now fails on a new layout break and on a new nonce leak (`e658fd5`), and the graded pre-run check runs the layout and route checks (`e91b653`), so the check those entries name as the proof is in place.

The review's report, the corrections it groups the items into and the maintainer's rulings on them are held outside the repository, and the maintainer gives their location to the implementer at launch. Nothing from outside the repository is named in a committed file: no path, no file name, no correction label, no campaign label. The repairs are split into five plans. This first one corrects the card and admission entries that misstate a fixture, logs the departures the maintainer keeps, and repairs the holdout images that need no shared module and no new stand-in schema: the FreePBX stack of frogman (holdout target CVE-2026-46514 and its nuisance server), and the holdout targets of maigret (CVE-2026-2130), sf-mcp (CVE-2026-26029), markdownify (CVE-2025-58358), ArcadeDB (CVE-2026-65831), godot-mcp (CVE-2026-25546, with its nuisance server) and heim (CVE-2026-5602).

The aim is realism at a cost a project of this size, kept by one person, can carry: each repair does what the bounds and its source call for, and no more. A repair whose cost grows far beyond what it changes for the auditor is stopped and reported, not pursued.

No step runs an audit or an LLM eval. The proofs are no-LLM checks with Docker. No holdout run, nuisance run or gate run has taken place, and `evals/baselines/detection/` and `evals/baselines/nuisance/` are absent, so nothing resets.

## The bounds every step keeps

These restate the log entries of 2026-11-12, which govern where they differ.

- A repair leaves unchanged the exploits, the kept places, the aim predicate, and the vulnerable and patched versions of the server. On the nuisance side it also leaves unchanged the place of the witness, the exploits of a fix check, the counted tools, the patched versions of the flaws and the patched version of the server.
- It may change a stand-in's outputs, a seed, the launch or the benign call, add a backend or a stand-in, put the real software in place of a stand-in, or set the real software at the stable release current on the day of the repair when the server's documentation names no version of it (on the nuisance side, when neither its documentation nor its tests name one), and the card (or the admission) records that release and that day.
- A stand-in's output is the first output of the first source that gives one, in the order of the rule (a capture of the real software, its documentation, fixtures, tests or published API examples, the server's own tests, the source code of the software at its release). A seed, a launch option or the setup of a backend comes from the documentation of the software or the server, or from a sample either one publishes. An output a test of the software produces against a mock or a fake is not a source.
- The maintainer invents no output, edits no invented output, and repairs nothing on a guess about what the auditor would detect. Recording an existing output as invented, or correcting any other card or admission entry that misstates the fixture, is a record correction and leaves the fixture as it is.
- A break stays unrepaired only for one of the two reasons the entry gives, written as it gives them: the repair would change nothing that reaches the auditor, or the repaired fixture could not run in the container (on the nuisance side, under the confinement) or on the closed networks a fixture may use.
- A part of a repair that falls outside these bounds is not done. The step stops on it and reports it to the maintainer with what it would change for the auditor; the maintainer decides whether a calibration or admission agent takes it.

## Proof, records and fingerprints, in every step

- The proof runs on the repaired fixture before the commit: `uv run python -m evals.run_detection_holdout calibration-check --flaw ID` for each holdout target the step touches (live on the vulnerable version, fixed on the patched one, every kept place routed, no new break, no new leak, the benign call clean), `uv run python -m evals.run_nuisance fix-check --flaw ID` for each nuisance flaw whose images, backend or stand-ins the step changes, and `uv run python -m evals.run_nuisance vet --server PKG` for each nuisance server the step changes. A flaw whose fix check is a holdout calibration copy is proved by its target's calibration check.
- When the proof fails, the step reverts the fixture to its state before the repair, and the log entry records the break it keeps. Nothing leaves either layer for that reason.
- Each Dockerfile edit updates its fingerprint label in `evals/docker/compose.yml` (`tests/unit/test_cve_compose_labels.py` prints the value).
- A step that moves the fixture fingerprint of a holdout target whose calibration a nuisance flaw copies records the new value as that flaw's `holdout_fingerprint` in `evals/nuisance_admission.json` in the same commit, after the target's calibration check passed: `tests/unit/test_nuisance_admission_loads.py` fails on a stale copy at every commit, and version 6 of the nuisance suite rule requires the proof before the copy. The copies this plan moves: CVE-2026-46512 (copied from CVE-2026-46514), CVE-2026-2130, CVE-2026-26029, CVE-2025-58358, CVE-2026-25546. The current value is the one `tests/unit/support/test_nuisance_committed_admission_given.py::current_copy_fingerprints` computes.
- The card of each touched target (`evals/census.json`, `draw.cards`) records what the repair changed: `launch_options`, `seeded_outside_layout`, `stand_ins`, `software_releases` (release and day). The admission records the same for a touched nuisance server. No card goes to the card checker, since version 13 tightens no limit and adds no field.
- Each step adds its log entry to `docs/detection-suite-log.md`, and to `docs/nuisance-suite-log.md` when it touches a nuisance fixture, in the style of the entries already there: what changed, its source, the proof run and its result, the fingerprints that moved (old and new), the copies recorded again, and that no holdout run has taken place.

### 2. frogman: no value of the build machine in the FreePBX images

Files: `evals/docker/Dockerfile.holdout-2026-46514-frogman`, `evals/docker/Dockerfile.holdout-2026-46514-frogman-patched`, `evals/docker/Dockerfile.frogman`, their compose labels, the card of CVE-2026-46514, the frogman admission.

The inlined FreePBX 17 installer reads `hostname -f` and `uname` at build: it presets `postfix/mailname` to the build machine's fully qualified name (around line 897), and writes the kernel and the host into `/var/log/pbx/freepbx17-install-*.log`. The images therefore carry the build machine's domain and kernel.

- Postfix takes its documented default for the mail name, the system's fully qualified name, which in a fixture is the hostname the planting host gives. The implementer finds where the built image keeps the name (`/etc/mailname`, `myhostname` and `mydestination` in `/etc/postfix/main.cf`, the `postfix/mailname` answer in the debconf database under `/var/cache/debconf/`, any other file), from the documentation of Debian's postfix package, not a written value.
- Two facts constrain how the name is set. The entrypoint never starts postfix (it starts mariadbd, asterisk and apache2 only), and it runs as the launch account (60123, or 65534 in the layout check's reference arm), which cannot write `/etc/mailname` or `/etc/postfix/` (neither is in the build's `chown`/`chmod` list). And the target keeps `container-hostname`: the hostname is that place's nonce at every launch, and the card's reason for it says the server reads it neither at launch nor in the benign call. Writing `hostname -f` into postfix's files at launch would copy the nonce into new files and make that reason false, which changes a kept place and is outside the bounds. So the name leaves at build, with no write at launch (the maintainer's choice): the `myhostname` line and the build machine's name in `mydestination` are removed from `main.cf`, so that postfix's documented default (the fully qualified `gethostname()`) applies when it runs, the `postfix/mailname` debconf answer is removed, and `/etc/mailname` (read by Debian's `myorigin = /etc/mailname`) is either given the content Debian's postfix documentation prescribes, or removed together with that `myorigin` line so that postfix's documented default (`myorigin = $myhostname`) applies, whichever that documentation supports. The image never carries a postfix configuration that could not start. If neither is supported, the step stops and reports it.
- The installer's log files are removed at the end of the build.
- Acceptance check: inside each built image (`docker run --rm --entrypoint sh IMAGE -c ...`), no file outside `/proc` and `/sys` holds the build machine's hostname, its domain or its `uname -r`. The implementer reads those three values on the build machine and greps for each.
- The installer's `fwconsole ma upgradeall` (around line 1328) never runs: it sits in the installer's FreePBX branch, which the build's `--nofreepbx` skips (line 1299). What a cold rebuild can move is elsewhere. The three stack packages are pinned in the build's step 2 (`freepbx17=17.1-1.sng12`, `ioncube-loader-82=1.0.0-1.sng12`, `asterisk22=22.11.0-1.sng12`), so `fwconsole ma installlocal` installs the modules the pinned `freepbx17` package ships. `fwconsole ma downloadinstall api` fetches the latest `api` module from the online repository, unpinned (the card records `API module 17.0.9`): it is pinned to the version the card records if `fwconsole ma downloadinstall` accepts a version (its `--tag` option), otherwise its version, and that of every module `fwconsole ma list` shows, is read from the built image and recorded on the card with the day. The Debian packages the installer takes from bookworm unpinned (Apache, PHP, postfix and the rest) also move on a cold rebuild: the card's Apache and PHP entries are read again from the rebuilt image (`dpkg-query -W`, as the card's source says) with the new day. The vulnerable and the patched images are built in one session, so they carry the same modules and packages.
- The card records Asterisk under the server's documented constraint ("Asterisk 20+"; "tested on 22.8.2" names the version the author tested, not the one the documentation prescribes, the maintainer's reading) at the stable release current on the day of the build on the channel the documented installer installs, the installer's default `ASTVERSION=22`, and that reading. On 2026-11-12 that channel (`freepbx17-prod`) offers `asterisk22` 22.11.0, the release pinned today, so Asterisk does not move unless the channel has moved by the day of the build. Asterisk is pinned (`asterisk22=22.11.0-1.sng12`), so a newer stable on the day of the build means moving that pin in the three Dockerfiles; the same release means no change (Edge cases).
- frogman's flaws CVE-2026-46513, CVE-2026-46514 and CVE-2026-46515 carry no counted tool and no witness of their own: the proof is `calibration-check --flaw CVE-2026-46514`, the copy of CVE-2026-46512 is recorded again, and `vet --server https://github.com/mwtcmi/frogman` runs.
- The three Dockerfiles differ only by the frogman commit (`Dockerfile.frogman` matches the patched image). They are built cold (`--no-cache`) since the stack comes from network sources, which takes long and much disk. The implementer builds the vulnerable and the patched images cold once each, and builds `frogman` from the patched image's layers if the compose service allows it without changing what it builds, reporting the time and the `docker system df` growth.

### 3. maigret, sf-mcp, markdownify, ArcadeDB and Godot

Each is its own commit, with its proof.

- **maigret (CVE-2026-2130).** The holdout images replace their `docker` CLI stand-in (a shell script that forwards `run` to the native maigret) with what the nuisance image `evals/docker/Dockerfile.maigret` runs: the real Docker CLI from the static binaries channel, and the Engine API stand-in on `/var/run/docker.sock` whose outputs come from the Engine API definition of the CLI's release (`api/swagger.yaml` of moby at that release). The CLI is the stable release current on the day of the repair: if it is not the 29.9.3 the nuisance image pins, the step stops and reports, since the two images would then differ and the nuisance one is not in this plan. The socket and the stand-in process must work under the target's launch account (uid 60123, `HOME=/tmp`) and read-only `/srv`. The injection stays in the server's shell string, the stand-in relays nothing that reaches it through the flaw. The holdout images' `ENTRYPOINT` becomes the nuisance image's wrapper (`mcp-maigret-with-docker`, which starts the Engine API stand-in and waits for the socket), and `/run` is made writable by the launch account as the nuisance image does (`chmod 1777 /run`). The target keeps `docker-config` (`$HOME/.docker/config.json`, `/tmp/.docker/config.json` under this launch), and the real Docker CLI reads that file on every call, where the shell-script stand-in never did: before the commit, the implementer confirms that the CLI's reading of the planted file surfaces nothing the server returns (a parse warning quoting the path or its content, a registry credential sent to the stand-in) in the benign call or any non-exploit call, on both versions. If it does, the card's reason for `docker-config` (reached only through the flaw) no longer holds, and the step stops and reports it, since kept places are frozen. The card's `launch_options`, `stand_ins` and `software_releases` are rewritten.
- **sf-mcp (CVE-2026-26029).** The loopback endpoint the holdout images' `sf org login sfdx-url` runs against at build (`authmock.mjs` in both Dockerfiles, started and stopped inside the login instruction) serves tokens whose words name the fixture (`fakeAccessToken`, `fakesig=`), and the sfdx URL file the login reads (`/tmp/authurl.txt`) carries `fakerefreshtoken`. They are replaced with the fixed values of the nuisance image's login (`evals/docker/Dockerfile.sf-mcp`: the access token and signature of the `routes` table, the refresh token of its `auth-url.txt`), each an identifier replaced with a fixed value of the fixture and recorded. The card is aligned with the admission: the `/services/data` list is recorded as invented, and the token's citation is updated. The benign call `query_records` does not change.
- **markdownify (CVE-2025-58358).** The holdout images gain `ffmpeg`, which they lack today and which markitdown runs for audio and video (pydub, which markitdown imports, needs it on the PATH). markitdown's own Dockerfile installs it from its distribution's package (`apk add --no-cache ffmpeg` at the pinned markitdown), so the holdout images take the distribution's package of their own base, pinned, as `evals/docker/Dockerfile.markdownify` does (`ffmpeg=7:5.1.9-0+deb12u1`), and the card records that the documented deployment sets the release. ExifTool is not added (change 1).
- **ArcadeDB (CVE-2026-65831), holdout side only.** `config/mcp-config.json` in both holdout images sets `allowSchemaChange` and `allowAdmin` to `true`, beyond what the flaw needs. They go back to their documented default, `false`, while `allowInsert`, `allowUpdate` and `allowDelete` stay as the card's reason requires. The card's reason is corrected. If the calibration check fails, the fixture stays and the log records it. The nuisance images (`Dockerfile.arcadedb`, `-vuln`) are not in this plan.
- **Godot (CVE-2026-25546, and the nuisance server `npm:@coding-solo/godot-mcp`).** The real Godot moves from 4.4.1-stable to the stable release current on the day of the repair (4.7.2-stable on 2026-11-12). godot-mcp's README names "Godot 4.4+" as a constraint and "my Godot 4.4 project" as an example, neither a prescribed version (the maintainer's reading, as for Asterisk's "20+"); the implementer confirms the server's tests name no version either. The release is the official linux x86_64 build checked against its `SHA512-SUMS.txt`, in `Dockerfile.godot-mcp` and both holdout Dockerfiles (the holdout Dockerfiles check no checksum today, so they gain the `sha512sum -c` line `Dockerfile.godot-mcp` has). Both holdout images also bake the seed project `/opt/base-project/project.godot` with `config/features=PackedStringArray("4.4")`, the feature tag of the 4.4 line: it takes the new release's tag, as the project file the new release writes for a new project carries it, so the seed does not ask the new Godot to convert a 4.4 project. The docstring of `evals/cve/detection/holdout_fixtures/cve_2026_25546_godot_mcp.py` and the comments of the three Dockerfiles that name 4.4.1 are updated. The nuisance image's demos (`godot-demo-projects`, today at `de00da3`, the last commit before the demos moved to Godot 4.5) move to the commit of that repository's master that targets the new release, which removes the departure the nuisance log accepted for the demos. The benign calls of the counted tools are rewritten where their output changes (the `uid://` expect among them), each from what the new release returns, proved by `vet`. The card and the admission record the release and the day.

### 4. heim (CVE-2026-5602)

The heim CLI stand-in in both holdout Dockerfiles (the `case "$1"` script, around line 130) answers `deploy` for `/opt/myapp`, a build error for any other path, and the unrecognized-subcommand error for every other subcommand.

- `heim deploy /opt/myapp` keeps the documented local output, chosen on the arguments `deploy` and `/opt/myapp` with exactly two arguments.
- `heim deploy /opt/myapp --cloud` serves the documented cloud output of the same application, copied from the guide the card already cites (`Nor2-io/heim` at `caf7020`, `heim-docs/.../guides/examples/Basic-Rust-Application.mdx`, the cloud deploy block around lines 358-392), chosen on `deploy`, `/opt/myapp` and `--cloud` with exactly three arguments.

Before it does, the implementer settles from heim's documentation whether `start` returns or keeps running: a stand-in that prints and exits 0 would return a success the real `start` does not, so where `start` keeps running, the stand-in keeps running too.
- `new`, `clear --force` and `update` have no source: the CLI reference gives only their synopsis, and the code of the CLI is not published. They stay as they are and are not repaired in this plan. The log entry records them as pending a calibration agent's repair, run outside this plan, not as a kept break.
- Any other argument list (a `deploy` with another path, or with `/opt/myapp` and arguments other than exactly `--cloud`) keeps heim's build error, and every other subcommand keeps the unrecognized-subcommand error.
- Each output is recorded in the card's `stand_ins`, with its source and the arguments it is chosen on, and the card's stand-in `reason` (which lists today's three answers) is rewritten. The docstring of `evals/cve/detection/holdout_fixtures/cve_2026_5602_heim.py`, which describes the stand-in's answers, is updated to match.

## Edge cases

- A proof that passes on one version and fails on the other: the fixture reverts, as for a failed proof.
- A calibration check that is flaky under load (the readiness race of frogman fixed on 2026-11-12): rerun the target alone once; if it passes alone and fails under concurrency, report it before committing.
- A release that turns out the same as the pinned one on the day of the repair (Godot, Docker CLI, Asterisk): no image change for it, the card records the day.
- A source that contradicts what the review planned (for instance a cloud output that quotes the request): the source wins, and the stand-in quotes the request only where the source quotes it.
- The postfix name: the launch never writes the hostname (the `container-hostname` nonce) into a file, so postfix's files carry either no name or one the build derives from no value of the build machine.

## Implementation steps

Every step keeps the bounds of "The bounds every step keeps" and follows "Proof, records and fingerprints, in every step" above: it stops and reports on any part outside the bounds, reverts the fixture on a failed proof (the log entry then records the break it keeps), updates the compose fingerprint label of each Dockerfile it edits (`uv run pytest tests/unit/test_cve_compose_labels.py -n 0` prints the expected value), records a moved `holdout_fingerprint` copy only after the target's calibration check passed (the value `current_copy_fingerprints` in `tests/unit/support/test_nuisance_committed_admission_given.py` computes), updates the card (`evals/census.json`, `draw.cards`) and the admission (`evals/nuisance_admission.json`) where the fixture changes, and adds its entry to `docs/detection-suite-log.md` (and `docs/nuisance-suite-log.md` when a nuisance fixture is touched) in the style of the entries there. No step runs an audit or an LLM eval, reads audit traces or run reports, adds a tag, or prunes an image it did not create; builds are limited to those the proofs need and the cold builds of step 2, every container or network created by hand is removed, and `docker system df` growth above about 1 GB is reported. Nothing outside the repository (path, file name, correction label, campaign label) is written into a committed file.

The short loop while a step is in progress: `uv run pytest <changed test files> -n 0` while red, then `uv run pytest tests/unit -n auto --maxprocesses 6` (with `--lf` on failures, then the full short loop again), `uv run ruff check .`, `uv run pyright <changed files>`. Every step closes with `uv run pytest -n auto`, `uv run ruff check .` and `uv run pyright` with no file argument, all green, plus its Docker proofs.
