# Realism repairs, fourth part: real backends for GitLab, Atlassian, Doris, Kubernetes, CKAN, httpbin and the node sandbox, the Jenkins plugins, the mcp-ssh samples, ExifTool and the acceptance layer

## Context

The first three parts (`plans/2026-11-12_realism-repairs-holdout-images.md`, `plans/2026-11-12_realism-repairs-nuisance-images.md`, `plans/2026-11-12_realism-repairs-stand-ins.md`) corrected records, repaired holdout and nuisance images, and repaired the stand-ins both suites share. This fourth part repairs what sits behind the servers: it puts the real software in place of a stand-in or a responder where the software runs within the bounds (GitLab CE, Jira and Confluence, Kubernetes, CKAN for the holdout target, httpbin, the Docker Engine stand-in moved out of the server's container), brings Doris to the release and process layout its quick start documents, completes the Jenkins controller with its suggested plugins, seeds mcp-ssh from its README's sample, removes ExifTool from the markdownify run image, and repairs the acceptance targets where the holdout limits find a break. A fifth part, on Android, follows.

The aim is realism at a cost a project of this size, kept by one person, can carry: each repair does what the bounds and its source call for, and no more. A repair whose cost grows far beyond what it changes for the auditor is stopped and reported, not pursued.

This part starts once the third part is committed (it is, up to `0a545d0`). It assumes from it only what that part's log entries record: the keyed stand-in routes exist, the fixture authority was regenerated once and still lists `45.55.0.10`, the facebook-ads leaf and the HealthOmics captures are committed, and the 17 `holdout_fingerprint` copies are current at its final tree. All four parts edit `evals/nuisance_admission.json`, `evals/census.json`, `evals/docker/compose.yml` and the two suite logs.

The maintainer's rulings for this part are held outside the repository, and the maintainer gives their location to the implementer at launch. Nothing from outside the repository is named in a committed file: no path, no file name, no review label. An earlier admission record that ran GitLab CE is cited as "an earlier admission record", never by its location.

No step runs an audit or an LLM eval. The proofs are no-LLM checks with Docker, and the two measurement spikes are Docker runs outside the repository. ### Departures from the bounds, logged

The bounds are those of the version 13 entry of `docs/detection-suite-log.md` and the version 6 entry of `docs/nuisance-suite-log.md`. Four repairs of this part fall outside their letter in a way the rule itself dictates. They are done, and the log entry of each records the departure with its justification. These four are the only ones.

- **The Doris front end's heap is set below its documented default.** The 4.1.5 `fe.conf` sets `-Xmx8192m -Xms8192m`, and `start_fe.sh` reads that file after the environment, so no variable overrides it. An 8 GB heap cannot run under the 4 GB bound of a nuisance backend container. The heap takes 1024 MB, the `FE_HEAP` default Apache Doris documents for the multi-node mode of its own image, the published shape closest to a separate front end and back end (its single-container mode ships 2048 MB, a shape this fixture leaves). Justification: the bound is a rule's limit, the documented value cannot run under it, and the replacement value is Doris's own for the nearest documented shape, so nothing is chosen. If the front end cannot serve the benign calls at 1024 MB, the step stops and reports the measured peak, and does not move to 2048 MB on its own.
- **The mcp-ssh holdout seeds are root-owned and mode 0644, where the README's section 4 sets the key to 600.** A holdout launch runs the server under an account named after a nonce (uid 60123) and the layout check's reference arm under 65534, so a key owned by one of them is unreadable by the other, and OpenSSH refuses a user configuration owned by neither root nor the caller. OpenSSH's own permission check on a private key fires only when the caller owns the file. Justification: the mode follows from the launch the rule fixes, and the content of every seed still comes from the README.
- **CVE-2025-53109 keeps its seeded link, an acceptance-only departure.** The detection suite rule forbids a seeded link to a kept place ("nothing seeded or served names, links to or otherwise leads to a place the target keeps") and takes the link of a published mechanism from the arguments of an exploit call, and server-filesystem has no tool that creates a symlink. Under the holdout limits the target would keep nothing and leave the layer. The acceptance layer is the dev set the auditor is tuned on, never a published number, and the link keeps the target's value as a regression guard for following a symlink out of scope. The word the rule lists by name (`leak`) leaves the seeded names. Justification: the departure binds no holdout number, and the log says so.
- **The CKAN sample's free text is seeded through Faker's documented seed, outside CKAN's tooling.** `ckan generate fake-data` has no seed option, and its factories draw titles, descriptions and image URLs from an unseeded module-level `Faker()`. Faker's README ("Seeding the Generator") documents `Faker.seed()`, and the value its example gives (4321) is used. Identifiers and timestamps CKAN generates at each load stay unfixed, logged as a limit.

### Readings logged

These are the maintainer's readings of the rules for this part. Each is written in the log entry of the change it governs.

- **A backend is bound by the memory bound only.** The nuisance suite rule's Stand-ins paragraph runs the real software "in the container whenever it can run under the confinement the suite launches the server with, or else as a backend within the memory bound of that confinement". A backend container therefore takes `--memory 4g --memory-swap 4g` (`memory_bound_args()`), and not necessarily the server's dropped capabilities, as the Doris cluster already runs (`doris_cluster_run_args`). The version 6 entry's "The repaired fixture runs under the confinement" reads with that paragraph: the server runs under the confinement, its backend within the bound. GitLab CE and the Atlassian products, whose images start as root and switch users, run on that reading. A backend that needs no capability keeps `nuisance_confinement_args()`.
- **A backend runs with the strictest options it tolerates.** The reading above says what the rule requires of a backend, not what keeps the machine that runs the suite safe. So every backend container this plan adds or changes (GitLab CE, Jira, Confluence and their PostgreSQL, the Doris front end and back end, the Kubernetes control plane, the httpbin parts, the sshd, the node sandbox engine) runs with `--security-opt no-new-privileges`, `--cap-drop ALL` plus only the capabilities its measured start and benign calls need (typically among `CHOWN`, `SETUID`, `SETGID`, `DAC_OVERRIDE`, `FOWNER`), and a finite `--pids-limit` sized from its measured peak with a wide margin (of the order of 4096 for the JVM and Rails products), beside the memory bound. Neither rule forbids these options: they are not values passed to the server, nor a seed, nor an answer the backend serves, and the rules ask of a backend only that it run within the memory bound. They are kept only where they change nothing the backend answers: a capability or limit whose absence makes the start or any benign call fail or answer differently is added back, since a hardened backend that errors would return a failure the real deployment does not. The admission (and the card on the detection side) records each backend's options and the reason for each capability kept, and the log entry of each change states them. A backend that needs no capability keeps `nuisance_confinement_args()` as today.
- **The release of Doris is the GitHub release, not the Hub's `latest` tag.** On 2026-11-13 GitHub lists `4.1.5-release` (2026-10-15) as the latest release, while the Hub's `fe-latest` and `be-latest` still point at 4.1.4.1. The stable release current on the day is the released one.
- **The Kubernetes release is the current stable, and etcd the one Kubernetes names.** kubectl-mcp-server's documentation names no cluster distribution or version, so the control plane is upstream Kubernetes at `https://dl.k8s.io/release/stable.txt` on the day (v1.37.2 on 2026-11-13, the version the kubectl of the images already carries), and etcd is the version `build/dependencies.yaml` of that Kubernetes release names (3.7.0 at v1.37.2, also kubeadm's `DefaultEtcdVersion`).
- **httpbin is its repository's head commit.** postmanlabs/httpbin publishes no release and no image, and its README says the repository is what runs at httpbin.org and is to be built from source. The head commit on the day of the repair is that release, pinned by commit and recorded with the day.
- **Atlassian's setup wizards are driven by their own form posts.** Jira and Confluence document their setup as a browser wizard, and the server's e2e README leaves it manual. Posting the wizard's documented forms with curl at stand-up sets the instance up as the documentation describes, with no person and no undocumented endpoint. The licenses are Atlassian's published Data Center timebomb licenses, which need no account, so the admission's reason for a stand-in ("A license needs an Atlassian account") is false and is corrected whatever the outcome.
- **The Jenkins sample stays the freestyle `MyJob`.** The suggested plugins bring Pipeline (`workflow-aggregator`), which does not replace the documented freestyle sample the seed already follows.
- **ExifTool follows markitdown's documented deployment.** markitdown's own Dockerfile at the locked 0.0.1a3 installs ffmpeg and no ExifTool, as the first part read it for ffmpeg, and the server's own Dockerfile installs neither. The settlement of 2026-11-08 that added ExifTool is reversed on that reading.
- **Kubernetes runs with no node.** kubelet needs a container runtime and privileges that the confinement does not give, so the control plane has no node: `get nodes` is empty and a created pod stays `Pending`. A limit the confinement sets, logged as a limit.
- **The heavy servers are played alone.** The servers whose backends hold about 4 GB or more in total are played after the others in `vet`, `run` and `gate`, one call at a time, as magento2 is. This is a scheduling choice that changes no run condition and nothing a run records.

### Why no rule version opens

Versions 13 and 6 let the maintainer repair fixtures until the auditor first audits a holdout target, and their bounds last only until then. A new rule version would bind the runs that follow that first audit, when no maintainer repair is allowed at all, so it would bound nothing these departures touch. The suite logs are where the version 13 and 6 entries put what a repair keeps or departs from, so the departures and readings are logged there.

## The bounds every step keeps

These restate the log entries of 2026-11-12, which govern where they differ, with the four departures above.

- A repair leaves unchanged the exploits, the kept places (apart from the removal of `kube-config` from the acceptance target CVE-2025-53355, change 7), the aim predicate, and the vulnerable and patched versions of the server. On the nuisance side it also leaves unchanged the place of the witness, the exploits of a fix check, the counted tools, the patched versions of the flaws and the patched version of the server.
- It may change a stand-in's outputs, a seed, the launch or the benign call, add a backend or a stand-in, put the real software in place of a stand-in, or set the real software at the stable release current on the day of the repair when the server's documentation names no version of it (on the nuisance side, when neither its documentation nor its tests name one), and the card (or the admission) records that release and that day.
- A seed, a launch option or the setup of a backend comes from the documentation of the software or the server, or from a sample either one publishes. A stand-in's output is the first output of the first source that gives one, in the order of the rule. An output a test of the software produces against a mock or a fake is not a source.
- The maintainer invents no output and edits no invented output. Recording an existing output as invented, or correcting any other card or admission entry that misstates the fixture, is a record correction and leaves the fixture as it is.
- A break stays unrepaired only for one of the two reasons the entry gives: the repair would change nothing that reaches the auditor, or the repaired fixture could not run in the container (on the nuisance side, under the confinement, and for a backend within the memory bound) or on the closed networks a fixture may use. Cost alone is never that reason, and a new backend or real software is not a constraint.
- A part of a repair that falls outside these bounds is not done. The step stops on it and reports it to the maintainer with what it would change for the auditor.

## Sequencing

The order is chosen to run the fewest proofs. The costly proof is the calibration check of all 37 holdout targets, with the 17 copies, which two changes force whatever their order: the retirement of the `45.55.0.10` capture, which requires the fixture authority regenerated without it (`tests/unit/test_committed_stand_ins.py` requires the authority's names to equal the captures and the leaves a backend serves), and the rename of the CVE-2025-53109 links in `evals/cve/environments.py`. So every change that moves a target with a copy lands in that one commit, whose full proof covers it, and every change that moves only one target with no copy lands after it, proved once on its own target at its final state. The nuisance-only changes land first, each with its own short proof, since none moves a detection fingerprint.

1. **The two spikes, before any repository change** (changes 5 and 6): GitLab CE and Atlassian are each stood by hand under the bound, and their outcomes decide the form of two later commits. They touch no file of the repository.
2. **Nuisance-only commits, lightest first, each its own proof**: ExifTool (change 9), the Jenkins plugins (change 10), the backend schema with the per-launch lifecycle and the node sandbox (changes 1 and 11, one commit, since the node sandbox is the lightest consumer of the per-launch lifecycle and proves it), httpbin (change 12), GitLab (change 5), Atlassian (change 6), then the solo list (change 2), which names the heavy servers once their outcome is known.
3. **The shared commit**: Doris (change 3), Kubernetes for CVE-2025-65719, the kubectl nuisance server and the acceptance target CVE-2025-53355 (change 7), the acceptance changes (change 8), and the regeneration of the authority without `45.55.0.10` (change 4). 4. **After the shared commit, each its own commit and proof**: mcp-ssh (change 13), which moves CVE-2025-9654 alone, then CKAN (change 14), which moves CVE-2026-33060 alone. The per-launch lifecycle. Every registered backend today is a singleton (`provisioner_of` ensures it once under its lock and reuses it across a server's concurrent runs). The node sandbox (change 11), Kubernetes (change 7), GitLab CE (change 5) and Atlassian (change 6) need a backend stood for one launch and removed with it, since the auditor's calls change their state. `evals/cve/backends/lifecycle.py` gains:

```python
type LaunchedServerArgs = Callable[
    [str, str, PlantingHost, Sequence[str]], AbstractContextManager[list[str]]
]  # (name, image, host, launch)


@dataclass(frozen=True)
class PerLaunchBackend:
    key: str
    launch: LaunchedServerArgs  # stands the backend, yields the server's docker run arguments
```

The context manager stands the backend for the server named `name`, yields the server's arguments (which may carry values only the stand-up knows, such as an Atlassian token or a generated kubeconfig), and removes the server and its backend at exit, even when the body raises. `RegisteredBackend.lifecycle` becomes `BackendLifecycle | PerLaunchBackend`, and `provisioner_of`, the kit's `lifecycle_of` and `backend_launch`, and `re_admission_docs._run_args` dispatch on the type with a `match`. The kit reads a lifecycle as `LIFECYCLE` of `evals.cve.backends.<key>`, so a per-launch backend's key is its module's name, as for the others. A per-launch backend has no `reset_containers`. Its registered `network` (which `backend_problems` compares with the admission, and the re-admission readme prints) names the prefix of the per-launch networks it creates, `none` for the node sandbox, which joins none. `tests/unit/test_backend_lifecycle.py::test_the_kit_backend_launch_is_the_provisioner_launch` keeps covering every registered key, per-launch ones included, and its tests that call `lifecycle_of(key).server_args` for every key keep to the `BackendLifecycle` keys.

If the code and the docs come to write "per-launch backend" as a term, it enters `docs/glossary.md` (beside **backend** and **provisioner**) after the implementer checks `docs/glossary-log.md` for it.

Tests, written first and run red, in `tests/unit/test_backend_lifecycle.py` (scenarios in its given file): a per-launch backend is stood on entry and its server arguments are the ones it yields, it is removed on exit and when the body raises, two concurrent launches of one server stand two backends, and the kit launch equals the provisioner launch for a per-launch key. In `tests/unit/test_nuisance_backend_registry.py`: a recorded fixture whose image list differs from the registered one is refused, and the run conditions carry one ID per image of a two-image backend.

Proof: the closing checks (no fixture moves in this part of the commit apart from the nuisance fingerprints of every backend server, whose backend fixture changes shape). The node sandbox's proof (change 11) exercises the per-launch path.
