# Realism repairs, third part: identifier-keyed stand-in routes, the stand-in captures, the facebook-ads certificate, a HealthOmics stand-in, the fixture authority and maigret

## Context

The first part (`plans/2026-11-12_realism-repairs-holdout-images.md`) corrected records, logged the departures the maintainer keeps and repaired holdout images that need no shared module. The second part (`plans/2026-11-12_realism-repairs-nuisance-images.md`) repaired nuisance images. This third part repairs what the stand-ins shared by both suites serve: the stand-in schema and the inlined server that serves it, the captures and written files of seven hosts, the certificate of the facebook-ads responder, a new set of stand-ins for the holdout target of the HealthOmics server (CVE-2026-15415), and the fixture authority, regenerated once for the new hosts. The aim is realism at a cost a project of this size, kept by one person, can carry: each repair does what the bounds and its source call for, and no more. A repair whose cost grows far beyond what it changes for the auditor is stopped and reported, not pursued.

This part starts once the second part is committed: all three edit `evals/nuisance_admission.json`, `evals/census.json`, `evals/docker/compose.yml` and the two suite logs.

No step runs an audit or an LLM eval. The proofs are no-LLM checks with Docker. No holdout run, nuisance run or gate run has taken place, and `evals/baselines/detection/` and `evals/baselines/nuisance/` are absent, so nothing resets.

### Three departures from the bounds, logged

The bounds are those of the version 13 entry of `docs/detection-suite-log.md` and the version 6 entry of `docs/nuisance-suite-log.md`. Three repairs of this part fall outside their letter in a way the rule itself dictates, with no latitude that could be fitted to the auditor. They are done, and the log entry of each records the departure with its justification. These three are the only ones.

- **The `docker-config` place of CVE-2026-2130 leaves the kept places (24 to 23).** With the real Docker CLI in the holdout images, the server reads `~/.docker/config.json` at launch (`docker --version` and `docker image inspect` in `ensureSetup`) and in the benign call, since every `docker` invocation loads that file. The rule does not keep a place that something other than the target reaches, the server at launch or a tool's own function (detection suite rule, the place criterion), and two precedents read "reaches" as "reads": `gh-hosts` for CVE-2025-53818 and `aws-credentials` for CVE-2026-4270. Justification: the removal applies the rule's own criterion to the repaired fixture, and the bound that freezes the kept places exists so that no one chooses places with knowledge of the auditor, and nothing is chosen here. A repair never adds a place.
- **The `etc-hosts` place of CVE-2026-15415 leaves the kept places (21 to 20).** A stand-in, which the bounds allow the maintainer to add, is resolved through the entries the holder writes in `/etc/hosts`, while a kept `etc-hosts` mounts the nonce file over that same file. The two cannot coexist, so the place goes, as the calibration of CVE-2026-2130 on 2026-11-06 dropped `etc-hosts` for the same launch conflict. Justification: the removal is the mechanical consequence of a repair the bounds allow, nothing is chosen, and a repair never adds a place.
- **Errors with no source beyond their documented name and status.** The maintainer writes an output reduced to what documentation fixes (the error code, the HTTP status, the protocol's documented error envelope), with no text the documentation does not give, and records it as invented. Justification: the only latitude an agent would add is free text, and there is none. It applies to Secrets Manager `ResourceNotFoundException` for an unknown `SecretId`, RDS `DBClusterNotFoundFault` for an unknown `DBClusterIdentifier`, the HealthOmics errors, and a GraphQL error for an unknown issue number on `api.github.com`, the last only if the GraphQL specification's error envelope, with nothing specific to GitHub, makes a complete error (change 7).

### Why no rule version opens

Versions 13 and 6 let the maintainer repair fixtures until the auditor first audits a holdout target, and their bounds last only until then. A new rule version would bind the runs that follow the first holdout audit, when no maintainer repair is allowed at all, so it would bound nothing these departures touch. The suite logs are where the version 13 and 6 entries put what a repair keeps or departs from, so the three departures are logged there.

The keyed routes need no rule change either. The detection suite rule says a stand-in "chooses its answer only on fixed words at fixed positions of the request" (`docs/detection-suite-rule.md`, What a fixture seeds and serves), and the nuisance suite rule that it "branches only on fixed words at fixed positions of the request" (`docs/nuisance-suite-rule.md`, Stand-ins). The value of an identifier at a fixed position of the request is such a word. The narrowing to "never on its value" is written only in the module docstring of `evals/cve/public_stand_ins.py`, which changes with the schema, as does the header comment of `evals/docker/Dockerfile.stand-in`, which describes the lookup.

## Changes

### 1. Identifier-keyed routes: the schema and the inlined server

Files: `evals/cve/public_stand_ins.py`, `evals/docker/Dockerfile.stand-in` and its label, `tests/unit/test_cve_public_stand_ins.py` with `tests/unit/support/test_cve_public_stand_ins_given.py`, `tests/integration/test_cve_planting_stand_ins.py` with `tests/integration/support/test_cve_planting_stand_ins_given.py`, `CLAUDE.md` (the capture command's line), `CHANGELOG.md`, `docs/glossary.md` and `docs/glossary-log.md`, `docs/labeling-log.md`.

A route may be keyed on the value of one identifier at a fixed position of the request, from a closed set of three locations: a field of an `application/x-www-form-urlencoded` body (the AWS query protocol), a top-level member of a JSON body (the AWS JSON protocols, which `X-Amz-Target` names), and a member of the `variables` object of a GraphQL request. A path identifier needs no key, since a route already matches its exact request target. The key and the action are separate fields, and every keyed route carries an action.

The model, in `evals/cve/public_stand_ins.py`:

```python
class RouteIdentifier(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    location: Literal["form", "json_member", "graphql_variable"]
    name: str = Field(min_length=1)
    value: StrictStr | StrictInt
```

`StandInRoute` gains `identifier: RouteIdentifier | None = None`. Its validators:

- An identifier keys a route that carries an action, so an identifier with no action is refused, as an action on a method other than `POST` already is. An identifier with a `form_field` is refused by the existing rule that an action and a form field are never on one route.
- A `form` identifier's value is a string (a form carries text). A `graphql_variable` identifier may be a string or an integer, since GraphQL's `Int` arrives as a JSON number (gh sends `number` as one). Booleans are refused by the strict types.

`StandInCapture` gains two validators, and its key check widens:

- `_one_route_per_key` keys on `(scheme, method, request_target, action, form_field, identifier)`.
- Every keyed route has its error route: a route of the same scheme, method, request target and action with no identifier. A keyed action without one is refused at load, since a request naming another value would otherwise fall through to the action-less route or the default, an answer the real service does not give to a known action.
- The keyed routes of one action share one location and one name, so the stand-in reads one identifier per action and never has to choose between two.

The inlined server in `Dockerfile.stand-in` keeps its route table for routes with no identifier, and builds a second list of keyed routes, since a keyed route and its error route share the five-part key the table uses today and the error route would otherwise be overwritten. For a request whose action is not `None`, it looks up, in order:

1. the first keyed route of `(scheme, method, target, action)` whose identifier's value equals the request's value at that location, read by `value_at(identifier, headers, body)`, the route's identifier carrying the location and the name, so the helper keeps to three arguments (`CLAUDE.md`, Coding standards): for `form`, `parse_qs(body)[name][0]` when the media type is the form one, for `json_member`, the member `name` of the body parsed as JSON whatever its media type (botocore sends `application/x-amz-json-1.1`), when the body is a JSON object, and for `graphql_variable`, `json.loads(body)["variables"][name]` when `variables` is an object. A missing body, field or member, or an unparsable body, gives no value. Equality is exact and typed (`type(a) is type(b) and a == b`), so the string `"1"` does not match the integer `1`.
2. the route of `(scheme, method, target, action)` with no identifier and no form field, which is the error route of a keyed action, or the action's only route when it is not keyed.
3. the form field route, the field-less route, the `GET` route for a `HEAD`, and the default, as today.

A keyed action's error route is therefore what a request with another value, or with no value, gets. Exact matching is stricter than AWS, which takes identifiers in any case and also as an ARN (RDS `DBClusterIdentifier`, Secrets Manager `SecretId`): each log entry that keys an AWS action records it as a limit. The Dockerfile's header comment and the module docstring describe the identifier, and the docstring drops "never on its value" (the Dockerfile's comment does not carry it). The inline source grows by about a dozen lines and stays one `ENTRYPOINT` string, since the fingerprint hashes instructions only.

The capture command records no identifier: keyed routes are written by hand, as action routes are. `evals/capture_stand_in.py` needs no change for this, and `evals/cve/planting_stand_ins.py` none either, since it mounts the capture text verbatim. The calibration dossier (`copy_kit_sources` in `evals/cve/detection/calibration_dossier.py`) and the nuisance dossier (`evals/cve/nuisance/dossier.py`) copy `Dockerfile.stand-in`, `evals/stand_ins/` and the loader's import closure, so the kits follow without a change: the implementer confirms it with `tests/unit/test_detection_calibration_dossier.py`, `tests/unit/test_nuisance_dossier.py` and `tests/unit/test_kit_isolation.py`, and reads `evals/cve/nuisance/re_admission_docs.py`, whose prose on captures is restated if it says a route never branches on a value.

Living docs: the capture command's line in `CLAUDE.md` ("a route carries an action or a form field, never both, and two routes ... are refused at load") states that a route with an action may also carry an identifier (`form`, `json_member` or `graphql_variable`, a name and a value), that a keyed action needs its error route, and that the key includes the identifier. `CHANGELOG.md` `[Unreleased]` gets one line. `docs/glossary.md` gets a **keyed route** entry (a stand-in route chosen on the value of one identifier at a fixed position of the request, beside its action's error route for every other value) and an **error route** entry (the route of a keyed action with no identifier, which answers every other value and a request with none), since `CLAUDE.md` and the log entries write both terms, after the implementer checks `docs/glossary-log.md` for the two words. The labeling log entry gives the four questions, the fingerprints before and after, and the state (no baseline).

Tests, written first and run red:

- Unit, in `tests/unit/test_cve_public_stand_ins.py` (scenarios in its given file): a keyed route with its error route loads, while a keyed route with no action, a keyed action without an error route, two keyed routes of one action on different names or locations, two keyed routes with one value, a `form` identifier with an integer value, a boolean value and a keyed route with a form field are each refused. Two keyed routes of one action with two values load.
- Integration, in `tests/integration/test_cve_planting_stand_ins.py` (Docker, the request builders in its given file): a JSON-protocol action keyed on a member answers the keyed value with its route and another value, a missing member and a non-JSON body with the error route. A query-protocol action keyed on a form field does the same. A GraphQL operation keyed on an integer variable answers `1` and not `"1"`. An unkeyed action keeps its answer for any body. The existing cases (an unknown action to the default, a form field present or absent, the GraphQL operation name) stay green.
- `tests/unit/test_committed_stand_ins.py` loads every committed capture with the new validators.

Proof: inside the shared commit (see Sequencing). Before the first proof that launches a stand-in, the `stand-in` image is rebuilt (`docker compose -f evals/docker/compose.yml build stand-in`), since the holdout calibration check refuses an image whose fingerprint label does not match and never rebuilds it, and the apify stand-in singletons are removed, since `Responder` (`evals/cve/backends/responder.py`) builds its image only when the tag is absent and reuses a running singleton.
