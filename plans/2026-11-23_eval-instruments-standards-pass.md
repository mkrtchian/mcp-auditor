# Standards pass on the LLM eval instruments

## Context

The LLM eval instruments were reviewed against the coding, testing and architecture standards of `CLAUDE.md`: the modules of `evals/` outside `evals/cve/` (the shared baseline, recording, gate, metrics, session, display and export code, the honeypot suite under `evals/honeypot/` and `evals/honeypots.py`, the judge eval under `evals/judge/` and `evals/draw_judge_cases.py`, the model probe under `evals/probe/`, and the `run_honeypot_suite`, `run_judge_eval`, `run_probe` and `capture_probe_corpus` entry points), their unit tests (`tests/unit/evals`), `tests/integration/committed/evals`, the gate fault injection test (`tests/integration/test_gate_fault_injection.py` with its given and then) and the fakes `tests/fakes/fixture_judge.py` and `tests/fakes/scripted_audit_model.py`, 132 files in all. The command modules of the CVE benchmark that sit at the top of `evals/` (`run_detection`, `run_detection_holdout`, `run_nuisance`, `run_census`, `detection_preflight`, `capture_stand_in`, `capture_defaults`) belong to the CVE benchmark and were left out.

A mechanical inventory listed the functions over 20 body lines, over 3 arguments and the files over 300 lines (54 items). Seventeen reviewers then read the code, thirteen file by file and four across the whole area (architecture and responsibilities, duplication and missing concepts, ubiquitous language, the test suite as a whole), and reported 108 findings. Ten more verified each finding against the code, rejected those that did not hold or traded one standard for another, merged the duplicates, and designed the fix of the rest. This plan carries the 65 fixes that survived: 24 of medium value and 41 of low value, 51 small and 14 medium in effort. No fix is a high-priority defect. Most of what is left is knowledge the honeypot suite and the judge eval each write in their own copy (the baseline-file rules of ADR 023, the recording rules, the floor-breach reasons, the exit codes, the refusals, the derivation of the model conditions, the console helpers), infrastructure every instrument uses that lives in a honeypot module (`REPO_ROOT`, the tracing guard, the provider usage accounting, the command-line number types, the prices), two untyped structures (the judge report, the comparisons keyed by string), names outside the glossary (`settle`, the probe's `refusal`, the bare `budget`) and test support that copies itself or tests the committed fault-injection fixture from unit tests.

## Approach

Each fix below is small and stands on its own, except where the order notes of its section say otherwise. They are grouped in eleven sections, in the order they are implemented:

1. the repository root and the honeypot session first, since moving `REPO_ROOT` to a leaf module and splitting `evals/eval_session.py` between the honeypot session and the shared session code change the import lines most later fixes edit;
2. the module moves that cross into the CVE benchmark's files through import lines (session usage, command-line arguments, `Cell` to `evals/ground_truth.py`), with the metrics and export fixes on the same modules;
3. the gate's floors split out of `evals/gate.py`, the shared floor-breach reasons and the exit codes;
4. the baseline and recording rules shared between the two instruments;
5. the shared refusals and model conditions, which build on sections 1 and 4;
6. the honeypot runs and the fault harness, on the session of section 1 and the trimmed recording of section 4;
7. the cell grid, the outcomes and the vocabulary fixes on the gate modules;
8. the displays and the typed judge report;
9. the judge session, the judge fixture and the draw;
10. the fault injection tests;
11. the model probe, last, since section 5 has already replaced its `ReferenceConditions`.

Within a section, the fixes are listed in the order the section's notes give. A reference such as "fix 5.2" names a fix of this plan. The notes and risks of a fix were written by its verifier before the sections were ordered, so a note that reads "another section" or that weighs a rename this plan rejects describes a neighbour, not a step to take: the order of the sections above wins.

## Decisions

- **Three fixes change what an instrument writes or reads, each in its own commit with a line in the `[Unreleased]` section of `CHANGELOG.md`**, which already records instrument changes: fix 4.1 (the baselines stop reading the retired `replay_rule` and `replays` keys, which no committed baseline carries any more; `docs/glossary-log.md`, line 9, and the retired-word exemptions lose the clause that kept it), fix 7.6 (a declared flip that names an unknown judge case says "names no judge case of the fixture" instead of "names no cell of the ground truth") and fix 11.8 (the model probe counts "incomplete batches", not "refusals": the report key `incomplete_batches`, the console column, `evals/probe_method.md`, a glossary entry and a log line). Every other fix is a refactoring and keeps behavior.
- **One labeling-log entry covers the plan's changes to scoring code.** ADR 016 asks for a `docs/labeling-log.md` entry for every instrument change, scoring code included, and the precedent of the 2026-11-11 entry applies: the scoring code of the honeypot suite and of the judge eval moves and is deduplicated (fixes 2.3, 2.4, 2.5, 3.1 to 3.4, 4.2, 4.3, 7.1), nothing it grades moves, no label, fixture or gate rule changes, and neither baseline is reset. ADR 020 defines the scoring code as what turns verdicts into cell observations and metrics, and asks for an entry for every change to the instrument, so the entry also covers the gate, recording and baseline code these fixes touch: the run outcome, its metrics, its recording and the gate decision (fixes 6.1 to 6.5), the judge answers turned into case observations (fix 9.1), the gate's exit codes (fix 3.6), the shared recording refusals (fix 5.1), the retest renames (fix 7.5), and the two changes of their own commits, the retired baseline keys no longer read (fix 4.1, which the 2026-11-11 entry announced) and the judge's declared-flip message (fix 7.6). The entry is written in the commit of fix 2.3, the first scoring-code change, and lists the later fixes it covers. It states that the ground truth fingerprint stays `072b33c72ecc3732df4df957ed3ff63662a6747ccb87ac29ed5332d1031cb025` and the judge inputs fingerprint `638da4313024181cc88b5c54f9032ff6b1d158664046bea12ed40f2b2b7aac73`, and answers the four questions of ADR 016.
- **The import rewrites a fix causes outside this area land in the same commit as the fix**: in `evals/cve/`, the CVE command modules at the top of `evals/`, `tests/unit/cve`, `tests/unit/detection`, `tests/unit/nuisance`, `tests/unit/support`, `tests/integration/committed`. They change import lines only. No module an eval fingerprint hashes imports a name these fixes rename or move, except `evals.baseline.fingerprint_sources`, which stays where it is, unchanged (checked against `GRAMMAR_PATHS` and `ENVIRONMENT_PATHS` of `evals/cve/detection/baseline.py`, `_COUNTER_PATHS` of `evals/cve/nuisance/counter.py`, `CONFINEMENT_SOURCE` and `PUBLIC_NAME_SOURCES` of `evals/cve/nuisance/fingerprint.py`, the files the backends serve and the targets' `backend_sources`), so no fingerprint moves. A move that changes what a dossier copies is caught by `tests/unit/cve/test_kit_isolation.py` and `tests/unit/nuisance/admission/test_nuisance_dossier.py`.
- **The duplication between the honeypot suite and the judge eval is removed with functions, never with a common base model**: a base class would reorder the keys of the next baseline written. Where the two instruments differ only in a noun ("cells" or "cases") or a side label, the shared function takes it as a parameter.
- **The committed test of the honeypot servers is renamed `tests/integration/committed/evals/test_honeypot_servers.py`** (fix 4.6), not `test_honeypots.py` as its verifier proposed, since fix 10.3 creates the unit test `tests/unit/evals/test_honeypots.py` and the code standards scan compares stems.
- **The follow-ups these fixes open in the CVE benchmark are left to the passes on those areas**, and listed here so they are not lost: the detection and nuisance gates can use `GateOutcome.exit_code` (fix 3.6), `RECORD_WITHOUT_BASELINE` and `DIRTY_TREE_REFUSAL` (fix 5.1), `ModelConditions.of` (fix 5.2), `run_count_problems`, `write_json_atomically` and `RecordingRef.of` (fix 4.3); `tests/unit/nuisance/gate/test_nuisance_gate.py` keeps the retired sense of "settle" (fix 7.5 renames it here only); `tests/unit/cve/support/cve_grammar_golden_corpus.py` restates the judge fixture path that fix 9.4 imports. Moving the detection and nuisance exports out of `evals/export.py`, whose imports load 101 modules of `evals/cve/` into the honeypot suite, is deferred to the detection area. Moving `tests/unit/auditor/support/report_builders.py` to `tests/unit/support/`, which the export test would reuse, is deferred to the shared test support area.

## Edge cases

- A module move can surface a circular import its old place masked (`evals/gate.py` imports `evals/metrics.py`, which is why fix 2.5 moves `Cell` to `evals/ground_truth.py`): the full test run catches it, and the fix is to import from the defining module, never to add a re-export.
- A rename that misses one reference fails `uv run pyrefly check`, which is the completeness check of every rename here. A move is different when the old module keeps importing the moved name for its own use (`evals/honeypots.py` imports `REPO_ROOT`, `evals/gate.py` imports `Cell`, `cell_key` and `parse_cell_key`, `evals/honeypot/runs.py` imports `tracing_enabled`, `evals/probe/candidates.py` imports `Prices` and `evals/probe/analysis.py` imports `call_cost`): an importer left on the old module still resolves through that implicit re-export, and neither pyrefly (strict preset, checked) nor ruff flags it. Those moves are checked with the AST command of the common checks, which follows multi-line imports, where `git grep` of a one-line pattern does not.
- A moved test keeps its assertions: moving it is not a reason to rewrite it.
- The honeypot baseline written by `--record-baseline` must stay byte-identical apart from `recorded_at` after fixes 4.2, 4.3 and 6.3: they change where the values are computed, never which values reach which fields.
- The judged-cases export (fixes 2.6 and 2.7) must write byte-identical JSONL, since `evals/draw_judge_cases.py` reads it and the draw record hashes past exports.

## Verification

A fix that adds a test for a function or property it creates (fix 3.6 `GateOutcome.exit_code`, fix 6.3 `RunsOutcome.recording` if its optional test is written, fix 6.4 `gate_basis`, fix 8.2 `build_judge_report`, fix 9.7 `honeypot_strata` and `target_strata`, fix 11.4 `judge_call_weight`) writes that test first and runs it red before the code (CLAUDE.md, Workflow: test-first). After each fix: the test files it touches with `uv run pytest <files> -n 0`, then the short loop `uv run pytest tests/unit -n auto --maxprocesses 6`, `uv run ruff check .`, `uv run ruff format .` and `uv run pyrefly check`. A fix that touches committed content or an integration test runs `uv run pytest tests/integration/committed -n auto` and those integration files too (`tests/integration/test_gate_fault_injection.py` for sections 6 and 10). Each section closes with `uv run pytest -n auto`. `tests/unit/project/test_code_standards.py` passes at every step without new debt. After section 4, loading both committed baselines through `load_baseline` and `load_judge_baseline` and checking them with `baseline_integrity` and `judge_baseline_integrity` returns no problem, as before the plan.
