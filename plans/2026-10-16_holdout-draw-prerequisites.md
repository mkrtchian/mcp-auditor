# CVE holdout: the prerequisites of the draw

## Context

The holdout layer of the CVE benchmark is pre-registered but no target is drawn. The selection rule (`docs/holdout-rule.md`, version 6), ADR 028, 029, 030 and 031 fix how a target is chosen, calibrated and measured. The census is built and loads (`evals/holdout_census.json`, 1280 flaws, the grouping by proof imported in `c1352ef`). What stands between the census and the draw is code the rule prescribes but that does not exist yet: the draw order the maintainer walks, the schema the census gains at the draw (the draw record and the calibration cards), the isolated calibration workshop the rule's `Calibration` section demands, the empty holdout-target module the draw fills, and the extension of the ADR 014 contamination test to the excluded servers' text.

This plan delivers that scaffolding. It runs no draw, calibrates nothing and writes no target: the draw itself (settling disagreements, running the calibration agent, reading cards, planting fixtures) is the maintainer's deferred draw session, deferred exactly as the nonce plan deferred its fixture shaping. It is also out of scope for `/implement-plan`. Likewise the holdout run mode (the switch, the closed channels, the refusal policy, the k/N number and the side split) is a separate later plan, built on the empty target module this plan leaves behind.

No change here edits `docs/holdout-rule.md` or the list of places: every artifact is an implementation the rule already prescribes, so no new rule version opens. Each artifact gets a dated `docs/holdout-log.md` line naming its commit and stating "No target is drawn, so no target changes", on the model of the 2026-10-12 projection entry.

## Approach

Six parts, each a prerequisite the draw needs, ordered so each stands alone and keeps `pytest`, `ruff` and `pyright` green:

1. **Draw order** (pure code, no LLM): the salted SHA-256 order over the draw-order candidates, each flaw's side on a cutoff, and a command that prints the order for the maintainer to walk.
2. **The census draw record and calibration cards** (schema only, optional, empty now): the structures the draw and calibration fill, validated on load when present.
3. **The isolated calibration workshop**: a `calibration-dossier` command that assembles, outside the repository, a self-contained kit (advisories, fixture format, grammar, places, layout, an MCP client and a Docker launch that import nothing from `mcp_auditor`) the calibration agent runs, plus an import-closure test that pins the isolation.
4. **The empty holdout-target module**: the format and loader for a drawn target (the analog of `evals/cve_targets.py`), empty until the draw, with tests that guarantee a holdout target can never reach the acceptance gate, the judge fixture draw or the probe corpus.
5. **The contamination test extended** to the text the excluded servers produced in the CVE cases of the judge fixture.
6. **Living docs and the holdout log**.

Everything in parts 1 and 2 reuses what `c1352ef` already laid down: `evals/holdout_exclusions.py` (`EXCLUDED_SERVERS`, `BENCHMARK_FLAWS`) and `evals/census_grouping._in_draw_order` (the draw-order criteria predicate).

## Part 1: the draw order

New module `evals/holdout_draw.py` and a new entry point `evals/run_holdout.py` (holdout-specific commands, kept out of `run_census.py`, which stays the census, and `run_cve_benchmark.py`, which stays the benchmark).

The salt and order are the rule's: ascending order of the lowercase hex SHA-256 of the UTF-8 string `"mcp-auditor-holdout:" + identifier`.

`evals/holdout_draw.py`:

- `DRAW_SALT = "mcp-auditor-holdout:"` and `draw_digest(identifier: str) -> str` returning the hex digest.
- `draw_order_flaws(classifications: dict[str, list[Classification]], candidates: set[str]) -> set[str]`: the flaws of `candidates` that meet the draw-order criteria, i.e. the `census_grouping._in_draw_order` predicate without the `runs_in_container` gate `gap_population` applies on top of it (a flaw of a server judged unable to run in a container is still drawn and calibrated, per the rule's `Grouping by proof`). To avoid duplicating the predicate, promote `_in_draw_order` to a public `in_draw_order(flaw, seen)` in `census_grouping.py` and call it from both `gap_population` and here; `gap_population` keeps its own `runs_in_container` clause. **`draw_order_flaws` itself lives in `census_grouping.py`, not in `holdout_draw.py`**: Part 2's load validation in `holdout_census.py` needs it too, and `holdout_census` must not import `holdout_draw` (which imports `HoldoutCensus` and `draw_candidates` back from `holdout_census`, a circular import that fails at load). `census_grouping` imports neither module, so both `holdout_draw` and `holdout_census` import `draw_order_flaws` from it with no cycle. `holdout_draw` imports it from `census_grouping`.
- `Side(StrEnum)`: `PRE_CUTOFF`, `POST_CUTOFF`, and `side_of(disclosure_date: date, cutoff: date) -> Side`: `PRE_CUTOFF` when the date is on or before the cutoff, `POST_CUTOFF` otherwise (rule `Sides`). **Both live in `evals/census_draw.py`, not in `holdout_draw.py`**, and Part 1 creates that module with these two alone (Part 2 adds the records to it). The reason is a cycle: `holdout_census` imports `DrawRecord` from `census_draw` (Part 2), `census_draw` needs `Side` for `DrawWalkStep` and the per-side count, and `holdout_draw` imports `HoldoutCensus` from `holdout_census`. With `Side` in `holdout_draw`, the chain `holdout_census -> census_draw -> holdout_draw -> holdout_census` fails at load. `census_draw` imports nothing from `holdout_draw` or `holdout_census`, so `holdout_draw`, `holdout_census` and `holdout_targets` (Part 4) all import `Side` from it with no cycle.
- `@dataclass(frozen=True) DrawEntry`: `digest: str`, `identifier: str`, `side: Side`, `disclosure_date: date`.
- `draw_order(census: HoldoutCensus, cutoff: date) -> list[DrawEntry]`: for every identifier in `draw_order_flaws(census.classifications, draw_candidates(census.flaws))`, build a `DrawEntry` with its digest, its side on `cutoff` and its disclosure date, sorted by digest ascending. This is the one order both sides are walked in. It does not apply the per-walk skips (a server already giving a target, a sibling of a flaw excluded at calibration) or the fill-to-10/backfill-to-20 logic: those depend on draw state the maintainer tracks as calibration proceeds and are recorded in the draw record (part 2), not computed up front. The function is the deterministic backbone the maintainer walks.

`evals/run_holdout.py`:

- `draw-order` subcommand: `--census PATH` (default `evals/holdout_census.json`), `--cutoff YYYY-MM-DD` (required), optional `--cutoff-type TEXT` and `--cutoff-note TEXT` echoed back for the record. It loads the census, computes `draw_order`, and prints, per entry, the digest prefix, the identifier, the side and the disclosure date, then a tally per side. No LLM, no network. Exit 0.
- The module's `main(argv)` follows `run_census.main`: an argparse subparser tree, `Refused` to exit 3, `ValueError` (a malformed census) to exit 3.

What stays unchanged: `census_grouping.gap_population`/`grouped_flaws`/`known_gap` behaviour (only the private predicate is promoted, byte-identical logic), `draw_candidates` in `holdout_census.py`.

Edge cases: a census that does not load raises and exits 3 before any order prints. A cutoff later than every disclosure date puts every flaw pre-cutoff (a legitimate state the tally shows). Two flaws can never share a digest (distinct identifiers), but the sort is stable on `(digest, identifier)` so the order is total and reproducible.

## Part 2: the census draw record and calibration cards

The rule's `Output` says the census records the grammar fingerprint at the draw, the calibration records and cards, and the number of give-ups per reason; ADR 028 says the census is committed with every settlement and calibration. These are draw-time content. This part adds the schema and its load validation, all optional and empty now, so the maintainer's draw session fills checked structures rather than inventing them.

New module `evals/census_draw.py`. Every record below is a pydantic `BaseModel`, like every other census schema type (`CensusFlaw`, `ProofJudgment`, `Classification`): `DrawRecord` is a field of the pydantic `HoldoutCensus` and is deserialized by `model_validate_json` on load, with the `Literal` reason sets enforced there, so a plain `@dataclass` would not get that validation.

- `KeptPlace`: `place_id: str`, `reason: str` (why only the target reaches it).
- `UnkeptPlace`: `place_id: str`, `reason: str` (one of the closed set the card lists: not reached, something else reaches it, no route, cannot be planted, or stated in full), `route_checked: bool | None` (the route check result for a layout place, `None` for a catalogue place).
- `LaunchOption`: `option: str`, `value: str`, `reason: str`, `documentation: str`.
- `SeededFile`: `path: str`, `reason: str`, `documentation: str`.
- `Sibling`: `flaw: str`, `mechanism: str`, `reach: str` (one of the three `reachable_by` tokens). The rule's `Proof`: the siblings are filed under the drawn identifier, the target's aim is their union, and the card carries each one's mechanism and reach.
- `CalibrationCard`: `flaw: str`, `mechanism: str`, `effect_class: str`, `siblings: list[Sibling]`, `kept: list[KeptPlace]`, `unkept: list[UnkeptPlace]`, `launch_options: list[LaunchOption]`, `seeded_in_layout: list[SeededFile]`, `fallback_scope: str | None`, `fallback_documentation: str | None`, `exploit_calls: list[str]`, `benign_call: str`, `patched_result: str`, `attempts: int`.
- `CardCheck`: `flaw: str`, `reported_gaps: list[str]` (what the second agent reports: each gap and each place left out for a reason outside the listed ones), `confirmed_gaps: list[ConfirmedGap]` with `ConfirmedGap(criterion: str, reason: str)` (the gaps the maintainer confirms, criterion by criterion, each sending the candidate back to calibration). The rule's `Calibration card` says both are recorded; a card with no card check cannot enter the holdout. The field shape is a proposal: the rule mandates the content (the reported gaps, and the confirmed gaps with their reasons), not the field names, so the draw session may refine the shape as long as `load_census` still checks that both are present for every drawn target.
- `GiveUpReason(StrEnum)`: the closed set of the rule's `Calibration`: `NO_PLACE_REACHED`, `PLACES_LEFT_OUT`, `CONTAINER_CANNOT_RUN`, `EXPLOIT_CANNOT_REPRODUCE`.
- `GiveUp`: `flaw: str`, `calibration: Literal[1, 2]`, `reason: GiveUpReason`, `detail: str`, `attempts: int`. One record per give-up, not one per excluded flaw: the rule records "the number of attempts and, for a give-up, a sentence of detail and one reason", and counts "the number of give-ups for each reason", and a first give-up followed by a second calibration that passes is a give-up that must be recorded beside the flaw's card. So a flaw has zero, one (first calibration gave up, the second passed and the flaw has a card) or two give-ups (excluded, no card). `attempts` is the real count of that calibration (the agent "makes as many attempts as it needs"), not a constant.
- `Settlement`: `flaw: str`, `criterion: Criterion`, `verdict: bool`, `reason: str` (a disagreement the maintainer settled for a reached candidate).
- `DrawWalkStep`: `identifier: str`, `side: Side`, `outcome: Literal["drawn", "skipped", "given_up", "excluded"]`, `reason: str` (skip reason, give-up pointer, or exclusion found at the draw).
- `DrawRecord`: `cutoff: date`, `cutoff_type: str`, `cutoff_note: str | None`, `rule_commit: str` (the rule the draw ran under), `grammar_fingerprint: str`, `settlements: list[Settlement]`, `walk: list[DrawWalkStep]`, `cards: list[CalibrationCard]`, `card_checks: list[CardCheck]`, `give_ups: list[GiveUp]`, `drawn: list[str]` (the identifiers that entered the holdout, in draw order).

The models of the calibration agents go where every other agent's model goes, `HoldoutCensus.agents` (the rule's `Census`: "the census records the model ID of each agent", the calibration step being "the calibration of its candidates, second calibrations included, and the check of their cards"). `census_work.AgentRole` gains `CALIBRATOR` and `CARD_CHECKER`; the draw session appends one `AgentRecord` per calibration (scope: the flaw identifier) and per card check, as `_reader_problems` already expects one per reader.

In `holdout_census.py`, add one optional field to `HoldoutCensus`: `draw: DrawRecord | None = None`. The validation itself is a helper in `census_draw.py` (keeping `holdout_census.py` under 300 lines and the schema's checks beside the schema). To keep `census_draw.py` free of any import back from `holdout_census.py` (which imports `DrawRecord` from it), the helper takes the `DrawRecord` and what `load_census` already has to hand rather than the whole census: `draw_problems(draw: DrawRecord, order: set[str], disclosure_dates: Mapping[str, date], place_ids: set[str], agents: Sequence[AgentRecord]) -> list[str]`, where `load_census` computes `order = draw_order_flaws(census.classifications, draw_candidates(census.flaws))` (`draw_order_flaws` imported from `census_grouping`, where Part 1 places it, not from `holdout_draw`), `disclosure_dates = {flaw.identifier: flaw.disclosure_date for flaw in census.flaws}` (its keys are the census flaws, and the per-side count below needs the dates, a bare set of identifiers cannot give it) and `place_ids = set(cve_places.load_places(cve_places.HOLDOUT_PLACES))`. `load_census` appends the helper's result when `draw is not None`. It checks:

- every `settlement`, `card`, `card_check` and `give_up` flaw is in the census and in `draw_order_flaws(census.classifications, draw_candidates(census.flaws))`;
- every `card.flaw` appears in `walk` with outcome `"drawn"`, every flaw with two give-ups appears with outcome `"given_up"` and has no card, a flaw with one give-up has that give-up at `calibration == 1` and a card, a give-up at `calibration == 2` has one at `calibration == 1` for the same flaw, and every `drawn` identifier has a card, a card check and a `"drawn"` walk step;
- `walk` identifiers are a subset of `draw_order_flaws`, none repeated;
- `cards` kept/unkept `place_id`s are ids of `evals/holdout_places.json` (via `cve_places.load_places`), so a card cannot cite a place that is not in the frozen list, and every `sibling.reach` is one of the three `reachable_by` tokens;
- `give_up.reason` is in the closed set (enforced by the `GiveUpReason` enum at deserialization);
- every card and give-up flaw has a `CALIBRATOR` agent record whose scope is that flaw, and every card check a `CARD_CHECKER` record;
- `len(drawn)` is at most 20 and at most 10 per side on `draw.cutoff` (each drawn flaw's side from `side_of(disclosure_dates[identifier], draw.cutoff)`).

What stays unchanged: `rule_version` stays `Literal[3]` (it names the version the census content was produced under; the draw opens no version and records its own `rule_commit`). Every existing census field and its validation. The committed `holdout_census.json` keeps loading, since `draw` defaults to `None` and the two new `AgentRole` members add values without removing any.

Edge cases: a card that cites a place id absent from `holdout_places.json` fails load, naming the id. A `drawn` list over 20, or a side over 10, fails load. The whole block is inert while `draw is None`, so this part changes no current behaviour and no fingerprint.

## Part 3: the isolated calibration workshop

The rule's `Calibration` says the agent works "from the fixture format, the grammar of the benchmark, the list of places, the deployment layout and the advisories of the other census flaws of the candidate's server, without access to the auditor's code, its prompts, its results or its traces." The chosen reading is strict: the workshop imports nothing from `mcp_auditor`, so the agent that develops a fixture cannot read the auditor. The workshop is exported outside the repository (like `classify-dossier --out DIR`), self-contained and runnable there.

The grammar and planting layers are already clean of `mcp_auditor` (`cve_grammar`, `cve_proofs`, `cve_units`, `cve_places`, `cve_layout`, `cve_planting*`, `cve_endpoint_address`, `cve_planting_base`, `cve_planting_spec`, `cve_planting_docker`). The `mcp_auditor` dependency of the acceptance calibration path lives in the MCP client (`cve_recording_client` → `MCPClientPort`, `ToolResponse`, `ToolDefinition`), the Docker launch (`cve_environments` → `StdioMCPClient`, `docker_client_env`, `ServerLaunch`, and its `Launch`/`LaunchShape` types every builder yields), the target type (`cve_targets.CVETarget`, whose `exploits` take an `MCPClientPort` and whose `builder` yields a `cve_environments.Launch`), the route check (`cve_route`) and the layout check (`cve_layout_check`, which imports `cve_environments`, `cve_route` and `cve_targets`). The workshop replaces the client, the launch and the target type with minimal equivalents and the driver with a reimplementation. It does not reimplement the route check or the layout check (see the review note below).

New package `evals/holdout_kit/`, every module free of `mcp_auditor`:

- `kit_client.py`: a minimal async MCP client over the `mcp` SDK directly (`mcp.client.stdio.stdio_client` + `mcp.ClientSession`, the two nested context managers the adapter note warns about, wrapped in one `async with`). It exposes `list_tools() -> list[KitTool]` and `call_tool(name, args) -> KitResponse`, where `KitResponse` has `content: str` and `is_error: bool` (the shape the grammar's `unit_of_exchanges` and the exploits consume, the same attribute names as `ToolResponse`, so an exploit written against the kit client runs unchanged against `MCPClientPort`). It does not wrap `AuditedServer`: the workshop runs the agent's own exploits, not the auditor, so the destructive-payload guard (ADR 013) does not apply, and the agent must be free to write the exploit it needs.
- `kit_launch.py`: a trimmed copy of `cve_environments`' launch logic (Docker run via the `docker` CLI, the layout mounted, the checkout as the working directory, the `--tmpfs`/`--user`/`--memory-swap` flags the landmine note pins) with its own `Launch` dataclass (the same fields as `cve_environments.Launch`), yielding a stdio launch command for `kit_client`. It also builds the candidate's images: the agent writes `docker/Dockerfile.<service>` and `docker/Dockerfile.<service>-patched` in the kit, and `kit_launch` builds each with `docker build -t mcp-auditor-cve-<service>:local` (the acceptance `image_tag` convention), so the fixture's `images`/`server_image`/`patched_image` names transplant unchanged when the maintainer moves the Dockerfiles into `evals/docker/` and `compose.yml`. The planting layer needs the sentinel image (`mcp-auditor-cve-sentinel:local`, a sidecar for network places and a namespace holder), so the kit copies `evals/docker/Dockerfile.sentinel` and the README says to build it first. It reuses the clean planting/layout modules by import inside the repo.
- `kit_target.py`: `@dataclass(frozen=True) KitTarget`, the fixture the agent writes and `kit_driver` consumes, a field-for-field mirror of Part 4's `HoldoutTarget` with `exploits`/`benign` typed against a kit-local client `Protocol` and `builder` against `kit_launch.Launch`. The kit cannot import `holdout_targets.py` (its `builder` type comes from `cve_environments` and its exploits take `MCPClientPort`), so the mirror is what makes the transplant mechanical: the maintainer copies the fixture into `holdout_targets.py` and swaps the import lines, nothing else. A unit test pins the two field-name sets equal, so the mirror cannot drift from the module it mirrors.
- `kit_driver.py`: the no-LLM check the agent runs, a reimplementation of `cve_calibration.check_target` on `kit_client` and the clean grammar: it plants the kept records, runs the benign call then the exploits on the vulnerable version and reports `dead_conditions`, then does the patched version and `patched_dead_conditions`. It depends on `cve_grammar`/`cve_proofs`/`cve_units` (clean) and a small kit-local recorder (the role `RecordingClient` plays, rewritten without `MCPClientPort`).

The layout check and the route check are NOT reimplemented in the kit. The rule's `Calibration` has them "being code, run on the fixture before it settles the places it keeps", and the card records the route check result per layout place. Both import `mcp_auditor` through `cve_environments`/`cve_targets`, and both are pinned by a committed golden master whose change opens a rule version (the rule's `Versioning`), so a kit copy that drifted would be a silent version change. So the maintainer runs `cve_layout_check` and `cve_route` in-repo on the transplanted fixture (a `KitTarget` reads back as a `CVETarget` once transplanted) and hands the layout-break verdict and the per-place route results back to the agent, which settles the layout places on them. The kit's README states this handoff, and the draw session runs the two checks in the repo, not the kit. The kit therefore replaces only the client, the launch and the driver; the route and layout checks stay the one in-repo implementation the golden master pins.

Why the kit duplicates rather than shares by import: `cve_environments.py`, `cve_layout.py`, `cve_places.py`, `cve_planting*.py` and `cve_endpoint_address.py` are `_ENVIRONMENT_PATHS` in `evals/cve_baseline.py`, fingerprinted by AST into every acceptance fixture fingerprint. Moving `Launch` and the builders out of `cve_environments.py` into a clean module the kit could import would move every fixture fingerprint, leave the acceptance baseline not comparable and redden the gate. Copying leaves those files byte-identical.

`evals/calibration_dossier.py` and a `calibration-dossier` subcommand in `run_holdout.py`: `--cve ID --out DIR`. It writes to `DIR`, outside the repository, a self-contained kit for that candidate:

- `advisories/<id>.json`: the candidate's `Dossier` (the shape `run_census._dossier` builds: `identifier`, `ids`, `advisory_urls`, `records`) plus the advisories of the other census flaws of the same `server_package` (the siblings-and-neighbours the rule grants the agent). It is rebuilt from the committed census, not by calling `run_census._dossier`: `_dossier` takes a `census_identity.Flaw` from the raw sources/work collection (the hand-downloaded exports, absent from a normal checkout), whereas each `CensusFlaw` already carries the `records` (`SourceRecord`s) and `ids` the `Dossier` needs, and `server_package` comes from the census `classifications`. So the command loads the census and assembles the dossier from `CensusFlaw` fields alone.
- the kit source: `kit_client.py`, `kit_launch.py`, `kit_target.py`, `kit_driver.py`, and byte-for-byte copies of the clean modules they need (`cve_grammar`, `cve_proofs`, `cve_units`, `cve_places`, `cve_layout`, `cve_planting*`, `cve_endpoint_address`, `cve_planting_base`, `cve_planting_spec`, `cve_planting_docker`) so the external dir runs with no repository on the path. `cve_places.HOLDOUT_PLACES` is `Path(__file__).parent / "holdout_places.json"`, so the copy of `holdout_places.json` sits beside the copied modules and the loader works unchanged.
- `docker/Dockerfile.sentinel` copied in (the planting layer's sidecar image), and an empty `docker/` slot for the candidate's two Dockerfiles.
- `holdout_places.json` copied in, and a `layout.md` describing the deployment layout nodes.
- `fixture_format.md`: the shape of a holdout target (`KitTarget`, the mirror of the Part 4 dataclass, and the two import lines the transplant swaps), the `Classification` and `CalibrationCard` JSON schemas, and `grammar_classes.md` (as `classify-dossier` writes it).
- `README.md`: the calibration procedure (build the sentinel, write the Dockerfiles and the fixture, run `kit_driver` until the candidate reproduces on the vulnerable version and is clean on the patched one, fill the card).

An import-closure test, `tests/unit/test_holdout_kit_isolation.py`: it imports every module of `evals/holdout_kit/` and asserts no module object in their transitive `sys.modules` closure is under `mcp_auditor`, and, statically, that no file under `evals/holdout_kit/` nor any clean module the dossier copies contains a `mcp_auditor` import (AST scan). This test is the pin that keeps the isolation from eroding, the way the acceptance conformance phase had to be re-pinned.

What stays unchanged: the acceptance calibration path (`cve_calibration`, `cve_environments`, `cve_recording_client`, `cve_route`) is untouched; it legitimately uses `mcp_auditor` because it runs inside the benchmark. The workshop is a second, isolated path, and the two share the clean grammar/planting modules by copy, not by a shared import that would break isolation.

Edge case and accepted cost: `kit_client`/`kit_launch`/`kit_target`/`kit_driver` duplicate logic that lives in `cve_environments`/`cve_recording_client`/`cve_targets`/`cve_calibration`. The duplication is the price of the strict isolation the rule's letter asks for, and of the fingerprint lock above. The drift risk is bounded by the clean modules being shared by copy (grammar, places, planting) and by the `KitTarget`/`HoldoutTarget` field parity test, so only the client, the launch, the target type and the driver are parallel, and each is small. A parity note goes in the module docstrings pointing at the acceptance twin.

The import-closure test pins isolation, not launch correctness, and `kit_launch` copies exactly the Docker flags the `CLAUDE.md` landmines pin as silently fragile: `--tmpfs /home/audit:exec,uid=<invoking uid>,gid=<invoking gid>` (drop the uid/gid and the tmpfs is root-owned, so `npx` fails EACCES under `--user`), `--memory-swap` (drop it and the memory bound never bites, `oom_killed` reads false), and the `--user` mapping. So `kit_launch` names each flag against its landmine in a comment, and an integration test does a real Docker launch of one server through `kit_launch` + `kit_client` and asserts `list_tools` succeeds and a benign `call_tool` returns, which is what catches a landmine flag lost in the copy (the unit import-closure test cannot). This integration test is skipped without Docker, like the existing CVE integration tests. The destructive-payload guard (ADR 013) is deliberately not in `kit_client`: the workshop runs the agent's own exploits, not the auditor, so the guard does not apply, and the only containment is the Docker target and the layout mounts, accepted because the kit holds no repository secret and has no exfiltration channel beyond the container.

## Part 4: the empty holdout-target module

New module `evals/holdout_targets.py`: the format and loader of a drawn target, with `HOLDOUT_TARGETS: tuple[HoldoutTarget, ...] = ()` empty until the draw. `HoldoutTarget` is a composition over the acceptance target, not a parallel dataclass: `HoldoutTarget(target: CVETarget, side: Side)` (`Side` imported from `census_draw`, see Part 1), with `identifier` read from `target.cve_id`. Every instrument the holdout run mode will reuse takes a `CVETarget` (`cve_calibration.check_target`, `cve_route`, `cve_layout_check`, `cve_baseline.fixture_fingerprint`), so composition lets the run-mode plan pass `entry.target` to each unchanged, with no Protocol over two types and no duplication. The maintainer fills this tuple at the draw.

`HoldoutTarget` is not clean of `mcp_auditor` (the composed `CVETarget` carries a `builder` yielding a `cve_environments.Launch` and exploits typed on `MCPClientPort`), and it does not need to be: the isolation test of Part 3 scans the kit, not this module. The kit's `KitTarget` (Part 3) mirrors `CVETarget`'s fields, and the transplant at the draw wraps the authored `KitTarget` into a `CVETarget`, then into `HoldoutTarget(target, side)`.

Isolation guarantees, as tests (`tests/unit/test_holdout_targets.py`):

- `HOLDOUT_TARGETS` identifiers (`entry.target.cve_id`) are disjoint from `CVE_TARGETS` and `OUT_OF_SCOPE_CVES` identifiers (a flaw cannot be both an acceptance and a holdout target), and every entry has `entry.target.tools_filter is None` and `ci_skip_reason is None` (a holdout run sets no tools filter);

## Part 5: the contamination test extended

The rule's `Reading` says "Before the draw, the contamination test of ADR 014 is extended to the text the excluded servers produced in the CVE cases of the judge fixture (tool descriptions, responses and errors, the auditor's own payloads echoed back left out)."

In `tests/unit/test_fixture_contamination.py` and its `given`/`then`: add a corpus built from the CVE cases of the judge fixture (`evals/fixtures/judge_cases.json`) whose server is an excluded server. For each such case, take the tool description, the response and the error text, and drop the substring the auditor's own payload contributed (the arguments the case recorded), so an echo of our payload is not counted as the server's text. Assert, as for the honeypot corpus, that no string constant of any `src/**/*.py` contains a discriminating whole word or shared three-word run of that excluded-server text. The test reads the fixture through the existing loader, not a new path.

What stays unchanged: the honeypot corpus check and the `/srv`/`app.git` layout substring check already there. The excluded servers come from `evals/holdout_exclusions.EXCLUDED_SERVERS`, matched to the judge cases by the server the case's CVE id resolves to (via the census, see the edge case below), since the case itself names only its CVE id, not its server.

Edge case: a judge CVE case carries no `cve_id` field; `source == "cve"` and the CVE id sits in `origin` as the string `"cve <CVE-ID>"` (the case's `inputs` are `arguments`, `category`, `description`, `error`, `response`, `tool_description`, `tool_name`, every one a string: `arguments` is the `repr` of the arguments dict, such as `"{'path': '/mcp-auditor-no-such-file-7f3a'}"`, and an absent `response` or `error` is the string `"None"`). The excluded-server match is by the server package, so the test maps each CVE case to its server by parsing the id out of `origin` and resolving it through the census (`classifications`' `server_package` for that flaw). `cve_targets.py` keys its targets by `cve_id` alone and carries no `server_package`, so it is not that map, and neither is `BENCHMARK_FLAWS`, a flat `frozenset` of CVE ids with no server attached. A CVE id the census does not classify fails the test (a silent skip would let the corpus go vacuous); today all six ids of the fixture, the dropped CVE-2025-68145 included, are classified under the four excluded packages, so the filter is not vacuous. If a future judge fixture draw adds a CVE case of a non-excluded server, that case is simply not in the corpus.

Dropping the auditor's own payload: the `repr` string never appears verbatim in a response, so the drop parses it (`ast.literal_eval`) and removes each string value, and it also removes the auditor's own marker constants (`mcp-auditor-probe` and the `mcp-auditor-no-such-file-…` probe path, both of `src/`), since a server echoes them inside a longer sentence (`Error: ENOENT: no such file or directory, scandir '/work/sandbox/;echo mcp-auditor-probe'`) and a run over the echo would flag the prompt that defines the marker.
