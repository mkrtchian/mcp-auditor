# Nuisance admissions under rule v4, third part: the new admissions that need no new backend

## Context

The version 4 admission campaign of the nuisance suite is settled outside the repository, and its readings of the rule are in `docs/nuisance-log.md` (entries of 2026-11-08). Its vesting is split into four parts. The repo changes and the readings' log entry are done (first part), and the re-admissions are done in two parts (lots L0 to L3, then L4 to L6, `plans/2026-11-08_nuisance-readmission-l0-l3.md` and `plans/2026-11-09_nuisance-readmission-l4-l6.md`): the admission now holds 52 servers. This part carries the campaign's **new admissions that need no new backend**, 11 servers, and logs the campaign's admission departures. A later part does the servers that need a new provisioner, the twin recalibrations and the recording of every `holdout_fingerprint`.

Everything this plan relies on per server is in the vesting manifest: one section per server, giving its outcome, the flaws that set its version, its counted tools with the reason for each one added or left out, the fixture retained file by file (from the record of agent a, of agent b, from a targeted pass, or mixed), the releases, the seed, the stand-ins, the fix check, the launch, the fields rule v3 and v4 add, the log lines, the agents' models and the points left open with a recommendation. The manifest, the maintainer's decision log, the two agents' records of each server, the targeted pass records and the fixtures they proposed are held outside the repository, and the maintainer gives their location to the implementer at launch. Where a manifest section and the decision log differ, the decision log wins. Where a section and the records differ, the records win. Where a section leaves a point open, its recommendation applies unless the decisions below say otherwise. The implementer never copies a witness or a recorded fix-check run, and never reads or quotes an exploit or witness field.

The 11 entrants are postgres (`PyPI:awslabs-postgres-mcp-server`), frogman (`https://github.com/mwtcmi/frogman`), kubectl (`PyPI:kubectl-mcp-server`), roslyncodelens (`NuGet:RoslynCodeLens.Mcp`), netlicensing (`PyPI:netlicensing-mcp`), dbt (`PyPI:dbt-mcp`), aws-cli (`https://github.com/alexei-led/aws-mcp-server`), skill-ninja (`npm:skill-ninja-mcp-server`), excel (`PyPI:excel-mcp-server`), houtini (`npm:@houtini/lm`) and memory-keeper (`npm:mcp-memory-keeper`). The admission goes from 52 to 63.

Nothing here runs an audit. Fix checks run through `run_nuisance calibrate` and benign calls through `run_nuisance vet`, both with Docker and no LLM. Each entrant is already reached by `run_nuisance walk`, so the walk record and the admission's `walk_problems` need no change: the admission entry's `reaching_flaw` is read from the walk, not from the manifest. For frogman the walk's reaching flaw is CVE-2026-46515 (a given-up flaw that does not set the version), while the flaw that sets its version and carries its counted tool is the sibling CVE-2026-46512, as apify already enters on a reaching flaw (CVE-2026-81093) distinct from its counted one.

## Decisions

These are the maintainer's, applied as stated.

1. **A copied holdout calibration on a sibling of a drawn target resolves to that target, test-first, in the first commit.** The rule (`docs/nuisance-rule.md`, "A fix verified by reproduction") exempts "the drawn flaw and its siblings, as the holdout rule's Proof section defines them" from a new fix check when the server's patched version is the one the holdout calibration checks. The siblings are filed under the drawn identifier on the target's calibration card in `evals/holdout_census.json` (`CalibrationCard.siblings`, `evals/census_draw.py`; the card of CVE-2026-46514 lists CVE-2026-46512). Today `evals/nuisance_holdout_copies.stale_holdout_copies`, called by `evals/run_nuisance._refuse_stale_holdout_copies`, keys the current fixture fingerprints by drawn `cve_id` only, so a copy recorded on a sibling reads "is no longer a drawn holdout target" and refuses the run. All 13 existing copies are on drawn ids. This part adds two sibling copies: postgres's CVE-2026-87911 (the card of CVE-2026-85787 lists it as a sibling) and frogman's CVE-2026-46512. CVE-2026-87911 is a counted flaw in `nuisance_counting.counted_flaws` even though it adds no counted tool (`_counts` asks for a non-empty `tools` and a passing fix check, not a counted tool), so the stale check, `nuisance_unrecorded` and the dossier all read it like any copy.
   - **The shared resolution**: one pure function (in `evals/nuisance_holdout_copies.py`) maps each copied-flaw id to the drawn id whose calibration it may copy: for each drawn target (a `HOLDOUT_TARGETS` `cve_id`), its own id and every id its card's `siblings` carry. It takes the drawn ids and the census's draw record (`HoldoutCensus.draw`, `DrawRecord | None`, so a census with no draw gives the drawn ids alone) and does no I/O. The module docstring follows: a copy is stale when its flaw is neither a drawn target nor a sibling a drawn target's card files, not only when it "is no longer a drawn target".
   - **The run** (needs it): `stale_holdout_copies` keeps its signature and body, and `_refuse_stale_holdout_copies` gains the draw record (`_run` passes `nuisance_census.census.draw`, already loaded) and builds `current` by pointing each copied-flaw id at its drawn target's current fixture fingerprint.
   - **The re-admission dossier** (needs it): `nuisance_readmission_dossier.holdout_references` maps by `cve_id` and raises "a holdout-calibration flaw with no target" for a sibling copy, and `test_every_holdout_calibration_flaw_resolves_to_one_target_and_one_fixture` runs it over the committed admission, so postgres's commit would turn it red. It takes the same mapping (passed down from `write_readmission_dossier`, which holds the census, through `readmission_dockerfiles`) and returns the drawn target of each copy, deduplicated (postgres's two copies give one twin).
   - **No change**: `evals/nuisance_holdout_reference` (it resolves the server's census flaws, which carry the drawn id itself: CVE-2026-85787 for postgres, CVE-2026-46514 for frogman), `evals/nuisance_unrecorded.py` (it reads the flaw record only), `calibrate` (a copy has no `FIX_CHECK_TARGETS` entry) and the later part's `holdout_fingerprint` recording, which is done by hand and has no code path: a sibling copy records its drawn target's fixture fingerprint, which the plan of the later part states.
   - **Tests**, Given/When/Then, the red test first: the mapping function (a sibling id points at its drawn target, a card whose flaw is not drawn adds nothing, no draw gives the drawn ids alone), in `tests/unit/test_nuisance_holdout_copies.py` and its given, whose existing cases stay green; `tests/unit/test_nuisance_readmission_dossier.py` and `tests/unit/support/test_nuisance_readmission_dossier_given.py` follow the new `holdout_references` signature, the committed-admission test asserting that each copied flaw resolves through the mapping, plus one crafted case: a copy on a sibling resolves to its drawn target. `tests/unit/test_run_nuisance_run.py` goes through `run_nuisance.main` and stays as it is.
   - **Docs**: one `docs/nuisance-log.md` line in this commit records that the run's stale check and the re-admission dossier now resolve a copy on a sibling to its drawn target, as the rule's sibling clause already allows; the change opens no rule version. The `CONTRIBUTING.md` run paragraph ("or the flaw is no longer a drawn target") follows, the flaw being neither a drawn target nor a sibling its card files. The `CHANGELOG.md` `[Unreleased]` sentence on the run's refusal of a stale copy ("`run` also refuses, before any LLM or Docker work, a counted flaw whose copied holdout calibration comes from a fixture that has since changed or left the holdout") gains that a copy on a sibling of a drawn target is read against that target's fixture, a user-facing change of what the run refuses.

2. **Form choices between the two records and the targeted pass**, each logged where it departs from the rule's letter or picks one record over the other:
   - postgres takes record a's fixture (the exposed record restored; the four pre-correction servers keep their original record a). The Dockerfiles run the PostgreSQL engine baked in the server image, the two AWS stand-ins `rds.us-east-1.amazonaws.com` and `secretsmanager.us-east-1.amazonaws.com` are the committed shared captures, served under their real names through the holder.
   - frogman takes record a's fixture (its run image at 1.6.2, a conforming copy of the holdout twin's patched image), the run image built cold (the FreePBX 17 stack builds from network sources).
   - kubectl takes record b's fixture: the committed `45.55.0.10` capture of its holdout twin, its TLS leaf, and the kubeconfig written under names `example`, the server installed from the commit its `v1.2.0` tag points to (decision 7). Its CVE-2025-69902 keeps record b's own fix-check module.
   - roslyncodelens takes record a (2 counted tools, `get_code_fixes` added; the `software_releases[0].day` left null by agent a is completed with the admission day).
   - netlicensing takes record b's fixture: the capture committed at the canonical `evals/stand_ins/go.netlicensing.io.json` (record a placed the same capture under `docker/captures/`), its host `go.netlicensing.io` added as a stand-in host (change 1).
   - dbt takes record a's fixture: its benign calls' `expect`s (record b's carry the argument `customers`), replacing any two-character `OK` expect that `load_admission` would refuse.
   - aws-cli takes record a's files unless the records show record b's are needed, without the records' exact pins from the tag's lock (decision 4 on the bounds).
   - skill-ninja counts 4 tools (`skillNinja_install`, `skillNinja_uninstall`, `skillNinja_list`, `skillNinja_recommend`), record b's fix check with its `Place` rewritten to describe the witness's real location (a directory name outside the root), run by `calibrate` under record a's default launch (the documented auto-detected project root, the `.github` marker recorded as a written value).
   - excel takes record b's Dockerfiles (the 1.0.0 run image, the vulnerable 0.1.7 and 0.1.8) and fix check, with the targeted pass's 17 benign calls, `real_software` verdicts and seed: of the two proposed `/data/sample.xlsx` seeds, the conforming one that writes the fewest values (the reading on seeds, below), logged.
   - houtini takes record b's fix check (its 3.1.0 is not the version the holdout twin calibrates, commit `35d97bca`, so no copy), with `declared_function_is_effect` false under the configuration-root reading.
   - memory-keeper takes record a (documented defaults; record b sets two environment variables the server does not need and labels written values "generated").

3. **The seed choice**, where the records or the pass leave it open: keep the conforming one that writes the fewest values, a file shipped under a project's tests being a published sample only when its documentation presents it as an example, a published tree keeping its layout, and of several samples the documentation names, the first. The choice is logged. For excel, both proposed seeds write a `/data/sample.xlsx` workbook (no published sample exists for the server or for openpyxl, verified on the sdist and the wheel), so the seed is `written`: the one that writes the fewest values is kept.

4. **Floating dependencies, following the documented install as is, the project's lock included when the documentation uses it.** When the server no longer starts, each package a run shows at fault gets its own loosest bound (preferably the one upstream publishes), recorded with the run that shows the failure without it. No package is bounded without such a run, and the whole tree is never frozen. In this part: netlicensing adds `mcp<2` (its `mcp[cli]>=1.7.0` resolves `mcp` 2.3.0, which removed `mcp.server.fastmcp`, and the import fails); dbt adds `pydantic<2.14` (dbt-mcp 1.17.x imports `pydantic._internal._typing_extra.eval_type_backport`, present through 2.13.4 and removed in 2.14, so under the floating 2.14.3 the server does not import; the proposed Dockerfiles' `pydantic<2.12` is loosened to it); aws-cli's both records pin `mcp==1.6.0` and `pydantic==2.11.3` (and record b `fastmcp==0.4.1`), the versions the tag's `uv.lock` records. The tag's documented install does not read its `uv.lock` (the README's `pip install -e .`, the Makefile's `uv pip install --system -e .`, the `deploy/docker/Dockerfile`'s `pip wheel`), so these exact pins are not kept: the implementer starts from the unpinned documented install and derives a loosest bound by runs for each package at fault (mcp 2.x removed `mcp.server.fastmcp`, mcp 1.12.3 removed the `**settings` catch-all through which FastMCP took the server's `version=` and `capabilities=` keywords), likely ending with bounds on `mcp`, `pydantic` and possibly `fastmcp`, each failing run logged. Each bound added is a `docs/nuisance-log.md` line with the run that shows the failure without it.

5. **The manifest's recommendations on open points apply otherwise.** Known particulars, each settled or logged: postgres's CVE-2026-87911 sets the version too (1.1.7, `command_execution`) but its only tool declares the effect of that class, so it stays in `tools` with `declared_function_is_effect` true and is not counted, while 87911 adds no counted tool; postgres's CVE-2026-85787 is classed `read_outside_scope` on the twin's card (its benign call's declared function is not the effect, so `run_query` is counted under it). frogman's CVE-2026-46513, CVE-2026-46514 (classed out of grammar on its own advisory, CWE-532, though the twin's card files it `command_execution` as a sibling) and CVE-2026-46515 (CWE-862, out of grammar, its response identical on 1.6.2 and 1.6.3 over stdio, the localhost caller being admin) are logged, not counted. netlicensing's CVE-2026-54446 is out of grammar (an authentication bypass in the HTTP transport only), logged. dbt's CVE-2026-44969, CVE-2026-44970 and CVE-2026-55837 are logged, not counted (each an effect never in a tool response; CVE-2026-55837 has a patched version, 1.20.0, but sets no version for that reason). excel's CVE-2026-85661 is logged under the reading on a flaw no source shows fixed (no version or commit in any source), its tools not removed: its fix check shows it closed on 1.0.0 (`patched_surfaces` false), so it does not set the version, does not make the server leave, and the inflation fix that removes a tool carrying an open flaw does not apply. Its fix check is a `FIX_CHECK_TARGETS` entry, so it is kept in `flaws` (Changes, section 2). houtini's known nondeterminism of CVE-2026-82112 (the model recopying the nonce, delay under load) is watched at calibrate: if the fix check is not stably green, the implementer stops and reports.

6. **Agent-written code is read whole before it runs.** Every fix-check module, builder or helper script copied from the proposed fixtures is read whole before its first `calibrate` and before any image build it triggers. It makes no network call other than to the fixture's own containers and the builds this plan authorizes, writes nothing on the host outside the system temporary directory and Docker, runs no host command beyond the Docker CLI the repository's other fix checks use, and reads nothing on the host outside the repository and the system temporary directory. On any departure the implementer stops and reports the server instead of editing around it.

7. **kubectl pinned by commit.** kubectl's run image and fix-check images install the server from the commit the `v1.2.0` tag points to, by its full hash, not from the tag name, as aws-cli's images pin their commit. The hash is resolved with `git ls-remote` on the `rohitg00/kubectl-mcp-server` repository and checked to be a commit, not an annotated tag object (for an annotated tag, the peeled `^{}` entry). Any other tag the kubectl images install, the vulnerable version's included, is pinned the same way. Each pin is logged.

The CVE-2026-5323 images are rebuilt and calibrated once, after the last server (Verification).

- A tool both records count but a decision leaves out: left out of `tools` where the rule removes it (an open flaw of an overlapping class, no benign call), or kept in `tools` with `declared_function_is_effect` true where the reading keeps it uncounted (postgres's `run_query` under 87911), its omission from the count logged, its agreement recorded as it was.

- A regeneration that moves another admitted server's fingerprint: logged with both values in netlicensing's commit.
- A copied fix-check module, builder or helper script that departs from decision 6's limits on the read-through (a network call, a host write or read, a host command beyond the Docker CLI): stop and report the server, never edit around it.
- aws-cli failing on several packages: each gets its own loosest bound with the run that shows its failure, never the tag's lock pins and never a bound no run shows needed (decision 4).
- A kubectl tag that `git ls-remote` lists as an annotated tag object: the commit it peels to is pinned, never the tag object's hash (decision 7).

Type-check changed files with `uv run pyright <files>` in the loop. - **Docker.** The builds and pulls `run_nuisance calibrate`, `run_nuisance vet`, `run_holdout calibrate --cve CVE-2026-5323` and `docker compose -f evals/docker/compose.yml build` make are authorized (frogman's run service built with `--no-cache`).
