# Nuisance vesting under rule v4, fourth part, first half: the twin repairs, the tool call timeout and the re-admissions with no new provisioner

## Context

The version 4 admission campaign of the nuisance suite is settled outside the repository and vested in parts. The repo changes, the re-admissions (`plans/2026-11-08_nuisance-readmission-l0-l3.md`, `plans/2026-11-09_nuisance-readmission-l4-l6.md`) and the admissions with no new backend (`plans/2026-11-09_nuisance-admission-without-new-backend.md`, commits `76edb39` to `948b697`, now pushed to `origin/main`) are done: the admission holds 62 servers. The rest is split in two. This part corrects the previous one, raises the tool call timeout of the auditor and of every suite, repairs the FreePBX web tier of the frogman holdout twin and admits frogman, and re-admits the five servers that need no new provisioner: figma, kanban, aws-api-mcp, sf-mcp and doris. The second half brings the new provisioners (adx, gravitino, mcp-ssh, a real Jenkins for jenkins), then one final wave: `run_holdout calibrate` of every twin a copy relies on, the recording of every `holdout_fingerprint`, the full `run_nuisance calibrate` and `vet`, and the CVE-2026-5323 rebuild and calibration.

Everything this part relies on per server is in the vesting manifest (one section per server), the maintainer's decision log, the two agents' records of each server, the records of the figma targeted pass and the fixtures they proposed. They are held outside the repository, and the maintainer gives their location to the implementer at launch. Where a manifest section and the decision log differ, the decision log wins. Where a section and the records differ, the records win. Where a section leaves a point open, its recommendation applies unless a decision below says otherwise. The implementer never copies a witness or a recorded fix-check run, and never reads or quotes an exploit or witness field. Nothing from outside the repository is named in a committed file: no path, no campaign label, no file name of that material, no model name beyond the `agents` entries, no cost.

frogman was prepared by the previous part and parked in `stash@{0}` (`step3-frogman-blocked`): its admission entry, its compose service, its log line, its living-doc edits and, in the stash's untracked part, `evals/docker/Dockerfile.frogman`, a byte-for-byte copy of `evals/docker/Dockerfile.holdout-2026-46514-frogman-patched`. Its `vet` fails because the image serves FreePBX through `php -S`, which writes a malformed HTTP status line (`HTTP/1.0: 200`), so `tools/list` returns no tool while `tools/call` works. The holdout twin CVE-2026-46514 has the same defect, unseen because its calibration calls tools by name, and a holdout run, which starts with `tools/list`, would see no tool on it.

The implementer runs no audit and no LLM eval. The timeout commit is a change to the system under test, so the honeypot evals run on it, launched by the maintainer (decision 3). Fix checks run through `run_nuisance calibrate`, benign calls through `run_nuisance vet`, twins through `run_holdout calibrate`, all with Docker and no LLM. No holdout run, nuisance run or gate run has taken place, and `evals/baselines/` holds only `honeypot_e2e.json` and `judge_isolation.json` (no `cve/`, no `nuisance/`).

## Decisions

These are the maintainer's, applied as stated, plus the form choices marked as such.

1. **Floating dependencies: the loosest bound per package a run shows at fault, recorded with that run, never a bound without one.** kubectl's `"mcp>=1.5.0,<2"` in `evals/docker/Dockerfile.kubectl` and `-vuln` was inherited from the twin's Dockerfiles with no run logged. The server's `setup.py` declares `mcp>=1.5.0` at both arms, and `kubectl_mcp_tool/minimal_wrapper.py` imports `mcp.server.fastmcp` when it starts the server (line 81 at commit `98f946e`), which `mcp` 2.x no longer has, so the run is expected to show the failure. The run: on the pinned `python:3.11-slim` base, `docker run --rm` installs the server from the commit archive (`https://github.com/rohitg00/kubectl-mcp-server/archive/<hash>.tar.gz`, no git in the slim image) with the image's other packages and no bound on `mcp`, then starts `python -m kubectl_mcp_tool.minimal_wrapper` with stdin closed, once for the patched commit and once for `kubectl-mcp-tool==1.2.0`, and records the resolved `mcp` version and the error. If both fail, the bound stays and the correction entry of section 1 records the run. If one arm starts, its bound goes, the image is rebuilt, `calibrate --cve CVE-2025-69902` and `vet --server PyPI:kubectl-mcp-server` run green again, and the fingerprint move is logged. No throwaway image is tagged. The twin CVE-2025-65719's two Dockerfiles carry the same bound with no run logged either: the same run, on the twin's two commits (`0c7fb95d` for v1.1.1, `98f946e3` for v1.2.0), goes in one new `docs/holdout-log.md` line of the corrections commit, with no fixture change while both fail.

2. **The "1.2.0" of the kubectl advisories is the git tag `v1.2.0`, not the PyPI release of the same number.** From the sources, as of the plan's date, the PyPI distribution `kubectl-mcp-tool` 1.2.0 was uploaded at 18:53Z on 2025-05-25, nine minutes before commit `fa14127a` (19:03Z) bumped `setup.py` from 1.1.1 to 1.2.0, so it was built from the working tree that commit later recorded. The fix of `run_kubectl_command` (`shlex.split`, `shell=False`) is commit `9eb90c01` of 2026-01-19, which came later, while `setup.py` still declared 1.2.0. The tag `v1.2.0` is an annotated tag peeling to `98f946e3` (2026-01-19), which carries the fix and declares version 1.2.0, and the first PyPI release that carries the fix is `kubectl-mcp-tool` 1.3.0 (2026-01-19). GHSA-94gr-w3q5-rfqr gives "fixed 1.2.0" for the PyPI and npm projects `kubectl-mcp-server`, neither of which publishes a 1.2.0. So the advisory's fixed 1.2.0 is the tree the repository declared as 1.2.0 when the fix landed, the tagged commit the run image installs, and the vulnerable arm `kubectl-mcp-tool==1.2.0` shares the number but predates the fix. The implementer verifies each of these facts again (`git ls-remote`, the GitHub commit history of `minimal_wrapper.py` and `setup.py`, the PyPI JSON of `kubectl-mcp-tool`) and the correction entry of section 1 corrects the 2026-11-09 kubectl entry, whose sentence "which carries the version the advisories name" reads the other way.

3. **The tool call timeout goes from 30 to 60 seconds, in the auditor's default and in the run conditions, so every suite and the product stay aligned.** Reason, which holds with every mention of a measurement deleted: a legitimate operation of real software can take longer than 30 seconds under load, and the auditor should not fail the call for it (magento2's real `setup-di-compile` takes about 18 seconds alone, single-threaded PHP, with no margin once the CPU is shared). The default moves where it is set: `Settings.tool_call_timeout` in `src/mcp_auditor/config.py` (the `MCP_AUDITOR_TOOL_CALL_TIMEOUT` environment variable), `_DEFAULT_TOOL_CALL_TIMEOUT` in `src/mcp_auditor/adapters/mcp_client.py`, `TOOL_CALL_TIMEOUT` in `evals/cve_environments.py` (commented as "the client's own default", read by the calibrations, the replay, `launch_audit` and the nuisance fallbacks), and the holdout kit's own copies (`evals/holdout_kit/kit_client.py`, `evals/holdout_kit/benign_probe.py`), with `"tool_call_timeout": 60` in `evals/holdout_conditions.json`. Then the holdout run, the nuisance run, its gate and `vet`'s default read 60 from the file, and the CVE acceptance benchmark, the honeypot evals and a user's audit read it from the product default, so the 2026-10-17 holdout-log principle (the holdout measures the timeout a user runs) still holds. `docs/holdout-rule.md` (Run conditions) asks only that the timeout be the same for every target and set in the log before the first run that uses it, and no holdout run has taken place, so this is a `docs/holdout-log.md` entry and a `docs/nuisance-log.md` entry and no new rule version (the nuisance rule reads the timeout "as `evals/holdout_conditions.json` records them"). `evals/cve_environments.py` is one of the environment modules every CVE fixture fingerprint hashes (`cve_baseline.ENVIRONMENT_PATHS`), so the fixture fingerprint of every holdout and acceptance target moves with no fixture changed, logged, and no CVE baseline exists to reset. The nuisance fixture fingerprint does not hash it. The baselines that exist do not embed the timeout: `evals/baselines/honeypot_e2e.json` records runs, budget, tools filter, provider, models, reasoning levels, the ground-truth fingerprint and each fixture's source fingerprint and chain settings, and `evals/baselines/judge_isolation.json` runs, provider, judge model, reasoning and inputs fingerprint. The timeout is not the budget either: ADR 016 lists the conditions a baseline records (runs, budget, tools filter, models, oracle version), the budget being the number of test cases per tool, and ADR 020's reset list (a fixture, the scoring code, the model, the runs, the budget) does not name it, so no reset applies and the change takes the path of any change to the system under test. Its commit message answers the four questions of ADR 016: (1) the change lands in the system under test, a default, and its justification survives the deletion test, (2) it was found in a nuisance pre-run check (`vet`), which measures no detection, not by reading an eval metric, (3) and (4) concern a label revision and do not apply, no label moving. No cell is expected to flip, since the honeypot servers answer well within 30 seconds, so `evals/declared_flips.json` gets nothing. The implementer does not launch the eval: it stops after this commit and reports to the maintainer the command, `uv run python -m evals.run_evals` (the judge isolation eval replays recorded cases through the judge, makes no tool call and does not read the timeout, so `run_judge_eval` is not needed), with its volume (the three honeypot fixtures, 3 runs each, budget 10) and its expected cost at the run conditions' prices. The maintainer runs it, and a red gate reverts the commit.

4. **FreePBX is served by Apache, as FreePBX 17's official installer configures it, in the twin and in the run image.** The installer (`sng_freepbx_debian_install.sh`, SCRIPTVER 1.15, inlined in both twin Dockerfiles and identical on that point to the published one) installs `apache2` and the PHP 8.2 packages, enables the modules `ssl`, `expires` and `rewrite`, edits the `apache2` SAPI's `php.ini` and `security.conf`, and, on a full install, runs `a2ensite freepbx.conf` and `a2ensite default-ssl` and restarts Apache, its post-install check expecting Apache on port 80. The twin runs it with `--nofreepbx` and installs `freepbx17` afterwards, so those two `a2ensite` lines never ran: the build adds them after step 2, the `freepbx.conf` site being what the `freepbx17` package ships and `/etc/apache2/envvars` what Debian's `apache2` package ships. The implementer verifies these sources before writing the change (the inlined installer, `dpkg -S` and the content of `/etc/apache2/sites-available/freepbx.conf` and `/etc/apache2/envvars` in a built image) and keeps the package's configuration, departing only where the confinement forces it, each departure logged: the entrypoint starts Apache undaemonized (`-D FOREGROUND`) in the background, where it started `php -S`, before it execs the MCP server, as the launch account (no root, so `User`/`Group` do not apply), with its run, lock and log directories writable by both accounts the launch uses (the planted account 60123 and the reference arm's 65534, as step 3 of the build already leaves the deployment tree). Apache listens on port 80, the installer's port (Debian's `ports.conf` left as shipped), reached at `127.0.0.1`, with no port departure: Docker sets `net.ipv4.ip_unprivileged_port_start=0` in a container with its own network namespace, a joiner inherits its holder's, and `evals/ckan_backend.py` already relies on it. `default-ssl` is enabled as the installer enables it, since the server reaching only the plain-HTTP ajax endpoint is no confinement force. The card's launch option `FROGMAN_FREEPBX_URL`, set by the `ENV` of both Dockerfiles, moves to port 80 (`http://127.0.0.1/admin/ajax.php`), and its reason, which says the account cannot bind port 80, is corrected to what holds: a launch option, not a kept place, an aim or an injection, so within decision 5's reading. `php -S` and its log go. Both twin Dockerfiles take the same change, and `evals/docker/Dockerfile.frogman` stays a byte-for-byte copy of the patched one.
