# Nuisance assembly, repository changes: settlement readings, GraphQL stand-in, fingerprint coverage, probe hygiene

## Context

The admission campaign under version 4 of the nuisance rule is finished outside the repository: 93 servers, two valid records each, read lot by lot and settled by the maintainer. None of it is in the repository yet. Its results reach the repository in several pieces of work. This one comes first and carries what the others rely on and nothing server-specific: the readings of the rule the maintainer settled for the whole campaign, the one change to the shared stand-in image a re-admitted server needs, a test pinning the fingerprint coverage that change relies on, and the tooling defects the campaign surfaced in the repository. No admission value, fixture, count or server changes here.

The maintainer's decisions and the campaign's readings are held outside the repository, and the maintainer gives their location to the implementer at launch. Everything this plan relies on is restated below, so the implementer needs them only to check a reading.

## Decisions

These are the maintainer's, applied as stated.

1. **The campaign's readings go to `docs/nuisance-log.md`, with no new version of the rule.** Each is a reading of the rule's existing text that the campaign needed applied the same way on every server. The servers each reading touches are named in the log entries of their own admission, not here.
2. **The shared stand-in answers a GraphQL request by its operation name.** The route key is the bare operation name (`IssueList`), not the keyword and the name.
3. **The CVE fixture fingerprint covers `Dockerfile.stand-in` for a target whose host declares stand-ins.** `docs/holdout-rule.md` says the fixture fingerprint covers what a target's stand-ins serve, and the stand-in's answering logic is inlined in that Dockerfile. Today this holds only by convention: every target declaring stand-ins (the 11 holdout targets and CVE-2025-65513) lists `stand-in` in its `images`, and `fixture_fingerprint` hashes the instructions of each image's Dockerfile. Nothing pins it, so a future target that omitted the image from `images` (its stand-in image built by another target) would move no fingerprint when the stand-in's answering changes. The coverage is pinned by a test rather than hashed a second time.

## Changes

One change per commit, in this order, so that the test pinning the fingerprint coverage lands before the stand-in change whose fingerprint move it guarantees.

### 1. Log entry of the campaign's readings (`docs/nuisance-log.md`)

One dated entry (2026-11-08) appended to the log, in the log's style (one bullet, plain sentences). It states that the version 4 admission campaign applied these readings of the rule on every server, that no version of the rule opens, and that each server they touch is recorded with its admission:

- **An evaluator whose fix removes only the escape.** A tool that evaluates the expression or runs the code an argument carries, whose fix restricts what it evaluates (a restricted parser, a sandbox, a runner) without removing the evaluation, still does the action of its class on what the argument carries, so its declared function is the effect whichever description is read: the fix does not remove the capability in the sense of The declared function. The settlements of 2026-10-31 that read such a fix as removing the capability no longer hold.
- **A dispatcher.** A tool that runs any registered tool an argument names, with arguments an argument carries, declares the union of the actions of the tools it can dispatch to.
- **A root from the configuration.** A root the server holds from its configuration (an environment variable, a launch option, a documented default) in force under the run's launch is a root the server declares: reading a path inside it is the fixed operation the rule gives as its example, and the declared function is not the effect. A directory an argument names is not such a root.
- **An argument that names the fetched host.** For `internal_fetch`, an argument that carries the base URL the tool fetches makes the declared function the effect. An argument that only selects records (a project filter) does not.
- **The tools of a flaw.** A tool is a tool of a flaw when an argument it receives reaches the faulty code. A tool the advisory names with no argument leading there is not.
- **Writers through a faulty read guard.** A tool that writes, moves or lists through the faulty guard of a `read_outside_scope` flaw, with a path the caller chooses, is a tool of the flaw, and its declared function is not the effect, the action of the class being reading.
- **Floating dependencies.** The image installs the server as its documentation says, keeping a lock the project ships when the documented command uses it. When the documented install no longer starts, the fixture adds the loosest bound on the single package at fault, preferably one the upstream project publishes (such as `mcp<2`), recorded with the run that shows the failure without it. The whole tree is never frozen.
- **A flaw never fixed.** A flaw that no source and no release shows fixed does not set the version of its server: it is recorded and its tools are not counted, as the fix-check clause says, and the server stays on its other flaws. A counted tool that also carries an open flaw whose class's categories overlap leaves the count, removed in data as `adb_shell` was.

The entry quotes no exploit, witness or audit result.

### 3. GraphQL operation as a route action (`evals/docker/Dockerfile.stand-in`, `evals/docker/compose.yml`, `evals/public_stand_ins.py`)

In the inlined server, `action_of` keeps its order and gains a last case: after `X-Amz-Target` and the `Action` field of a form body, for a body whose media type (parameters stripped) is `application/json`, the action is the name of the first GraphQL operation its `query` string declares, the word after the first `query` or `mutation` keyword, matched by `(?:^|\s)(?:query|mutation)\s+([A-Za-z_][A-Za-z0-9_]*)` (the word gh's own test registry matches a GraphQL request on). A body that is not JSON, has no string `query`, or declares an anonymous operation has no action. Import `re` in the inlined program. The route lookup is unchanged: the route of the request's action, else the form-field route, else the action-less route of the target, else the default. A capture with no action route on a JSON POST is therefore answered exactly as today, which is every committed capture.

The header comment of the Dockerfile says where a JSON body's action comes from. The `stand-in` service's `org.mcp-auditor.dockerfile-fingerprint` label in `evals/docker/compose.yml` takes the new value, which `tests/unit/test_cve_compose_labels.py` prints. `public_stand_ins.py`: the module docstring says a `POST` route written by hand may carry the action it answers, an AWS action as today or the operation name of a GraphQL API (`IssueList` for `api.github.com`), and the validator's message drops "AWS" ("only a POST route carries an action"). The validation itself is unchanged.

Tests (`tests/integration/test_cve_planting_stand_ins.py`, beside `test_a_planted_stand_in_answers_a_post_by_its_aws_action`, with its given helpers): a planted stand-in whose capture has a `POST /graphql` route with action `IssueList` and an action-less `POST /graphql` route answers a JSON POST whose query declares `query IssueList(...)` with the first, a JSON POST declaring another operation with the second, and a JSON POST with an anonymous query (`query { viewer { login } }`) with the second. These tests need Docker and skip without it, like their neighbours.

The stand-in image rebuilds by itself: the CVE preflight rebuilds a stale image, and the nuisance run, gate and `vet` rebuild it when a launch needs it.

### 4. Probe containers named and removed (`evals/cve_planting_docker.py`, `evals/doris_backend.py`)

Three short-lived `docker run --rm` calls run under a `subprocess` timeout with no name: `_probe_read` and `_probe_connect` in `cve_planting_docker.py`, `_doris_sql` in `doris_backend.py`. A client killed between the container's creation and its start, which a loaded daemon makes happen, leaves a `Created` container that `--rm` never removes. Each call gives its container a name (`f"{LABEL}-probe-{secrets.token_hex(6)}"`, the form `_run_detached` uses, with a `probe` infix) and removes it with a best-effort `docker rm -f <name>` in a `finally`, through `_best_effort` and `doris_rm` respectively. So that neither planting probe grows past the 20-line guideline (`_probe_read` is near 30 lines already), the two share one helper, placed below them, that names the container, runs it under `_PROBE_RUN_TIMEOUT` and removes it in its `finally`, letting `OSError` and `TimeoutExpired` reach the probe that catches them. The removal of a container `--rm` already removed fails and is ignored. Return values and exception behaviour stay as they are: the two planting probes swallow `OSError` and `TimeoutExpired`, while `_doris_sql` lets them propagate from `_doris_run` (its `timeout=60`), so its `finally` removes the container and re-raises.

Test (integration, Docker, in `tests/integration/test_cve_planting.py`, whose module fixture already skips without Docker and ensures the sentinel image `_probe_connect` runs; outside that fixture a missing `mcp-auditor-cve-sentinel:local` would fail the `docker run` before any container exists and the test would pass vacuously): drive a planting probe past its run timeout (monkeypatch `_PROBE_RUN_TIMEOUT` below `_SENTINEL_FETCH_TIMEOUT` but above a container's start time, and make `nc -w` wait the whole fetch timeout: an unroutable address fails at once and an empty address on the probe's own subnet fails after ARP, both before the timeout fires, so the probe needs a target that holds it for the whole fetch timeout; the simplest is to drive `_probe_read` rather than `_probe_connect`, against a listener that accepts and never answers (a sentinel container running `nc -l -p 80` on a closed network the test makes), where busybox `wget -T` waits; both probes share the helper, so the test covers the pattern; the helper reads `_PROBE_RUN_TIMEOUT` at call time, never as a default argument, or the monkeypatch does nothing) and find no container left once the call returns. The test must be seen red before the change, so it cannot pick the leftover out by the probe name, which the unnamed container of today does not carry: it passes, in `target_args`, a label of its own with a fresh value (`--label` travels into the probe's `docker run`) and looks for containers carrying that label, which also keeps it independent of the containers parallel tests start. Today the killed client leaves the container running until `nc -w` gives up, so the test fails; with the change, the `finally` removes it. The labelled arguments go in a `given` helper of `tests/integration/support/test_cve_planting_given.py` and the check that no container carries the label in a `then` helper of `tests/integration/support/test_cve_planting_then.py`, beside `no_container_it_started_outlives`. One test covers the pattern, the doris call takes it by reading.

Effect: `cve_planting_docker.py` is one of the environment modules every CVE fixture fingerprint hashes (`ENVIRONMENT_PATHS`, AST fingerprint), so every holdout and acceptance target's fingerprint moves, and `doris_backend.py` moves the fingerprint of the holdout target CVE-2025-66335 and the nuisance fixture fingerprint of `PyPI:doris-mcp-server` (its backend's served files). `cve_planting_docker.py` is also among the planting modules the nuisance fingerprint hashes for a backend-less server with public names, of which none is admitted today. Nothing that reaches the auditor or the oracle changes. One nuisance flaw records a holdout fingerprint today (CVE-2026-85788, `awslabs-mysql-mcp-server`, `source` `holdout_calibration`), already stale since change 3, so `run_nuisance run` refuses it as a stale copy until its twin calibrates green at the new fingerprint and the fingerprint is recorded again, which the servers' admission does with every copy it records.

## Edge cases

- A JSON POST carrying `X-Amz-Target`: the header wins, as today (the AWS JSON protocol posts `application/x-amz-json-1.1`, which is not `application/json` anyway).
- A JSON body that is not an object, or whose `query` is not a string: no action, the action-less route.
- A query declaring several operations: the first one.
- A route whose action is an operation name on a target that also has an action-less route: both load, since the uniqueness check already keys on the action.
- A probe client killed while the daemon is still creating the container: the `finally` removal may run before the container exists. The test checks what is left once the call returns; if it proves flaky on that race, report it rather than loosen the assertion.
