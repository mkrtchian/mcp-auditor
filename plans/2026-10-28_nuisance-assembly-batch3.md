# Nuisance suite assembly, third batch: seven more admitted servers, two with a provisioned backend

## Context

The nuisance suite admits sixteen servers after the first two batches (`evals/nuisance_admission.json`), with the fix-check mechanism (`evals/nuisance_fix_checks/`, `FIX_CHECK_TARGETS`, `run_nuisance calibrate`, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` tests), the backend registry (`evals/nuisance_backends.py`, with `doris`, `ckan`, `contextforge` wired), and the kit builders those used. A third admission batch produced two independent blind records per server for nine more servers and a maintainer adjudication for each; seven are admitted and two are dropped. This plan turns those settlements into committed artifacts, extending the admission from sixteen servers to twenty-three.

Scope is seven servers: godot-mcp, sf-mcp, biome, heim, magento2, mysql and n8n. All are holdout twins whose counted flaw(s) are their holdout targets' calibrated CVEs. Five are command_execution injection through a CLI wrapper (godot, sf-mcp, biome, heim, magento2), one is read_outside_scope on a bounded SQL tool (mysql), and one is internal_fetch via SSRF redirect (n8n). Two differ from every batch-2 server by needing a provisioned backend: **mysql** (a separate MySQL server plus a moto AWS stand-in) and **n8n** (a stand-in n8n API). That backend code is the new work this batch carries over batch 2, which admitted only backend-free twins.

Two servers are dropped and only logged, never admitted, both by the ratified dfie principle (Principle A, locus-irrelevant contract test): mcp-shell (CVE-2026-55581 and three siblings, all on `shell_exec`, whose declared contract is to execute the caller's shell command) and a11y (CVE-2026-5323, on `audit_webpage`/`get_summary`, whose declared contract is to fetch the caller's URL).

## Approach

Same split as the first two assemblies: eval data (the admission entries and any Dockerfiles) is authored directly and committed by hand; repo logic (backend provisioners, a fix-check module with its own builder, tests) goes through the implementation flow. Unlike batch 2, the repo-logic surface is not empty: two backend provisioners and n8n's fresh fix-check.

Run Dockerfiles, as at batch 2, are deferred to the run phase and maintainer-authored (`Dockerfile.<service>` plus a compose service, a nuisance `service` slug that is not an acceptance service); none exists for the six holdout_calibration servers. The exception is n8n, whose 2.50.2 image is also the fix-check `server_patched_service`, so `Dockerfile.n8n` is authored at Step 3 and doubles as the run image. Where the entry is `holdout_calibration`, the run Dockerfile must pin exactly the holdout patched image's version, or the recopied booleans do not describe the run image: godot is pinned to git commit `21c785d` in `Dockerfile.holdout-2026-25546-godot-mcp-patched` (not the npm/registry 0.1.1), sf-mcp `99fba0171b8c22b5ee3c0405053ccfd2910a066d`, biome `335e1727147efeef011f1ff8b05dd751d8a660be`, heim `c321d8a`, magento2 `aa1ffcc0aea1b212c69787391783af27df15ae9d`, mysql `awslabs.mysql-mcp-server==1.0.23`. The two backend servers need run images unlike their holdout twins: mysql's is **server-only** (the holdout image bakes mysqld and moto in, the run image must not, since the backend is the provisioned pair), n8n's is the `n8n-mcp@2.50.2` install with the responder's env baked in.

Fix-check source per server follows the policy the first assembly set (holdout_calibration where the counted flaw is the twin's own holdout-calibrated flaw at the same patched version, recopying the holdout calibration's witness and booleans, no committed vulnerable fixture, no `FixCheckTarget`). Six of the seven qualify: godot, sf-mcp, biome, heim, magento2 and mysql, each a single counted flaw equal to its holdout flaw at the holdout's patched version. **n8n is the exception** and carries fresh fix-check work (see its per-server entry and the fix-check policy section).

The admission data each server contributes is one `AdmittedServer` entry merged after the existing sixteen (untouched), with its counted flaw(s), the settled counted tools, a benign call per counted tool, its dropped flaws kept with their real or null class, its `agents`/`agreement`/`settlements`, a `fix_check` block, and for mysql and n8n a `backend` naming the provisioner.

## What this batch reuses, and therefore does not build

The first two assemblies built, and this batch does not touch: `evals/nuisance_fix_checks/` and its module convention, `FIX_CHECK_TARGETS` and its mechanism (Step 3 only imports the two n8n modules into the aggregator `evals/nuisance_fixtures.py` and extends the tuple), the `run_nuisance calibrate` command and its holdout_calibration handling, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` tests' logic (which treat a holdout_calibration flaw as covered without a target and gain the new rows automatically; Step 3 only adds the closure scan to the file), the kit builders `command_injection_env`, `filesystem_env`, `ssrf_env`, the backend registry mechanism (`RegisteredBackend`, `backend_problems`), and the existing sixteen entries. The `doris` provisioner is the nearest precedent for mysql's (`evals/doris_backend.py` ensures one persistent container, on a bridge plus a link-local network, and uses a transient `mysql` client container for its readiness probe; it does not keep two persistent containers up, so mysql's two-container stand-up is new, only its ensure/server-args/reap shape carries over), and n8n's follows `ckan`/`contextforge` on the shared `evals/responder_backend.py` `Responder`.

## Fix-check source policy

Six servers (godot, sf-mcp, biome, heim, magento2, mysql) are `holdout_calibration`: the counted flaw is the twin's own holdout-calibrated flaw at the holdout's patched version, so the `fix_check` recopies the holdout calibration's witness, exploit_calls and surfacing booleans (reproduced per twin with `uv run python -m evals.run_holdout calibrate --cve <id>`, Docker, no LLM, then recopied), and the server adds no `FixCheckTarget` and no committed vulnerable Dockerfile. `calibrate` does not visit these (it iterates `FIX_CHECK_TARGETS` only).

n8n is the exception: both flaws are `source` fix_check with a `FixCheckTarget` (the batch 2 rule: a recopy holds only when the run version equals the holdout's calibrated version, and the run image is 2.50.2 while the holdout calibrated 2.50.1). GHSA-8g7g's target spans 2.50.0 / 2.50.1 / 2.50.2 (`server_patched_surfaces` computed at 2.50.2), CVE-2026-44694's spans 2.50.1 / 2.50.2. Both use a builder authored in the n8n fixture module (see "Fix-check builder placement").

## Edge cases

A `RegisteredBackend` standing two containers (mysql + moto) is new; `backend_problems` checks one `image`, so the entry names the primary image and the provisioner stands both, as doris's entry names `DORIS_IMAGE` while its provisioner also stands a MySQL client. A counted flaw whose patched version differs from the server's (n8n's GHSA-8g7g at 2.50.1 vs server 2.50.2) needs `server_patched_surfaces` set and a `server_patched_service` 2.50.2 arm (2.50.1 and 2.50.0 are its other two services); `_patched_version_problems` enforces null-iff-equal. A counted tool with no benign call fails `_benign_call_problems` (mysql run_query, n8n's two tools each need one). A dropped flaw stays in the admission with its real or null class and is not deleted. The n8n responder must bind a public-range address that overlaps no other backend bridge (ckan `203.0.113.0/24`, contextforge `198.51.100.0/24`) so the patched server's SSRF guard passes its benign call. mysql's pair needs no static address (container-name DNS on its own bridge). mysql's `db_endpoint` benign argument is a fixed container name, not a per-launch uuid name. The server-level `backend` for the five backend-free servers is null.
