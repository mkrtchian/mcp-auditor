# Nuisance vesting under rule v4, fourth part, second half: the new provisioners and the final wave

## Context

The version 4 admission campaign of the nuisance suite is settled outside the repository and vested in parts. The repo changes, the re-admissions (`plans/2026-11-08_nuisance-readmission-l0-l3.md`, `plans/2026-11-09_nuisance-readmission-l4-l6.md`), the admissions with no new backend (`plans/2026-11-09_nuisance-admission-without-new-backend.md`) and the first half of this part (`plans/2026-11-10_nuisance-vesting-twins-and-timeout.md`, commits `2c62d99` to `7ed57d4`, not yet pushed) are done: the admission holds 63 servers and the tool call timeout is 60 seconds everywhere. This second half is the last. It corrects three wordings of the first half's log entries, repairs desktop-commander's `write_pdf`, brings the servers that need a new provisioner (gravitino and mcp-ssh enter, jenkins is re-admitted on a real Jenkins), has the backends whose counted tools write their state start from their seed at every run, vet and gate, logs why adx stays not admitted, and closes with one final wave: every twin a copied holdout calibration relies on calibrated green, every `holdout_fingerprint` recorded, the full `run_nuisance calibrate`, the CVE-2026-5323 rebuild and calibration, the full `run_nuisance vet`, and a check that `run_nuisance run` no longer refuses (no acceptance server is admitted, so `gate` has nothing to audit). The admission goes from 63 to 65 servers.

Everything this part relies on per server is in the vesting manifest (one section per server), the maintainer's decision log, the two agents' records of each server (and, for gravitino and mcp-ssh, the record A written again on its own and the voided first one) and the fixtures they proposed. They are held outside the repository, and the maintainer gives their location to the implementer at launch. Where a manifest section and the decision log differ, the decision log wins. Where a section and the records differ, the records win. Where a section leaves a point open, its recommendation applies unless a decision below says otherwise. The implementer never copies a witness, a planted value, a verification call or a recorded fix-check run, and never reads or quotes an exploit or witness field: every fix check is replayed by `run_nuisance calibrate`. Nothing from outside the repository is named in a committed file: no path, no campaign label, no file name of that material, no model name beyond the `agents` entries, no cost.

The implementer runs no audit, no LLM eval and no baseline recording. Fix checks run through `run_nuisance calibrate`, benign calls through `run_nuisance vet`, twins through `run_holdout calibrate`, all with Docker and no LLM. No holdout run, nuisance run or gate run has taken place, `evals/baselines/` holds only `honeypot_e2e.json` and `judge_isolation.json`, and no acceptance server is admitted, so `gate` has nothing to audit.

## Implementation steps

### Conventions for every step

- **One commit per step**, in the order of Changes: step N is commit (N). Log entries are dated the day of their commit. Before step 1, `git status -sb` tells whether the first half is still ahead of `origin/main` (decision 1).
- **Commands.** The short loop is `uv run pytest tests/unit -n auto --maxprocesses 6`, with `uv run pytest <test files> -n 0` while a test being written is red and `--lf` on a failing loop, then the full short loop again. Type-check changed files with `uv run pyright <files>` in the loop. Every step closes with `uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format .` and `uv run pyright` with no file argument, all green.
- **Docker (decision 10).** Authorized: the builds and pulls `run_nuisance calibrate`, `run_nuisance vet` and `run_holdout calibrate --cve <ID>` (CVE-2025-66335 in step 7, the sixteen twins of step 8 and CVE-2026-5323 in step 9 only) make; the `docker compose -f evals/docker/compose.yml build` commands a step names; the reads a step names, each a `docker run --rm --network none` on a built or pinned image, with no image tagged; the pulls of the digests a backend module pins. Before every image build, check the free disk with `df`: if it would fall under 10 GB, stop and report, pruning nothing further. Between steps, purge the build cache only with `docker builder prune --keep-storage <size>`, never `-a`. `docker rmi` only the images of a holdout twin or of a fix check, right after its calibration is green; never a nuisance server image, never a frogman twin image.
- **External material.** The server steps (2 to 5), and any other step that needs them, read the vesting manifest, the maintainer's decision log, the agents' records (for gravitino and mcp-ssh, the record A written again on its own and the voided first one too) and the proposed fixtures, at the location the maintainer gives at launch. Where a manifest section and the decision log differ, the decision log wins. Where a section and the records differ, the records win. Where a section leaves a point open, its recommendation applies unless a decision of this plan says otherwise. Nothing from outside the repository is named in a committed file: no path, no campaign label, no file name of that material, no model name beyond the `agents` entries, no cost. Never copy a witness, a planted value, a verification call or a recorded fix-check run, never read or quote an exploit or witness field.
- **Compose labels.** Every step that adds, changes or removes a Dockerfile updates or removes its compose service's fingerprint label in the same commit, the value printed by `tests/unit/test_cve_compose_labels.py`, so that test and `tests/unit/test_holdout_targets.py` pass at every commit. A fix-check-only Dockerfile gets no compose service.
- **New backend (steps 3 to 5), decisions 3 and 9.** A module `evals/<key>_backend.py` exporting `LIFECYCLE` (a `BackendLifecycle`), registered in `evals/nuisance_backends.py` as a `RegisteredBackend` built directly (never `_responder`), its `served` from `_served(<module>.__file__, *built_services)`. Its singleton run argv is exposed as a function, so each joins the parametrized list of `test_every_built_backend_container_argv_carries_the_memory_bound_and_the_resolver_option` in `tests/unit/test_backend_lifecycle.py` (written first). Pulled images pinned by digest in the module, or in a built part's Dockerfile `FROM`. No alias, seeded value or name carries an `mcp-auditor` word or a prefix of the records' own naming. No singleton carries a witness: a fix check stands its own instance at a per-launch address of the bridge (or on a closed network of its own) and reaps it.
