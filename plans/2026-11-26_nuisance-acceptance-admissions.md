# Nuisance acceptance admissions: the first servers of the nuisance gate

## Context

The nuisance suite rule (`docs/nuisance-suite-rule.md`, version 7, Eligibility) sends the server of each current acceptance target of the detection suite through the admission, outside the nuisance walk, and makes it once admitted a **nuisance acceptance server**: a nuisance holdout run never audits it, the nuisance gate audits it in a run of its own, and its traces may be read (Reading). None is admitted today, so `uv run python -m evals.run_nuisance gate` prints "no nuisance acceptance server is admitted", `evals/baselines/nuisance/` does not exist, and no trace of a patched server can be read to diagnose a FAIL verdict on it.

The detection acceptance layer has four targets (`ACCEPTANCE_TARGETS`, `evals/cve/detection/targets.py`), whose servers are `npm:@modelcontextprotocol/server-filesystem` (CVE-2025-53109, with CVE-2025-53110), `PyPI:mcp-server-git` (CVE-2025-68143), `npm:mcp-server-kubernetes` (CVE-2025-53355) and `npm:mcp-fetch-server` (CVE-2025-65513). On 2026-11-25 two admission agents per server, independent of each other, each in its own session and blind to the auditor, carried out the admission in a dossier written by `uv run python -m evals.run_nuisance nuisance-dossier`, the kubernetes one with `--backend kubernetes`. The maintainer settled their records field by field, on the advisories and on the servers' sources at the versions concerned.

The two records of each server, the fixtures they proposed and the maintainer's decision log are held outside the repository, and the maintainer gives their location to the implementer at launch. Where the decision log and a record differ, the decision log wins. Where this plan and the decision log differ, the implementer stops and reports. The implementer never copies a witness or a recorded fix-check run, and never reads out or quotes an exploit argument: every fix check is run again by `uv run python -m evals.run_nuisance fix-check --flaw ID`, and the admission records what that command prints.

This plan vests the outcome: three servers admitted (filesystem, git, kubernetes), one not admitted (fetch), the code the vet lacks to reach them, and the first baseline of the nuisance gate. `evals/nuisance_admission.json` goes from 65 to 68 servers. The 65 already admitted stay the nuisance holdout servers, and nothing about them moves.

A nuisance acceptance server is recognized in code by its package, not by a field of its entry: `nuisance_acceptance_servers` (`evals/cve/nuisance/admission/walk.py`) is the set of servers of the `ACCEPTANCE_TARGETS` flaws, `gate_servers` (`evals/cve/nuisance/gate/gate_servers.py`) intersects it with the admission, `walk_problems` (`evals/cve/nuisance/admission/admission_walk.py`) skips the server of every current or dropped acceptance target (`acceptance_target_servers`), whose reaching flaw it then does not check against the nuisance walk, which reaches none of the four, and `run_population` (`evals/cve/nuisance/holdout_servers.py`) files an admitted one among the exits of a nuisance holdout run. Each entry's `reaching_flaw` is the flaw of its acceptance target.

Nothing in changes 1 to 7 runs an audit or calls a model: fix checks and benign calls need Docker only. Change 8, the gate baseline, is the one step that audits, and it is the maintainer's.

## Decisions

The flaw is the server handing caller paths to `repo.index.add`, which GitPython confines from 3.1.58 on (2026-08-04), and 2025.12.18 declares `gitpython>=3.1.45`. The rule keeps transitive dependencies floating on the image a run builds (Run conditions) and says of the vulnerable Dockerfile only that it serves the fix check. So the two images the fix check of this flaw uses, and only they, carry `gitpython<3.1.58`: the vulnerable 2025.12.18 and a fix-check-only 2026.1.14. The bound on the patched arm is what lets the check show that the server's own fix holds, and not GitPython's. The run image floats. The exploit is the records', unchanged. It reveals the staged content through `git_diff_staged`, which is listed in the flaw's tools for that reason, as `context_get` is for CVE-2026-54561, and which CVE-2025-68145 counts already. The same holds for MINI-mch8-8h85-3j5v. This is done at the vesting, a departure from the letter of the rule (a Dockerfile repair falls to the admission agents since the first audit), logged with its reason: it touches only images no audit sees, and its one value is read from GitPython's releases.

4. **The benign calls are one record's per tool, as the rule allows.** kubernetes takes record b's, except `kubectl_create` and `kubectl_scale`, which take record a's: record b's expected texts for these two are contained in their own arguments, which `load_admission` refuses. The chart directory and the release name the Helm calls use are recorded as written values.

5. **An exploit per tool is written at the assembly.** The committed test `test_the_exploits_call_exactly_the_flaws_tools` asks that the exploits of a fix-check fixture call exactly the non-removed tools of its flaw, and the records bring an exploit for one or two tools per flaw. For each tool of a counted flaw that no exploit of the records calls, the implementer writes one aimed exploit, on the model of the records' exploit for that flaw and aimed at the same place, as the admissions of 2026-11-09 did. `fix-check --flaw` plays them all. An exploit only has to read as aimed: the witness has to surface through at least one. A fixture's benign calls are the ones its own launch can play, for every counted tool of its flaw or for none, as the committed test `test_every_counted_tool_has_a_benign_call` asks, and the vet is what plays the admission's benign calls on the run image.

6. **Agent-written code is read whole before it runs.** Every fix-check module, builder or helper copied from the proposed fixtures is read whole before its first `fix-check` and before any image build it triggers. It makes no network call other than to the fixture's own containers and the builds this plan authorizes, writes nothing on the host outside the system temporary directory and Docker, runs no host command beyond the Docker CLI the repository's other fix checks use, and creates a network only through `evals/cve/closed_network.py`. On any departure the implementer stops and reports the server.

7. **The vet reaches the gate's servers.** `vet` vets the servers a nuisance holdout run audits, among which `run_population` never puts a nuisance acceptance server, so today the benign calls of one are played only inside `gate`, right before paid audits. `vet --gate` vets the gate's servers instead (change 1).

8. **The gate baseline is recorded by the maintainer, last, under the default settings.** Its conditions are the ones `gate_conditions` reads (`evals/cve/nuisance/gate/gate_baseline.py`): 3 runs, a test budget of 10, the server's counted tools as tools filter (decision 9), the chain settings and tool call timeout of `evals/holdout_conditions.json`, the provider, models and reasoning levels of the settings at launch, the grammar fingerprint and the counter fingerprint.

9. **The gate audits each server's counted tools only, as the detection gate audits its target's tools filter.** The rule's run conditions fix no tools filter for a nuisance holdout run, which stays as it is, while the gate audits "under the run conditions its baseline records" (Run conditions and statistic), so a filter on the gate opens no rule version. An alarm is a FAIL on a counted tool, so the filter keeps every tool the gate decides on and drops the cost of the others, which matters since the acceptance layer is the one whose traces are read and run often. What the filter loses is the attack context the other tools would give the auditor: a regression in which a tool that is not counted leads the auditor to a false alarm on a counted one shows in a nuisance holdout run, not in the gate. `gate --no-tools-filter` audits every tool, as `run_detection --no-tools-filter` does, in a run that reports and never gates.

## Edge cases

- `fix-check --flaw CVE-2026-27735` does not surface the witness on the bounded vulnerable image, or surfaces it on the bounded patched one: the implementer stops and reports, and commits nothing of git. The version of git and its counted flaws are then the maintainer's to settle again.
- A fix check that does not come out green on the kept fixture, or whose printed result the entry cannot record as it is: stop and report the server, never record a `fix_check` no `fix-check` printed.
- An exploit of the other record that does not play on the kept builder (another witness place, another image): left out of the module, logged, never adapted by rewriting its target.
- A tool of a counted flaw for which no aimed exploit can be written on the model of the records' (no argument of it leads to the faulty code): stop and report, since the tool list is then wrong, never drop the tool to make the test pass.
- A benign call `vet --gate` cannot play as recorded: the other record's call for that tool is taken, and logged. If neither answers, stop and report: taking a tool out of the count falls to the admission agents.
- An expected text contained in its call's arguments or in a prerequisite call, a second benign call for one tool across the counted flaws, or a `real_software` record that differs across the flaws of one tool: `load_admission` refuses each, and the entry is corrected from the records before the commit.
- A seed pin `test_every_seed_pin_is_in_the_fingerprinted_content` does not find in the Dockerfile: the pin is the checksum or version string the Dockerfile carries.
- A heredoc or a `RUN` line a committed Dockerfile check refuses (a base image not pinned by digest, a copy from the build context, an `ADD` with no checksum): rewritten with no change to what the image builds.
- The kubernetes audits stand one control plane per launch, of about 410 MiB each: `fix-check`, `vet --gate` and `gate` at their default concurrency of 6 hold it, and a machine short of memory lowers `--concurrency`.
- The free disk would fall under 10 GB during the builds: stop and report. The implementer prunes nothing and removes no image.
- A later nuisance holdout run lists the three admitted servers in its first exits table under "the server of a current or dropped acceptance target", where the run of 2026-11-19 listed none, fetch and the dropped target's server being neither admitted nor reached by the nuisance walk. This is `run_population` as tested, and the docs of change 6 say it.
- A gate recording that refuses (a benign call failing both passes, a dirty tree, a run that does not complete): nothing is written, and the cause is repaired before another recording, never by recording fewer servers.
- A server flagged in a run of its baseline is recorded as it is: it is unstable, not gated, and a new alarm on it reads as inconclusive. Its traces may be read, and no fixture, counted tool or benign call is changed because of what they show.
