# Holdout transplant, foundation and first batch

## Context

The holdout layer of the CVE benchmark has a pre-registered selection rule, a run mode (`python -m evals.run_holdout run`), an isolated calibration kit, and an empty target module (`evals/holdout_targets.py`, `HOLDOUT_TARGETS = ()`). The draw is finished: 30 targets were drawn and each calibrated standalone in its own kit (the maintainer's calibration kits, produced by `run_holdout calibration-dossier` and held outside the repository, blind to the auditor). What is missing is the transplant: carrying each drawn target from its kit into `HOLDOUT_TARGETS` so the run mode can audit it, with its two server images (vulnerable and patched) wired into `evals/docker/compose.yml` and starting cleanly under the repository's container confinement.

Thirty targets across several server stacks is a large, repetitive job with real per-target friction (a server that crashes under `--network none`, a working directory that is `EACCES` under the `/srv` layout, an external CLI that needs a benign stub). Rather than guess the friction up front, this is the first of two plans. This plan builds the shared transplant machinery and carries one representative batch of six targets all the way to a green calibration. It is the worked example: it fixes the recipe and surfaces the confinement frictions on one target per builder family plus the awkward cases (a custom environment builder, a containerised backend, a benign stub, a network sidecar, a multi-place layout). The second plan carries the remaining twenty-four, grouped by builder family, written from what this one learns rather than from a guess.

This plan does not run a scored holdout audit. The first scored run happens later, at the frozen commit, under the chosen model. Here, a target is done when it calibrates: its exploits surface the nonce on the vulnerable image, the benign call is clean, no nonce surfaces on the patched image, and every kept layout place has a route. Calibration needs Docker but no LLM.

The kit was designed so the fixture port is narrow. Each kit ships an authored `KitTarget` in its fixture module under `evals/holdout_kit/`. The module filename varies by kit (`kit_fixture.py`, `holdout_fixture.py`, or `cve_<id>_fixture.py`), so the implementer locates the one fixture module per kit rather than assuming a fixed name. The kit's docstring describes the transplant as swapping two import lines (`kit_client` to the auditor's `MCPClientPort`, `kit_launch` to `evals.cve_environments`) and wrapping the `KitTarget` into a `CVETarget`. `test_holdout_kit_isolation.py` pins the field parity so the mirror cannot drift. The shared modules the fixture body imports (`cve_places`, `cve_planting`, `cve_planting_spec`, `cve_grammar`) already live in the repository, so the body is close to copy-paste.

## What was verified against the kits and the code before writing this

- The places catalogue is shared and stable. The three kits sampled (`CVE-2026-4270`, `CVE-2026-85788`, `CVE-2026-33060`) carry exactly the same 36 `place_id` values as `evals/holdout_places.json`; the JSON differs only in whitespace and ordering. No new place and no layout work.
- The four shared environment builders (`command_injection_env`, `filesystem_env`, `git_init_traversal_env`, `ssrf_env`) are defined identically in every kit's `kit_launch.py` and in `evals/cve_environments.py`. Most targets reuse them unchanged after the import swap. A few ship a custom builder absent from `cve_environments` (confirmed: `mysql_db_env` for the mysql target; to verify during batches: arcadedb, the .NET SDK target, the Puppeteer target). A custom builder is ported into `cve_environments` within the batch that first needs it.
- `CVETarget` (`evals/cve_targets.py`) carries four fields the `KitTarget` does not: `severity`, `awaited_capability`, `note`, `tools_filter` (plus the optional `ci_skip_reason`). The transplant supplies them explicitly (see "CVETarget field mapping"). `CVETarget` is left with no new defaults, so the acceptance targets stay honest.
- There is no in-repository calibration path for holdout targets. `evals/run_cve_benchmark.py` is hardwired to `CVE_TARGETS` and must not import `holdout_targets` (the isolation test forbids an instrument module from importing it). So this plan adds the calibration entrypoint to `run_holdout`, which already imports `holdout_targets`.
- `evals/docker/compose.yml` is a hand-maintained build manifest. Each service carries an `org.mcp-auditor.dockerfile-fingerprint` label (the SHA-256 of its Dockerfile instructions), pinned by `tests/unit/test_cve_compose_labels.py`, which prints the value to paste after a Dockerfile edit.

## Approach

Three pieces of shared machinery first, then the six targets.

1. An image-tag namespace for holdout services, so no holdout service collides with another or with an acceptance service.
2. A `run_holdout calibrate` subcommand that mirrors the acceptance calibrate path over `HOLDOUT_TARGETS`: `cve_calibration.check_target` on both versions, the route check and the layout check, per target, no LLM. This is the per-batch gate for both plans.
3. A per-target fixture layout: one module per target under `evals/holdout_fixtures/`, each exporting a `CVETarget`; `holdout_targets.py` imports them and assembles `HOLDOUT_TARGETS`. One module per target keeps each file small and keeps a review diff per target; a single module holding thirty targets would break the file-size guideline and make per-target review noisy.

Then, for each of the six batch-1 targets: copy its Dockerfiles into `evals/docker/` under the namespace, add its services to `compose.yml` with fingerprint labels, port its fixture, build, and calibrate green. Prune the build cache and orphaned volumes after the batch.

### Image-tag namespace

`evals/cve_targets.image_tag(name)` already returns `mcp-auditor-cve-{name}:local`. Holdout service names take the form `holdout-<year>-<num>-<service>`, so the authoritative kit's `aws-api-mcp` service for CVE-2026-4270 becomes `holdout-2026-4270-aws-api-mcp`, tagged `mcp-auditor-cve-holdout-2026-4270-aws-api-mcp:local`. The redundant `cve` token is dropped since `image_tag` already prefixes `mcp-auditor-cve-`. This namespace is applied to the service strings in each transplanted fixture's `images`, `server_image`, `patched_image`, and to the Dockerfile filenames and compose service keys. No change to `image_tag` itself. The sentinel is the exception: it stays the shared, non-namespaced `sentinel` service (`SENTINEL_IMAGE = mcp-auditor-cve-sentinel:local`, hardcoded in `cve_planting_base`), so an SSRF target's `images` carries the literal `"sentinel"` beside its namespaced server service.

### `run_holdout calibrate`

A new subparser `calibrate` in `evals/run_holdout.py`, alongside `draw-order`, `calibration-dossier` and `run`. It loads `evals/holdout_places.json` via `cve_places.load_places(HOLDOUT_PLACES)`, iterates `HOLDOUT_TARGETS` (filtered by an optional `--cve` argument), and for each target runs the same no-LLM checks the acceptance `--calibrate` runs, reusing the same helpers: `cve_calibration.calibrate_all` over `cve_calibration.calibrate_one` (which calls `check_target`) for the live-on-vulnerable and dead-on-patched conditions, and `cve_layout_check.confirm_admission` for the route check and the layout check. It prints per target what surfaced on each version and the route result, and exits non-zero if any target is not live-on-vulnerable, not dead-on-patched, or has a kept layout place with no route. With `HOLDOUT_TARGETS` empty it prints that nothing is drawn and exits 0, so the command is testable before any target lands. It reuses `--concurrency` like the acceptance calibrate. `_parser` in `run_holdout.py` already sits at the 20-line guideline, so the new subparser goes in its own helper beside it rather than inline.

A calibrate configuration error (an unknown kept id, a `planting_spec` refusal) raises `ValueError` out of `check_target`. It must not fall through `main`'s `except ValueError` handler, which prints "Refused: the census is malformed." (the census is not even consulted by calibrate) and returns `REFUSED_EXIT = 3`. The calibrate command reports a configuration error as a crash and exits 4, matching the acceptance calibrate (`run_cve_benchmark.main` catches it as a crash, not as Python's exit 1 which reads as a dead fixture), so a fixture-config bug in a transplanted target is told apart from a dead fixture (exit 1) and from a malformed census (exit 3). The command's own dispatch catches the calibrate path's errors rather than leaning on the shared `main` wrapper.

### Per-target fixture module

`evals/holdout_fixtures/<slug>.py` (slug derived from the CVE id and server, e.g. `cve_2026_4270_aws_api_mcp.py`) holds the ported fixture: the exploit and benign closures, the kept-place tuple, the aim pattern, and a module-level `TARGET: CVETarget`. The body is the kit's fixture module with its kit imports swapped (`kit_client` to the auditor's `MCPClientPort`, `kit_launch` to `cve_environments`, `kit_target`'s `KitTarget`/`KitExploit` to `cve_targets.CVETarget` and the repo exploit callable type), the `image_tag` import dropped, the service names namespaced, and `images` set to plain service names (see the field mapping). The body is ported, not pasted: it is held to the repository's comment rule like any other module (a docstring or comment that restates the function name or the code is dropped, one that explains a non-obvious why, such as the kit's note on why `aws-credentials` is not kept, stays), in English throughout. `evals/holdout_targets.py` becomes a thin assembler that imports each module's `TARGET` and builds `HOLDOUT_TARGETS`. `evals/holdout_fixtures/__init__.py` stays empty.

## CVETarget field mapping (kit KitTarget to repo CVETarget)

Carried straight from the `KitTarget`: `cve_id`, `mechanism`, `aim`, `reaches`, `kept_places`, `planting_host`, `builder` (now resolving to `cve_environments`), `exploits`, `benign`, `launch_mode`, `fallback_scope`. Rewritten, not carried straight: `images`, `server_image`, `patched_image`. The kit's `KitTarget.images` holds the full image tags (`image_tag(service)`) for both versions, but the repo's `CVETarget.images` holds the plain compose service names of the vulnerable image only (plus the literal `"sentinel"` for an SSRF target): `cve_preflight`, `cve_baseline` and `cve_session_recording` read `images` as compose service names, and `CVETarget.environment` applies `image_tag(service)` itself off `server_image`/`patched_image`. So the transplant sets `images` to the namespaced plain service name(s) (e.g. `("holdout-2026-4270-aws-api-mcp",)`), `server_image`/`patched_image` to the namespaced plain service names, and drops the fixture's `image_tag(...)` wrapping together with its `image_tag` import (which is not available from `cve_environments` anyway: `image_tag` lives in `cve_targets`). Added at transplant:

- `severity`: the CVSS string from the advisory or CVE record the kit cites (its id is in the kit, and the superseded 4270 card carried the CVSS inline in its flaw text), filled by hand at transplant, in the same form the acceptance targets use (score, version, source). No holdout module reads `severity`; it keeps the acceptance form so that a target later moved to acceptance by retire-on-read carries a real CVSS. The calibration cards and the kit advisory JSONs carry no structured CVSS field, so the literal comes from the cited record, not from a card field.
- `awaited_capability`: `None`. The holdout does no error analysis, so the diagnostic field carries nothing.
- `note`: one short line naming the mechanism, drawn from the card's flaw description. English, no cross-reference.
- `tools_filter`: `None`. The holdout runs unfiltered, so the acceptance invariant that `tools_filter` must name the tool the exploit calls does not apply.
- `ci_skip_reason`: always `None` for a holdout target. The holdout never runs in CI (it runs locally at the frozen commit), so no holdout target carries a CI-skip reason. `tests/unit/test_holdout_targets.py` already pins `ci_skip_reason is None` for every target in `HOLDOUT_TARGETS`; the transplant honours that invariant rather than loosening the test.

## Prerequisites (once, at the start of this plan)

- Free disk and reset Docker's reclaimable space: `docker volume prune` (orphaned volumes, ~1.5 GB) and `docker builder prune`. The census archives under `output/holdout_census/` are removable now that the draw is closed, if more room is wanted.
- Confirm the batch-1 calibration kits are intact (fixtures and Dockerfiles present and readable), and identify the authoritative kit per target. A target that was recalibrated has a later kit that supersedes the first: CVE-2026-4270's authoritative kit is the recalibrated one (service `aws-api-mcp`, `Dockerfile.aws-api-mcp`), not the first (service `awsapi`). Transplant each target from its authoritative kit; a superseded kit can carry a stale package pin or exploit shape.
- Rebuild the acceptance filesystem images, whose local tags may have been overwritten by a kit that reused the generic `filesystem` service name during the draw: `docker compose -f evals/docker/compose.yml build filesystem filesystem-patched`, then confirm the acceptance calibration is still green for the filesystem target (`python -m evals.run_cve_benchmark --calibrate --cve CVE-2025-53109`). The namespace this plan introduces prevents the collision for every transplanted target from here on.

## Batch 1 (six targets, chosen for friction coverage)

The six are picked so that each awkward case appears once (a custom builder, a containerised backend, a benign stub, a network sidecar, a multi-place layout), to fix the recipe and de-risk the remaining twenty-four. They cover three of the four shared builders (`filesystem_env`, `command_injection_env`, `ssrf_env`) plus the first custom builder; `git_init_traversal_env` is deferred to the second plan, since the acceptance git target already exercises it. The exact membership can be adjusted at review; the rationale is coverage, not draw order (order governed selection, not transplant).

1. CVE-2026-4270, awslabs.aws-api-mcp (`filesystem_env`, no network): the baseline read-outside-scope recipe, the recal kit's kept secret-file places (about two dozen catalogue file places the flaw reads by absolute path), and one pending guarded layout place whose route the maintainer settles here (the recal card already resolves `bare-remote-url` and `bare-history-env` as not routed).
2. CVE-2026-2130, mcp-maigret (`command_injection_env`, no backend): the simplest command-execution shape, to fix the command-injection recipe with nothing else in the way.
3. CVE-2026-104120, the reference mcp-server-fetch (`ssrf_env` + the shared sentinel sidecar + network): the SSRF recipe with `has_network=True` and the shared `sentinel` service (reused, not rebuilt per target), the one family whose `images` carries a second, non-server service.
4. CVE-2026-85788, awslabs mysql-mcp (custom `mysql_db_env` + containerised MySQL backend): ports the first custom environment builder into `cve_environments` and exercises a target whose backend is a database container.
5. CVE-2026-25546, godot-mcp (`command_injection_env` + benign external-CLI stub): the stub case, where the injection lives in the real server code and the external tool is stubbed benign.
6. CVE-2025-11489, desktop-commander (`filesystem_env`, symlink-following, settlement place plus two siblings): a multi-place filesystem target with siblings, exercising the route and layout checks on more than one place.

### Per-target steps (applied to each of the six)

1. Copy the kit's two server Dockerfiles (and `entrypoint.sh`) from the target's authoritative calibration kit into `evals/docker/`, renamed to the namespace (`Dockerfile.holdout-2026-4270-aws-api-mcp`, `-patched`). The SSRF target needs no sentinel Dockerfile: it reuses the shared `sentinel` service (`mcp-auditor-cve-sentinel:local`), already built for the acceptance fetch target, whose served nonce is injected at runtime (`-e FLAG=...`), so one image serves every SSRF target. The kit's own `Dockerfile.sentinel` is a standalone copy of that same sentinel and is not carried over.
2. Add the services to `compose.yml` (two per target, the vulnerable and patched server; the SSRF target adds no sentinel service, it reuses the existing shared `sentinel`), each with its `image:` tag and a fingerprint label. Run `tests/unit/test_cve_compose_labels.py` to print the fingerprints to paste, then confirm the test is green.
3. Build the images: `docker compose -f evals/docker/compose.yml build <service> <service-patched>` (the shared `sentinel` is already built; rebuild it only if its fingerprint is stale).
4. Write `evals/holdout_fixtures/<slug>.py` from the kit's `kit_fixture.py`: swap the kit imports (`kit_client`, `kit_launch`, `kit_target`), drop the `image_tag` import, namespace the service names, set `images` to the namespaced plain service name(s) (plus the literal `"sentinel"` for the SSRF target), add the four `CVETarget` fields. For CVE-2026-85788, port `mysql_db_env` into `cve_environments.py` first (the fixture's `builder` then resolves to it after the import swap).
5. Append the target to `HOLDOUT_TARGETS` via `holdout_targets.py`.
6. Calibrate: `python -m evals.run_holdout calibrate --cve <CVE>`. Resolve any confinement friction (no network, `/srv` permissions, missing backend, stub) until the target is live-on-vulnerable, dead-on-patched, routes OK.
7. For CVE-2026-4270 and CVE-2025-11489, settle the guarded layout places: run the route check and decide which layout place the fixture keeps, recording the decision in the fixture (as the acceptance targets do in their `kept_places` comments).

After all six calibrate green: `docker builder prune` (keeps tagged images, clears build cache).

## What stays unchanged

- `evals/cve_targets.py`, `CVE_TARGETS`, and the acceptance baselines and gate. Filling `HOLDOUT_TARGETS` does not touch the acceptance layer; the two live in separate modules and the isolation test keeps instruments from importing `holdout_targets`.
- The honeypot and judge instruments, their baselines and gates.
- `image_tag`, `cve_calibration`, `cve_route`, `cve_layout_check`, `cve_places` and the places file. The calibrate command reuses them; it does not change them. (Porting `mysql_db_env` adds a builder to `cve_environments` but changes no existing builder.)
- The selection rule, the census, the draw record, the run conditions file, and the run mode's reporting. This plan fills the target list the run mode already knows how to read; it does not change how a run is scored or reported.
- The kit directory and the `holdout_kit` modules. The transplant reads the kits; it does not write them.

## Edge cases and confinement frictions

- A server that starts standalone in its kit but crashes under the repository's confinement (`--network none` for a non-SSRF target, the `/srv` layout mounted with a 0700 home, the tmpfs home created with the invoking uid/gid). The kit calibrated under its own `kit_launch`; the repository's `cve_environments` confinement can differ, so each target is re-calibrated in-repo and the friction fixed in the Dockerfile or the launch, never by loosening the shared confinement.
- A target whose exploit needs an external CLI the container does not have (godot, and later heim): the kit stubs the CLI benign while the injection stays in the real server code. The stub is part of the image and must be carried over faithfully; calibration confirms the injection still surfaces the nonce.
- A target with a containerised backend (mysql, and later arcadedb, neo4j): the backend runs inside the target image or a sidecar, not as a host service. Its readiness is part of the benign-call-clean check; a flaky backend reads as a dead condition and must be made deterministic.
- An SSRF target's sentinel sidecar: it has no patched twin and is not a server image (mirror the acceptance fetch target, `images=("<namespaced-fetch>", "sentinel")` with the literal `"sentinel"` as the second entry). The sentinel is the one shared, non-namespaced service: the planting layer launches `SENTINEL_IMAGE` (`mcp-auditor-cve-sentinel:local`, hardcoded in `cve_planting_base`) with the per-run nonce injected via `-e FLAG=...`, so every SSRF target reuses the same image, and `cve_session_recording`'s `SENTINEL_SERVICE not in target.images` check needs the literal `"sentinel"` present in `images`. A namespaced per-target sentinel would never be launched (the constant is used, not the fixture field) and would break that check.
- A guarded layout place with no route (the `bare-history-env` kind, reachable only by a different flaw class): the route check keeps it out, exactly as CVE-2025-68145 left the acceptance layer. The fixture keeps only the layout places the route check routes.
- A kit Dockerfile that `COPY`s a support file from the build context (the mysql seed and config, the godot stub, a docker-shim). `tests/unit/test_cve_compose_labels.py::test_no_dockerfile_copies_from_the_build_context` forbids `COPY`/`ADD` from the context in `evals/docker/`, so each support file is baked into the image with an inline `RUN` heredoc instead of copied. The implementer checks the authoritative kit's Dockerfiles for `COPY`/`ADD` and converts them on transplant; calibration confirms the baked-in file behaves as the kit's copied one did.

## Test scenarios

- `run_holdout calibrate` with `HOLDOUT_TARGETS` empty prints that nothing is drawn and exits 0 (unit-testable without Docker, mirroring the empty-`run` test).
- `run_holdout calibrate` iterates the targets and surfaces per-target dead conditions; a unit test with a fake calibration over a tiny stand-in target list confirms the exit code is non-zero when a target reports a dead condition and zero when all are live-and-dead-correct. (The real Docker calibration is the manual batch gate, not a CI test.)
- `test_holdout_kit_isolation.py` still passes: the `KitTarget` / `CVETarget` field parity is unchanged by the transplant.
- The unit test pinning that no instrument module imports `holdout_targets` still passes: `holdout_fixtures` is imported only by `holdout_targets`, and `run_holdout` is not an instrument.
- `test_cve_compose_labels.py` passes with the new services and their fingerprints.
- The acceptance filesystem calibration is green after the prerequisite rebuild (guards against the overwritten-tag regression).
- Each of the six targets calibrates: exploits surface the nonce on the vulnerable image, benign call clean, no nonce on the patched image, kept layout places routed.

## Implementation steps

Step 1 is pure code (no Docker). Steps 2-7 each transplant one target and close on a Docker calibration (no LLM); they are ordered so step 2 establishes the per-target fixture pattern and the thin assembler that steps 3-7 extend. Step 8 updates the living docs once every target has landed. One commit per step.

Verification commands (from `CLAUDE.md`): full check `uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run pyright` (no file argument); short loop `uv run pytest tests/unit -n auto --maxprocesses 4`; image build `docker compose -f evals/docker/compose.yml build <service> <service-patched>`; holdout calibrate `uv run python -m evals.run_holdout calibrate [--cve <CVE>]`; acceptance filesystem guard `uv run python -m evals.run_cve_benchmark --calibrate --cve CVE-2025-53109`.

Shared facts for the fixture ports (steps 2-7): the import swaps are `from evals.holdout_kit.kit_client import KitClient` to `from mcp_auditor.domain.ports import MCPClientPort` (and every `KitClient` annotation in the exploit/benign closures to `MCPClientPort`), `from evals.holdout_kit.kit_launch import <builder>` to `from evals.cve_environments import <builder>`, and the `kit_target` import dropped. The kit's fixture module (its filename varies by kit: `kit_fixture.py`, `holdout_fixture.py` or `cve_<id>_fixture.py`) exposes either a `build_target(places) -> KitTarget` factory or an already module-level `TARGET` (CVE-2026-104120 and CVE-2025-11489 ship the latter and have no `build_target`). The transplant produces a module-level `TARGET: CVETarget` either way (the exploit/benign closures and `KEPT_PLACES`/`AIM` stay as module functions and constants). `CVETarget` lives in `evals/cve_targets.py`; its `exploits` is `tuple[Callable[[Places, MCPClientPort], Awaitable[None]], ...]` and `benign` is `Callable[[Places, MCPClientPort], Awaitable[None]]`.
