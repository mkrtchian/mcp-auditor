# A second pass for the nuisance vet

## Context

Before a nuisance run, the vet makes the benign call of every audited server, and a server whose benign call fails is reported as not run and leaves N, the number of servers the holdout nuisance rate counts, for the whole run (`docs/nuisance-suite-rule.md`, "The benign call"). The vet plays each server once: `drop_failing_servers` (`evals/cve/nuisance/vetting.py`) gathers the benign calls over every server, then plays the solo servers, and once a server is connected an answer that fails is not retried (the docstring of `benign_call` says why: retrying an answer keeps the best of several tries).

On 2026-11-17 the full `run_nuisance vet` answered 64 of 65: `npm:@zereight/mcp-gitlab` read a job status GitLab CE sets in the background. Two `vet --server` right after answered, and the expect was repaired the same day (`docs/nuisance-suite-log.md`, entry of 2026-11-17 on the play and retry expects). The repair removes that race. It does not remove the class of failure: a fixture whose real software is slow or nondeterministic under a shared host can fail one pass while sound, and the server then leaves N for an instrument flake rather than a broken fixture.

The detection holdout met the same problem on 2026-11-07 and answered it with a second pass (`evals/cve/detection/holdout_pre_run_check.py`, `docs/detection-suite-log.md` entry of 2026-11-07): a target the parallel pass would drop is checked once more, alone, once every first pass has finished, and runs if that second pass finds nothing. The report names the targets that ran on their second pass. This plan gives the nuisance vet the same second pass.

## Decisions taken with the maintainer

- The second pass applies to the vet, the run and the gate alike, so the three commands decide in one way which server is audited. No nuisance acceptance server is admitted yet, so no gate baseline is compared today. Under `--record-baseline`, a server that fails both passes still refuses the recording.
- Before its second pass, a server's own backend containers are removed, so its provisioner stands the backend again from its image and its seed: a first pass can change a shared backend's state (Jenkins' `trigger_build` makes a build 2 that `get_build_log` and `get_build_status` on `lastBuild` would then read). This includes the Doris cluster, whose counted SQL tools can write its state, at the cost of standing it again (one cluster stand-up, about 25 seconds as `CONTRIBUTING.md` gives it), paid only when Doris failed its first pass.
- The second pass is accepted on integrity grounds: it runs before any audit and without an LLM, so it cannot be fitted to the auditor. Its one effect is to admit a fixture that fails intermittently, which may then answer the auditor with errors during an audit: noise in both directions, not a bias for the auditor. The detection holdout accepted the same trade on 2026-11-07. The run result and the report name the servers that ran only through their second pass, so it stays visible.
- The second pass is easier than the run, and the log says so beside the integrity argument: it plays alone on a backend stood again, while the audits run in parallel on a shared backend the first pass's benign calls have already changed, so a failure caused by a neighbour on the same backend can be masked at the vet and come back during the audits.
- The first pass's reason is kept for every server that runs on its second pass: `second_pass` is a `dict[str, str]`, from server package to the reason its first pass failed with, in `VetResult`, in `NuisanceRunResult` and in the report model. This departs on purpose from the detection's `list[str]`: the reason is the lever for repairing an intermittent fixture, and without it a second-pass server names a flake nobody can trace. A server that fails both passes keeps only its second reason in `not_run`, as in the detection. The first-pass reason is publishable: it is a result of the benign call, of the same kind as the reasons `not_run` already writes into the report ("A server whose benign call fails is reported as not run with that reason", `docs/nuisance-suite-rule.md`, "The benign call"), and the rule's Reading section says that "the result of the benign call" spends nothing.
- A server run only on its second pass is to be repaired by the admission agents, or its instability explained in the nuisance suite log, before the next nuisance run, so an intermittent fixture does not stay in N run after run. This ties the second pass to the rule's repair clause ("Its benign call or its fixture is repaired by the admission agents before a later run", "The benign call"): a server that fails one pass carries a fixture to repair as one that fails both does. It is written in the log entry, not automated: no check enforces it.
- No rule version opens. A nuisance suite log entry reads the rule's "a server whose benign call fails" as a server whose benign call fails on both passes, as the detection suite log reads its own check on 2026-11-07.

## Approach

One function decides, for the three commands: `drop_failing_servers` gains the second pass and a container host to remove a server's backend before it, and returns `VetResult` (moved from `vet_command.py`, which already holds the not-run and surviving servers) carrying beside them the second-pass servers, each with its first-pass reason. The vet prints the second-pass servers with that reason, the run carries them into its result, its report and its Markdown, and the gate uses the same function in place of its own gathering. Nothing else changes in how a server is launched or audited.

## Code details

### `evals/cve/nuisance/vetting.py`

- `VetResult` moves here from `vet_command.py` (no other module imports it) and gains `second_pass`, on the model of the detection's `PreRunCheck`. A second value object of the same shape beside it would duplicate it, and "pre-run check" is the detection's term. Unlike `PreRunCheck.second_pass` (`list[str]`), the field maps each package to the reason its first pass failed with, on purpose: the reason is the lever for repairing an intermittent fixture (see the decisions):

  ```python
  @dataclass(frozen=True)
  class VetResult:
      not_run: list[NotRunServer]
      surviving: list[AdmittedServer]
      second_pass: dict[str, str]  # run only after a clean second pass, to the first pass's reason
  ```

- `drop_failing_servers(servers, benign_call, host: ContainerHost) -> VetResult`:
  - first pass: `gathered_then_alone(servers, benign_call)` as today (the other servers together, then each solo server alone);
  - then, for each server whose first reason is not `None`, in the servers' order, one at a time: remove its backend containers with `remove_backend_containers(host, run_images([server]))` (`evals/cve/nuisance/run_containers.py`, unchanged), then `await benign_call(server)` again. The final reason is the second pass's. A server that answered its first pass is called once;
  - `not_run` keeps `NotRunCause.BENIGN_CALL_FAILED` with the second pass's reason, `surviving` keeps the servers' order, `second_pass` maps, in the servers' order, each package whose first reason was not `None` and whose second is to its first reason.
  - The function stays within the 20-line bound of `CLAUDE.md`: the second pass of one server (the removal, then the call) goes in a private helper right below it (newspaper rule), as `check_before_run` keeps `_check_one` below it.
- The module docstring states the second pass and why (the detection's wording adapted: a fixture whose real software is slow or nondeterministic, or a backend that sets a state in the background, can fail one pass while sound, and a broken fixture fails both), and that the server's backend is stood again before it.
- `benign_call`'s behavior is unchanged: within one pass, an answer that fails once connected is still not retried. The second pass is a fresh launch after every first pass has finished, on a backend stood again, not a retry inside the session. Its docstring's reason ("retrying it would keep the best of several tries") would otherwise read against `drop_failing_servers`, which keeps the better of two passes: the docstring gains one clause saying the vet's second pass (`drop_failing_servers`) is the one further try, made on a fresh launch after every first pass.
- `ContainerHost` is the existing protocol of `run_containers.py` (`running_containers`, `remove_containers`), which `NuisanceDeps`, `VetDeps` and the gate's `ContainerSweep` already satisfy (each is already passed to `remove_backend_containers` today).

### `evals/cve/nuisance/run_containers.py`

- Code unchanged. Its module docstring says a built backend container is removed at the start of a run, a vet and a gate: it gains that a server's own backend containers (and the Doris cluster, by name) are removed again before that server's second pass of the vet (`vetting.drop_failing_servers`). The docstring of `remove_backend_containers` ("Before the rebuild: ...") explains why the start-of-command removal precedes the rebuild; it gains that a removal after the rebuild (the second pass) finds the containers by tag, since they were started from the rebuilt image. No fingerprint reads this module.

The removal before a second pass is safe at that point: every first pass has finished and no audit has started, so no other launch uses the backend. A per-launch backend (GitLab CE, the Kubernetes control plane, the node sandbox engine) has no container left running between launches, so its removal finds nothing and its next launch stands it as always. A shared backend that other servers use is stood again on their first audit's launch by its provisioner, as at the start of a run, when `remove_backend_containers` removes every built backend container.

### `evals/cve/nuisance/run.py`

- `_run_surviving` calls `vetted = await drop_failing_servers(population.audited, deps.benign_call, deps)` and carries `vetted.second_pass` into the result, the partial result of an interrupted run included (on the model of `holdout_run.py`, which replaces `second_pass` on both).
- `run.py` is at 305 lines: the change must not grow it. Carrying `second_pass` into both results wraps two lines and adds about three, so a self-contained part moves out: `_backend_images` (used by `_assemble_run` alone) beside `backend_image_ids` in `evals/cve/nuisance/images.py`. `default_deps` cannot move alone: the module holding it would import `NuisanceDeps` from `run.py`, which imports `default_deps` from it, a cycle at load time.

### `evals/cve/nuisance/results.py`

- `NuisanceRunResult` gains `second_pass: dict[str, str]`, from server package to its first-pass reason, with an empty default so the givens that build it stay valid (`field(default_factory=dict[str, str])`), carried by `dataclasses.asdict` into `<report>.result.json`. No code reads a result file back (`evals/cve/run_files.py` only writes), so no compatibility default is needed beyond the givens.

### `evals/cve/nuisance/report.py` and `evals/cve/nuisance/markdown.py`

- The report model gains `second_pass: dict[str, str]`, copied from the run result (`dict(run.second_pass)`).
- `_not_run_section` of `markdown.py` takes `report.second_pass` as a third argument and gains, after the not-run lines, one line per second-pass server, in the order of the mapping: `- <pkg>: run after a clean solo second pass of the vet (first pass: <reason>)`. It follows the not-run section's per-server lines (`- <pkg>: <reason>`), one server and its reason per line, and the detection's wording (`evals/cve/detection/holdout_not_run.py`) with the nuisance term. The detection prints its second-pass targets on one joined line since it has no reason to show. Nothing is printed when the mapping is empty. The function returns early today on an empty `not_run` (`["## Not run", "- none", ""]`): the second-pass lines must be printed in that branch too, after `- none`, since a server that answers on its second pass while no server is not run is the likeliest case. `_not_run_section` is already at the 20-line bound of `CLAUDE.md`: the second-pass lines are built by a private helper right below it (newspaper rule), called from both branches, so the function does not grow.

### `evals/cve/nuisance/vet_command.py`

- `VetResult` moves to `vetting.py` (see there) and is imported from it. `vet_servers` passes `deps` as the host and returns `drop_failing_servers`' result as is.
- `_print_vet_results` prints `ok, on its second pass (first pass: <reason>)` in place of `ok` for a second-pass server, then the ping answer as today: `<pkg>: ok, on its second pass (first pass: <reason>), answers the ping: <yes|no|unknown>`. The closing count is unchanged (`<k> of <n> servers answer their benign calls`, a second-pass server among the k). The ping answer recorded is the last one the server gave: its second pass's when that pass connected, else its first pass's (`on_ping` is never called by a launch that never connects), unchanged code.
- Exit codes unchanged: 0 when every server answers (on either pass), 1 when one fails both.

### `evals/cve/nuisance/gate/gate_session.py`

- `_vetted` calls `drop_failing_servers(servers, opened.harness.benign_call, opened.harness.sweep)` in place of its own `gathered_then_alone`, and builds its `not_run` dict (`{entry.server_package: entry.reason}`) from the result's `not_run`. Its docstring and the module docstring ("A server whose benign call fails is not audited") name the second pass: a server whose benign call fails on both passes. Under `--record-baseline`, a server in `not_run` (both passes failed) refuses the recording as today. A second-pass server is audited and compared like any other. The gate names no second-pass server in its result: no nuisance acceptance server is admitted, and naming it in the gate report is left to the change that admits one.

## Edge cases

- A server that fails its first pass on a launch failure (it never connected after `PRE_RUN_LAUNCH_ATTEMPTS`) gets a second pass like any other failure.
- A solo server (magento2) that fails its first pass gets its second pass in turn, after every first pass, solo servers' included.
- Two servers sharing one backend both fail their first pass: each second pass removes the backend before its own call, so the second server's call reads a backend stood again too.
- A server that fails both passes is not run with its second reason. Its first reason is not kept: `not_run` carries the reason of the final pass, as the detection does. Only a server that answers its second pass keeps its first reason, in `second_pass`.
- A server whose second pass raises (a bug, not a failure reason) propagates as a first-pass raise does today.
- No server fails its first pass: no removal, no second call, `second_pass` empty, the output identical to today's.
- A run interrupted during the audits still writes `second_pass` in its partial result.
