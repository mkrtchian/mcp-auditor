# Nuisance suite assembly, second batch: seven more admitted servers, all holdout twins

## Context

The nuisance suite already has nine admitted servers (`evals/nuisance_admission.json`), the fix-check mechanism (`evals/nuisance_fix_checks/`, `FIX_CHECK_TARGETS` in `evals/nuisance_fixtures.py`, the `run_nuisance calibrate` command, the `ADMISSION_PATH` loading and coverage/parity tests), the backend registry (`evals/nuisance_backends.py`), and the kit builders those nine used. A second admission batch produced two independent records per server for ten more servers and a maintainer settlement for each; seven are admitted and three are dropped. This plan turns those settlements into committed artifacts, extending the admission from nine servers to sixteen. It adds no repo mechanism: the batch exercises only what the first assembly built.

Scope is seven servers: maigret, nmap, android, markdownify, desktop-commander, taskwarrior and wireshark. Every one is a holdout twin whose single counted flaw is exactly its holdout target's calibrated CVE, and every one is backend-free (`backend_need` none). Six counted flaws are `command_execution` injection through a CLI wrapper (maigret, nmap, android, markdownify, taskwarrior, wireshark) and one is `read_outside_scope` on a filesystem read (desktop-commander). The builders they need already exist in the kit (`command_injection_env`, `filesystem_env`): no kit port, no new builder.

Three servers are dropped and only logged, never admitted: mcp-ssh (CVE-2025-9654, `declared_function_is_effect` true: `runRemoteCommand`'s declared contract is to execute the command the caller gives it), searxng (every flaw `declared_function_is_effect` true as a fetch tool, or class null), and open-websearch (CVE-2026-42260, `declared_function_is_effect` true: `fetchWebContent` is a fetch tool).

## Approach

This batch is almost entirely hand-authored eval data plus a living-docs reconciliation, because the repo code it would otherwise add already exists. It follows the same split as the first assembly: eval data and fixtures are authored directly and committed by hand; repo logic goes through the implementation flow. The difference is that this batch's repo-logic surface is small, and in the default case empty.

Every counted flaw here is the server's holdout twin's own calibrated flaw. By the fix-check source policy the first assembly set (holdout_calibration where the counted flaw is the twin's own holdout-calibrated flaw at the same version, the aws-api precedent), each server's `fix_check` defaults to `source` `holdout_calibration`: the witness, `exploit_calls` and the surfacing booleans are recopied from the holdout calibration the twin already passed (aws-api's CVE-2026-4270 and doris's CVE-2025-66335 are the two committed precedents), and the server carries no committed vulnerable fixture and no `FixCheckTarget`. No holdout calibration output is committed, so the maintainer reproduces it with `uv run python -m evals.run_holdout calibrate --cve <id>` (Docker, no LLM) before recopying; all seven twins are in `HOLDOUT_TARGETS`. A fresh nuisance fix-check (a committed vulnerable Dockerfile plus a `FixCheckTarget` module under `evals/nuisance_fix_checks/`, calibrated in the nuisance image namespace) is authored only for a server whose settled patched version differs from its holdout twin's calibrated patched version, so the recopied booleans would not describe the nuisance run image. Whether any server falls in that case is a per-server settlement resolved at calibration (see Decisions).

The data each server contributes is one `AdmittedServer` entry in `evals/nuisance_admission.json`: its counted flaw with the settled counted tools and a benign call per counted tool, its dropped flaws kept with their real or null class, its `agents` / `agreement` / `settlements`, and a `fix_check` block (recopied from the holdout calibration in the default case). The admission grows from nine entries to sixteen; the existing nine are untouched.

## What this batch reuses, and therefore does not build

The first assembly built all of this; this batch changes none of it. `evals/nuisance_fix_checks/` and its per-flaw module convention. `FIX_CHECK_TARGETS` and the thin aggregator `evals/nuisance_fixtures.py`. The `run_nuisance calibrate` command, which iterates `FIX_CHECK_TARGETS` only: a `holdout_calibration` flaw has no target, so `calibrate` never visits it (its `source`-field exclusion only matters for a target whose record is `holdout_calibration`, which none is today). The coverage test treats such a flaw as satisfied without a `FixCheckTarget`. The `tests/unit/test_nuisance_admission_loads.py` `ADMISSION_PATH` test and the `tests/unit/test_nuisance_fix_checks.py` coverage/parity tests, which already treat a `holdout_calibration` flaw as covered without a target. The kit builders `command_injection_env` and `filesystem_env` (`evals/holdout_kit/kit_launch.py`; the holdout twin fixtures import them from `evals/cve_environments.py`). The backend registry (no server here needs a backend).

## Fix-check source policy

The default for all seven is `fix_check.source` `holdout_calibration`: the counted flaw is the twin's own holdout-calibrated flaw, so the `fix_check` block recopies that calibration's witness, `exploit_calls`, `vulnerable_surfaces`, `patched_surfaces`, `server_patched_surfaces` and `patched_benign_errored`, exactly as aws-api does today, and the server carries no `FixCheckTarget` and no committed vulnerable Dockerfile. `calibrate` iterates `FIX_CHECK_TARGETS` only, so it never visits these flaws, and the coverage test treats such a flaw as satisfied without a target (already in place). Nothing in the nuisance loop re-verifies a recopied flaw: its real confirmation is `run_holdout calibrate --cve <id>` on the twin, run at assembly and again whenever the holdout fixture moves.

The one condition that would break the recopy for a given server: its settled patched (run) version differs from the holdout twin's calibrated patched version, so the recopied booleans (which describe the holdout patched image) would not describe the nuisance run image. For such a server the `fix_check` is `source` `fix_check` with a committed vulnerable fixture authored on the same kit builder, a `FixCheckTarget` module under `evals/nuisance_fix_checks/` named `cve_YYYY_NNNNN_<slug>.py`, and the vulnerable and patched Dockerfiles that the first assembly's convention names (`Dockerfile.<slug>-vuln`, `Dockerfile.<slug>`), calibrated green in the nuisance namespace. Whether any server falls here is resolved per server before the admission entry is written (Decision below), comparing each settled run version with the pin of its `Dockerfile.holdout-<id>-<slug>-patched` (maigret `mcp-maigret@1.0.13`, desktop-commander `@0.2.33`, nmap `30a6b9e1`, android `14e2bf27`, taskwarrior `1ee3d282`, wireshark `6e56043c`, markdownify `a31204de058b`); the default expectation, since each server's single counted flaw is its holdout flaw and the holdout patched image is that flaw's first-fix, is that none do and the batch adds no `evals/nuisance_fix_checks/` module.

## Edge cases

A counted flaw whose settled patched version differs from the holdout twin's calibrated version cannot use the holdout_calibration recopy and needs a fresh nuisance fix-check (vulnerable fixture, `FixCheckTarget`, Dockerfiles); the coverage test enforces that a non-`holdout_calibration` counted flaw has a target, and `_patched_version_problems` enforces that `server_patched_surfaces` is null exactly when the flaw's patched version equals the server's. A counted tool with no benign call fails `_benign_call_problems`, so the android and markdownify tool-set settlements must author one benign call per settled counted tool. A dropped flaw stays in the admission with its real or null class and must not be deleted (the record is the provenance). For a `holdout_calibration` server, the deferred run Dockerfile (`Dockerfile.<slug>`, run phase) must pin the exact holdout patched version the recopied booleans describe, or the run image and the recorded fix_check diverge. A benign call that errors on the patched image is only observed at run time for a `holdout_calibration` server (calibrate does not re-verify a recopied flaw's benign calls), as with aws-api today.
