# Test review: fix the tests added since the suite review

## Context

The suite review of `plans/2026-10-20_test-suite-review.md` ended at commit 5672314. Since then 174 test files (about 20,600 lines, 212 files counting the ones that grew) were added, almost all for the eval harness: the nuisance suite, the CVE benchmark, the holdout and the stand-ins. They were reviewed against the testing standards of `CLAUDE.md` with the same method: 143 findings, each checked against the code (probes, runs, reasoning on which assertion survives a mutation). 105 hold, 33 hold in part, 5 do not. Verification found about 25 more issues, included below. This plan covers every finding recommended for application. The rest is listed under "Out of scope" with the reason.

The findings fall into the same five kinds as the reference plan: tests that cannot fail, names that promise more than the test checks, coupling to data or wiring that changes for good reasons, tests of the library or of a constant, and Given/When/Then structure. Two traits set this batch apart from the first one:

1. **The duplication is in production as much as in the tests.** Thirteen provisioners copy the kit's `backend_launch`, two `_audit` functions copy each other, two calibrate commands compute the same exit rule, and a test `then` holds fifty lines of validation logic with its own tests. The tests mirror it: one file per fix check, one per backend, the same argv lookups in 27 files. The cure is a named concept in production, then one parametrized test over the registry, not a cleanup file by file.
2. **One coupling is a hazard, not a cost.** The two calibrate commands are tested by patching the module that defines the drawn set (`"evals.holdout_targets.HOLDOUT_TARGETS"`, `nuisance_fixtures.FIX_CHECK_TARGETS`, `kit_launch.build_images`). A simulated switch to `from ... import` made those tests run a real `docker network create` and a real `docker build`, and one of them would have audited the 30 real holdout targets with a test key. A patch on the consumer's own binding fails loudly when the name moves (`monkeypatch.setattr` raises, ruff flags the orphan import); only a patch on the defining module goes silent.

Every change keeps or strengthens what the suite guards. Where a test is deleted, the behavior it named is covered elsewhere (named in the item) or was never observable through it.

## Approach

Nine areas. Area 0 lands first: the shared test support every other area uses. Area A holds the production refactorings, each its own commit carrying only the test edits its new signature forces, ahead of the area that rewrites the tests on top of it: a revert then undoes the refactoring alone. Areas B to H are test-only apart from the small production edits flagged in them. The breakdown may split an area further.

Production refactorings go test-first like any change: write the tests against the new signature or the new public name, see them fail (an import or type error is the expected red for a rename or a signature change), then change production. A refactoring that keeps behavior is checked by the existing tests staying green on top of the new tests.

Registry-wide parametrized tests that replace copied files are green on arrival, since they characterize code that already works. Each one is checked for sensitivity before its copies are deleted: break one fixture by hand in the working tree (an aim that no longer matches its exploit, a counted tool renamed, a service with no Dockerfile), see the test go red with that target's id, revert. The commit message records which mutation was tried.

Shared decisions across areas:

- Fakes of production collaborators live in `tests/fakes/` (exported from `tests/fakes/__init__.py`), test vocabulary of one bounded context lives in that context's `tests/unit/support/test_<x>_given.py`. No generic grab-bag module: a helper goes where its concept lives.
- The committed admission is loaded once, cached, by `support/test_nuisance_committed_admission_given.py`. A missing file fails loudly, it never parametrizes to nothing.
- A message is specified once, at the module that owns it. Callers assert the effect, not the wording again.
- An attempt budget, a timeout, a count of registry members: tests read the constant or derive the value, never restate the literal.
