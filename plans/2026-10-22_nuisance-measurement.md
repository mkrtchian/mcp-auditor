# Nuisance suite: the counter, the run and the figure

## Context

The nuisance suite's input side is built (`plans/2026-10-22_nuisance-admission.md`): the walk, the admission file schema with its load checks and derived reads (`counted_flaws`, `counted_tools`), the isolated admission workshop with its fix-check driver, and the patched-image namespace with the fixture fingerprint. What is missing is the measurement side the rule prescribes: the counter that turns an audit of a patched server into a flagged-or-not verdict, the run orchestrator that audits every admitted server and assembles the result, the server-unit statistic with its cutoff-side split, and the report with its figure, its exits tables and its raw count. The acceptance gate the rule also defines (its own baseline, the ADR 016 replay, the CI wiring) is a separate later plan (plan 3, decided by the maintainer on 2026-10-22): it gates a future change of the auditor on the four acceptance servers, which matters when the detection features arrive, whereas the figure is what the first nuisance run needs.

This plan delivers the measurement machinery. It admits no server and runs no real audit: the admission file is empty until the maintainer's deferred admission session, exactly as `HOLDOUT_TARGETS` was empty when the holdout run mode was built. So every module here is testable with fakes and crafted admitted servers, and `python -m evals.run_nuisance run` prints that no server is admitted and exits 0 while the admission file is absent (`evals/nuisance_admission.json` does not exist until the session: `load_admission` raises `FileNotFoundError` on it, and the `run` subcommand reads that as an empty admission) or lists no server, as the holdout run does with no drawn target.

The seam mirrors the holdout's run mode (`plans/2026-10-16_holdout-run-mode.md`), and the parallel is deliberate: `nuisance_run` is the sibling of `holdout_run`, `nuisance_statistic` of `holdout_statistic`, `nuisance_results` of `holdout_results`, `nuisance_report`/`nuisance_markdown` of theirs. Where a holdout module is already generic over count and N (`holdout_intervals`, `holdout_hierarchical`), the nuisance side imports it unchanged rather than copying it. Where the two differ, they differ because the nuisance audit plants nothing and grades nothing: it launches the patched image, runs the graph with no tools filter, and counts FAIL verdicts on counted tools in valid categories. There is no nonce, no place, no layout check, no replay, no grade.

This plan edits no rule and no ADR: `docs/nuisance-rule.md` (version 1) and ADR 033 already prescribe every artifact here, so no rule version opens. It adds one field to the admission schema (`AdmittedServer.host`, a `cve_planting_base.PlantingHost`, the container's user and network stance a holdout `CVETarget.planting_host` already carries, see Part 2), which the measurement needs and the input-side plan deferred, and which the dossier's fixture-format text gains. No server being admitted, the schema can still move at no cost. It does not touch `evals/cve_grammar.py` and moves no grammar fingerprint, no acceptance fixture fingerprint and no baseline. It also refactors the holdout's per-target result, behavior-preserving, into the shape the nuisance result takes (a tuple of per-run statuses with the aggregates as properties, Part 2), so both suites carry their per-run facts the same way. Each committed nuisance step gets a dated `docs/nuisance-log.md` line naming its commit and stating that no server is admitted, so no figure is produced, on the model of the version 1 entry. The holdout refactor is not a nuisance-log event: its record is a `CHANGELOG.md` tooling line.

## Approach

Seven parts, each standing alone and keeping `pytest`, `ruff` and `pyright` green:

1. **The counter** (`nuisance_counter.py`): a pure reader from an `AuditReport` and a server's `counted_tools` map to the set of counted tools flagged in that audit, plus the raw FAIL count, plus a `counter_fingerprint()` over the counter's own modules (`ast.dump`, separate from the grammar's, as ADR 033 requires).
2. **The result value objects** (`nuisance_results.py`, and the holdout mirror): the per-server result as a tuple of per-run statuses (`NuisanceRunStatus`) with its aggregates as properties, the run result, the not-run and exit rows, defined in their own module so the statistic, the report and the orchestrator share them without a cycle, exactly as `holdout_results.py` is. The holdout's `HoldoutTargetResult` takes the same shape first, in a behavior-preserving refactor of its own (`HoldoutRunStatus`), so the nuisance mirrors a shape that already exists.
3. **The server-unit statistic** (`nuisance_statistic.py`): the figure (mean over runs of f/N), its Wilson interval and controls, the cutoff-side split (each server through its first draw-order flaw with a counted tool), the Newcombe contrast and the conclusion check, and the incomplete-run sensitivity, every per-server read a property read. Reuses `holdout_intervals` and `holdout_hierarchical` unchanged.
4. **The nuisance audit and launch** (`nuisance_audit.py`): the benign pre-run check and the one-audit-of-one-server path over the patched image, with the suite's retry and refusal policy (a refused step is not retried and an alarm stands through it, an infra failure is retried twice, a benign-call failure drops the server from N for the run).
5. **The run orchestrator** (`nuisance_run.py` and the pure per-server assembly in `nuisance_assembly.py`): the sibling of `holdout_run.run_holdout`, refusing tracing and a dirty tree, rebuilding the patched images, vetting each server by its benign call, auditing the survivors over the runs, and assembling the run result.
6. **The report and its markdown** (`nuisance_report.py`, `nuisance_markdown.py`): the proof-free report model, the figure published "at most" with its interval, the split, the two exits tables and the raw count, under the holdout's reading discipline (no proof, no judge input, no verdict per case).
7. **The `run` subcommand, the `host` schema field, the living docs and the log** (`run_nuisance.py`, `nuisance_admission.py`, docs).

Parts 1 to 3 are pure and need no Docker or LLM. Part 4 is the only one that would launch a container, and it is injected behind a dependency so the unit tests fake it. Parts reuse the holdout's building blocks: `holdout_intervals`, `holdout_hierarchical`, `holdout_conditions` (the same `evals/holdout_conditions.json`, read unchanged), `holdout_draw.draw_order` (for the split's first-flaw rule), `cve_audit.build_auditor`/`RunOverrides`, `cve_environments.connect`, `holdout_run.rebuild_images`/`HOLDOUT_BUDGET` and `cve_baseline.image_ids` (with the nuisance tag injected through its new `tag` parameter, Part 5).

## Part 1: the counter

New module `evals/nuisance_counter.py`, pure, the only bridge from an audit report to the nuisance verdict, and the module whose change resets the suite's gate baseline (the rule's Versioning section). It reads the report keyed by tool, which `cve_report_units.units_of` does not do (it flattens across tools and drops the tool name, and the nuisance verdict is per tool).

- `@dataclass(frozen=True) class ToolVerdict`: `tool: str`, `category: JudgeCategory | None`, `verdict: Verdict | None`. One per case and per chain of the report, carrying the tool it ran on. No field tells a chain from a case: the rule counts both the same way and nothing downstream reads the difference. `Verdict` is the `cve_units` enum and `JudgeCategory` its `NewType` over `str` (the ones `counted_tools` returns), converted from the domain's `EvalResult.category: AuditCategory` and `EvalResult.verdict: EvalVerdict` through their `.value`, exactly as `cve_report_units._judgment` does, both `None` when `eval_result` is `None`.
- `tool_verdicts(report: AuditReport) -> list[ToolVerdict]`: over `report.tool_reports`, one `ToolVerdict` per case (`tool_report.tool.name`, the case's `eval_result.category`/`verdict`) and one per chain (same tool, the chain's `eval_result`). It reads only these domain fields: `tool_reports`, `tool.name`, `cases`, `chains`, `eval_result.verdict`, `eval_result.category`. The docstring lists them, as `cve_report_units.units_of` lists its own.
- `flagged_tools(report, counted: Mapping[str, frozenset[JudgeCategory]]) -> frozenset[str]`: the counted tools (keys of `counted`) that a case or a chain calls and that is judged FAIL in a category the tool's `counted` set admits. A chain counts when it calls such a tool, as a case does: the rule's "a chain counts when any of its steps calls such a tool" is satisfied exactly by reading the chain's owning tool, since every step of a chain calls the tool it was planned against (`chain_nodes.make_execute_step` sends each step to `state["current_tool"]`, and a `ChainStep` carries no tool name of its own). A comment records that.
- `raw_fail_count(report) -> int`: the number of `tool_verdicts` with `verdict == Verdict.FAIL`, on every tool and in every category. The rule's raw count, never compared, report-only.
- `counter_fingerprint() -> str`: `evals.baseline.fingerprint_sources` over the counter's own source (the `ast.dump` hash that drops comments, formatting and module docstrings), by the model of `cve_baseline.grammar_fingerprint`. It covers `nuisance_counter.py` and `nuisance_counting.py` (the two modules that decide what counts: the verdict predicate here and the counted-flaw/counted-tool derivation there), and not `cve_grammar.py`, which has its own fingerprint and whose `VALID_CATEGORIES` the counter reads but does not own. A new `_COUNTER_PATHS` tuple lists the two files, as `cve_baseline._ENVIRONMENT_PATHS`/`grammar_fingerprint` list theirs.

Decision recorded (the maintainer, 2026-10-22, the CLAUDE.md spirit settling it): the counter fingerprint covers `nuisance_counter` and `nuisance_counting` and excludes the grammar. ADR 033 says the counter "has its own fingerprint" and "reads the categories valid for a flaw's class from the grammar", so the grammar's own fingerprint covers `VALID_CATEGORIES` and the counter's covers the predicate and the derivation. A change to either counter module resets the nuisance gate baseline (plan 3) and bars a comparison across it. A change to the grammar resets it too, through the grammar fingerprint, and additionally makes a holdout number exploratory.

## Part 2: the result value objects and the schema field

New module `evals/nuisance_results.py`, the value objects the statistic, the report and the orchestrator share, defined apart to break the cycle (the orchestrator imports the statistic and the report, which both consume these), exactly as `holdout_results.py` notes for the holdout.

The per-server result carries its per-run facts as a tuple of per-run status objects, and every aggregate the statistic and the report read is a read-only property over that tuple. Decision by the maintainer (2026-10-22): a result that stores `runs`, `flagged_per_run`, `flagged_runs`, `flagged_share`, `split_flagged_runs`, `incomplete_runs`, `incomplete_unflagged_runs` and `raw_fail_per_run` side by side holds invariants nothing enforces (`flagged_runs == sum(flagged_per_run)`, `flagged_share == flagged_runs / runs`, `incomplete_unflagged_runs <= incomplete_runs`, every list of length `runs`), and a crafted test result can break them silently. Computed from the statuses, they cannot. The holdout result takes the same shape first (below), so the two suites read their per-run facts the same way: that is what the symmetry means here. Each side keeps its own status type, because the per-run payloads differ (detection credits on the holdout, flagged, split and raw count on the nuisance). The shared thing is the pattern, not a type.

- `@dataclass(frozen=True) class NuisanceRunStatus`: the facts of one run of one server. `flagged: bool` (the rule's status in that run), `split_flagged: bool` (flagged through a counted tool of the split flaw), `incomplete: bool` (a step refused or unreadable), `raw_fail_count: int` (the rule's raw count for that run, report-only).
- `@dataclass(frozen=True) class NuisanceServerResult`: `server_package: str`, `split_flaw: str | None` (the identifier of the first draw-order flaw with a counted tool, None when the server leaves the split), `split_disclosure_date: date | None` (that flaw's census date, both kept as `str` and `date`, no `DrawEntry` dragged into the result), `statuses: tuple[NuisanceRunStatus, ...]` (one per run, in run order), `counted_tools_count: int`, `tools_count: int` (the `_count` suffix as `HoldoutTargetResult.tools_count`, and because `counted_tools` is already the name of the `nuisance_counting` function that returns the map), `run_cost: float`. Its read-only properties: `runs` (`len(statuses)`), `flagged_per_run: list[bool]` (the status per run, which the report prints), `flagged_runs: int`, `flagged_share: float` (`flagged_runs / runs`), `split_flagged_runs: int`, `incomplete_runs: int` (runs with a refused or unreadable step, flagged or not), `incomplete_unflagged_runs: int` (the incomplete runs not flagged, the incomplete-run sensitivity's subject, see Part 3), `raw_fail_per_run: list[int]` (one count per run, the rule's raw count "per report-only server and per run", report-only).
- `class NotRunCause(StrEnum)`: `BENIGN_CALL_FAILED`, `LAUNCH_FAILURE`, `THROTTLED`. The causes that take a server out of N for the whole nuisance run.
- `DROPPED_RUN_REASONS: dict[NotRunCause, str]`, the two causes of a drop during the runs only (`LAUNCH_FAILURE`, `THROTTLED`), as `holdout_results.DROPPED_RUN_REASONS`: the report counts them against the servers launched. A benign-call failure gets no entry: its row carries the check's own reason (which tool failed and how), as the holdout's pre-run check does, and the server was never launched for the runs.
- `@dataclass(frozen=True) class NotRunServer`: `server_package: str`, `reason: str`, `cause: NotRunCause`. A server left out of N for this run.
- `@dataclass(frozen=True) class FigureExit`: `server_package: str`, `reason: str`. A server outside the figure for a standing reason, one row of the rule's first exits table ("the servers outside the figure": no counted tool, an acceptance server, an excluded server, and so on). Not named `ExcludedServer`: "an excluded server" is one reason of that list (the holdout log's exclusions, `EXCLUDED_SERVERS`), not the table. Fed by the walk and the admission, not computed here: the orchestrator records the ones it is given.
- `@dataclass(frozen=True) class NuisanceRunResult`: the run-level fields on the model of `HoldoutRunResult` (runs, budget, provider, model, judge_model, reasoning, judge_reasoning, cutoffs, chain_budget, max_chain_steps, tool_call_timeout, grammar_fingerprint, counter_fingerprint, fixture_fingerprints, commit, census_commit, image_ids, prices_as_of), plus `recorded_at: str` (the ISO timestamp of the run, the rule's "each run records its date, since a model can change behind one identifier", which `HoldoutRunResult` has no field for because the holdout rule has no such clause. The clock is injected, Part 5), `servers: Sequence[NuisanceServerResult]`, `not_run: Sequence[NotRunServer]`, `outside_figure: Sequence[FigureExit]`, `incomplete_run_count: int`, `total_cost: float`.

**The holdout mirror** (`evals/holdout_results.py`, `evals/holdout_run.py`, behavior-preserving, its own step and commit). `HoldoutTargetResult` stops carrying `runs`, `detected_runs`, `detection_share`, `detected_runs_if_unchecked_missed`, `surfaced_places`, `struck_places`, `unchecked_places`, `aimed_runs`, `fail_without_proof_runs` and `incomplete_runs` as stored fields and carries `statuses: tuple[HoldoutRunStatus, ...]` instead, one per run in run order, beside its unchanged `cve_id`, `disclosure_date`, `mechanism_label`, `tools_count`, `ran_in_fallback` and `run_cost`. `@dataclass(frozen=True) class HoldoutRunStatus` holds exactly what `holdout_run._assemble_target` fills per run today from the run's `RunGrade | None`: `detected: bool` (the grade's status in `DETECTION_RUNGS`), `detected_if_unchecked_missed: bool` (`status_if_unchecked_missed or status` in the rungs), `surfaced_places: list[str]`, `struck_places: list[str]`, `unchecked_places: list[str]` (sorted place ids, empty on an incomplete run), `aimed: bool`, `fail_without_proof: bool` (False on an incomplete run), `incomplete: bool` (the run produced no grade). The former fields become read-only properties with the same names and the same values: `runs` (`len(statuses)`, equal to the run count since every assembled outcome is a graded or incomplete run), `detected_runs`, `detection_share`, `detected_runs_if_unchecked_missed`, `surfaced_places`/`struck_places`/`unchecked_places` (`list[list[str]]`, the per-run lists the report's `TargetLine` takes unchanged), `aimed_runs`, `fail_without_proof_runs`, `incomplete_runs`. `_assemble_target` builds the tuple through a private `_run_status(grade: RunGrade | None) -> HoldoutRunStatus` that absorbs `_detected` and `_detected_if_unchecked_missed`, so the grammar reads (`DETECTION_RUNGS`) stay in `holdout_run` and `holdout_results` keeps importing nothing from the grammar. The reads in `holdout_statistic.py` (`detection_share`, `detected_runs`, `detected_runs_if_unchecked_missed`), `holdout_report.py` (`detected_runs` for the ladder, every per-run field in `_target_line`) and `holdout_run._assemble_run` (`incomplete_runs`, `run_cost`) become property reads without a source change, and `holdout_markdown.py` reads the report model only. The two test constructors, `tests/unit/test_holdout_statistic.py`'s `_result` and `tests/unit/test_holdout_report.py`'s `_target`, build `statuses` from their count arguments instead of the flat fields, and `tests/unit/test_holdout_run.py`'s assertions on the assembled target read the properties unchanged. The refactor moves no eval number: the holdout is report-only, has no baseline and no drawn target, and every aggregate keeps its value, which those three test files assert. Its record is a `CHANGELOG.md` `[Unreleased]` tooling line, not a nuisance-log entry.

Schema field added to `evals/nuisance_admission.py`: `AdmittedServer.host: PlantingHost`, imported from `evals.cve_planting_base`, the container's user and network stance. It is the value object a holdout `CVETarget.planting_host` already carries (`user: SymbolicUser`, `HOST` or `UNPRIVILEGED`, `working_directory: str`, `has_network: bool`), set per target by calibration through the three `cve_targets` constants (`_HOST_NO_NETWORK`, `_UNPRIVILEGED_NO_NETWORK`, `_UNPRIVILEGED_WITH_NETWORK`). Decision by the maintainer (2026-10-22): the admitted server reuses it rather than a bare network bool beside a loose user decision (CLAUDE.md: when parameters accumulate, a concept is missing, and this one the codebase already names). The admission agents record it per server, exactly as calibration sets a holdout target's `planting_host`, and the maintainer settles a disagreement on it as any other field (a `FieldAgreement`/`AdmissionSettlement` on `host`). The field is required, with no default: a default would silently pick a user for a server nobody looked at, and no admission file exists yet to keep loading. Two readings the field carries. The user: an image without a `USER` runs as root inside the container, and the auditor's payloads reach the server, so `UNPRIVILEGED` (`--user 65534:65534 -e HOME=/tmp`) is the stance to record unless the patched image needs the host user (an npx or pip based image whose cache breaks under uid 65534 and `HOME=/tmp`), which the agents establish with the fix-check driver. The network: a patched server of an SSRF class answers its benign call by reaching an external host (example.com), so with no network it would error, leave N every run and never count. `has_network=True` records that. The input-side plan has no field for either, and the rule's Admission list has none, so the agents could not express them. `nuisance_launch` (Part 4) turns the field into `docker run` arguments. It is covered by `nuisance_fixture_fingerprint` (below), since it changes how the server runs. The dossier's `fixture_format.md` gains a line for it. Pydantic v2 validates a stdlib frozen dataclass as a field type natively, from JSON and to JSON (verified on the pinned 2.12.5): no `arbitrary_types_allowed`, no wrapper model.

`nuisance_images.nuisance_fixture_fingerprint` gains `planting_host_parts(server.host)` in its hashed parts (one line), the `[user.value, working_directory, has_network]` list `cve_baseline` already hashes into the acceptance fixture fingerprint as `_planting_host_parts`, made public in a rename (one touch to `cve_baseline.py`, behavior unchanged, the acceptance fingerprint unmoved) rather than redefined. Its docstring's "in" list names the host's user, working directory and network stance. A test pins that the fingerprint moves when any `PlantingHost` field changes.

## Part 3: the server-unit statistic

New module `evals/nuisance_statistic.py`, the sibling of `holdout_statistic.py` with the server as the unit and the flagged share in place of the detection share. It imports `wilson`, `newcombe`, `jeffreys`, `clopper_pearson`, `agresti_caffo` from `holdout_intervals` and `GammaPrior`, `hierarchical_interval`, `contrast_hierarchical` from `holdout_hierarchical`, unchanged.

- `Side`, `Placement`, `Contrast`, `MethodPlacement`, `ConclusionVerdict` are generic (none names `HoldoutTargetResult`): imported from `holdout_statistic`, not redefined. `holdout_statistic._placed` and `_placement` are the placement reading both suites share, so they go public (`placed`, `placement_of`) in a rename the holdout tests do not see (one touch to `holdout_statistic.py`, behavior unchanged). Only `SideStatistic` is typed on the result, so the nuisance defines its own, with `results: tuple[NuisanceServerResult, ...]`, `servers` (the count, as `targets` is the holdout's) and `split_share_sum` summing the split count (see `split_by_side` below). It is not called `share_sum` as the holdout's is: that name would read as the sum of `flagged_share`, which the side does not use.
- `figure(results) -> float`: `sum(r.flagged_share for r in results) / len(results)`.
- `cited_interval(results) -> Interval`: `wilson(sum of flagged_share, len)`.
- `split_by_side(results, run_cutoff: date) -> dict[Side, SideStatistic]`: each server on the side its `split_disclosure_date` places against the run cutoff, pre-cutoff when `<= cutoff`. A server whose `split_flaw is None` leaves the split (not in either side), as the rule says. The side's count is the sum of `split_flagged_runs / runs` over its members, not `flagged_share`: a server is flagged for the split through a counted tool of its split flaw only (the rule), so the split uses `split_flagged_runs`, not the whole-server `flagged_runs`.
- `side_of(disclosure_date, cutoff) -> Side` is generic too (two dates in, pre-cutoff when `disclosure_date <= cutoff`): imported from `holdout_statistic`, not redefined.
- `contrast(side_a, side_b) -> Contrast | None`: `None` below `_MIN_SIDE = 5`, else `newcombe` over the two split sums.
- `primary_controls(results, runs) -> dict[str, Interval]`: `jeffreys`, `clopper_pearson`, two hierarchical priors (`gamma_1_1`, `gamma_2_2`) over the per-server `flagged_runs`, and an `incomplete_as_flagged_wilson` sensitivity (the figure's Wilson with every incomplete, not-flagged audit counted as flagged instead of not, see the incomplete-run sensitivity below). It takes the place of the holdout's `unchecked_as_misses_wilson`: the nuisance audit has no replay credit, so that control has no analog, and the incomplete-run bound is the rule's own sensitivity.
- `check_conclusion(side_a, side_b, runs) -> ConclusionVerdict | None`: the Newcombe-cited contrast against zero, checked by agreement across eight methods on the model of the holdout's eight: `newcombe`, `agresti_caffo`, `hierarchical_gamma_1_1`, `hierarchical_gamma_2_2` over the split counts, and the same four suffixed `_incomplete_as_flagged` over the split counts with every incomplete, not-flagged run counted as flagged (`split_flagged_runs + incomplete_unflagged_runs` per server, the per-server counts raised the same way for the hierarchical methods). Inconclusive when any disagrees with the cited Newcombe, as the holdout's does, which is how the rule's "a conclusion that changes when these audits count as flagged is reported as inconclusive" is enforced.

Every per-server read of the statistic (`flagged_share`, `flagged_runs`, `split_flagged_runs`, `incomplete_unflagged_runs`, `runs`) is a property read over the result's `statuses` (Part 2), the same reads the holdout statistic makes on its own properties once the holdout mirror is in. The statistic never looks at a `NuisanceRunStatus` itself.

Incomplete-run sensitivity. The rule: "An audit that raises no counted FAIL, in which the model provider refused a step or a step came back unreadable, counts as not flagged in that run. ... A conclusion that changes when these audits count as flagged is reported as inconclusive." The name follows the status field (`incomplete`), the properties (`incomplete_runs`, `incomplete_unflagged_runs`) and the report line "Incomplete runs (a step refused or unreadable)": "refused" alone would leave the unreadable step out of the name. Each `NuisanceServerResult` exposes `incomplete_runs` and `incomplete_unflagged_runs` over its statuses. A server flagged in a run is flagged whatever step was refused (an alarm stands) and is not a sensitivity subject. A server not flagged in a run that had a refused or unreadable step is: the figure recomputed with its `flagged_runs` raised by `incomplete_unflagged_runs` bounds the other direction. `incomplete_as_flagged_wilson` publishes that bound, and the four `_incomplete_as_flagged` conclusion methods make the conclusion inconclusive when it flips the placement. The raised sum is a private `_incomplete_as_flagged_sum(results, runs)` as the holdout's `_unchecked_sum` is, with no public figure of its own (nothing would read it: the report publishes the bound as the control's interval). A test covers a server with an incomplete, not-flagged run moving the bound.

## Part 4: the nuisance audit and launch

New module `evals/nuisance_audit.py`, the one-audit-of-one-server path, injected behind a dependency so the unit tests fake it. It plants nothing and grades nothing: it launches the patched image, runs the graph with no tools filter and the run's chain settings and timeout, and returns the `AuditReport`. The retry and refusal policy is the suite's, close to `holdout_audit` but with a report (not a grade) as the outcome.

- `nuisance_launch(server: AdmittedServer) -> Launch`: a `cve_environments.Launch` of `command="docker"`, `args=["run", "-i", "--rm", *confinement_args(), *_user_args(server.host.user), "-w", server.host.working_directory, *_network_args(server.host.has_network), nuisance_images.image_tag(server.service), *server.launch]`, `chain_budget`/`max_chain_steps` left at the launch defaults (the run overrides carry the conditions). `confinement_args`, `no_network_args`, `host_user_args` and `unprivileged_user_args` come from `cve_planting_base` (`confinement_args` is also re-exported by `cve_planting`). `_user_args(user)` maps `SymbolicUser.HOST` to `host_user_args()` and `SymbolicUser.UNPRIVILEGED` to `unprivileged_user_args()` (`--user 65534:65534 -e HOME=/tmp`), the same mapping `cve_planting._symbolic_user_args` holds for planting, restated in a two-line match and never reused by making that helper public: `cve_planting.py` is in `cve_baseline._ENVIRONMENT_PATHS`, so renaming anything in it (an AST change) moves every acceptance fixture fingerprint and makes the CVE gate not comparable, which "What stays unchanged" forbids. `_network_args(has_network)` returns `["--network", "bridge"]` when `has_network` and `no_network_args()` (`--network none`) otherwise. The nuisance nuance, stated in the docstring: unlike the holdout, where `has_network=True` means a dedicated network with a sidecar, a holder or a planted endpoint, here it gives the plain default bridge with internet egress and nothing else, because a nuisance run plants nothing. It exists only so a patched SSRF server's benign call can reach an external host. No mount, no layout, no planting: a nuisance run plants nothing (the rule). The patched server's image seeds what it needs to start, the launch adds confinement, the user, the working directory and the network stance, each read from `server.host`. This fixes the meaning of `AdmittedServer.launch`, which the schema leaves undefined: it is the container command, the argv appended after the image tag (the image's `ENTRYPOINT`, when it has one, applies to it), as the acceptance launches append their server arguments. The dossier's `fixture_format.md` says so (Part 7).
- `async def benign_call_failure(server, mcp_client) -> str | None`: calls each counted tool's benign call (the `BenignCall` of every counted flaw whose `tool` is a counted tool, deduplicated by tool) through `MCPClientPort.call_tool(name, args)`, and returns the reason when any raises (a protocol error) or returns a `ToolResponse` with `is_error=True`, else `None`. Named for what it returns, as `holdout_run.vet_reason` is: a `benign_calls_pass` that is truthy on failure would read backwards at the call site. The orchestrator's vet runs it once per nuisance run, before the runs, over a short-lived connection (Part 5), and a failure drops the server from N for the run (`NotRunCause.BENIGN_CALL_FAILED`).
- `@dataclass(frozen=True) class LaunchFailed`: `reason: str`, the infra-failure sentinel. An attempt is `AuditReport | LaunchFailed`: a nuisance audit always produces a report unless the launch itself failed, and a refused, unreadable or throttled step is a `MissedStep` in the report, not a failure.
- `async def audit_once(server, auditor, overrides) -> AuditReport | LaunchFailed`: open the launched patched server (`cve_environments.connect(launch, devnull, tool_call_timeout=overrides.tool_call_timeout)`, the stderr to `os.devnull` as `cve_audit._silent_client` does), build the graph (`build_graph(auditor.llm, AuditedServer(client), judge_llm=auditor.judge_llm, tools_filter=None)`), `ainvoke` under `one_audit()` with `test_budget=auditor.budget`, a fresh `AttackContext()` and the overrides' `chain_budget`/`max_chain_steps`, return `result["audit_report"]`. No benign check here: the vet did it once before the runs. Any exception out of the launch, the connection or the graph is caught and returned as `LaunchFailed(str(exc))`, as `cve_audit._audit` wraps every exception in `LaunchError` and `attempt_once` maps it to a skip.
- `async def nuisance_audit(server, attempt) -> AuditReport | DroppedRun`: one run of one server. A report with no throttled step stands (an alarm in it stands whatever step was refused, and a report with no counted FAIL and a refused step reads as not flagged downstream). A report holding a `MissedStep` with `MissCause.PROVIDER_THROTTLED` is thrown away as a throttled attempt, exactly as `cve_audit.attempt_once` turns it into `ThrottledAttempt`, and is retried like an infra failure. A `LaunchFailed` is retried. At most `NUISANCE_INFRA_ATTEMPTS = 3` calls in all, and the run drops when every attempt failed: `DroppedRun(THROTTLED)` when any attempt was throttled, else `DroppedRun(LAUNCH_FAILURE)`. This mirrors `holdout_audit`, with the report (for counting) in place of the grade.

The audit does not record calls (`RecordingClient`), does not replay, does not grade. It reuses `build_auditor`, `RunOverrides`, `one_audit()` and `AttackContext`. The 429 count printed per attempt reads `report.provider_usage.throttled_requests` as `cve_audit._print_incidents` does, for display only. What drops a run is the `PROVIDER_THROTTLED` missed step above. An incomplete run is a kept report holding a `MissedStep` whose cause is `MissCause.PROVIDER_REFUSAL` or `MissCause.UNREADABLE_ANSWER` (the rule's "refused a step or a step came back unreadable"): the assembly (Part 5) records it as `incomplete=True` on that run's `NuisanceRunStatus`, and the server's `incomplete_runs` and `incomplete_unflagged_runs` properties count them.

## Part 5: the run orchestrator

New module `evals/nuisance_run.py`, the sibling of `holdout_run.py`. It audits every admitted server at one commit under the run conditions, keeps no per-case trace, and assembles the per-server and whole-run result.

- `NUISANCE_RUNS = 3` (the default the log sets before the first real run, a `--runs` flag lowers it, as the holdout's does), `NUISANCE_CONCURRENCY = 6`. The budget is the holdout's: the rule reads the figure beside "the holdout run the figure is read beside", whose budget is the constant `holdout_run.HOLDOUT_BUDGET` ("a constant, not a flag", holdout-rule.md:227), so the nuisance imports that constant and adds no flag and no constant of its own. A `--budget` flag would let a figure be produced under a budget no holdout run has, and nothing would catch it.
- `@dataclass(frozen=True) class NuisanceDeps`: `audit: Callable[[AdmittedServer], Awaitable[AuditReport | DroppedRun]]`, `benign_call: Callable[[AdmittedServer], Awaitable[str | None]]` (the pre-run benign check, its failure reason or None, gathered over every server before any audit), `rebuild: Callable[[Sequence[str]], None]`, `image_ids: Callable[[Sequence[str]], dict[str, str]]`, `read_tree: Callable[[], TreeState]`, `clock: Callable[[], str]` (the ISO timestamp `recorded_at` records, injected as `cve_session_model.Harness.clock` is: CLAUDE.md puts clock access behind an injected dependency, never a direct call). Faked by the tests, built from the live settings by `default_deps(overrides, concurrency)`, whose `clock` is `lambda: datetime.now(UTC).isoformat()` as `run_cve_benchmark` composes it. The `RunOverrides` it takes is built from the conditions inside `run_nuisance` (chain budget, chain steps, timeout, each asserted non-None after `require_ready`), as `holdout_run._overrides` does, restated locally since that helper is private.
- `@dataclass(frozen=True) class RunPopulation`: `audited: Sequence[AdmittedServer]` (the admitted servers the run audits) and `outside_figure: Sequence[FigureExit]` (the standing exits, recorded in the result, never audited). The two lists are one concept, the admitted population partitioned by the rule's exits: `run_population` (Part 7) computes both from the same reads, and the orchestrator takes both, so they travel as one value object rather than as two arguments (CLAUDE.md: when parameters accumulate, a concept is missing).
- `async def run_nuisance(population: RunPopulation, draw_order, conditions, settings, census_commit, *, runs=NUISANCE_RUNS, concurrency=NUISANCE_CONCURRENCY, deps=None) -> NuisanceRunResult`: `draw_order` is the `Sequence[DrawEntry]` of `holdout_draw.draw_order(census)`, the one object the split needs (each entry carries its `identifier` and its `disclosure_date` in draw order), in place of a disclosure-date mapping and a draw-order index passed side by side (CLAUDE.md, few arguments: the two mappings were one concept, the draw order, which the code already names). Refuse tracing, refuse a dirty tree, `require_ready` the conditions on the run's models, rebuild the patched images, vet each audited server by its benign call (a failure is a `NotRunServer(BENIGN_CALL_FAILED)`, out of N for the run), audit the survivors over the runs, assemble. No server surviving the vet and the runs is a `Refused("nuisance run refused", ...)` listing the not-run reasons, as `run_holdout` refuses with no surviving target (a figure over zero servers has no interval). `population.outside_figure` is recorded in the result unchanged.
- The per-server assembly, pure over the reports, lives in `evals/nuisance_assembly.py` from the start rather than in the orchestrator: `holdout_run.py` carries its assembly inline and is past 300 lines (CLAUDE.md, files rarely exceed 300 lines), and the nuisance orchestrator has the same shape. It picks the split flaw first: the first `DrawEntry` of `draw_order` whose identifier is one of the server's counted flaws with a counted tool (a counted flaw absent from the draw order is never the split flaw), and stores its `identifier` as `split_flaw` and its `disclosure_date` as `split_disclosure_date`. It then builds one `NuisanceRunStatus` per report, in run order: `flagged` (`flagged_tools` non-empty), `split_flagged` (the flagged set meets the split flaw's counted tools, False with no split flaw), `incomplete` (`nuisance_audit.is_incomplete`), `raw_fail_count` (`raw_fail_count` of the report). The rest is `tools_count` (`len(reports[0].tool_reports)`, as the holdout's) and `run_cost` (as `holdout_run._run_cost`, over the generator and judge usage at the conditions' prices). No aggregate is computed here: `flagged_runs`, `flagged_share`, `split_flagged_runs`, `incomplete_runs`, `incomplete_unflagged_runs` and `raw_fail_per_run` are the result's properties (Part 2). The split needs the counted tools of one flaw, which `nuisance_counting` does not expose today (`counted_tools(server)` aggregates over the server): it gains `flaw_counted_tools(flaw: FlawRecord) -> frozenset[str]` (the flaw's non-removed `patched_name`s, empty when the flaw `needs_backend` or its `declared_function_is_effect`), extracted from the loop of `counted_tools`, which then calls it. A counted flaw with an empty set is skipped when the split flaw is chosen (the rule's "that still has a counted tool"). The module is in `_COUNTER_PATHS`, so this moves the counter fingerprint, which is new in this plan and pinned by no baseline.
- `default_deps` builds the auditor with `build_auditor(HOLDOUT_BUDGET)`, the audit from `nuisance_audit.audit_once` wrapped in `nuisance_audit.nuisance_audit`, the benign call from `benign_call_failure` over a short-lived connection to the same `nuisance_launch`, both `bounded` by the concurrency as the holdout's are, `read_tree` as the holdout's. `rebuild` is `holdout_run.rebuild_images` (an unconditional `docker compose -f compose.yml build <services>`, with the build cache) over each admitted `service`, whose compose entry the admission session writes in `evals/docker/compose.yml` (the one `COMPOSE_FILE` `rebuild_images` reads, with its `Dockerfile.<service>` under `evals/docker/`, where `nuisance_fixture_fingerprint` reads it) with `image: mcp-auditor-nuisance-<service>:local`: the rule says "before each nuisance run, every image is built again from its committed Dockerfile, with the build cache", which `cve_images.ensure_images` does not do (it skips an image whose fingerprint label is current), so the injected-tag `ensure_images` stays with the preflight and is not used here. `image_ids` cannot be `cve_baseline.image_ids` as it stands: it inspects `cve_targets.image_tag(name)`, the acceptance namespace, so on a nuisance service it would inspect a tag that does not exist and raise. It gains a `tag: Callable[[str], str] = image_tag` parameter, exactly as `cve_images.stale_services` did, and nothing else: the nuisance passes `nuisance_images.image_tag` (`functools.partial`), the acceptance and holdout call sites are unchanged, and the function keeps its direct `subprocess.run(["docker", "image", "inspect", ...])`. Decision by the maintainer (2026-10-22): no port is opened for it. `image_ids` has no unit test at HEAD and keeps none: the run tests fake `image_ids` whole through `NuisanceDeps`, as the holdout's do through `HoldoutDeps`, and the only live caller of the partial is `default_deps`, which no unit test covers either way (CLAUDE.md: maintainability beats coverage). Moving the inspect call behind `cve_images.ImageStore` would add a method to the port and to its two implementations for a one-line default-parameter change, out of this plan's scope.

The refusals (`_refuse_tracing`, `_refuse_dirty_tree`) are rewritten locally with the nuisance title: the holdout's say "holdout run refused", so they are not shared. The retry policy lives in `nuisance_audit`, not here, and the per-server assembly in `nuisance_assembly`, so `nuisance_run.py` holds the orchestration, `NuisanceDeps`, `default_deps` and `run_population` (Part 7) and stays under 300 lines.

## Part 6: the report and its markdown

New modules `evals/nuisance_report.py` and `evals/nuisance_markdown.py`, the siblings of the holdout's, rendering a proof-free report model. No `evidence`, no judge input, no verdict per case is written or printed (the rule's Reading section): the report carries per-server statuses, the figure, the split, the controls, the two exits tables and the raw count only.

- `NuisanceReport` (pydantic): `figure: float`, `cited_interval`, `controls`, `run_cutoff`, `sides`, `contrast`, `conclusion`, `servers: list[ServerLine]` (per server: package, flagged share, `flagged_per_run` (the status per run), incomplete runs, `counted_tools_count`, `tools_count`, `raw_fail_per_run`, run cost, each per-run or aggregate value read from the result's properties over its `statuses`, as the holdout's `_target_line` reads its own), `not_run: list[NotRunLine]`, `outside_figure: list[FigureExitLine]`, `incomplete_run_count`, `total_cost`, and the run conditions and provenance (provider, model, judge_model, reasoning, judge_reasoning, runs, budget, cutoffs, chain settings, grammar_fingerprint, counter_fingerprint, fixture_fingerprints, image_ids, commit, census_commit, prices_as_of, `recorded_at`), so a reader tells two runs apart. The generic line models (`IntervalModel`, `MethodLine`, `ConclusionLine`, `CutoffModel`, `RunCutoffModel`) are imported from `holdout_report`, not redefined. `SideLine` is redefined with `servers` in place of `targets`, and `ServerLine`, `NotRunLine` (keyed on `server_package`, with the nuisance `NotRunCause`) and `FigureExitLine` are the nuisance's own.
- `build_report(run: NuisanceRunResult) -> NuisanceReport`, by the model of `holdout_report.build_report`: the figure, the split against the run cutoff, the contrast and conclusion. Two touches to `holdout_report.py`, behavior unchanged, so both reports share what is generic: `_run_cutoff` (the latest cutoff among the run's models, the generator first on a tie) goes public as `run_cutoff`, and `_method_line` becomes `MethodLine.of(method)`, the module's own idiom (`IntervalModel.of`, `CutoffModel.of`, `NotRunLine.of`). `_conclusion_line` stays private in the holdout: it is typed on the holdout's `SideStatistic` and `check_conclusion`, so the nuisance report restates its five lines over `nuisance_statistic.check_conclusion`.
- `render_markdown(report) -> str`: a `# Nuisance suite` header, the recorded-at line, the figure line published "at most" (`Figure: at most {figure:.3f} (95% Wilson {span})`), the split section, the controls, the **two exits tables** (the rule's "one row per reason with its count": the standing exits from `outside_figure` grouped by reason, and the out-of-N-for-this-run from `not_run` grouped by cause, each row naming its servers), the raw count per server and per run, the per-server rows, the incomplete-runs line and the total cost. The raw count is labeled report-only and never compared.

The exits tables are the rule's two: the servers outside the figure (no counted tool, acceptance, excluded, not stdio, not containerisable, spent by a reading, and so on), fed from `outside_figure`, and the servers left out of N for this run only (benign call failed, not run after retries), fed from `not_run`.

## Edge cases

- An empty admission: `run` prints `no server is admitted` and exits 0, the machinery wired and tested before the session.
- A server with a counted tool but whose every run had a refused step and no counted FAIL: every status `flagged=False, incomplete=True`, so flagged share 0 and `incomplete_runs` equal to the runs, surfaced in the incomplete-run sensitivity and the incomplete-runs line.
- A server flagged in a run that also had a refused step: flagged (an alarm stands through a refusal), not a sensitivity subject.
- A server whose benign call fails in one run: out of N for that run (`NotRunServer(BENIGN_CALL_FAILED)`), and since N must be the same in every run, a server that fails any run is out of N for the whole nuisance run (the rule). The orchestrator vets once before the runs, so a benign failure drops the server from the whole run, which keeps N constant. A run-to-run benign flake is not modeled (the vet is once per nuisance run, before its runs).
- A server with no counted flaw reaching the split's draw-order frontier (no `split_flaw`): it leaves the split but stays in the figure.
- A chain stepping through another tool than the one it was planned against: cannot happen in this graph, every step of a chain calls `state["current_tool"]` (`chain_nodes.make_execute_step`), so reading the chain's owning tool is the rule's "any of its steps calls such a tool" exactly, which the comment in `tool_verdicts` records.
- An SSRF-class server with `host.has_network=False` by mistake: its benign call errors, it drops from N, and the exits table names it (`benign call failed`), so the mistake is visible, not silent. The same for a `host.user` the image cannot run under: the benign call fails to connect, and the row names it.

## Test scenarios

Layout (CLAUDE.md, Given/When/Then): one `tests/unit/test_<module>.py` per new module, its setup in `tests/unit/support/test_<module>_given.py` only where a helper abstracts something (a crafted `NuisanceServerResult`, a scripted audit, the faked `NuisanceDeps`, as `test_holdout_run_given.py` does), a one-liner inlined. The `with_host` mutator joins `test_nuisance_admission_given.py`. Every scenario asserts on what the function returns or prints, never on a private constant or on which calls were made.

- The holdout mirror: no new scenario. The existing holdout statistic, report and run tests assert on the same aggregate values (`detected_runs`, `detection_share`, `detected_runs_if_unchecked_missed`, `unchecked_places`, `aimed_runs`, `fail_without_proof_runs`, `incomplete_runs`, the ladder, the incomplete-runs line) before and after the refactor, which is the guard: only their two constructors change, to build `statuses`.
- `tool_verdicts` over a report with cases and chains on several tools: one verdict per case and per chain, each carrying its tool, the read fields only.
- `flagged_tools`: a counted tool judged FAIL in a valid category is flagged. The same tool FAIL in a category its set excludes is not, a non-counted tool FAIL is not, a counted tool PASS is not. A chain FAIL on a counted tool flags it.
- `raw_fail_count`: every FAIL counted, on every tool and category, PASS and None excluded.
- `counter_fingerprint`: stable across two calls and distinct from `grammar_fingerprint()` (the grammar is not in it); no literal is pinned (every edit of the counter would move it) and the private path tuple is not asserted on (CLAUDE.md: tests assert on observable outcomes, never on internal structure; `GRAMMAR_PATHS` has no such test either). The comment and formatting invariance is `fingerprint_source`'s, already tested in `evals/baseline.py`'s tests, not re-tested here.
- `flaw_counted_tools`: the non-removed patched names of a flaw; empty when it `needs_backend` or its `declared_function_is_effect`; `counted_tools` unchanged on the existing cases.
- `figure`, `cited_interval` over crafted server results: the mean of flagged shares and its Wilson.
- `split_by_side`: a server pre-cutoff and one post-cutoff by their `split_disclosure_date`; a server with `split_flaw None` leaves the split; the side count uses `split_flagged_runs`, not `flagged_runs` (a server flagged on another flaw's tool but not the split flaw's contributes 0 to its side).
- `contrast`, `check_conclusion`: `None` below five a side. Above, the Newcombe contrast and the eight-method agreement, a disagreement reading inconclusive.
- the incomplete-run sensitivity: a server with a not-flagged incomplete run moves `incomplete_as_flagged_wilson`, and a side whose `_incomplete_as_flagged` methods place the contrast differently from the cited Newcombe reads inconclusive.
- `nuisance_launch`: `--network none` when `host.has_network=False`, a bridge when True; `--user 65534:65534` when `host.user` is `UNPRIVILEGED`, the host user's uid and gid when `HOST`; `-w` with `host.working_directory`; the image is `mcp-auditor-nuisance-<service>:local`; confinement present; no mount, no layout args.
- `benign_call_failure` over a fake client: `None` when every counted tool's benign call returns clean, a reason when one returns a tool error or raises a protocol error.
- `nuisance_audit` over a fake attempt: a report stands; a `LaunchFailed` is retried twice then drops (`LAUNCH_FAILURE`); a report holding a `PROVIDER_THROTTLED` missed step is retried and, when every attempt fails, drops as `THROTTLED`; a report with a refused step and an alarm stands flagged; a report with a refused or unreadable step and no counted FAIL is kept and `is_incomplete` on it (the fact the assembly records as that run's `incomplete` status).
- `run_nuisance` over faked deps and a crafted run population: the per-server results, the not-run and outside-figure rows, the figure, the split, N constant across runs; a benign-failing server out of N; an infra-dropped server out of N; the run conditions and fingerprints in the result; the budget in the result is `HOLDOUT_BUDGET`; no survivor is `Refused`.
- `run_population`: a walk-marked server, a `runs_over_stdio=False` server and a `runs_in_container=False` server each give one `FigureExit` with its reason and are absent from `audited`; an unmarked, stdio, containerised server is in `audited`.
- `assemble_server` over three reports: the `statuses` tuple carries the per-run facts in run order, and the properties read from it (`flagged_runs`, `flagged_share`, `split_flagged_runs`, `incomplete_runs`, `incomplete_unflagged_runs`, `raw_fail_per_run`) give the expected counts. No scenario for `cve_baseline.image_ids`: it has no unit test at HEAD and gains none (Part 5), the run tests fake `image_ids` whole.
- `build_report`/`render_markdown`: the figure line reads "at most", the two exits tables each have a row per reason, the per-server line shows the status per run, the raw count is present and labeled report-only, no proof or judge input appears anywhere in the output.
- `nuisance_fixture_fingerprint` moves when any `PlantingHost` field changes (the user, the working directory, the network stance).
- `run_nuisance.main(["run", "--census", ..., "--admission", ...])`: with `--admission` pointing at a missing file exits 0 and prints `no server is admitted`; with a written admission whose `servers` is empty, the same; tracing set exits 3 (refused) before the admission is read.
