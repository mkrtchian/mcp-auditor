# Nuisance suite assembly, fifth batch: closing the first eighty-six draw positions

## Context

The nuisance suite admits twenty-nine servers after the first four batches (`evals/nuisance_admission.json`), with the fix-check mechanism (`evals/nuisance_fix_checks/`, `FIX_CHECK_TARGETS`, `run_nuisance calibrate`, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` tests), the backend registry (`evals/nuisance_backends.py`, with `doris`, `mysql`, `ckan`, `contextforge`, `n8n`, `atlassian`, `apify` wired), and the kit builders those used. A fifth admission batch produced two independent blind records per server for ten more candidates and a maintainer adjudication for each; five are admitted firmly, one is conditional on calibration, and four are dropped. This plan turns those settlements into committed artifacts, extending the admission from twenty-nine servers to thirty-three (thirty-four if the conditional server calibrates).

This batch closes the first eighty-six positions of the salted draw order. Unlike batches 2 and 3, none of its servers is a holdout twin (one exception: the second flaw on ContextForge, a server already admitted), so there is no `holdout_calibration` recopy: every counted flaw carries a fresh `FixCheckTarget` calibrated under Docker. Unlike batches 2 to 4 the scope mixes four mechanism classes and two new backend provisioners, and one of the counted flaws is a second `FlawRecord` added to an existing admission entry rather than a new server.

Scope is five servers plus one edit:

- **kubectl** (PyPI:kubectl-mcp-server), command_execution, no backend.
- **gemini-bridge** (PyPI:gemini-bridge), read_outside_scope, no backend.
- **contextforge** second flaw CVE-2026-53710 (PyPI:mcp-contextforge-gateway), command_execution: **deferred out of this batch (Decisions 7, option (c))** because `execute_code` lives in a separate stdio server (`python_sandbox_server`), not the audited gateway wrapper; to be admitted later as its own server.
- **jenkins** (`https://github.com/hekmon8/Jenkins-server-mcp`, the census spelling `server_package` must carry exactly, `_foreign_flaws` matches on it), internal_fetch, a new mock-Jenkins responder backend.
- **neo4j-cypher** (PyPI:mcp-neo4j-cypher), internal_fetch, a new Neo4j database backend.
- **sylphxltd/filesystem** (npm:@sylphxltd/filesystem-mcp), read_outside_scope, no backend, conditional: admitted only if its patched release answers the benign call cleanly, dropped and logged otherwise.

Four servers are dropped and only logged, never admitted, all by the ratified dfie principle (Principle A, locus-irrelevant contract test): repomix (CVE-2026-49988, `attach_packed_output` reads a caller-named local file), auth-fetch (CVE-2026-49857, a URL-fetch tool whose effect is also invisible in any response), houtini/lm (CVE-2026-82112, `code_task_files` reads caller-named absolute paths), excel (CVE-2026-40576 and CVE-2026-85661, `read_range` reads a caller-named workbook path).

## Approach

Same split as the earlier assemblies: eval data (the admission entries and any Dockerfiles) is authored directly and committed by hand; repo logic (backend provisioners, a fix-check module with its own builder, tests) goes through the implementation flow. The repo-logic surface this batch is the largest since batch 1: two new backend provisioners and five fresh fix-check modules (four counted servers plus the ContextForge second flaw; the conditional sylphxltd adds a sixth if it calibrates).

Run Dockerfiles, as at every batch since 2, are maintainer-authored (`Dockerfile.<service>`, a nuisance `service` slug that is not an acceptance service). The nuisance Dockerfiles are not compose services (batch 4 corrected the batch 3 wording: `calibrate` builds the fix-check images through `kit_launch.build_images`, `Responder.ensure` builds a responder image), so no compose entry and no fingerprint label is added. The acceptance service names are `filesystem`, `filesystem-patched`, `git`, `git-patched-68143`, `kubernetes`, `kubernetes-patched`, `fetch`, `fetch-patched` (`calibration_dossier.acceptance_services()`, enforced by `namespace_problems`): the sylphxltd service must not be named `filesystem`, use `sylphxltd-filesystem`. Because no server here is a `holdout_calibration` twin, every counted flaw carries a `FixCheckTarget`, so every counted server's vulnerable and patched Dockerfiles are authored in this batch (there is no deferred-only server); the patched one doubles as the run image.

The admission data each new server contributes is one `AdmittedServer` entry merged after the existing twenty-nine (untouched), with its counted flaw(s), the settled counted tools, a benign call per counted tool, its dropped flaws kept with their real or null class, its `agents`/`agreement`/`settlements`, a `fix_check` block (`source` `fix_check`, with a `FixCheckTarget`), and for jenkins and neo4j a `backend` naming the provisioner. The ContextForge second flaw is a new `FlawRecord` appended to the existing entry's `flaws` list; nothing else in that entry changes.

## What this batch reuses, and therefore does not build

The earlier assemblies built, and this batch does not touch: `evals/nuisance_fix_checks/` and its module convention (this batch adds modules and imports them into `evals/nuisance_fixtures.py`, extending `FIX_CHECK_TARGETS`), the `run_nuisance calibrate` command and its handling, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` coverage/parity tests' logic (new rows are picked up automatically), the backend registry mechanism (`RegisteredBackend`, `backend_problems`, `backend_image_ids`), the kit builders, and the existing twenty-nine entries. The `apify` fix-check (`evals/nuisance_fix_checks/cve_2026_46341_apify.py`) is the nearest precedent for jenkins: an internal_fetch flaw whose builder stands a per-launch responder carrying the random witness nonce on the backend bridge and reaps it when the launch ends, with a `FixCheckTarget` whose `vulnerable_service`/`patched_service` name the two server images. The `doris`/`mysql` provisioners (`evals/doris_backend.py`, `evals/mysql_backend.py`) are the nearest precedent for neo4j's separate-database backend (ensure one persistent container on a labeled bridge, reach it by container name, reap on teardown), and the `ckan`/`contextforge`/`apify` responder provisioners on `evals/responder_backend.py` are the precedent for jenkins's mock responder. The command_execution fix-checks already in the tree (kanban `cve_2025_53818_github_kanban.py`, token-optimizer `cve_2026_55157_token_optimizer.py`) are the precedent for kubectl and the ContextForge escape, and the read_outside_scope fix-checks are the precedent for gemini-bridge and sylphxltd.

### kubectl (nb45), new server

Counted flaw CVE-2025-65719 (command_execution), dfie False (the settled disagreement is none: records A and B agree False). Counted tool **`port_forward`**: it builds a shell string from the `namespace` argument and passes it to `os.system`, and the declared contract of a port-forward tool is to forward a port, so the injection is a bypass, not the contract. `backend_need` none. Patched **1.23.1** source `fix_commit` (the advisory names 1.2.0, a stale numbering absent from PyPI; the PyPI history starts at 1.12.0, the vulnerable reaching version; 1.23.1 is the first release that replaces `os.system` with a list-form `subprocess` call). `server_patched_surfaces` null (the flaw's patched version is the server's). Witness (Decisions 6): the counted tool is `port_forward` alone, and the injected command's output is reflected in `port_forward`'s own response (the kanban precedent: the injecting tool surfaces the command output, so the exploit calls only the injection point and the parity test `test_each_target_mechanism_and_tools_match_the_admission_flaw` holds with `tools=[port_forward]`). The nonce comes from a planted witness file (a `PlantKind.FILE` Place the injected command reads, `command_injection_env` as the kanban fix-check does), never from the exploit text, so the grammar's anti-echo rule credits the surfacing. `list_contexts` is not a counted tool. The kubeconfig and any written path must be writable under the read-only launch (`HOME=/tmp` from `unprivileged_user_args`). Confirm at calibration that `port_forward` reflects the injected output; if it cannot, the witness is reconsidered there rather than counting a read-back tool. Benign call: `port_forward` with ordinary arguments; with no cluster it returns an error dict (not an MCP error, `isError` false), so `patched_benign_errored` is false (confirm the harness reads it clean at calibration). Launch landmines, from record B, to honor in both Dockerfiles: pin `fastmcp==3.4.11` (the bare `fastmcp>=3.0.0b1` resolves a 4.x release, 4.0.0 stable since 2026-08-31 and 4.1.4 the latest, that breaks the import), and set the entrypoint to `kubectl-mcp-serve serve --transport stdio` for both versions (the `kubectl-mcp` entrypoint of 1.23.1 is broken, it passes a removed `non_destructive` kwarg). The vulnerable reaching version is 1.12.0.

### contextforge second flaw CVE-2026-53710 (nb50), edit of the existing entry

**Deferred out of this batch (Decisions 7, option (c)); this section is retained for the future separate-server admission of `python_sandbox_server`, which ships `execute_code`.** This is a second counted `FlawRecord` added to the existing `PyPI:mcp-contextforge-gateway` entry (service `contextforge`, already admitted for CVE-2026-18905 internal_fetch with the `contextforge` backend). Counted flaw CVE-2026-53710 (command_execution), dfie False. Counted tool **`execute_code`**: a RestrictedPython sandbox escape (a raw `getattr` in `safe_builtins` walks the class hierarchy to `subprocess.Popen`). The declared contract of `execute_code` is *confined* execution (the RestrictedPython sandbox), and the flaw and its fix are about the OS escape, not about evaluating Python, so a command_execution finding on the patched server is a false alarm to count. (The settlement records the contested history: records A and B said dfie False, the maintainer flipped to True, an independent adversarial review reversed the flip, the maintainer stood down to False; the deciding test is that the counted effect, OS command execution, does not fire on the patched server by construction, so dfie is False.) `backend_need` none (the escape needs no responder, unlike the 18905 SSRF). Patched **1.0.2** source advisory. The server's `patched_version` stays **1.0.7** (the pin that fixes 18905 and also fixes 53710), so 1.0.7 differs from 1.0.2 and `server_patched_surfaces` is **set** for this flaw, checked at 1.0.7, exactly as n8n's GHSA-8g7g is set because the server's version exceeds the flaw's (so `_patched_version_problems` stays satisfied: the server's 1.0.7 is in the counted set {1.0.7 for 18905, 1.0.2 for 53710}, and 53710's differing version carries a set `server_patched_surfaces`). **Calibration condition (raised in adversarial review)**: the witness must be the OS escape (a shell command surfacing the nonce via `subprocess`), which fails on 1.0.2, not a plain `print(1+1)` (which would succeed on the patched sandbox and be a false witness). `validate_code`/`get_sandbox_info` are not counted (not the effect). Nothing else in the ContextForge entry changes beyond what follows: the existing 18905 flaw, its `contextforge` backend, host and launch are untouched.

Three gaps found in review, to settle before the edit is committed:

1. **Server identity settlement (blocking for `load_admission`)**: the census classifies CVE-2026-53710 under `https://github.com/IBM/mcp-context-forge`, not `PyPI:mcp-contextforge-gateway`. `_foreign_flaws` rejects a flaw that is not a census flaw of the entry's `server_package` unless the entry carries a settlement `{server_package: "PyPI:mcp-contextforge-gateway", flaw: "CVE-2026-53710", field: "server_package", value: "PyPI:mcp-contextforge-gateway", reason}` (`_settled_to_server`). The edit appends that settlement (the existing entry has only its `runs_over_stdio` one), plus the agents' and agreement rows for the new flaw. This is the "repository identifier of mcp-contextforge-gateway" case the nuisance log entry of the addition names.
2. **Three arms, three images**: the census records the flaw as affecting `< 1.0.2`, vulnerable version **1.0.1**, so the existing `contextforge-vuln` (1.0.6, already past the 53710 fix) cannot be the vulnerable arm. The target needs a new vulnerable image (1.0.1) and a new patched image (1.0.2), with `server_patched_service="contextforge"` (the existing 1.0.7 image). Name them after the n8n/flyto precedent, for instance `contextforge-flaw-1.0.1` and `contextforge-flaw-1.0.2`, none an acceptance service. Their Dockerfiles must boot under the same bootstrap as `Dockerfile.contextforge` (the `/tools/`, `/servers/` and `mcpgateway.utils.create_jwt_token` / `mcpgateway.wrapper` interfaces of the entrypoint); that those 1.0.1 and 1.0.2 releases honour them is unverified and is checked at the first build.
3. **Where `execute_code` is exposed**: the census reason says the flaw is in the `execute_code` tool of the *python sandbox MCP server* the package ships, a separate stdio server, not a tool of the gateway wrapper that the existing image's entrypoint exposes (its tool list is the registered REST tools such as `fetch-report`). An `AdmittedServer` has one `service`, one `launch` and one `backend`, and the nuisance run audits that one launch, so a counted `execute_code` is vacuous in the run (it can never be flagged) unless the run image exposes it. The fix-check can reach it by its own builder and entrypoint override, but the run cannot without changing `Dockerfile.contextforge` (which would move the 18905 entry's fixture fingerprint and its patched and server-patched arms). **Settled (Decisions 7, option (c)): 53710 is deferred out of this batch** and admitted later as its own server (`python_sandbox_server`); options (a) (extend the gateway image, moving the 18905 fingerprint) and (b) (count a tool the run never exposes) are both rejected.

### jenkins (nb41), new server, new backend

Counted flaw CVE-2026-10276 (internal_fetch), dfie False (**a flip from records A and B, which both said True**, confirmed on the source `src/index.ts` and by an independent adversarial review): `axios.create({baseURL: JENKINS_URL})` fixes the host, and `validateJobPath` blocks absolute schemes and the literal `..` form, but the counted exploit uses **percent-encoded traversal in `jobPath`** (`%2f`/`%5c`/`%2e%2e`) to escape the job namespace and reach an internal Jenkins path under the configured host. The declared contract is to fetch a build log from the *configured* Jenkins (a bounded target), so the encoded-traversal bypass is not the contract. Patched **`fix_commit` `dcee5f1`** ("block encoded path separators in jobPath", 2026-05-12), the commit that rejects `%2f`/`%5c`/`%2e%2e`; `833d321` (record B) rejects only the literal `..` form and is still vulnerable to the encoded one, so it is not the patched arm. The vulnerable arm is a pre-fix commit lacking the encoded check (candidate `b1f32a7`, settled at calibration). `buildNumber` stays unvalidated on both arms, so the witness travels through `jobPath`, never `buildNumber` (Decisions 3 and 11). Counted tools: **`get_build_log`** (returns `consoleText`, the fetched body) and **`get_build_status`** (returns `/api/json`); `get_failed_build_log` is confirmed at calibration (it validates `jobPath` and returns a log); `trigger_build` is not counted (its response is a queue status, not the reached body). `backend_need` fixture (the `jenkins` provisioner). `server_patched_surfaces` null (patched is the server's version). Host `has_network` true (the server joins the provisioner bridge). Witness: the encoded-traversal `jobPath` reaches a sentinel path on the mock Jenkins whose body carries the nonce, surfaced through the counted tool's response. Benign call per counted tool against a legitimate build endpoint the responder serves. The server's `JENKINS_URL`/`JENKINS_USER`/`JENKINS_TOKEN` point at the responder, from the run Dockerfile `ENV` (the singleton's fixed address). The fix-check stands a per-launch responder on another address of the bridge (as apify's does, in the 100 to 250 range of 198.18.2.0/24, the singleton below it), so its builder overrides `JENKINS_URL` with a `-e` on the server's `docker run`, which wins over the baked `ENV`. The fix-check Dockerfiles of the two arms (`jenkins-vuln`, `jenkins`) must therefore not depend on the baked address.

## Fix-check source policy

Every counted flaw this batch is `source` `fix_check` with its own `FixCheckTarget` (none is a holdout twin at the holdout's calibrated version, so no `holdout_calibration` recopy applies). `run_nuisance calibrate` visits each target, builds the vulnerable version and confirms the witness surfaces there and on neither the patched nor (where set) the server-patched version, with the benign call clean. The ContextForge 53710 target spans three versions (vulnerable, patched 1.0.2, server-patched 1.0.7, `server_patched_surfaces` set); every other target spans two (vulnerable, patched, `server_patched_service` None). The per-launch random nonce is excluded from the fix-check comparison (`fix_check_mismatches` excludes `witness`, commit `b1ab38b`); do not reintroduce a nonce comparison.

## Backend provisioners (repo code, the new work)

jenkins and neo4j each need a `RegisteredBackend` in `evals/nuisance_backends.py`; neither key exists yet. A `RegisteredBackend(provisioner, network, image)` names a `BackendProvisioner`, a bridge network and the backend image; `backend_problems` checks a server's `backend` matches the registry entry field for field.

**jenkins**: a responder provisioner in the `ckan`/`contextforge`/`apify` shape on `evals/responder_backend.py`. A new `evals/jenkins_backend.py` stands a mock-Jenkins responder for the **run** (benign only: it serves the legitimate build endpoints `get_build_log`/`get_build_status`/`trigger_build` reach, no sentinel route) as a singleton on a fixed public-range IP of its own bridge, with a new `evals/docker/Dockerfile.jenkins-responder` (inlined, no COPY, as `Dockerfile.contextforge-responder`). Subnet **198.18.2.0/24** (RFC 2544, overlapping neither atlassian `198.18.0.0/24`, apify `198.18.1.0/24`, ckan `203.0.113.0/24`, contextforge `198.51.100.0/24` nor n8n `192.0.2.0/24`). Public exports mirroring `apify_backend.py`: `JENKINS_BRIDGE`, `JENKINS_SUBNET`, `JENKINS_RESPONDER_IMAGE`, `JENKINS_LAUNCH_LOCK`, `ensure_jenkins_responder`, `jenkins_rm`, `jenkins_server_args` (or the equivalent `*_network_args` the server image needs). The server's `JENKINS_URL`/`JENKINS_USER`/`JENKINS_TOKEN` come from the run image's Dockerfile `ENV`. Register `jenkins` in `BACKENDS` (image the responder tag, network its bridge) and add the registry-parity and provisioner-wiring tests mirroring the contextforge/apify tests. Registering `jenkins` and `neo4j` takes `evals/nuisance_backends.py` past 300 lines, so per **Decisions 8 (split (a))** the nine provisioner functions move to a sibling `evals/nuisance_provisioners.py` while `RegisteredBackend`, `BACKENDS` and `backend_problems` stay here and import them. This is the run backend; the fix-check stand-in (benign plus the sentinel path-injection route, carrying the per-exercise nonce) is separate, built inline in the fix-check module as apify's responder is.

**neo4j**: a separate-database provisioner in the `doris`/`mysql` shape. A new `evals/neo4j_backend.py` ensures one persistent Neo4j container (APOC installed, `apoc.import.file.enabled` false, authentication configured) on a labeled bridge, reachable by container name, public surface `ensure_neo4j`, `neo4j_server_args`, `neo4j_rm`, `NEO4J_LAUNCH_LOCK` (a plain `threading.Lock` serialising only the stand-up, not held across the yield), `NEO4J_BRIDGE`, `NEO4J_IMAGE`, with a module docstring naming the lifecycle as `doris_backend.py` does. Pin the Neo4j image by digest (`image:tag@sha256:...`, as `_MOTO_IMAGE`; `DORIS_IMAGE` and `MYSQL_IMAGE` are pinned the same way), since `BackendFixture.image` is compared field for field and any Dockerfile built from it is held to digest pinning by `test_every_base_image_is_pinned_by_digest`. ## Implementation model

The exploit, fixture and Docker-calibration steps are done directly, not dispatched to a sub-agent, on Opus 4.8 or Fable and never 5.5, as for the rest of this work; the review, standards and docs passes may be delegated. Docker calibration is run for real before any `server_patched_surfaces` or surfacing boolean is trusted, and the calibration-held items are settled there before the entries that depend on them are committed.
