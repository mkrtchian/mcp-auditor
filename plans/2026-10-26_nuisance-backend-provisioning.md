# Nuisance suite: provision server backends in the fixture

## Context

The nuisance suite (`docs/nuisance-rule.md`, version 2) now says a server's fixture brings up the backend the server needs to start and to answer its benign calls, the way its holdout fixture does, with nothing planted in it. Version 1 launched every server in a single container with no backend (`nuisance_launch` in `evals/nuisance_audit.py`), so a server whose tool needs a backend to answer a benign call was dropped on `needs_backend`, even a holdout twin whose backend is a provisionable database or service. That dropped two calibrated holdout twins, Doris (CVE-2025-66335, an FE+BE cluster) and n8n (GHSA-8g7g-hmwm-6rv2-n8n, needs the n8n API), and the whole class of database and gateway servers, which biases the figure away from those servers' alarm profile.

This plan implements the version 2 rule: the admission records a backend fixture per server, the fix check and the run bring it up, the fixture fingerprint covers it, and a server leaves the figure only for a backend the fixture cannot provide (a remote third-party service, a credential or an account the maintainer does not have, or a proprietary binary). It writes no `evals/nuisance_admission.json`: the file is absent until the admission session and no server is admitted. It builds the mechanism so the admission session can admit a backend server, and wires Doris as the one reference backend that exercises the mechanism end to end.

The rule is committed (`93de2d8`). This plan is the code that makes the suite behave as the rule now reads. It touches only the nuisance suite, the kit and `evals/doris_backend.py`, never the auditor under test, and resets nothing: the suite has no admitted server, no baseline under `evals/baselines/nuisance/` and no run, so the fixture fingerprint change has no stored figure to invalidate. It must also leave the CVE acceptance baselines (`evals/baselines/cve/`, four recorded targets) comparable: `cve_baseline._ENVIRONMENT_PATHS` fingerprints `cve_environments.py` and the `cve_planting*` modules by AST, so any code change there moves every acceptance fixture fingerprint and turns the CVE gate not comparable. `evals/doris_backend.py` is not in that tuple, so it can change; `cve_environments.py` (`doris_db_env` included) is not edited by this plan.

## Decisions taken (with the user, 2026-10-26)

The backend is provisioned by named per-backend builders, the holdout's own mechanism, not a declarative `BackendSpec`. The holdout drives each heavy backend through a dedicated lifecycle (Doris through `evals/doris_backend.py`, wired by `doris_db_env` in `evals/cve_environments.py`): imperative Python per backend, the cluster provisioned once and reused, the health wait and schema provisioning in code. We reuse that rather than re-expressing a 240 s health wait and `CREATE DATABASE/TABLE` declaratively, which would be fragile for the two or three backend servers in range.

A pulled backend image is pinned by its tag, as the holdout pins `apache/doris:all-in-one-4.1.3` and `mysql:8.0.46`, not by a digest. The rule's "every image is built again from its committed Dockerfile, the backend's included when the fixture builds it" scopes the base-digest pin to a built backend; a pulled service is not built, so no rule clause is needed and no version 3 opens. The pinned tag is recorded in the backend fixture and so enters the fixture fingerprint.

## Approach

`nuisance_launch(server) -> Launch` becomes `nuisance_environment(server) -> AbstractContextManager[Launch]`. When the server records no backend fixture, the context manager yields the current single-container launch unchanged. When it records one, it delegates to the backend's provisioner, which ensures the cluster is up and query-ready, stands any per-run helpers, and yields the server `Launch` wired to the backend's network, exactly as `doris_db_env` does. The provisioner owns the network, so no third network stance is added to `PlantingHost`: a backend server's launch comes from the provisioner, not from `_network_args(host.has_network)`.

The admission schema gains a backend fixture on `AdmittedServer` and splits the per-flaw backend fact into "needs a backend" and "the fixture cannot provide it". The counter drops a tool only for the second. The fingerprint covers the backend fixture and the host (the host was already hashed; the rule now names it, and this plan matches the rule's coverage list to the code).

The kit's fix check gains a backend builder so a backend server's counted flaws that the holdout did not calibrate (its non-drawn census flaws) are checked fresh with the backend up. The kit imports nothing from `mcp_auditor`, and `evals/doris_backend.py` already satisfies that (it imports only `cve_planting` and `cve_planting_base`, both in `calibration_dossier.CLEAN_MODULES`, which the kit modules already import). What keeps the kit from importing it today is the exported tree: `copy_clean_sources` copies only `CLEAN_MODULES` and the named kit modules, so the dossier's import-closure test fails on the missing module. The Doris cluster lifecycle therefore has to ship with the dossier, see the backend provisioner core section.

Doris is the one reference backend wired end to end, the motivating twin. arcadedb (CVE-2026-65831) and n8n reuse the same mechanism when the admission session admits them, each with its own provisioner following `arcadedb_mcp_env` and the n8n redirect env; this plan does not wire them.

## What stays unchanged

The auditor under test, its prompts, its graph. The grammar (`evals/cve_grammar.py`) and the counter's predicate (`evals/nuisance_counting.py` beyond the `needs_backend` split). The acceptance layer, the CVE benchmark, the holdout run, `evals/cve_environments.py` (`doris_db_env` keeps its own launch wiring untouched, see the Context section on `_ENVIRONMENT_PATHS`) and the behaviour of `evals/doris_backend.py` (the holdout keeps driving it through `doris_db_env`; this plan moves its cluster core and adds a server-launch helper, it does not change what the holdout does). The census classification's own `runs_in_container` (`evals/census_classification.py`, `census_grouping.py`, their tests and `evals/holdout_census.json`) is a different model and keeps its name. `evals/nuisance_admission.json` stays absent. No baseline is recorded. The statistic, the report and the gate logic stay as they are, apart from passing the backend image id through provenance.

## Files to modify

### `evals/nuisance_admission.py` (schema)

Add a `BackendFixture` record and carry it on `AdmittedServer`; split the per-flaw backend fact.

`BackendFixture(BaseModel)`: `provisioner: str` (the key naming the backend's lifecycle, e.g. `"doris"`), `image: str` (the pinned image tag the provisioner pulls, recorded for the fingerprint and provenance), `network: str` (the bridge the server joins). No "or built image's tag" dual sense: no built backend exists, and a built backend would fingerprint by its Dockerfile instructions like the server image, not by a `:local` tag, so that case arrives as its own variant when it arrives (Beck review E). The launch wiring (the `--db-host` family of arguments) stays in `AdmittedServer.launch`, which the provisioner appends to the server image, as `doris_db_env` passes `--db-host DORIS_CONTAINER ...`.

`AdmittedServer` gains `backend: BackendFixture | None` (None when the server needs no backend or bakes it into the image, like the self-contained MySQL-MCP image). `runs_in_container: bool` is renamed `runs_under_docker: bool` to match the rule's wording and remove the single-container reading; the agreement field label and the dossier follow, and so does `nuisance_population.standing_exit`, which reads the field and whose exit text "its patched version does not run in a container" becomes "its patched version does not run under Docker" (the rule's exit list wording), with `tests/unit/test_nuisance_population.py` and the `field="runs_in_container"` labels of `tests/unit/test_nuisance_images.py` and `tests/unit/support/test_nuisance_admission_given.py`.

`FlawRecord.needs_backend: bool` is replaced by `backend_need: Literal["none", "fixture", "external"]`, so the record carries the two facts the rule records (a tool needs a backend, and whether the fixture can run it) rather than one boolean whose False collapses three states (Evans review C). `"none"`: no tool of the flaw needs a backend. `"fixture"`: a tool needs a backend the fixture provides, either `AdmittedServer.backend` or one baked into the server image. `"external"`: a tool needs a backend the fixture cannot provide (a remote third-party service, a credential or an account the maintainer does not have, a proprietary binary), which drops the tool, as the rule's counted-tool clause reads. The counter drops a tool only on `"external"`. A load check becomes legible instead of a comment: `backend_need == "fixture"` with `AdmittedServer.backend is None` is the baked-in case (allowed, the MySQL-MCP server), with a backend set is the provisioned case; `"external"` needs no backend fixture.

Add `_backend_problems(server, backends)` to `admission_problems` (the registry passed in, as `admission_problems` already takes `grammar_fingerprint` for the same testability reason, Beck review F): when `server.backend` is set, its `provisioner` names a registered backend, and the fixture equals the one that backend defines, `server.backend != BackendFixture(provisioner=key, image=entry.image, network=entry.network)` giving one problem that names the expected fixture (Evans review D: one equality check, not three field comparisons, since the provisioner pulls its own pinned image and wires its own network whatever the fixture says). `_backend_problems` and the registry live in a new `evals/nuisance_backends.py`, not in `evals/nuisance_audit.py`: that module imports `nuisance_admission`, and `nuisance_admission` importing it back is a cycle (`nuisance_counting` and `nuisance_images` avoid the same cycle with `TYPE_CHECKING` imports; `nuisance_walk` does not import `nuisance_admission` at all). `nuisance_backends` imports `AdmittedServer` under `TYPE_CHECKING` only.

### `evals/nuisance_counting.py` (counting)

`flaw_counted_tools` drops a tool on `flaw.backend_need == "external"` in place of `flaw.needs_backend`; the docstring changes from "whose backend is present" to "whose backend is not one the fixture cannot provide". `counted_flaws`/`counted_tools` are otherwise unchanged.

### `evals/nuisance_audit.py` (launch)

`nuisance_launch(server) -> Launch` becomes `nuisance_environment(server, backends=BACKENDS) -> AbstractContextManager[Launch]` (a `@contextmanager` generator; `backends` injectable so a test passes its own dict instead of monkeypatching the module global, Beck review F). With `server.backend is None` it yields the current launch (user, working directory, `_network_args(host.has_network)`, the server image, `server.launch`). With a backend it looks the provisioner up in `backends` and delegates, yielding the server `Launch` the provisioner builds (the provisioner ensures the cluster, wires `--network server.backend.network`, emits the server's user and working directory from `server.host`, appends `server.launch`, and reaps its per-run container on exit, as `doris_db_env` does except that `doris_db_env` emits no user or working directory, see the backend-core section on the host).

`audit_once` enters the context around `_audit`. The provisioner is sync (like `doris_db_env`, a sync `@contextmanager`) and blocks: `ensure_doris` sleeps in its health and schema loops for up to 240 s + 180 s, and `DORIS_LAUNCH_LOCK` is a `threading.Lock`. A plain `with nuisance_environment(server) as launch:` inside the coroutine would freeze the event loop for that long and, worse, deadlock: `_run_server` gathers the server's `NUISANCE_RUNS` audits concurrently (the gate gathers its runs the same way), so the second coroutine would block the loop thread on a lock the first holds across its `await`. So `audit_once` enters it as the acceptance layer does (`cve_targets.CVETarget.launched`): `async with entered_in_thread(nuisance_environment(server)) as launch:` from `evals.concurrency`, then `await _audit(launch, ...)`. `nuisance_run.benign_call` (the pre-run vetting, which the gate's `default_harness` reuses) builds its launch with `nuisance_launch(server)` today and takes the same `entered_in_thread(nuisance_environment(server))` path, or a backend server's benign call connects to a server with no backend and vets it out. A provisioner failure (cluster never healthy) raises out of `__enter__`, which `audit_once`'s `except Exception` turns into `LaunchFailed`, retried by `nuisance_audit`, the same path a launch failure takes today.

The provisioner registry lives in `evals/nuisance_backends.py` (see the import-cycle note under the schema): a frozen `RegisteredBackend(provisioner, network, image)` named for its role (not a bare `Backend`, Evans review D), and a module-level `BACKENDS: dict[str, RegisteredBackend]` with `"doris"` wired to the Doris provisioner, `DORIS_BRIDGE` and `DORIS_IMAGE`. `BackendProvisioner = Callable[[AdmittedServer], AbstractContextManager[Launch]]`. The Doris provisioner takes `DORIS_LAUNCH_LOCK` around `ensure_doris()` only, not across the yield: `doris_db_env` holds it across the yield because its sentinel is a singleton at a fixed IP, and the nuisance run stands no sentinel, so holding it would only serialise the server's concurrent runs on one cluster that serves them all. The per-run server container keeps the uuid name and the `doris_rm` on exit.

### Backend provisioner core (`evals/doris_backend.py` stays, `kit_backends.py` is the kit builder)

`evals/doris_backend.py` is **not moved** (Beck review A: the move plus a `__all__` re-export shim is the biggest step of the plan and unnecessary, and a compat shim is what `CLAUDE.md` forbids). It stays in place with its cluster lifecycle (`ensure_doris`, `_wait_doris_healthy`, `_provision_doris_schema`, `doris_rm`, `DORIS_LAUNCH_LOCK`, `DORIS_BRIDGE`, `DORIS_CONTAINER`, `DORIS_DB`, the `_doris_*` wrappers, `start_doris_sentinel`), so `cve_environments.py` and `tests/unit/test_doris_serialization.py` keep importing the same names unchanged. It gains two pure additions, free of any `Launch` type: `DORIS_SERVER_LAUNCH` (the `--db-host DORIS_CONTAINER --db-port 9030 --db-user root --db-database DORIS_DB` family) and `doris_server_args(name, image, host, server_launch) -> list[str]`, the `docker run` argument list `confinement_args()`, `--name <uuid>`, `--label LABEL`, `--network DORIS_BRIDGE`, `_user_args(host.user)`, `-w host.working_directory`, the image, then `server_launch`. The user and working directory come from `host` (Evans/general review B): `doris_db_env` emits neither, but `nuisance_fixture_fingerprint` hashes the server's `host`, so a backend launch that ignored it would fingerprint a host it does not honour. `_user_args` resolves `host_user_args`/`unprivileged_user_args`, both in `cve_planting_base` (clean). Its docstring is trimmed to the cluster lifecycle, naming no CVE and no mechanism (contamination guard, see below). The deliberate duplication: `doris_db_env` keeps its own wiring because `cve_environments.py` is AST-fingerprinted into every acceptance fixture (Context section), with a comment naming `doris_server_args` as the twin that folds back at the next acceptance reset (when `cve_environments.py` moves anyway), and a parity test (Test scenarios).

Two `Launch` types sit on either side of the kit boundary: `kit_launch.Launch` is the kit-local mirror of `cve_environments.Launch` (the swap pair is named in `calibration_dossier.py`), and the kit cannot import the evals one since `cve_environments` imports `mcp_auditor`. So `doris_server_args` is a pure `list[str]` that neither `Launch` type touches, and each side wraps it: the **kit builder** `doris_backend_env` (a `KitBuilder`, the only content of the new `evals/holdout_kit/kit_backends.py`) imports the lifecycle and `doris_server_args` from `doris_backend`, ensures the cluster, stands the fix check's own sentinel on the link-local net for a fetch-class flaw (`spec.sentinels`, holding `DORIS_LAUNCH_LOCK` across its yield as `doris_db_env` does since the sentinel sits at a fixed IP), and yields a `kit_launch.Launch`; the **nuisance provisioner** `doris_provisioner` (in `nuisance_backends.py`, evals-side) wraps `doris_server_args` in `cve_environments.Launch`, holding the lock around `ensure_doris()` only. Both import `doris_backend`, which imports only `cve_planting`/`cve_planting_base` (both `CLEAN_MODULES`), so the kit tree import-closes once the dossier copies `doris_backend` and `kit_backends` together.

**Contamination (decided with the user, 2026-10-26, route b, refined by Beck review A).** Two guards keep a drawn holdout target's mechanism out of a blind agent's context. First, `doris_backend.py`'s docstring is trimmed to the cluster lifecycle alone, naming no CVE and no mechanism (its current docstring, which names both, is rewritten). Second, the nuisance dossier copies `doris_backend` and `kit_backends` **only for a server admitted with that backend** (`--backend doris`), not for every server, so a non-backend or other-backend admission receives neither. Doris is a drawn holdout target, so its mechanism is contamination for any blind agent not admitting Doris itself (holdout contamination scope). A second backend gets its own kit builder copied only for its own server. `CLEAN_MODULES` is not used for this (it would ship the lifecycle with every holdout calibration kit too).

The gate session shares the same launch path through `nuisance_environment` and the same `benign_call`, so bringing up the backend in the gate falls out of the launch change.

## Edge cases

A server whose backend is baked into its own image (the self-contained MySQL-MCP image, started by the entrypoint): `backend` None, `backend_need` `"fixture"` on its flaws, no provisioner, the current single-container launch. Counted.

A server whose tool needs an irreducibly external backend (a hosted account, a proprietary binary): `backend_need` `"external"` on that flaw, the tool drops, and if the server has no counted tool left `_counted_tool_problems` refuses the admission at load, as today: that exit never reaches the admission file, the nuisance log carries it (`run_population`'s docstring), so no new row appears in the run's exit table.

A backend that never becomes healthy within the provisioner's deadline: the provisioner raises, `nuisance_environment` propagates, `audit_once` returns `LaunchFailed`, and `nuisance_audit` retries up to `NUISANCE_INFRA_ATTEMPTS`, then drops the server as a launch failure for the run. The gate takes the same path.

The persistent Doris cluster is shared across a run's servers and across the run's repeats. The nuisance provisioner holds `DORIS_LAUNCH_LOCK` only around `ensure_doris()`, not across the yield, so a server's concurrent runs are not serialised: they share the one cluster that serves them all. Two nuisance runs of the same server reuse that cluster. If the cluster dies mid-run, a sibling run's `ensure_doris` (which checks `_doris_exists`, not `_doris_running`) force-removes and relaunches it, and the in-flight run fails its tool call and is retried by `nuisance_audit` (general review 14). Two processes that share no lock (a `run_holdout calibrate` and a `run_nuisance run` at once) race the `docker run --name`, and the loser fails and is retried. Nothing is planted, so neither races corrupts a figure, only a run attempt.

A pulled backend image absent from the daemon: the provisioner pulls it at `ensure` time (as `ensure_doris` runs `docker run` which pulls if absent). `rebuild_images` does not build it.

## Open decisions and limitations

A brand-new backend server that is not a holdout twin needs a provisioner the maintainer writes; the blind admission agents record the backend and flag it, and the maintainer wires the provisioner at settlement. The current population's backend servers (Doris, arcadedb, n8n) are holdout twins whose provisioners exist or follow the three existing patterns, so this does not block the admission session.

This plan wires Doris as the reference backend. arcadedb and n8n follow the same mechanism at their admission, each reusing its holdout env (`arcadedb_mcp_env`, the n8n redirect env) through a nuisance provisioner and, for a fresh fix check of a non-drawn flaw, a kit backend builder; they are out of scope here.

`ADR 033` still reads "a tool whose backend the container cannot provide" and names only the many-flaws population bias. It is immutable. The database and gateway exclusion bias that version 2 closes, and the "container" wording, are superseded by the rule; a future ADR that revisits the suite records it. Not part of this plan.

**Holdout parity.** Most of this plan is the nuisance catching up to the holdout, not the reverse: the holdout already provisions the Doris backend (`doris_db_env`) and already enters its environment off the event loop (`cve_targets.CVETarget.launched` through `entered_in_thread`), so neither carries a gap this plan should backport. Two changes do run one way only, and they surface a real holdout gap rather than fixing one here. This plan makes the nuisance record the backend image id in its provenance and cover `BackendFixture.image` in its fixture fingerprint; the holdout does neither. `cve_baseline.image_ids` inspects only the target services (`target_services`), not the pulled Doris image, so the holdout run's provenance does not name the backend it ran against. And `cve_baseline._ENVIRONMENT_PATHS` fingerprints `cve_environments.py` and the `cve_planting*` modules by AST but not `doris_backend.py` (nor, after the move, `kit_backends.py`), where `DORIS_IMAGE` lives, so the Doris image tag is outside the holdout fixture fingerprint: a re-push or a change of that tag would not reset the holdout's comparability, and ADR 032 would pair two differently-backed runs as if same-fixture. Recommendation, not implemented here: the provenance gap is a small separate holdout follow-up (record the Doris backend image id beside the target ids), low-risk and free while the holdout has no committed run; the fingerprint gap is governed, since adding the backend image to the fingerprint through `_ENVIRONMENT_PATHS` would move every acceptance fixture fingerprint and turn the CVE gate not comparable, so it is settled at the next acceptance reset or through a holdout-only fingerprint part, never folded into this nuisance plan. The tag-pin currency risk (a tag re-push changing the backend under an unchanged fingerprint) is identical on both sides and accepted on both, aligned with the holdout's existing tag pin.
