# Realism repairs, fifth part: the Android emulator behind the Android servers and targets, and SearXNG behind mcp-searxng

## Context

The first four parts (`plans/2026-11-12_realism-repairs-holdout-images.md`, `plans/2026-11-12_realism-repairs-nuisance-images.md`, `plans/2026-11-12_realism-repairs-stand-ins.md`, `plans/2026-11-13_realism-repairs-backends.md`) corrected records, repaired images and stand-ins, and put real backends behind the servers where they run within the bounds. This fifth part repairs what they left. It puts the real Android Emulator in place of the device stand-in behind the two Android nuisance servers (`https://github.com/jiantao88/android-mcp-server` and `npm:adb-mcp`) and the two Android holdout targets (CVE-2026-19978 and CVE-2026-81562). It tries a real SearXNG behind mcp-searxng (CVE-2026-58485). And it logs why the settings of git-mcp (`npm:@cyanheads/git-mcp-server`) that the 2026-11-12 entry left for a later part stay as they are, with no fixture change.

The aim is realism at a cost a project of this size, kept by one person, can carry: each repair does what the bounds and its source call for, and no more. A repair whose cost grows far beyond what it changes for the auditor is stopped and reported, not pursued.

The maintainer's rulings for this part are held outside the repository, and the maintainer gives their location to the implementer at launch. Nothing from outside the repository is named in a committed file: no path, no file name, no review label, and no value of the machine that runs the suite (the group that owns `/dev/kvm` is read at launch, never written down).

No step runs an audit or an LLM eval. The proofs are no-LLM checks with Docker, and the two spikes are Docker runs outside the repository. No holdout run, nuisance run or gate run has taken place, and `evals/baselines/detection/` and `evals/baselines/nuisance/` are absent, so nothing resets.

It depends on no other detail of that part.

### Readings logged

These are the maintainer's readings of the rules for this part. Each is written in the log entry of the change it governs.

- **The Android Emulator is real software.** Google publishes it as the device the Android SDK runs on a workstation, and adb-mcp's README says it "was built using one" (the maintainer's ruling of 2026-11-06). The emulator with the published system image therefore replaces the device stand-in, as the bounds of detection suite rule v13 and nuisance suite rule v6 allow ("put the real software in place of a stand-in").
- **The emulator is a backend, and a backend may be given a device.** Under the fourth part's reading a backend is bound by the memory bound only, so the emulator container receives `/dev/kvm` and the group that owns it, which the server's confinement never would. The server keeps its confinement and gains no device, mount of `/dev` or capability.
- **The device relay is network plumbing, not a stand-in.** The server image keeps a process on `127.0.0.1:5554` and `127.0.0.1:5555`, the console and adb ports of the first emulator, that copies bytes to and from unix sockets the emulator container serves. It answers nothing itself, so it has no output to source, and adb still finds the device as `emulator-5554`. Two other links were weighed and rejected: `adb connect` registers a TCP device, not an emulator, so android-mcp-server's `useEmulator` (`-e`) and its `kill-server` tool would lose the device, and an emulator joining the namespace holder would let the guest's user-mode NAT reach the link-local sentinels the holder serves.
- **The 2026-11-12 free-shell limit falls away for both suites.** That limit held because the device stand-in ran in the server's container, where a real shell would read the kept places and the witness. The emulator runs in its own container with no network and no mount but the socket directory and its AVD volume, so the guest's `mksh` reads none of them, and a free shell command gets a real shell's output. The entries of 2026-11-12 stay as they are, and the new entries say the limit no longer holds.
- **The AVD is the phone Android Studio proposes by default.** The device a developer gets from Android Studio's device manager without choosing is the "Medium Phone" profile, under the AVD name Studio generates for it, so the fixture's AVD is that profile and that name, read on the day and recorded (the maintainer's ruling of 2026-11-13). The example of the `avdmanager` page (a generic profile, the name `test`) is not taken, since its name names the fixture. The AVD is still created with the command-line tools, `avdmanager create avd -d <the profile's id>`, the spike confirms the profile id and the name Studio generates from Studio's documentation, and the card and the admission record both.
- **The `emulator` and `avdmanager` packages are the tools.** The Android documentation now points to the `android` CLI, but the emulator and cmdline-tools packages are the published releases the rulings pin, so the fixture uses them and the records say why (the maintainer's ruling of 2026-11-13).
- **The emulator release is the only stable one that meets the system image's minimum.** The system image r06 states its emulator as a minimum, not a pin: its `source.properties` requires `emulator#37.2.11`, and Google's `sys-img2-3.xml` gives the same dependency (minimum revision 37.2.11). Google no longer publishes 37.2.11: on 2026-11-13 `repository2-3.xml` lists only 37.2.13 on channel-0 and 37.3.9 on channel-1, and no archive carries 37.2.11. The fixture therefore runs Android Emulator 37.2.13, the only stable release Google publishes that meets the minimum, taken for availability and not as a move to a newer release (the maintainer's reading of 2026-11-13). The card and the admission record this reading beside the release.
- **No value of the machine reaches the guest.** The emulator takes its default time zone and DNS servers from the host, so the launch sets `-timezone Etc/UTC`, and no host DNS reaches the guest: with no network there is none to forward, which the spike confirms with `getprop net.dns1` showing no host value, else the launch sets `-dns-server` to the virtual address the emulator's networking page documents. The guest CPU model, which shows the host's under KVM, is hidden with the emulator's documented `-qemu` pass-through, `-qemu -cpu <a generic model QEMU documents>` (a documented setting, its source QEMU's documentation). These are logged as required by the ban on values of the machine that runs the suite, not as choices (the maintainer's ruling of 2026-11-13). If the CPU setting fails to hide the host's model or breaks the boot, change 1's stop condition holds and the fallback is the capture (change 7).
- **adb authorization uses a seeded key, never `-skip-adb-auth`.** `-skip-adb-auth` is not on the emulator's documented options page, so it is not used. If the system image requires authorization, a key pair made by `adb keygen` is seeded, as on a developer's machine that authorized the device once (the maintainer's ruling of 2026-11-13).
- **Accepted risks.** A guest shell driven by the auditor runs on the host's `/dev/kvm`, with no network, no capability, a non-root account, and the memory and pids bounds, and that risk is accepted. A private key committed for the fixture alone (the adb key pair, if the image requires one) is accepted and recorded as `generated` (the maintainer's ruling of 2026-11-13).
- **The release of SearXNG is the image published on the day.** SearXNG publishes no numbered release: it publishes dated images from its main branch. If its spike passes, the fixture runs the image current on the day, pinned by digest and recorded with its tag and the day, as the fourth part read httpbin's head commit.
- **git-mcp keeps its settings, on a documented configuration and on a reason the bounds give.** The 2026-11-12 entry left `GIT_SIGN_COMMITS=false` and `MCP_LOG_LEVEL=error` in the git-mcp images for a later part (the maintainer's ruling of 2026-11-13). At 2.15.1 and 2.15.3 the server's `.env.example` documents `GIT_SIGN_COMMITS` with the default `true` and says to set it to false to opt out entirely, giving environments without a signing key configured as the example, and its CHANGELOG (v2.13.0) says to set `GIT_SIGN_COMMITS=false` "to opt out in environments without a signing key". The fixture has no signing key, so the 2.15.x images follow that documented configuration. At 2.1.4 and 2.1.5, `false` is the README's documented default. `MCP_LOG_LEVEL` and `LOGS_DIR` reach no tool response: at 2.15.x the logger writes to stderr when stdout is not a terminal and to files under `LOGS_DIR` when set, at 2.1.x it writes to files under the package's `logs` directory (2.1.x reads no `LOGS_DIR`) and to the console only at `debug` on a terminal, and neither version forwards its log records to the client. They are left as they are on the first reason the bounds give, the repair changing nothing that reaches the auditor. One entry in `docs/nuisance-suite-log.md` records this reading, with no fixture change, no proof run and no fingerprint moved.

### Departures from the bounds

This part makes none. A spike that finds one needed (a guest memory below the device profile's default to fit the bound, a capability whose absence changes what the device answers, a SearXNG setting that neither SearXNG's documentation nor the server's sets) stops and reports it with the measurement, before any repository change.

### Why no rule version opens

Detection suite rule v13 and nuisance suite rule v6 let the maintainer repair fixtures until the auditor first audits a holdout target, and their bounds last only until then. A new rule version would bind the runs that follow that first audit, when no maintainer repair is allowed at all, so it would bound nothing these repairs touch. The suite logs are where the entries of detection suite rule v13 and nuisance suite rule v6 put what a repair keeps or departs from, so the readings are logged there.

## The bounds every step keeps

These restate the log entries of 2026-11-12, which govern where they differ.

- A repair leaves unchanged the exploits, the kept places, the aim predicate, and the vulnerable and patched versions of the server. On the nuisance side it also leaves unchanged the place of the witness, the exploits of a fix check, the counted tools, the patched versions of the flaws and the patched version of the server.
- It may change a stand-in's outputs, a seed, the launch or the benign call, add a backend or a stand-in, put the real software in place of a stand-in, or set the real software at the stable release current on the day of the repair when the server's documentation names no version of it (on the nuisance side, when neither its documentation nor its tests name one), and the card (or the admission) records that release and that day.
- A seed, a launch option or the setup of a backend comes from the documentation of the software or the server, or from a sample either one publishes. A stand-in's output is the first output of the first source that gives one, in the order of the rule. An output a test of the software produces against a mock or a fake is not a source.
- The maintainer invents no output and edits no invented output. Recording an existing output as invented, or correcting any other card or admission entry that misstates the fixture, is a record correction and leaves the fixture as it is.
- A break stays unrepaired only for one of the two reasons the entry gives: the repair would change nothing that reaches the auditor, or the repaired fixture could not run in the container (on the nuisance side, under the confinement, and for a backend within the memory bound) or on the closed networks a fixture may use. Cost alone is never that reason.
- A part of a repair that falls outside these bounds is not done. The step stops on it and reports it to the maintainer with what it would change for the auditor.

## Proof, records and fingerprints, in every step

- The proof runs on the repaired fixture before the commit: `uv run python -m evals.run_detection_holdout calibration-check --flaw ID` for each holdout target the step touches, `uv run python -m evals.run_nuisance fix-check --flaw ID` for each nuisance flaw whose images, backend or stand-ins the step changes and that has a fix-check module, and `uv run python -m evals.run_nuisance vet --server PKG` for each nuisance server the step changes. ## Sequencing

The order is chosen to run the fewest proofs and to touch the repository only once the spikes have decided the form of the two heavy changes. No two commits share a target or a nuisance server, apart from the emulator module, which the two Android commits share, and adb-mcp, whose fix check and vet the second Android commit runs again because it edits that module.

1. **The two spikes, before any repository change**: the emulator on adb-mcp (change 1) and SearXNG (change 5). Their outcomes decide whether changes 2, 3 and 6 take the real software or their fallback. They touch no file of the repository.
2. **SearXNG** (change 6) if its spike passes, which moves CVE-2026-58485 alone and has no copy, its own commit with its calibration check. If the spike stops, the commit holds the log entry that re-checks the departure's reason, and no code. In both outcomes this first commit also carries the nuisance log entry of the git-mcp reading (the Readings logged), which changes no fixture and runs no proof.
3. **The emulator backend with adb-mcp** (change 2), its own commit: the image, the module, the lifecycle and lock, the KVM refusal, the living docs of the new prerequisite, and adb-mcp's images, fix check and records. adb-mcp is the lightest consumer (three counted tools and a fix check of its own), so it proves the backend before the targets lean on it.
4. **android-mcp-server and the two holdout targets** (change 3), one commit, since they share the holdout builder and android-mcp-server's copy is CVE-2026-19978's calibration. The solo measurement (change 4) runs in this commit, once both Android servers stand the emulator, and writes its value in the lock's comment in `evals/cve/backends/android_emulator.py`, so this commit also reruns adb-mcp's fix check and vet and logs adb-mcp's fingerprint move.
5. **One launch shape for the Kubernetes and mcp-ssh holdout builders** (change 8), its own commit, last, on either Android path: it touches no Android file, and it moves CVE-2025-65719, CVE-2025-9654 and CVE-2025-53355, which no other commit of this part proves.

If the emulator spike stops, items 3 and 4 become the fallback (change 7): one commit for the two nuisance stand-ins and the two holdout stand-ins, proved by the same commands.

## Changes

### 1. The emulator spike, on adb-mcp, before any repository change

The spike stands the emulator by hand, outside the repository, in the form change 2 commits, and plays adb-mcp against it. Nothing it builds is tagged with a repository service name, and everything it creates is removed at its end, apart from the build cache, which change 2's build of the same instructions reuses.

What it builds and runs:

- The packages, downloaded once, each checked against the sha1 Google publishes for it, and its sha256 computed and kept for change 2's `ADD --checksum`: Android Emulator 37.2.13, the only stable release Google publishes that meets the system image's minimum (the Readings logged, `emulator-linux_x64-16740729.zip`, sha1 `f41f9e31eb5ca64926603c03265c50bbc0ff4172`, channel-0 of `https://dl.google.com/android/repository/repository2-3.xml`), the system image `system-images;android-37.0;default;x86_64` r06 (`https://dl.google.com/android/repository/sys-img/android/x86_64-37.0_r06.zip`, sha1 `8842a57a6b146423debb46c1496a9c0986aa1b9e`, channel-0 of `sys-img2-3.xml`, which requires emulator 37.2.11 or later), and cmdline-tools 23.0 for `avdmanager` (`commandlinetools-linux-16111833_latest.zip`, sha1 `e025545c62a8e64c7559119566a569fb1dec5f60`, channel-0 of `repository2-3.xml`). If channel-0 no longer lists 37.2.13 or r06 on the day, the spike stops and reports before building, since the rulings name both, and the maintainer rules.
- The AVD, created by `avdmanager create avd -d <the profile's id>` with the system image above and the "Medium Phone" profile that Android Studio's device manager proposes by default, under the AVD name Studio generates for it (the Readings logged), `config.ini` left at what `avdmanager` writes. The spike reads the profile id and the name Studio generates from Studio's documentation on the day, confirms that `avdmanager list device` lists that id in cmdline-tools 23.0, and checks the name against the words the detection suite rule forbids in a seeded name (it shows in the guest's `getprop`). If the profile id is not listed or the name carries a forbidden word, the spike reports it and the maintainer rules before change 2 starts.
- An emulator container: non-root, `--device /dev/kvm`, `--group-add` the group that owns `/dev/kvm` read at launch, `--cap-drop ALL`, `--security-opt no-new-privileges`, the default seccomp profile, a finite `--pids-limit`, `--memory 4g --memory-swap 4g`, `--network none` with the resolver option of `no_network_args()`, a home tmpfs owned by the account, the documented headless options `-no-window -no-audio -no-boot-anim -gpu swiftshader_indirect`, `-timezone Etc/UTC`, and last on the command line, as the emulator documents for its pass-through, `-qemu -cpu <a generic model QEMU documents>`. Two `socat` processes serve `adb` and `console` unix sockets in a host directory mounted into both containers, each copying to `127.0.0.1:5555` and `127.0.0.1:5554` inside the emulator container.
- A snapshot: the first stand-up boots cold, waits for boot completion and stops the emulator in the way its documentation saves a Quick Boot snapshot. Every later launch boots from it with `-read-only -no-snapshot-save`, which the emulator release notes (28.0.16) describe as several read-only instances sharing one AVD and never saving, the source the records cite for `-read-only`.
- A scratch image derived from `mcp-auditor-nuisance-adb-mcp:local` whose entrypoint starts the device relay of change 2 in place of the stand-in, run under the nuisance confinement with the socket directory mounted.

What it measures, written in the spike's report:

- Cold boot to `sys.boot_completed=1` (stop above about 180 s) and snapshot boot (stop above about 30 s), each with no option or capability beyond the list above. A capability the boot needs is acceptable only if it is measured and changes nothing the device answers.
- Peak resident memory of the emulator container across boot and adb-mcp's benign calls, from `docker stats --no-stream` sampled through the run (stop above about 3.5 GB), and the peak thread count for the `--pids-limit`.
- adb authorization: whether `adb devices` shows `device` or `unauthorized` on the image's default state, and, if `unauthorized`, whether a key pair made by `adb keygen` and seeded on both sides resolves it. `-skip-adb-auth` is never tried.
- Isolation: from a guest shell, no connection opens to anything in the server's namespace (the adb server on 5037, a listener the spike starts on the server's loopback), nor to the link-local addresses the holdout targets' sentinels use, nor to any external address (stop on any).
- Host values: `getprop`, `dumpsys connectivity`, `dumpsys display`, `adb devices -l`, `date`, `uname -a`, `cat /proc/cpuinfo` and `cat /proc/meminfo` on the guest, read for the hostname, a user name, the timezone, a DNS address, the kernel or any other value of the machine that runs the suite (stop on any that no documented setting removes). The time zone must read `Etc/UTC` under `-timezone Etc/UTC`. `getprop net.dns1` (and the other `net.dns*` properties) must show no host value: if one shows, the spike adds `-dns-server` with the virtual address the emulator's networking page documents and measures again. The host's CPU model, which the guest's `/proc/cpuinfo` shows under KVM, must give way to the generic model of `-qemu -cpu`: if the pass-through fails to hide the host's model or breaks the boot, the spike stops and reports, and the fallback is the capture (a value of the machine that runs the suite stays out of what a fixture serves, whatever the real software would show).
- Freshness: a file pushed and a package installed in one launch are absent in the next.
- adb-mcp's four benign calls and four exploits, by hand, on both images: the exploits surface the witness on 0.1.0 and none on 0.1.1, `adb_install`, `adb_logcat` and `adb_pull` answer without error, and their real outputs are kept for change 2's expects. `/system/build.prop` on the device is compared with the file of the image zip that adb-mcp's admission pins (`a9366112...4c724aa`).
- Readiness: whether the emulator prints a boot-completed line the provisioner can wait on, so no second adb client ever connects to the emulator (the emulator's adb port takes one host connection).
- The sizes: the image, the AVD volume after the snapshot, and the `docker system df` growth.

Stop conditions, any of which sends changes 2 and 3 to the fallback (change 7): a boot outside the limits above under the listed options, an authorization that neither the image's default state nor a seeded key (change 2) resolves, a guest connection that reaches the server's namespace or a sentinel address, a listed host value that no documented setting removes (the host's CPU model included, when `-qemu -cpu` fails to hide it or breaks the boot), a peak above about 3.5 GB, or exploits and benign calls that do not behave as above. A benign call of a counted tool that fails on the real device for every argument its description allows is not a stop for the spike, but it would change a counted tool, which the bounds freeze, so the spike reports it and the maintainer rules before change 2 starts.

### 2. The emulator backend, and adb-mcp on it

Files: new `evals/docker/Dockerfile.android-emulator` and its compose service `android-emulator` (under the `nuisance` profile, since the registry lists it among its built services, which also keeps the 4 GB image out of the bare `docker compose build`, change 3's targets building it by name), new `evals/cve/backends/android_emulator.py`, `evals/cve/nuisance/backend_registry.py`, `evals/cve/run_images.py`, the command modules that call `refuse_without_closed_networks` for the nuisance commands (`evals/cve/nuisance/vet_command.py`, `evals/cve/nuisance/run.py`, `evals/cve/nuisance/fix_check_command.py`, `evals/cve/nuisance/gate_session.py`), `evals/docker/Dockerfile.adb-mcp` and `Dockerfile.adb-mcp-vuln`, `evals/cve/nuisance/fix_checks/cve_2025_59834_adb_mcp.py`, the admission of `npm:adb-mcp`, new `tests/unit/test_android_emulator.py` with its given file `tests/unit/support/test_android_emulator_given.py` (and a then file beside it only for an assertion that abstracts something), `tests/unit/test_cve_run_images.py`, `tests/unit/test_nuisance_backend_registry.py`, new `tests/integration/test_android_emulator_backend.py`, `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`, `CHANGELOG.md`, `docs/glossary.md`, `docs/glossary-log.md`, `docs/nuisance-suite-log.md`, `docs/labeling-log.md`.

The image. `Dockerfile.android-emulator` has two stages on the `debian:bookworm-slim` base `evals/docker` already pins by digest.

- The first stage installs a headless JRE from Debian (cmdline-tools needs one), adds the three packages of change 1 by `ADD --checksum=sha256:...` from `dl.google.com`, unpacks them into an SDK tree (`emulator/`, `system-images/android-37.0/default/x86_64/`, `cmdline-tools/latest/`), and runs `avdmanager create avd -d <the profile's id>` with the AVD name as change 1 confirmed them. ## Edge cases

- A machine without `/dev/kvm`: every command that would launch an Android fixture refuses with exit 3 before building, naming the targets or servers. Commands on other fixtures run as before.
- A snapshot the emulator cannot load (another emulator build, another CPU): the emulator boots cold, so a launch over 30 s with a snapshot present makes the stand-up recreate the volume once, and a second slow launch is reported, never waited out silently.
- Two emulators that do not fit beside a nuisance command's other backends: the lock takes 1, and the time a calibration check or a vet then takes is reported.
- An audit or a vet waiting on the launch lock: the wait counts toward no tool call timeout, since the server starts only once its emulator is up.
- A real adb operation slower than the stand-in (an install): a benign call over the tool call timeout of the run conditions is reported, never fixed by widening the timeout.
- The emulator's adb port takes one host connection: the stand-up never runs a second adb against it, and the spike's readiness measurement decides where the wait lives.
- A guest output that carries a value of the machine outside the listed ones: reported by the spike for the maintainer to rule, never removed by an option the emulator does not document. The host CPU's model, the time zone and the DNS servers are listed values, handled by `-qemu -cpu`, `-timezone Etc/UTC` and, if needed, `-dns-server` as change 1 says. A `-qemu -cpu` model that fails to hide the host's model or breaks the boot is a stop, and the fallback is the capture.
- An image that requires adb authorization: a key pair made by `adb keygen` is seeded, never `-skip-adb-auth`.
- An auditor-driven guest shell on the host's `/dev/kvm`: an accepted risk under the Readings logged, bounded by no network, no capability, a non-root account and the memory and pids bounds. A step that finds the guest reaching beyond these (a network, a mount, a device other than `/dev/kvm`) stops and reports.
- The route procedure or the layout check finding a new nonce on the real device (a tool whose minimal call reads a kept file through `push`): the step stops and reports before any commit, since the bounds admit no new leak.
- A Docker integration test that fails once under the full parallel run and passes alone: the step reruns it alone, reports it, and does not widen a wait.
- A proof that fails for a cause older than the repair (a rebuild that brings out a break the layer cache hid): the step stops and reports the cause before reverting, and the maintainer decides whether its repair joins the step.
- A release that moved on the day (SearXNG's image): the source wins and the record says so. For the emulator and the system image, which the rulings name, the step stops and reports.
