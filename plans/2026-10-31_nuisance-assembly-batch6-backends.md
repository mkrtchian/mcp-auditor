# Nuisance suite assembly, sixth batch, second plan: the three backend servers

## Context

The nuisance suite admits thirty-nine servers after the first batch-6 plan (`evals/nuisance_admission.json`), with the fix-check mechanism (`evals/nuisance_fix_checks/`, `FIX_CHECK_TARGETS`, `run_nuisance calibrate`, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` tests), the backend registry (`RegisteredBackend`, `BACKENDS` and `backend_problems` in `evals/nuisance_backends.py`, the nine provisioners in `evals/nuisance_provisioners.py`), the responder shape of `evals/responder_backend.py`, and the kit builders those use. The sixth admission batch was adjudicated at thirteen admits across positions 90 to 128 of the salted draw order; its first plan committed the ten no-backend candidates (six admitted, three dropped at calibration, one deferred for the inter-tool-chain mechanism). This second plan handles the three that need a provisioned backend or a baked stub: ios-simulator, gitlab and googleapis/mcp-toolbox. It extends the admission from thirty-nine to up to forty-two servers (fewer if a server drops at calibration).

The three mix mechanism classes and backend shapes. ios-simulator is command_execution behind a baked simulator-CLI stub (no registered provisioner, `AdmittedServer.backend` null, `backend_need` fixture). gitlab is internal_fetch behind a baked mock-GitLab node stub (again no registered provisioner, `backend` null, `backend_need` fixture), its fix-check standing the sentinel through the kit's existing `ssrf_env` builder. googleapis/mcp-toolbox counts two flaws (CVE-2026-11720 read_outside_scope, CVE-2026-14540 internal_fetch), both reaching an upstream that a new `googleapis` responder provisioner stands on a public-range address, with its third flaw CVE-2026-102242 **deferred** (Decision 1): 102242 is a symlink escape against a GCS backend that would need a fake-gcs-server emulator and a composite backend (responder plus emulator), which the single-field `AdmittedServer.backend` does not model; it is kept as a null-class logged flaw and admitted later when the composite shape is designed, with no re-pin since the server image is 1.10.0 either way.

Scope is three servers, each one new admission entry, no edits to existing entries.

## Approach

Same split as the earlier assemblies: eval data (the admission entries and the Dockerfiles) is authored directly by the maintainer and committed by hand; repo logic (the fix-check modules, the one new backend provisioner with its registry entry, their imports into `evals/nuisance_fixtures.py`, the tests) goes through the implementation flow. The repo-logic surface is one new responder provisioner (`googleapis`, in the apify/jenkins shape) plus fresh fix-check modules (one each for ios-simulator and gitlab, one or two for googleapis); gitlab and ios-simulator add no provisioner (their run backend is a stub baked into the server image, and their fix-check builder is either the kit's `ssrf_env` for gitlab or a fresh `command_injection_env`-based builder for ios-simulator).

Run Dockerfiles, as at every batch since 2, are maintainer-authored (`Dockerfile.<service>`, a nuisance `service` slug that is not an acceptance service), digest-pinned `FROM`, no `COPY`/`ADD` from the build context (`tests/unit/test_cve_compose_labels.py`); they are not compose services, so no `compose.yml` entry and no fingerprint label is added. The service slugs are `ios-simulator`, `gitlab` and `googleapis`, each with a `-vuln` arm slug for its vulnerable image (`ios-simulator-vuln`, `gitlab-vuln`, `googleapis-vuln`), none an acceptance service (`filesystem`, `git`, `kubernetes`, `fetch` and their patched variants) and none matching an existing `evals/docker/Dockerfile.*`. A baked stub (ios-simulator's simulator CLI, gitlab's mock-GitLab node) is inlined by `RUN`, never `COPY`ed, as siri's `shortcuts` stub and kanban's `gh` stub are.

Each counted server is host unprivileged, `runs_over_stdio` true, `runs_under_docker` true. `server_patched_surfaces` is null when the counted flaw's patched version equals the server's, set otherwise; here ios-simulator and gitlab are single-counted-flaw with the patched version equal to the server's (null), and googleapis records both counted flaws' patched version as the run image 1.10.0 (null for both, Decision 1). The admission data each server contributes is one `AdmittedServer` entry merged after the existing thirty-nine (untouched), with its counted flaw(s), the settled counted tools, a benign call per counted tool, its dropped flaws kept with their real or null class, its `agents`/`agreement`/`settlements`, a `fix_check` block (`source` `fix_check`, with a `FixCheckTarget`), `backend_need` fixture for all three, and a `backend` naming the `googleapis` provisioner for googleapis only (null for ios-simulator and gitlab, whose stub is baked). The top-level `rule_commit` stays `93de2d8` and `grammar_fingerprint` stays `cve_baseline.grammar_fingerprint()`.

## What this batch reuses, and therefore does not build

The earlier assemblies built, and this plan does not touch: the fix-check mechanism and its coverage/parity tests' logic, the `run_nuisance calibrate` command, the backend registry mechanism (`RegisteredBackend`, `backend_problems`, `backend_image_ids`), `evals/nuisance_provisioners.py`'s nine existing provisioners, the kit builders (gitlab reuses `ssrf_env` unchanged), and the existing thirty-nine entries. The `apify` and `jenkins` responder provisioners (`evals/apify_backend.py`, `evals/jenkins_backend.py` on `evals/responder_backend.py`'s `Responder`) are the nearest precedent for the new `googleapis` responder: a singleton HTTP responder on a fixed public-range IP of its own bridge, serving the benign upstream the run's HTTP-tool calls reach, with a `RegisteredBackend` in `BACKENDS` and a provisioner in `evals/nuisance_provisioners.py`. The internal_fetch fix-checks that stand a per-launch responder carrying the nonce (`cve_2026_46341_apify.py`, `cve_2026_10276_jenkins.py`) are the precedent for the googleapis and gitlab fix-check builders (gitlab via the kit's `ssrf_env`, googleapis via its own inline responder). The command_execution fix-checks (`cve_2025_53818_github_kanban.py`, `cve_2026_55157_token_optimizer.py`) are the precedent for ios-simulator. Each fix-check module imports only from `evals.holdout_kit`, the clean `evals.cve_*` modules and, for a registered backend, that backend's lifecycle module (`evals.apify_backend` and `evals.jenkins_backend` are imported this way), never `evals.cve_environments`; the import-closure scan enforces it.

Witness: the injected command reads a planted witness file, reflected in the counted tool's response (the kanban precedent, `command_injection_env`). The siri-shortcuts `shortcuts` stub is the precedent that stubbing a macOS-only CLI the injection merely has to execute is admissible; stata was dropped because its fixture needed a proprietary binary the census forbids stubbing (`docs/nuisance-log.md`, 2026-10-27), so the admit-or-drop also asks which of the two this server is. Vulnerable **1.3.2** (the release before 1.3.3, due diligence).

### gitlab (nb63), new server, baked stub, fix-check via `ssrf_env`

Counted flaw CVE-2026-61462 (internal_fetch), dfie False (a flip from record B's read_outside_scope, confirmed on source by a contradictor: the host is fixed by `GITLAB_API_URL` and only the path moves through `../`, so it is internal_fetch, and the numeric `job_id` is an argument of a fixed "get job trace/artifacts" operation, not the declared function). Launch **`GITLAB_TOOLSETS=all`** (the pipelines toolset is not the default, a `launch_option` on the entry). Patched **2.1.38** (`fix_commit`, the `encodeGitLabPathSegment` fix of commit `e2a81a0`): 2.1.18 and 2.1.30 still interpolate the raw `jobId` and are still vulnerable, and the OSV "fixed" value is wrong because its affected list stops at 2.1.17, so the records' 2.1.38 stands and an earlier override is rejected. Vulnerable **2.1.17** or **2.1.30** (settled at calibration). `backend_need` fixture, `backend` **null**: a mock-GitLab node stub is baked into the server image for the run's benign calls (record A's `fixture`, not record B's `none`), inlined by `RUN`. `server_patched_surfaces` null (patched is the server's version). Witness: the percent-encoded traversal in the path reaches an internal sentinel path under the fixed host, surfaced through a counted tool's response; the fix-check stands the sentinel through the kit's existing **`ssrf_env`** builder (record A's fixture, not record B's `arcadedb_env` copy-paste), as `cve_2026_73845_ckan.py` does: an `HTTP_ENDPOINT` witness place, `benign_calls=()` in the `FixCheckTarget` (the run-time benign call is a run concern recorded in the admission, so the baked stub never has to answer under the sentinel). `ssrf_env` passes no `-e` (only the planted env places), so the server reaches the sentinel only if the image's baked `GITLAB_API_URL` names the host the witness place claims (a name aliased to the sentinel by the planted `--add-host`, or `localhost` served on the holder's loopback). The same baked value must also reach the baked stub in the run, which runs with no planting: the stub must therefore listen at that same address in the run and stand aside (not collide on the address and port) when the sentinel holds it in the fix-check. This is the one hard point of the image design, settled before the entry is committed (calibration item 3 below). Benign call per counted tool: a legitimate job fetch the baked stub serves. Dropped flaws kept with their real or null class and logged: CVE-2026-61560 (the witness would be a stub artifact, not a real response, and its dfie is contestable), CVE-2026-61559 and CVE-2026-61568 (SSE/HTTP transport only, not routable over stdio, the grafana/68145 motive), GHSA-5648-rgj9-v224.

### googleapis/mcp-toolbox (nb71), new server, new `googleapis` responder provisioner

Two counted flaws, both dfie False, 102242 deferred (Decision 1). Server `Go:github.com/googleapis/mcp-toolbox` (the census spelling; the positions-107-and-119 census rows are one server, fourteen advisories, merged). Run image **1.10.0** (the first version fixing every version-setting flaw of the server, 102242 included, so the patched server carries no live counted-or-deferrable flaw and a finding on it is a false alarm). Both counted flaws record their patched version as **1.10.0** (the run image, which fixes them; their earlier first-fix versions, 1.3.0 for 11720 and 1.5.0 for 14540, are due-diligence notes, not the recorded `patched_version`), so `server.patched_version` 1.10.0 is a counted flaw's and `server_patched_surfaces` is null for both. This departs from the census `first_patched_version` of each flaw (the usual flyto/praisonai shape records the flaw's own first fix and a non-null `server_patched_surfaces` on the server's later version, which needs a counted flaw at 1.10.0 to anchor the server, and 102242 is the only such flaw and is deferred): `_patched_version_problems` and `_counts` accept the scheme, nothing else reads `patched_version` against the census, and each counted flaw carries a `patched_version` settlement (`flaw` the CVE, `field` `patched_version`, `value` `1.10.0`) whose reason names the first-fix version and that the recorded one is the run image, so the entry does not read as contradicting the advisory. Both counted flaws use `patched_source` `none` (OSV names 1.10.0 as the fix for neither counted flaw, so `none` is the honest value over `advisory`; no code reads the field). The HTTP tool is configured in the documented `http-tool.md` form with a neutral description (dfie is read off the description). A single `googleapis` responder on a public-range address serves the upstream both flaws reach; the SSRF guard present since 1.5.0 (PR #3448) blocks loopback and RFC1918, so the responder sits on a public-range `/24` of its own bridge, free of every other backend's (the three TEST-NET blocks are taken by n8n, contextforge and ckan, so the next free RFC 2544 block `198.18.3.0/24` is the first candidate, kept only if the 1.10.0 guard lets its benign fetch through, settled at Step 1).

- **CVE-2026-11720** (read_outside_scope): a base-path escape (record B's fixture, base `/api/v1/users/`, exploit `../../../admin/secret`, not record A's fixture whose exploit and benign resolve to the same URL and so prove no escape). The fix imposes the base-path scope and rejects host override, a "stay under the base path" contract, so the escape is the flaw, not the declared fetch. Counted tool the HTTP tool reaching the upstream.
- **CVE-2026-14540** (internal_fetch): a redirect off the configured upstream. dfie False (the configured upstream is the bounded target). Counted tool the HTTP tool.
- Witness: the out-of-scope or redirected fetch reaches the responder's sentinel path, whose body carries the nonce, surfaced through the counted tool's response. Benign call per counted tool: a legitimate fetch of the configured upstream the responder serves.
- **CVE-2026-102242 deferred** (Decision 1): a symlink escape out of `allowedLocalRoots` against a GCS backend, which needs a fake-gcs-server emulator and so a composite backend (responder plus emulator) the single-field `AdmittedServer.backend` does not model. It is kept in the entry as a flaw with **null `effect_class`** (so `_counts` returns False and it is neither counted nor given a `FixCheckTarget`), logged as deferred, and admitted later as a counted flaw when the composite-backend shape is designed. The run image is already 1.10.0 (which fixes it), so adding it later needs no re-pin. The eleven other census flaws of the server (fourteen in all, minus the three above) stay dropped (null class, out of grammar or needing real GCP, the BigQuery/Storage/Healthcare `external` ones), kept and logged. Three of the fourteen (CVE-2026-14541, CVE-2026-14539, CVE-2026-14538) are classified under the spelling `https://github.com/googleapis/mcp-toolbox`, the others under `Go:github.com/googleapis/mcp-toolbox`: `_foreign_flaws` rejects a flaw whose census server differs from the entry's `server_package` unless a settlement with `field` `server_package` and `value` the entry's package names it (the ContextForge case, `_settled_to_server`), so the entry carries one such settlement per flaw under the other spelling. Three of the eleven are classified in a graded class by the census (CVE-2026-16481 `internal_fetch`, CVE-2026-15829 and CVE-2026-14538 `read_outside_scope`): each is uncounted because its effect needs a real Google Cloud backend the fixture cannot provide (16481 a Healthcare FHIR fetch, 15829 and 14538 BigQuery), so each carries `backend_need` `external`, which empties `flaw_counted_tools` and removes it from the count, recorded with that settlement reason and logged.

## Edge cases

A counted tool with no benign call fails `_benign_call_problems`. A dropped or deferred flaw stays in the entry with its real or null class and is not deleted (gitlab's four, googleapis's twelve); a deferred flaw set to null class is not counted (`_counts` requires a non-null `effect_class`), so 102242 needs no `FixCheckTarget`. `_patched_version_problems` requires `server.patched_version` to be one of the counted flaws' `patched_version` and null-iff-equal `server_patched_surfaces` per counted flaw: googleapis satisfies it by recording both counted flaws' `patched_version` as 1.10.0 (the run image), so 102242 need not be counted to anchor 1.10.0. `test_each_target_mechanism_and_tools_match_the_admission_flaw` raises `KeyError` on a target whose flaw has no admission record, so each fix-check module and its `FIX_CHECK_TARGETS` row land in the same commit as its entry, never before, and a server authored speculatively (ios-simulator) commits its module, row and entry together or not at all. The googleapis responder must bind a public-range address overlapping no other backend bridge so the patched server's SSRF guard (present since 1.5.0, so at the 1.10.0 run image) lets the benign fetch through. A benign argument that enters the fixture fingerprint must be a stable string, not a per-launch uuid. gitlab's baked stub and ios-simulator's baked stub are inlined by `RUN`, never `COPY`ed. A `RegisteredBackend` whose provisioner stands one responder (googleapis) matches the apify/jenkins precedent; `backend_problems` checks one `image`.

## Implementation steps

Five steps, one commit each, in dependency order. The `googleapis` provisioner lands before the entry that names it, so `load_admission` stays valid at each commit, and each server's entry, fix-check module and `FIX_CHECK_TARGETS` row land in the same commit (`test_each_target_mechanism_and_tools_match_the_admission_flaw` raises `KeyError` on a target whose flaw has no admission record, and the coverage test is red on an entry without a target). Steps 2 to 4 each add one admission entry merged after the existing thirty-nine; none edits an existing entry. Repo code goes through the implementation flow. Eval data (every `evals/nuisance_admission.json` entry and every Dockerfile) is hand-authored by the maintainer and committed by hand, and each step says what must exist before the implementer starts. The calibration-held items of the Decisions section stay the maintainer's, resolved at the step that cites them, before the entry depending on them is committed.

Why not fewer steps: Step 1 (provisioner, 5 files) and Step 2 (two fix-checks plus entry) would together exceed the 6-7 file budget, and the provisioner must be committed before any entry names it. Step 3 and Step 4 are separate because Step 4 is speculative and may produce no commit. The docs step waits on Step 4's admit-or-drop outcome.

Test-first within every repo-code step (CLAUDE.md Workflow): the step's unit tests are written and run red before the code that makes them pass.

Verification common to every step: the short loop while working (`uv run pytest tests/unit -n auto --maxprocesses 4`, `uv run pyright <changed files>`), then the step-closing full checks with no file argument: `uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format .`, `uv run pyright`. Docker calibration is a maintainer action per step and never gates the unit checks. `tests/unit/test_cve_compose_labels.py` constrains every maintainer-authored Dockerfile: every `FROM` pinned by digest, no `COPY`/`ADD` from the build context (stubs and tool files are inlined by `RUN`). The nuisance Dockerfiles are not compose services: no `compose.yml` entry, no fingerprint label.
