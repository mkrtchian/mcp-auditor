# Holdout run mode

## Context

The holdout layer of the CVE benchmark has a pre-registered selection rule (ADR 028, `docs/holdout-rule.md`, version 6), a census, a draw order, an isolated calibration kit and an empty target module (`evals/holdout_targets.py`, `HOLDOUT_TARGETS = ()`). What is missing is the run mode: the command that audits the drawn targets under the rule's run conditions, keeps no per-case trace, and reports the capability number the rule defines. It follows the draw prerequisites shipped on 2026-10-16 (`plans/2026-10-16_holdout-draw-prerequisites.md`). The draw itself is the maintainer's deferred session and is out of scope here; this plan builds the machinery the draw session will run, and leaves `HOLDOUT_TARGETS` empty.

The rule sections this plan implements are "Run conditions and statistic", "Reading" and the split and contrast parts of the statistic. The decisions this plan builds on: the first holdout run uses the default configuration (`gpt-6-luna` at `none`), and a run under another model is a different run condition, read side by side and never paired against a number of the default configuration. The run conditions file ships now with the cutoffs and prices filled and the chain settings and tool call timeout deferred to the acceptance run with chains enabled that sets their values on cost. Cost is attributed per role (generator and judge priced separately) so a later run whose judge differs from its generator prices correctly. All the interval math the rule names is built now, in pure Python.

## Approach

A holdout run is a sibling of the acceptance gated session (`evals/cve_session.py`), not a reuse of it: it has no gate, no baseline, no judged-case export, and an opposite refusal policy. It reuses the real audit of one target (`cve_audit`), the no-LLM pre-run check on both versions (`cve_calibration.check_target`), the layout check (the verdict `cve_layout_check.confirm_admission` computes, exposed as `layout_check` since `confirm_admission` returns only the route failures and prints the break), the replay (already inside the audit's grade) and the fixture fingerprint (`cve_baseline.fixture_fingerprint`). Each of these takes the acceptance `CVETarget` a `HoldoutTarget` composes (`entry.target`), with whatever other arguments the acceptance callers already pass it (`check_target(target, places)`, `fixture_fingerprint(target, places)`). It adds: a run-conditions loader that refuses an incomplete file, a holdout audit wrapper with the holdout refusal and error policy, a per-target assembly, the interval math, and a report model that structurally cannot hold proof text. The command is `python -m evals.run_holdout run`; with `HOLDOUT_TARGETS` empty it prints that no target is drawn and exits 0, so the command is wired and tested before the draw.

The single src change is the per-role usage split, kept minimal: a new additive `judge_usage` state channel the two judge nodes write, and an `AuditReport.judge_usage` field, leaving `provider_usage` the grand total so every existing reader is untouched. The generator usage is the total minus the judge usage, computed where the cost needs it.

## Files to modify

### src: per-role usage split (the only hexagon change)

`src/mcp_auditor/domain/models.py`: `AuditStep` gains no member; add a module-level `JUDGE_STEPS = frozenset({AuditStep.JUDGMENT, AuditStep.CHAIN_JUDGMENT})` and `def is_judge_step(step: AuditStep) -> bool`. `ProviderUsage` gains `def sub(self, other: "ProviderUsage") -> "ProviderUsage"` mirroring `add` (field by field; `cached_input_tokens` and `reasoning_tokens` stay subsets, `throttled_requests` subtracts too). `AuditReport` gains `judge_usage: ProviderUsage = ProviderUsage()` (stored) and a computed property `generator_usage` returning `self.provider_usage.sub(self.judge_usage)`. `provider_usage` stays the stored grand total, so `console.py`, `metrics.SessionThrottles.count`, `cve_audit` throttle counting and every existing test that reads or builds `provider_usage` are unchanged. `checkpointing.py` serialises `AuditReport`, so a new checkpoint carries `judge_usage`; because the field is optional with a default, an old checkpoint deserialises with `judge_usage = ProviderUsage()` (so `generator_usage` reads as the full total), and no committed golden pins the full JSON shape of an `AuditReport` (verified), so none drifts.

`src/mcp_auditor/graph/state.py`: add `judge_usage: Annotated[list[ProviderUsage], operator.add]` to `GraphState`, `AuditToolState` and `ChainAuditState`, beside the existing `provider_usage` channel (not replacing it).

`src/mcp_auditor/graph/nodes.py`: in `judge_response`, the success return adds `"judge_usage": [usage]` beside the existing `"provider_usage": [usage]`. In `generate_report`, compute `judge_usage = _sum_provider_usage(state.get("judge_usage", []))` and pass `judge_usage=judge_usage` to `AuditReport`. `provider_usage` keeps summing the full `state["provider_usage"]` channel (judge usage included), so it stays the grand total.

`src/mcp_auditor/graph/chain_nodes.py`: in `judge_chain`, the success return adds `"judge_usage": [usage]`.

`src/mcp_auditor/graph/refusals.py`: `Refused` gains `is_judge: bool`; `call_model` sets it with `is_judge_step(call.step)`; `Refused.state_update()` adds `"judge_usage": [self.usage]` when `self.is_judge`, so a refused judgment's billed usage lands in both channels like a successful one. Generator refusals are unchanged (they write only `provider_usage`).

What the split must preserve: `provider_usage` is the sum of every billed call, judge included, exactly as today. `judge_usage` is the judge subset. `generator_usage = provider_usage - judge_usage`. When the generator and judge run on one model (the first holdout run, Luna for both), `provider_usage × price` equals `generator_usage × price + judge_usage × price`, so the split changes no number for an equal-model run; it only lets an unequal-model run price each role.

### evals: run conditions

New `evals/holdout_conditions.py`: the dataclasses and loader for `evals/holdout_conditions.json`. `@dataclass(frozen=True)` `Cutoff(date: date, type: str | None, note: str | None)`, the existing `evals/probe_candidates.Prices` (dollars per million tokens, `input`, `cached_input`, `output`) reused as the price type rather than redefined, and `HoldoutConditions(chain_budget: int | None, max_chain_steps: int | None, tool_call_timeout: int | None, cutoffs: dict[str, Cutoff], prices: dict[str, Prices], prices_as_of: date)`. The cost of a usage at a price is the existing `evals.probe.call_cost(usage, prices)` (uncached input, cached input and output priced apart), not a second formula. `load_conditions(path: Path) -> HoldoutConditions` parses the JSON and raises `Refused` (reused from `eval_session`) with a clear message when the file is absent. `HoldoutConditions.require_ready(model_ids: Sequence[str]) -> None` raises `Refused` when any of `chain_budget`, `max_chain_steps`, `tool_call_timeout` is `None` ("chain settings and tool call timeout not set, set them in evals/holdout_conditions.json"), or when a model of the run has no cutoff ("no logged cutoff for <model>") or no price ("no price for <model>"). The loader itself never calls `require_ready`; the run command calls it with the run's models, so loading the file for inspection stays cheap and the refusal names exactly what is missing. `HoldoutConditions.run_cutoff(model_ids: Sequence[str]) -> date` returns the latest cutoff date among the run's models (the rule's "cutoff of its own models"), which `split_by_side` uses; it assumes `require_ready` already passed, so every model has a cutoff.

New data file `evals/holdout_conditions.json`: `chain_budget`, `max_chain_steps`, `tool_call_timeout` all `null` (deferred until their values are set), `cutoffs` with `gpt-6-luna` at `{"date": "2026-05-18", "type": "<vendor wording, confirmed at draw>", "note": null}`, `prices` with `gpt-6-luna` at its list price on `prices_as_of`, taken from `evals/probe_candidates.py` (`PRICES_DATE` and the Luna entry), `prices_as_of` that same date. The file is committed almost-ready: only the chain and timeout values are missing, and the loader refuses a run until they are set.

### evals: holdout audit policy

`evals/cve_audit.py`: expose the single attempt by renaming `_attempt` to `attempt_once` (public) and the guard `graded_or_refused` stays as is. `audit_target` keeps using `graded_despite_refusals` for acceptance, unchanged. No behaviour change on the acceptance path. Calling `attempt_once` needs the auditor it is bound to (an `_Auditor` built from `load_settings()`, `create_llm`, `create_judge_llm`), plus a `SessionThrottles` and `Places`: expose that construction too (make `_Auditor` public, or add a `build_auditor(budget) -> Auditor` factory), since the holdout orchestrator builds the attempt thunk itself and must not go through `graded_despite_refusals`. The stale `_attempt` mention in `cve_replay.py`'s comment is updated to `attempt_once`.

Two more changes to `cve_audit.py`, both inert on the acceptance path:

- `RefusedAttempt` gains `report: AuditReport` (`graded_or_refused(grade, report)` has it at hand). A refused run is billed, and the rule reports the cost of the run and the tools count of every target, so the holdout needs the report's `provider_usage`/`judge_usage` and `len(report.tool_reports)` from a refused run too. `graded_despite_refusals` only `isinstance`-checks it, so acceptance reads nothing of it. The two bare `RefusedAttempt()` constructions in `tests/unit/test_cve_audit.py` (lines 60 and 72) get a crafted report.
- The run conditions have to reach the audit. Today the chain settings come from the target's builder (`Launch.chain_budget`/`max_chain_steps`, 3 and 5 on the git builder, 0 and 3 elsewhere) and the tool call timeout is the `TOOL_CALL_TIMEOUT` default `_silent_client` leaves on `connect`. The rule makes all three "the same for every target", so `attempt_once` takes an optional `RunOverrides(chain_budget, max_chain_steps, tool_call_timeout)` (a frozen dataclass in `cve_audit.py`), default `None`: when given, `_audit` puts its chain settings in the graph input instead of the launch's, and `_silent_client` passes its timeout to `connect`. Acceptance passes `None`, so its numbers do not move. The holdout orchestrator builds it from `HoldoutConditions` once `require_ready` passed. Without this the conditions file is decorative: `require_ready` would refuse on values the run never applies. The plumbing is built now, with the run mode, and only the values wait for the chains-enabled acceptance run: the mechanism that applies uniform chain settings and a uniform timeout is part of what "run the holdout" means, and the first holdout run, after the draw and after those values are set, needs it in place. `require_ready` refusing until the values are filled is the intended guard, not a smell.

Nothing in these two changes touches `graded_despite_refusals`, `REFUSAL_ATTEMPTS` or the replay.

New `evals/holdout_audit.py`: the holdout refusal and error policy, opposite to acceptance. `RefusedRun(report: AuditReport)` (a run whose step the provider refused, with no detection, counted as not detected and never retried; it carries the report only for the usage and the tools count, as `RefusedAttempt` does). `holdout_audit(target, attempt) -> GradedAudit | RefusedRun | None`: one call to `attempt`; a `GradedAudit` returns as is (a detection stands whatever step was refused, which `graded_or_refused` already encodes); a `RefusedAttempt` returns `RefusedRun` with no retry (unlike acceptance, a retry would keep the best of several attempts, holdout-rule.md:249); `None` (launch or infra failure) is retried at most twice, then returns `None`. The retry count is a module constant `HOLDOUT_INFRA_ATTEMPTS = 3` (one try, two retries). It prints the refusal and the retries as counts, never proof text.

### evals: the orchestrator

New `evals/holdout_run.py`: the run of all drawn targets at one commit. `HoldoutTargetResult` (per target, after the replay): `cve_id`, `side` (the drawn side, for the composition), `disclosure_date` (joined from the census by `cve_id`, `CensusFlaw.disclosure_date`, so the split can recompute the side against the run's cutoff), `mechanism_label` (`target.mechanism.value`, or `None` under no class), `tools_count` (`len(report.tool_reports)` of a run, the same every run), `ran_in_fallback` (`target.launch_mode is LaunchMode.FALLBACK`), and per-run data drawn from the grades: `runs` (the run count, constant across targets since a `RefusedRun` is a run), `detected_runs` (runs whose status after replay is in `DETECTION_RUNGS`, an integer, the hierarchical interval's binomial count) and `detection_share` (`detected_runs / runs`), `detected_runs_if_unchecked_missed` (the same count with each run's `RunGrade.status_if_unchecked_missed` read in place of its `status` where it is not `None`, the rule's unchecked-as-misses recomputation, holdout-rule.md:245), `surfaced_places` / `struck_places` / `unchecked_places` per run (reused from the grade, place ids only), `aimed_runs`, `fail_without_proof_runs`, `refused_runs`, and `run_cost` (the dollars summed over its runs, refused runs included, each run's `generator_usage` and `judge_usage` priced with `call_cost` at the conditions' price of the generator and of the judge model). `HoldoutRunResult`: the run conditions the rule names (holdout-rule.md:225-231: `runs`, `budget`, `provider`, `model`, `judge_model`, `reasoning`, `judge_reasoning`, the cutoff of each model with its type and note, the chain settings and the tool call timeout, the grammar fingerprint and each target's fixture fingerprint), the provenance (`commit`, `census_commit`, and the image ID of each target's images, holdout-rule.md:233), the per-target results, the targets left out of N with their reason, the refused-run count with the targets it touched, the total cost and `prices_as_of`. The models of the run come from `load_settings()`: `settings.resolve_model()` and `settings.resolve_judge_model()`, with `settings.resolve_reasoning(...)` for each; these are the `model_ids` handed to `require_ready` and `run_cutoff`. The grammar fingerprint is `fingerprint_sources` over `GRAMMAR_PATHS`, and the image IDs `docker image inspect` per tag: both live in `evals/run_cve_benchmark.py` today (`GRAMMAR_PATHS`, `_image_ids`); move them to `evals/cve_baseline.py` (as `grammar_fingerprint()` and `image_ids(names)`) and import them from both callers rather than import the acceptance CLI module from the holdout.

The orchestrator: refuses up front when `LANGSMITH_TRACING` or `LANGCHAIN_TRACING_V2` is set (reuse `eval_runs._tracing_enabled`, made public as `tracing_enabled` since a second module now reads it), refuses when any drawn target carries a `tools_filter` (the rule runs with none, holdout-rule.md:227; `test_holdout_targets.py` already pins it on the committed tuple, the refusal covers a monkeypatched one), loads and `require_ready`-checks the conditions for the run's models, rebuilds the images (see below), then runs the pre-run check on every target on both versions. The check is two calls per target, `check_target(entry.target, places)` (the dead conditions on either version, holdout-rule.md:223) and the layout check (holdout-rule.md:159). `confirm_admission` cannot serve the second: it returns only the unrouted-kept-place failures and merely prints the break, while the rule drops a target when the check finds a break calibration did not find. So `cve_layout_check` exposes the verdict it already computes: `layout_check(target, places) -> LayoutCheck` (frozen: `gave_up: str | None` from `admission_gave_up` on either version, `breaks: bool` from `layout_breaks_any` over both versions' surface pairs, `unrouted: list[str]` the kept layout places without a route), and `confirm_admission` is refactored to call it per target and print from it, its own return value unchanged. The orchestrator drops a target from N when `check_target` returns a condition, when the layout check gave up, when `breaks and target.launch_mode is LaunchMode.NORMAL` (calibrated under a launch it can no longer use), or when a kept layout place has no route; a break on a `FALLBACK` target keeps its fallback, and no break on one does too (holdout-rule.md:159). Each drop is reported not run with its reason. It then audits each surviving target `runs` times with `holdout_audit` (budget `HOLDOUT_BUDGET = 10`, a module constant from holdout-rule.md:227, not a flag), the audits bounded by `evals.concurrency.bounded` at a `--concurrency` the CLI takes (default 6 like the acceptance, 1 for a sequence), drops from N a target whose any run returned `None` after retries (so N is the same in every run), and assembles `HoldoutTargetResult`s from the grades and the reports' usage alone. It never builds a `CVEResult` (which carries `evidence`), never calls `export_cve_judged_cases`, never writes a baseline and never gates.

Image rebuild: a thin `rebuild_images(services: Sequence[str]) -> None` that runs `docker compose -f evals/docker/compose.yml build <services>` with the build cache, over the services of every target (`images` and `patched_image`). The service-collection is a pure helper tested on its own; the subprocess call is a thin wrapper the maintainer smoke-runs when targets exist. With `HOLDOUT_TARGETS` empty, rebuild is a no-op.

### evals: the interval math

New `evals/holdout_intervals.py`: the interval primitives, pure, `math` only, no numpy or scipy. `wilson(count: float, n: int) -> Interval` (two-sided 95 %, no continuity correction, `count` a possibly non-integer sum of detection shares, `z = 1.959963984540054`). `newcombe(count_a, n_a, count_b, n_b) -> Interval` (hybrid score for the difference, each arm's Wilson bounds combined by the Newcombe formula). `jeffreys(count, n)` and `clopper_pearson(count, n)`, both via Beta quantiles in the Beta-quantile form the rule names for a non-integer count. `agresti_caffo(count_a, n_a, count_b, n_b)` (add one success and one failure per arm, then Wald on the difference). The Beta quantile `beta_ppf(p, a, b)` is a bisection on the regularized incomplete beta `betainc(x, a, b)`, itself a Lentz continued fraction (`betacf`) with `math.lgamma` for the prefactor, the standard Numerical Recipes algorithm, ~40 lines. `Interval` is a frozen dataclass `(low, high)`, clamped to `[0, 1]` for proportions and `[-1, 1]` for the contrast.

New `evals/holdout_hierarchical.py`: the hierarchical Beta-Binomial credible interval, kept apart because it integrates. Per-target detected runs are Binomial over the runs; the per-target rate is Beta with mean theta and concentration d, so the per-target marginal is Beta-Binomial, its log pmf from `math.lgamma`. The posterior over theta (and the nuisance d) is a grid integral: a grid over theta in (0,1) and d on a log grid, the likelihood the product of per-target Beta-Binomial pmfs, the prior theta ~ Beta(1,1) and d ~ Gamma(shape, scale). `hierarchical_interval(detected_per_target: Sequence[int], runs: int, d_prior: GammaPrior) -> Interval` marginalises d and returns the 95 % equal-tailed credible interval on theta. The two priors the rule names, Gamma(1,1) then Gamma(2,2), are two calls, a sensitivity check. `contrast_hierarchical(side_a, side_b, runs, d_prior) -> Interval` shares one d across both sides and returns the posterior of the difference of the two thetas. Grid sizes are module constants, chosen so the result is stable to the cited precision on 20 targets; a test pins stability against a finer grid.

New `evals/holdout_statistic.py`: the holdout-specific aggregation over `HoldoutTargetResult`s. `primary_number(results) -> float` (mean over runs of k/N, equal to the sum of detection shares over N). `cited_interval(results) -> Interval` (Wilson on the sum of shares over N). `split_by_side(results, run_cutoff) -> dict[Side, SideStatistic]` (each side's primary number and Wilson). The split is on the run's own cutoff, not the drawn side: `run_cutoff` is the latest knowledge cutoff among the run's models (read from the conditions' cutoff table), and each target's side here is recomputed, PRE when its `disclosure_date` is on or before `run_cutoff` else POST (holdout-rule.md:208 and :241; the drawn side only set the composition). For the first run the models are the default configuration at the draw, so `run_cutoff` equals the draw cutoff and the recomputed side coincides with the drawn one; a later run under a model with a different cutoff splits correctly without a redraw. `contrast(side_a, side_b) -> Contrast | None` (Newcombe when each side has at least 5 targets, else `None` and the two reported side by side). `primary_controls(results, runs) -> dict[str, Interval]` computes the control intervals the rule names for the primary number (holdout-rule.md:245): Jeffreys and Clopper-Pearson on the same non-integer count, the hierarchical interval under Gamma(1,1) and Gamma(2,2) on the per-target `detected_runs`, and Wilson on the unchecked-as-misses count (the sum of `detected_runs_if_unchecked_missed / runs`). The one conclusion the report draws is the contrast against zero (is there a side gap), so `check_conclusion(side_a, side_b, runs) -> ConclusionVerdict` is about the contrast, not a count and threshold: it places each interval against zero (`above`, `below` or `straddles`) for the cited Newcombe, the Agresti-Caffo control, the hierarchical contrast under both priors, and each of those four again on the unchecked-as-misses counts, and returns the Newcombe placement as the conclusion when every method agrees, else `inconclusive` with the disagreeing methods and their intervals. It is `None` when `contrast` is (fewer than 5 targets a side). The primary number cites Wilson and shows its controls beside it without drawing a fixed-threshold conclusion, since the rule names no threshold for it.

### evals: the report

New `evals/holdout_report.py`: the report model and its markdown, the structural guarantee that a holdout run keeps no proof. `HoldoutReport` is a pydantic model holding only the run conditions and provenance of `HoldoutRunResult` (so a reader can tell two runs apart, holdout-rule.md:247), the primary number, its Wilson interval and control intervals, the per-side numbers, the contrast and its conclusion verdict, and per target: the class label, the detection share, the runs where a nonce surfaced and from which places (ids only), the refused credits and the unchecked credits (ids only), the aimed runs, the fail-without-proof runs, the refused runs, whether it ran in the fallback, the tools count and the cost. It has no field for `evidence`, no judge input, no per-case verdict, so a holdout run cannot write proof text even by mistake. `render_markdown(report)` prints the primary number with its interval, the ladder of statuses, the split, the contrast, the control intervals as controls, the not-run targets with their reason, the refused-run count, and the total cost in dollars at the conditions' list prices. The run writes this report's JSON and markdown to `--report` and prints the markdown; it writes nothing else.

## What stays unchanged

`HOLDOUT_TARGETS` stays empty; the draw fills it. `CVE_TARGETS`, `OUT_OF_SCOPE_CVES`, the acceptance gate, the judge fixture draw and the probe corpus are untouched, and the test that no instrument imports `evals.holdout_targets` stays green (the orchestrator imports it, and the orchestrator is not an instrument on that list; it is added to neither the gate nor the draw nor the probe). `provider_usage` keeps its meaning (grand total) everywhere. The acceptance audit policy (`graded_despite_refusals`, retry refusal three times) is unchanged. `docs/holdout-rule.md` and the ADRs are not edited: the run mode is code the rule already describes, so it opens no rule version. The grammar, the places and the layout are not touched.

## Edge cases

A conditions file present but with the chain and timeout values still `null`: `require_ready` refuses with the message naming them, the run does not start. A run model with no logged cutoff or no price: refused, named. Tracing on: refused before any container. `HOLDOUT_TARGETS` empty: the command prints that no target is drawn and exits 0, so the plan's own tests and CI exercise the wiring without a draw. A target that fails the pre-run check on either version: not run, out of N, reason recorded, N stays the same across the run's three runs. A target the layout check finds broken when calibration found no break (`launch_mode` NORMAL): not run, out of N (holdout-rule.md:159); a FALLBACK target keeps its fallback whatever the check finds. A drawn target carrying a `tools_filter`: refused before any container. A refused run is billed: its usage enters the target's cost and the total. A target whose any run fails to launch after the two retries: not run for the whole holdout run, out of N. A run whose step the provider refused with no detection: counted as not detected in that run, the target stays in N, the refused-run count rises; a detection with a refused step stands. A replay that cannot be checked: its credit is kept and reported unchecked, and the unchecked-as-misses recomputation feeds the conclusion check. A side with fewer than 5 targets: no Newcombe, the two sides reported side by side. The generator and judge on one model: the cost split changes no number.

## Test scenarios

Per-role usage (unit, `graph`): an audit whose generator and judge both run on a `FakeLLM` with distinct per-call usage yields an `AuditReport` whose `judge_usage` sums only the judgment and chain-judgment calls, whose `generator_usage` is the complement, and whose `provider_usage` is the unchanged grand total. A refused judgment adds its billed usage to `judge_usage`; a refused generation does not. `ProviderUsage.sub` is the field-by-field inverse of `add`.

Conditions loader (unit): a complete file loads; an absent file refuses; `require_ready` refuses a file with a `null` chain setting or timeout, and refuses a model with no cutoff or no price, each with the naming message; a file with the cutoffs and prices but the chain and timeout values `null` loads but refuses `require_ready` (the committed state).

Holdout audit policy (unit, with a fake attempt): a `GradedAudit` passes through; a detection with a refused step passes through; a `RefusedAttempt` returns `RefusedRun` with exactly one call (no retry); an infra failure returns `None` after exactly three calls.
