# Holdout fix batch (post-transplant review findings)

## Context

The batch-2 holdout transplant is complete: all thirty drawn CVE holdout targets are in `HOLDOUT_TARGETS` and calibrate green (whole-set `run_holdout calibrate`, 30 live, 0 dead), commits up to `80912b2` on `main`. Review after the transplant surfaced a set of correctness and fidelity issues that calibration cannot catch on its own, because calibration runs each target's arms sequentially and one target at a time, while the defects live in the concurrent scored path and in one target's kept-place accounting. This plan fixes them. It runs no scored LLM audit: the gate is Docker calibration (no LLM), as in the transplant plan.

The holdout is a blind holdout. Each target's external per-target facts (affected and first-patched versions, git commits/tags, base images, CVSS) are pinned in the maintainer's per-target calibration kit, held outside the repository and blind to the auditor, and re-checking them against live PyPI/NVD/GHSA is contraindicated: an upstream rescore or a yanked release must not move a fixture pinned to a calibrated vulnerable/patched pair. The authoritative source for every per-target value is the target's own kit on local disk, never the web. A kit-vs-fixture comparison (reading the kit on disk) is in scope; a web lookup of a pinned fact is not.

## Approach

Each fix is an independent, self-contained change with its own commit, ordered by severity: the two P1 correctness/fidelity fixes first, then the P2 hygiene pair, then the P3 items the implementer may do or defer. A step that touches an environment builder or a fixture is gated by that target's Docker calibration (`run_holdout calibrate --cve <ID>`, no LLM); the full non-Docker check (`uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run pyright`) closes every step. No step edits the shared places catalogue, the acceptance layer, the instruments, or any baseline.

## P1 a. Doris target collides with itself under concurrent scored runs

`evals/cve_environments.py`, the `doris_db_env` builder (lines ~389-436) and its helpers `_ensure_doris` (~516), `_start_doris_sentinel` (~565), `_doris_rm` (~622). The scored `run_holdout run` audits each target `HOLDOUT_RUNS` (default 3) times concurrently under `HOLDOUT_CONCURRENCY` (default 6), so the three runs of a given target overlap. `doris_db_env`, alone among the builders, does not isolate per-launch state behind `planted()`'s uuid-unique holder: it stands sentinels at a fixed link-local metadata IP (`sentinel.host`, e.g. `169.254.169.254`) on the shared persistent `_DORIS_LLNET`, named from the host alone (`{LABEL}-doris-sentinel-<host-with-dashes>`), force-removing any existing one first (`_doris_rm(name)`); and `_ensure_doris` races three-ways on `docker run --name mcp-auditor-cve-doris`. Three concurrent Doris launches therefore (a) collide on the sentinel container name and on the static `--ip` (two `docker run --ip` on the same network and IP fail with a `CalledProcessError` out of `_doris_run(..., check=True)`), (b) have each run's `_doris_rm(name)` tear down a sibling run's live sentinel mid-audit, and (c) race the first cluster provisioning. The effect is dropped or incomplete Doris runs, or a spurious non-detection, i.e. a corrupted capability number for that one target at the first scored run.

The sentinel cannot be made per-launch-unique by IP: the exploit payload is pinned ground truth that fetches the real metadata IP, and the single shared Doris backend reaches exactly one sentinel at that IP. The sentinel is therefore a singleton resource for the duration of an audit, and the correct fix is to serialize the Doris target's concurrent runs, not to vary their resources. This keeps the deliberate shared-persistent-cluster design (standing a Doris FE+BE cluster up three times would be wasteful and slow) and corrects only the per-run isolation, so it needs no ADR: the design intent is unchanged.

Fix: introduce a module-level `threading.Lock` (name it for its role, e.g. `_DORIS_LAUNCH_LOCK`) and acquire it inside `doris_db_env` around the whole critical region, from `_ensure_doris()` and the sentinel stand-up, through the `yield`, to the teardown in the `finally`. Because the builder is entered and exited in a worker thread (`entered_in_thread`) and the generator frame stays suspended at the `yield` while the async audit runs on the event loop, a `threading.Lock` held across the `yield` serializes the three Doris audits: run 1 proceeds, runs 2 and 3 block in `__enter__` in their worker threads until run 1's `__exit__` releases. It must be a plain `threading.Lock`, **not** an `RLock`: `entered_in_thread` runs `__enter__` and `__exit__` as two separate `asyncio.to_thread` submissions (`evals/concurrency.py`), which may land on different pool threads, so the lock is acquired on one worker thread and released on another; a plain `Lock` permits cross-thread release, an `RLock` (owner-bound) would raise `RuntimeError` out of `__exit__` on release. A lightweight guard against regressing this: the serialization unit test releases on a different thread than it acquired on. Give the sentinel container a uuid-suffixed name as well (`f"{LABEL}-doris-sentinel-{uuid4().hex}"`), so the name no longer derives from the host and a stale sibling can never be matched or force-removed; the static `--ip sentinel.host` stays (it is the metadata IP the exploit targets) and is now safe because only one run holds the lock at a time. Holding the lock also makes the `_ensure_doris` first-provision race moot (only one run provisions), so no separate guard there is required, though the existing `_doris_running()`/`_doris_exists()` idempotence is kept.

Code shape (illustrative, not prescriptive):

```python
_DORIS_LAUNCH_LOCK = threading.Lock()

@contextmanager
def doris_db_env(image, spec, shape=LaunchShape.NORMAL):
    with _DORIS_LAUNCH_LOCK:
        _ensure_doris()
        server = f"{LABEL}-doris-server-{uuid4().hex}"
        sentinels: list[str] = []
        try:
            for sentinel in spec.sentinels:
                sentinels.append(_start_doris_sentinel(sentinel))
            time.sleep(2)
            yield Launch(command="docker", args=[...])  # unchanged
        finally:
            _doris_rm(server)
            for name in sentinels:
                _doris_rm(name)
```

and in `_start_doris_sentinel`, replace `name = f"{LABEL}-doris-sentinel-{sentinel.host.replace('.', '-')}"` + `_doris_rm(name)` with a uuid name and drop the pre-emptive `_doris_rm` (nothing to collide with under the lock). Add `import threading` to the module imports.

Edge cases: the lock must wrap the teardown too, not only enter→yield, so a run's `finally` cannot remove a sentinel while the next run has already begun standing its own; holding across the `yield` is deliberate and correct, not a mistake to "optimise" into a shorter critical section. The persistent cluster and its two networks are still left running on purpose (reused across exercises); the lock does not change that. On thread-pool headroom, the binding constraint is the per-target fan-out `runs` (fixed at 3 by the rule, lowerable only), not `HOLDOUT_CONCURRENCY`: at most `runs - 1` (two) Doris `__enter__` calls park on the lock, against the `asyncio.to_thread` default executor size (`min(32, cpu + 4)`, floor 5), so the lock holder's `__exit__` always has a free pool thread and there is no starvation or deadlock at the rule's fixed `runs`. A change that later raised `runs` toward the pool size would have to re-check this.

What stays unchanged in this fix: the `Launch` the builder yields (command, args, networks, `--db-*` flags) is byte-identical; the exploit/benign fixture (`cve_2025_66335_doris.py`) is untouched; the shared cluster, bridge and llnet names and the metadata IPs are untouched.

Gate: `run_holdout calibrate --cve CVE-2025-66335` stays green (the single-run calibration path is unaffected by the lock), plus a no-Docker serialization test on the real builder. The test must drive `doris_db_env` itself, not a stand-in wrapping the private `_DORIS_LAUNCH_LOCK` (which would only re-test the stdlib and would stay green if a refactor dropped the lock from the builder), with its Docker-touching helpers monkeypatched to no-ops/fakes (`_ensure_doris`, `_start_doris_sentinel`, `_doris_rm`, `time.sleep`) and a minimal `spec`, entered three times concurrently through `evals.concurrency.entered_in_thread`, asserting the critical regions do not overlap and that a cross-thread acquire/release completes without raising. Driving the real builder is what makes the test go red if the lock is ever removed from it, the invariant this step exists to guard. If monkeypatching the builder proves impractical, a documented manual check recorded in the step is the fallback.

## P1 b. CVE-2026-4270 (aws_api_mcp) kept-places fidelity

`evals/holdout_fixtures/cve_2026_4270_aws_api_mcp.py` (a batch-1 fixture), and the target's authoritative recalibration kit (held outside the repository). The recal calibration card lists twenty-one kept places, the twenty-first being `workspace-dotenv`, annotated "route found -> kept": it is readable via `@=file:///srv/.env`, one level above the declared working directory `/srv/app`, which is a genuine scope escape attributable to this flaw (the `@=file://` paramfile operator reads an absolute path outside the workdir). But the repo fixture's `KEPT_PLACES` holds only twenty (no `workspace-dotenv`), and its comment at lines 30-31 claims "no layout place is kept". The recal kit is internally inconsistent: its card says twenty-one with the route found, its own `kit_fixture` says twenty, and the repo copied the twenty. This is the only one of the thirty targets where the kit card and the fixture disagree on the kept set.

This re-settles a batch-1 target's calibration, so it is a maintainer decision, recorded in the fixture's `KEPT_PLACES` comment (which way, and the reason). The decision must rest on a route check, not on the card's recorded word alone, because the card and the kit fixture already contradict each other and one of them is wrong.

Fix: run the in-repo Docker route check for `workspace-dotenv` on the transplanted 4270 fixture (the same route check `run_holdout calibrate` runs, which confirms a kept place's nonce surfaces through the exploit path). If it routes (the `@=file:///srv/.env` read surfaces the planted nonce on the vulnerable image and not on the patched one), add `workspace-dotenv` to `KEPT_PLACES` (making twenty-one), rewrite the false "no layout place is kept" comment to state that `workspace-dotenv` is kept and why (absolute read above the workdir) and that the two guarded git layout places still route-check as not routed, and reconcile the recal kit's own `kit_fixture` to list twenty-one so the authoritative artifact is self-consistent. If it does not route, keep twenty, and rewrite the comment to record that the card's "route found" did not reproduce under the transplanted fixture and `workspace-dotenv` is therefore dropped, and reconcile the card's note accordingly. Either way the fixture's comment and the kit stop contradicting each other.

Code details: `workspace-dotenv` is **not** a FILE-kind place. In `evals/holdout_places.json` it is `kind: "dotenv"` (a `LAYOUT_KINDS` member), `source: "layout"`, with coordinates `{"anchor": "workspace", "relpath": ".env"}` and **no** `path`/`paths` field. Its container path is the layout anchor resolved against the frozen tree: `ANCHOR_PATHS[LayoutAnchor.WORKSPACE]` (`/srv`) joined with `relpath` (`.env`) = `/srv/.env`. The fixture's current `_readable_path` does **not** handle this: for a non-ENV/non-HOSTNAME kind it does `coordinates.path or next(iter(coordinates.paths or ()))`, and with both `path` and `paths` `None` that raises `StopIteration`. So adding `workspace-dotenv` to `KEPT_PLACES` as-is would crash the exploit builder at the route check, not read `/srv/.env`. The step must therefore, if the place routes, add a branch to `_readable_path` that resolves a layout place (anchor + relpath) to its container path (`ANCHOR_PATHS[place.coordinates.anchor] + "/" + place.coordinates.relpath`, or the shared layout-path helper if one exists), importing `ANCHOR_PATHS`/`LayoutAnchor` from `evals.cve_layout`; `_read_command` and the `@=file://{path}` operator are then path-generic and unchanged. The nonce itself is planted by the generic layout layer (`LayoutNode(anchor, relpath, content)` under the read-only `/srv` mount), so no symlink or extra structure is needed, unlike the catalogue file places. The implementer settles the route from the Docker check and the kit, not by guessing; if the kit's own exploit builds no read for this place either, that is itself evidence the card's "kept" is wrong and the place stays dropped.

What stays unchanged: `evals/holdout_places.json` (the shared catalogue is not edited; this is a per-fixture kept-list change, and `workspace-dotenv` already exists in the catalogue); 4270's `severity` (`"CVSS 6.8 (v4.0, kit card)"`, a real kit-card value, not a placeholder), its builder (`filesystem_env`), its `PlantingHost` (`SymbolicUser.HOST`, `/srv/app`), and its exploit/benign shapes (the tool call and the `@=file://` operator; only `_readable_path` may gain the layout-resolution branch described above if the place is kept).

Gate: `run_holdout calibrate --cve CVE-2026-4270` green with the settled kept set (all kept places route, exploit live on the vulnerable image, clean on the patched one), and `tests/unit/test_holdout_targets.py` green (reaches in vocabulary, kept places within reach and placeable).
