# Nuisance re-admission under rule v4, second part: the servers of lots L4 to L6

## Context

The version 4 admission campaign of the nuisance suite is settled outside the repository, and its readings of the rule are in `docs/nuisance-log.md` (entry of 2026-11-08). The first part of its re-admission (lots L0 to L3, commits `18be22d` to `eacfe4b`) made the counter read the declared function per tool, extended the stand-in authority tests to every captured host and backend-served TLS name, accepted a copy pinned by checksum or digest in `unsourced_copies`, and re-admitted 23 servers: the admission now holds 55 servers. This part carries the re-admitted servers of the campaign's lots L4 to L6: 23 servers stay and 3 leave. Six servers of these lots also stay but follow in a later piece of work, because each needs a new provisioner, a pass or a holdout recalibration on a shared file: jenkins, figma, kanban and aws-api-mcp here, sf-mcp and doris from the first lots.

Everything this plan relies on per server is in the vesting manifest: one section per server, giving its outcome, the flaws that set its version, its counted tools with the reason for each one added or removed, the fixture retained file by file (from the record of agent a, of agent b, or mixed), the releases, the seed, the stand-ins and backend, the fix check, the launch, the fields rule v3 and v4 add, the log lines, the agents' models and the points left open with a recommendation. The manifest, the maintainer's decision log, the two agents' records of each server and the fixtures they proposed are held outside the repository, and the maintainer gives their location to the implementer at launch. Where a manifest section and the decision log differ, the decision log wins. Where a section leaves a point open, its recommendation applies unless the decisions below say otherwise.

Nothing here runs an audit. Fix checks run through `run_nuisance calibrate` and benign calls through `run_nuisance vet`, both with Docker and no LLM.

## Decisions

These are the maintainer's, applied as stated.

1. **The counter already reads the declared function per tool.** A tool whose declared function is the effect stays in its flaw's `tools` with `declared_function_is_effect` true and is not counted. It is never removed in data for that reason. This settles flyto's `execute_module`, mcp-rtfm's `read_doc` and `refresh_documentation`, grok-faf's tools that declare the effect and python-notebook's `initialize_workspace` and `read_notebook`, whose sections recommend a removal in data. python-notebook stays.
2. **A tool reached with no benign call written does not count.** A tool that reaches a flaw but for which neither record writes and plays a benign call is left out of the flaw's `tools` and logged, as `run_job` was. In this part: mcpvault's `write_note`, `delete_note` and `update_frontmatter` (mcpvault stays at 12 counted tools). geekgod-fs is not such a case: both records add its nine other tools (`write_file_tool`, `list_directory_tool`, `create_directory_tool`, `delete_file_tool`, `delete_directory_tool`, `move_file_tool`, `copy_file_tool`, `search_files_tool`, `get_file_info_tool`), which pass the faulty guard of its read flaw with a path the caller chooses, and write a benign call for each. They count under the campaign's reading of writers through a faulty read guard (`docs/nuisance-log.md` 2026-11-08), each with `declared_function_is_effect` false, and geekgod-fs counts 10 tools once `vet` plays their calls.

3. **A counted tool that still carries the flaw on the patched version leaves the count.** A tool on which the patched version is still open to the same flaw (mcp-package-docs's `describe_python_package`) or that carries an open flaw whose categories overlap (fast-filesystem's `fast_read_file` and `fast_read_multiple_files` under CVE-2025-67364) is left out of `tools` and logged, the campaign's reading of a flaw never fixed (`docs/nuisance-log.md` 2026-11-08). mcp-package-docs counts the other tools both records agree on. A residual defect of the patched code that is no census flaw (jenkins's `buildNumber`, outside this part) is logged as an observation with no action.
4. **No server runs as the host user, and the host-user code goes.** git-mcp and auto-commit go from `host` to `unprivileged`: the rule's confinement is the same for every server, its user included, and nothing passed to the server is taken from the machine. The repair is the one agent b made for auto-commit: the seeded repository owned by the unprivileged account and `safe.directory` narrowed to it. Once both are re-admitted, no holdout target, acceptance target, fix check or nuisance host uses `SymbolicUser.HOST` (`test_no_holdout_target_runs_as_the_host_user`, `test_no_acceptance_target_runs_as_the_host_user` and `test_no_fix_check_runs_as_the_host_user` already pin the first three). A last commit of this part removes the dead code, with no shim: `host_user_args` (`evals/cve_planting_base.py`), the `HOST` member of `SymbolicUser` and its branches (`cve_planting._symbolic_user_args`, `nuisance_confinement.user_args`, the account-place refusal in `cve_planting_spec`), so the admission loader refuses a `host` user through the enum. The three tests that refuse `HOST`, and the committed-admission one this part adds (change 2), go with the member, since the type no longer admits it and a test that cannot fail is a liability, and the tests that exercised the host branches follow, as does every test helper that takes `SymbolicUser.HOST` as an arbitrary user (found by a search, moved to `UNPRIVILEGED`, the member that stays). The re-admission dossier's generated `confinement.md` text (`evals/nuisance_readmission_docs.py`, "the `host` user takes the invoking user's uid and gid") and any other generated dossier text that describes the host user follow, found by a search for the words as well as the symbols. Every CVE and nuisance fixture fingerprint moves with the hashed environment and confinement modules, with no fixture changed: one `docs/holdout-log.md` line and one `docs/nuisance-log.md` line say so (no baseline and no run exist). The `CLAUDE.md` landmine on the confined home tmpfs is kept, it concerns the invoking `uid` of the `--tmpfs` options, not the host user; any living doc that names the host user follows.

5. **System utilities the documentation does not version come from the base image, logged.** token-optimizer's `getent` and `id` (Debian 13) and fast-filesystem's coreutils (Debian 12) are the base image's packages, and each log entry records the departure from "the stable release current on the day". mcp-rtfm takes git 2.56.0 (agent b) and git-mcp keeps git 2.39.5 (both records), both logged.
6. **neo4j's engine runs in the server's image at Neo4j 5.26.1**, the release its README names and its holdout twin runs, as agent b's retained `Dockerfile.neo4j` pins it: `backend` goes to `null`, `host.has_network` to false, and the `neo4j` registry entry goes with its lifecycle once a search shows nothing else uses it. The fix check of CVE-2026-35402 is a module of its own (`evals/nuisance_fix_checks/cve_2026_35402_neo4j_cypher.py`, source `fix_check`, no holdout copy): it imports `NEO4J_IMAGE` and `NEO4J_BACKEND_DOCKERFILE` from `evals/neo4j_backend.py` and stands its own database from `Dockerfile.neo4j-backend`, building that image itself. Those stay for the fix check, as `evals/apify_backend.py` and `Dockerfile.apify-responder` stayed for apify's, and `Dockerfile.neo4j-backend` moves from 5.26.32 to 5.26.1 (the digest the twin's Dockerfiles pin, and its APOC copy from the hard-coded `apoc-5.26.32-core.jar` to the `apoc-*-core.jar` form the twin's Dockerfiles use), so the fix check verifies the release the run serves. The fix check and the lifecycle build `mcp-auditor-cve-neo4j-backend:local` only when the tag is absent, and `calibrate` does not rebuild it, so the implementer rebuilds the tag explicitly from the changed Dockerfile (`docker build -t mcp-auditor-cve-neo4j-backend:local -f evals/docker/Dockerfile.neo4j-backend evals/docker`, which retags and removes nothing) and checks with `docker image inspect` that it now derives from 5.26.1, before `calibrate --cve CVE-2026-35402` runs green, logged. The registry entry, `LIFECYCLE`, the run-only parts of `evals/neo4j_backend.py` (`ensure_neo4j`, `neo4j_server_args`, `neo4j_rm`, the bridge, alias and URI) and the `neo4j-backend` compose service go.

7. **The manifest's recommendations on open points apply**, with the exceptions above. In this part they settle, among others: gitlab keeps agent a's stand-in, the departure from running the real GitLab logged; googleapis serves the stand-in sourced from the project's tests (agent b) and keeps the six tools of its never-fixed flaws out of `tools`; facebook-ads keeps `graph.facebook.com` served by its backend responder, not named in `host.public_names`; agentic-flow counts its committed tool plus agent b's eight additions, `agentic_flow_agent`'s benign call taken from agent a, whose record alone writes one (with a's `api.anthropic.com` stand-in it reaches), else decision 2 leaves it out; auto-commit restores the lock its documented install reads; scrapling takes agent b's fixture; arcadedb keeps its SQL `query` benign call and drops the Cypher one, which `load_admission` refuses as a second call; mcpvault's `get_frontmatter` takes agent b's call (no prerequisite, `expect` `{}`); sylphxltd keeps `Cargo.lock` and takes the project's `README.md` as its seed; mcp-rtfm records its seed as `generated`; git-mcp counts 23 tools. Where a section leaves a choice between the two records' seeds open without a recommendation (agentic-flow, auto-commit, python-notebook, geekgod-fs, fast-filesystem), the maintainer's reading on seeds applies: keep the conforming one that writes the fewest values, a file shipped under a project's tests being a published sample only when its documentation presents it as an example, a published tree keeping its layout, and of several samples the documentation names, the first. The choice is logged.
8. **The stand-in authority is regenerated with each commit that adds a stand-in host, and no `holdout_fingerprint` is recorded**, as in the first part: every regeneration moves the fixture fingerprint of the holdout targets whose hosts declare stand-ins, and the copies' fingerprints are recorded once, after the last regeneration of the campaign.

## Changes

### 1. Stand-in authority with this part's hosts

The hosts this part adds are `api.anthropic.com` (agentic-flow), `raw.githubusercontent.com` (mcp-package-docs) and `api.openai.com` (auto-commit), each with a stand-in file and named in its server's `host.public_names.stand_ins` in the same commit, which `declared_stand_in_hosts` reads. facebook-ads adds none: agent b's responder keeps its fixed self-signed pair (trusted through `REQUESTS_CA_BUNDLE`), and its `graph.facebook.com.captures.json` is a record of the real host's answers that the responder's Dockerfile copies inline, not a stand-in file, kept under `evals/stand_ins/facebook-ads-responder/` where no top-level `*.json` glob of the stand-in tests reads it, with no leaf and no regeneration. Each server commit that adds a host runs `evals/stand_ins/tls/generate.sh` with every captured host plus every TLS name a registered backend serves from a fixture leaf (the set `tests/unit/support/test_committed_stand_ins_given.authority_hosts` computes), copies the new `fixture-authority.pem` into `evals/docker/Dockerfile.holdout-2026-5323-a11y` and `-patched`, and updates their fingerprint labels in `evals/docker/compose.yml`, so the stand-in tests and the holdout stale-PEM test pass at every commit. A route written from the service's published specification is `source: software_sources`. A stand-in file holds one host under one `source` (`public_stand_ins`), so agent a's `api.anthropic.com`, marked `capture` while its success route is written from Anthropic's documentation, cannot be split by route: it becomes a `software_sources` file as a whole (no `captured_at`, `command` naming the documentation, `address` a fixed global address), as the reading on stand-ins of remote APIs admits it. The CVE-2026-5323 images are rebuilt and calibrated once, after the last server.

Before and after each regeneration, `evals.nuisance_fingerprint.nuisance_fixture_fingerprint` shows which admitted servers' fingerprints move: every server other than the one the commit re-admits that moves, from the first part or re-admitted earlier in this one, gets a line in that commit's `docs/nuisance-log.md` entry with both values, as the first part's regenerations logged them. One `docs/holdout-log.md` entry, in the first regeneration's commit, as in the first part, so no commit moves the holdout fingerprints unlogged: the authority is regenerated with the nuisance hosts this part adds, which moves the fixture fingerprint of the holdout targets whose hosts declare stand-ins and of the acceptance target CVE-2025-65513, with no fixture of theirs changed. No CVE acceptance baseline is committed (`evals/baselines/cve/` absent), so nothing resets. If one has been recorded by then, the regeneration is a fixture change under ADR 016 and the baseline is deleted in its own commit.

## Edge cases

- A tool both records count but a decision leaves out: left out of `tools`, its omission logged, its agreement recorded as it was.
- A benign call `load_admission` refuses that the section's recommendation does not fix: the implementer stops and reports the server.
- A fix check the implementer cannot run green on the retained fixture (git-mcp and auto-commit under `unprivileged` included): stop and report the server, never record a `fix_check` that no calibration printed.
- A removal that a holdout target or a fix check still references: keep the file.
- A regeneration that moves the fingerprint of another admitted server: log it with both values.

### Conventions for every step

- **Commands.** The short loop is `uv run pytest tests/unit -n auto --maxprocesses 6`, with `uv run pytest <test files> -n 0` while a test being written is red and `--lf` on a failing loop, then the full short loop again. Type-check changed files with `uv run pyright <files>` in the loop. Every step closes with `uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format .` and `uv run pyright` with no file argument, all green.
- **Docker.** The builds and pulls `run_nuisance calibrate`, `run_nuisance vet`, `run_holdout calibrate --cve CVE-2026-5323`, `docker compose ... build` and step 1's `docker build` of the Neo4j backend tag make are authorized. Prune nothing, remove no image and make the Docker disk use grow no more than these commands need: cleanup stays with the maintainer.
- **External material.** Steps 1 to 23 read the vesting manifest, the maintainer's decision log, the two agents' records and the proposed fixtures, held outside the repository at the location the maintainer gives at launch. Where a manifest section and the decision log differ, the decision log wins. Where a section leaves a point open, its recommendation applies unless a decision of this plan says otherwise. Nothing from outside the repository is named in a committed file: no path, no campaign label, no file name of the external material.
- **Server steps (1 to 23) follow change 2 in full.** One commit per server. In order:
  1. Read the server's manifest section and the decision log lines on it, then its current admission entry, run Dockerfile `evals/docker/Dockerfile.<service>`, its fix-check Dockerfiles, its fix-check module under `evals/nuisance_fix_checks/` and, for a backend server, its backend module and registry entry.
  2. Write first the tests whose pins the section changes (red), then move the fixture. Search `tests/` for the name of every module the step replaces or removes.
  3. Copy each retained fixture file to its repository path, with the section's repairs. A copied Python module meets the coding standards (function and file length, few arguments, newspaper order, names), refactored with no change to what it launches. A heredoc line reading `from x import y` is rewritten (`import x`, then `x.y`) with no change to what the image builds. A copy passes `unsourced_copies` (`ADD --checksum`, `COPY --from` an image pinned by digest or an earlier stage). A Dockerfile under `evals/docker/` that has a compose service gets its fingerprint label updated in `evals/docker/compose.yml` (`tests/unit/test_cve_compose_labels.py` prints the value), a new compose service carries the labels and `nuisance` profile its neighbours carry, and an image only a fix-check module builds (`-vuln`, `-patched`, `-flaw-*`, `Dockerfile.facebook-ads-sentinel`, `Dockerfile.googleapis-witness-responder`, `Dockerfile.sylphxltd-filesystem-fixcheck`) gets no compose service.
