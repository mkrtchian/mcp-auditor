## Decisions

Taken with the maintainer before this plan: everything in `evals/` and tests; the dossier stays generated by the repository so the isolation tests keep guaranteeing that nothing copied imports `mcp_auditor`; the memory bound is `--memory` and `--memory-swap` set equal in the confinement every nuisance server runs with, as the product's confined regime does; instrument changes are logged in `docs/nuisance-log.md` and `docs/holdout-log.md`; the living docs follow. Taken with the maintainer on this plan's review: the fix checks stay unbounded (in decision 1), the value (decision 2), the backend containers (decision 3) and no integration test for the probe (decision 14). Taken in this plan, on the code and the standards:

1. **The memory bound applies to the containers of the nuisance run launch, the server's and its backends'**, through a new clean module `evals/nuisance_confinement.py`, not through `confinement_args`. The rule puts the bound in the options "every nuisance server runs with", the holdout rule has none, and `confinement_args` carries a written reason against a memory kill on the acceptance and holdout launches. Changing it would move the 34 acceptance and holdout fingerprints and the kit's launch for a suite whose rule does not ask for it. So `confinement_args` and `cve_planting_base.py` stay byte-identical, and no acceptance fingerprint moves. On the server side the bound covers the run launch (`_single_container_launch` and every backend's server argv), hence `run_nuisance vet`, `run`, `gate` and the benign probe, which all launch through it. The backends' own containers are decision 3. The sentinels and the fix checks' launches (their server containers and their own per-launch responder containers, `responder_args` in the fix-check modules) keep `confinement_args()` and no memory bound (maintainer decision). The shared singleton responders a fix check ensures (`ensure_<key>_responder()`, called by the apify, atlassian, facebook_ads, figma, gitlab, googleapis and jenkins fix checks) are backend containers and carry the bound under decision 3, so `run_nuisance calibrate` exercises those fix checks against bounded singletons. One fix-check launch carries the bound (maintainer decision): the doris kit builder, `kit_backends.doris_backend_env`, which `tests/integration/test_nuisance_doris_backend.py` also drives, builds its server argv with `doris_server_args`, so it shares the provisioner's argv and its server container runs under `nuisance_confinement_args()`. This is harmless: the fix checks were left unbounded because the bound serves them nothing, not because it would harm them, and a single argv for the doris server keeps the kit builder and the run from drifting apart. The criterion "returns without error under the confinement" is checked on the run's launch by the vet and, for the agents, by the benign probe, and a fix check sends no resource-abuse payload, so a bound on its launches would check nothing the vet does not.
2. **The bound's value: `4g`** (maintainer decision), fixed before any run, the same for every server. The reason: the smallest bound under which every admitted server starts as its documentation prescribes, plus headroom for an audit's load. Measured on this host on 2026-11-03 at `ac03d53` (the server container's cgroup `memory.peak`, sampled every 50 ms through a full `run_nuisance vet --concurrency 3`, then again with the bound applied to every server container, Docker only, no LLM): all 59 servers answer under the current launch; under `2g`, 58 of 59 answer and arcadedb (`Maven:com.arcadedb:arcadedb-server`) is OOM-killed at start on all three attempts, because its image's own `mcp-stdio.sh` starts the JVM with `-XX:+UseZGC -Xms2G -Xmx2G` and ZGC commits the whole heap at once as shared memory (`shmem` exactly 2 GiB, anon about 80 MiB, peak 2154 to 2201 MiB). It answers at `2560m` and at `3g` (peak 2159 MiB). Every other server peaks at 316 MiB or less (contextforge 315, vibe-trading 290, maigret 271, serverless 259, the rest under 170). The measurement covers start, listing and benign calls only, not an audit's payloads, hence the headroom above arcadedb's start peak: an audit's load adds the JVM's off-heap memory under queries, and Doris, about 2.14 GiB at rest, runs under the same bound (decision 3) and grows under queries. The reason that decides it holds without the measurement: the bound is there to stop a runaway server, not to keep a server from starting with the launch its documentation gives, and the rule takes a tool out only for a container failure the fixture cannot repair, which a suite-chosen bound below the software's own fixed heap would manufacture. It departs from the product's `2g` (`ContainerProfile.memory`), which would not start arcadedb for a user either: that is a fact about the product's default, logged, not a reason to drop the server here. The host holds it: 31 GB of RAM, and the worst case, the Doris cluster plus three concurrent servers at the bound (16 GiB), stays under it. A resource-abuse verdict cannot become a counted alarm because of the bound: the categories valid for the graded classes are `injection` and `info_leakage` (`cve_grammar.VALID_CATEGORIES`), so a server killed on memory mid-audit shows in the run's health (lost connection), never in the figure.
3. **Every backend container gets the same bound** (maintainer decision for the real software, this plan's choice for the stand-ins), `--memory` and `--memory-swap` equal to `MEMORY_BOUND` through `nuisance_confinement.memory_bound_args()` in each backend's `docker run -d`. The rule's Stand-ins paragraph lets the real software run "as a backend within the memory bound of that confinement". Per module, the real software is the Doris cluster (`doris_backend`, `apache/doris` all-in-one), the MySQL engine (`mysql_backend`, `mysql:8.0.46`) and Neo4j (`neo4j_backend`, the `neo4j-backend` image on the Neo4j server). The stand-ins are the moto AWS stub beside MySQL (`mysql_backend`), the ten responders (`Responder.ensure`) and the apify stand-in (the generic stand-in image, itself a `Responder`). They are bounded too, the simplest consistent choice: one rule, every container of a nuisance run launch runs under the bound, so no per-backend classification has to be kept up as backends are added, and it costs one line in `Responder.ensure` for eleven containers and one in `mysql_backend._ensure_container` for the pair, where a stand-in using a few tens of MiB never meets the bound. The Doris cluster, MySQL and Neo4j carry no `confinement_args()` today and get the bound only (dropping capabilities on a database engine is not this plan's change). A persistent container already running without the bound would silently keep the old launch, so each `ensure` treats a container whose `HostConfig.Memory` is not the bound as absent, removing and starting it again. The Doris cluster is shared with holdout CVE-2025-66335 (`cve_environments.doris_db_env` and the kit's `kit_backends.doris_backend_env` both call `ensure_doris`): that target's backend container runs under the bound too, its server launch does not, and its fixture fingerprint, which hashes `evals/doris_backend.py` through `backend_sources`, already moves in this plan (decision 13), so it moves once. The holdout rule names no bound: the bound on the shared backend container is logged in the holdout log, it opens no rule version.
4. **The nuisance fixture fingerprint covers the confinement.** `nuisance_fixture_fingerprint` gains the AST fingerprint of `evals/nuisance_confinement.py`, which holds the bound, the user arguments and the single-container argv. The rule's fingerprint covers "the host, the launch", and the bound is a run condition: a later change of it must reset any nuisance baseline. Every nuisance fingerprint moves once, before any nuisance run or gate run, and none is stored.
5. **`user_args` moves to `nuisance_confinement`.** It maps a `SymbolicUser` to the user arguments of a nuisance launch and lives today in `doris_backend`, which `responder_backend`, `mysql_backend`, `neo4j_backend` and `nuisance_audit` import for it. `doris_backend` must import the bound from `nuisance_confinement`, so `user_args` staying in `doris_backend` would make a cycle. Every importer is updated, no re-export.
6. **`DOCKER_DIRECTORY` and `image_dockerfile` move to a new clean module `evals/docker_paths.py`**, and every importer (18 in `evals/`, 6 in `tests/`) imports them from there. The requirement kept a re-export in `cve_targets`; the standards refuse a redundant export, and the change is mechanical. `cve_targets.py` is not fingerprinted, `cve_baseline.py` and `cve_images.py` change one import line each, so no fixture fingerprint moves through this.
7. **One backend lifecycle record per backend module, one generic kit launch.** Each of the 13 backend modules exposes `LIFECYCLE = BackendLifecycle(key, lock, ensure, server_args, remove)` (`evals/backend_lifecycle.py`, new and clean), and a new kit module `evals/holdout_kit/kit_backend_launch.py` yields the kit `Launch` of a run launch from any lifecycle, in the provisioners' exact shape. The kit resolves a record's backend key to `evals.<key>_backend.LIFECYCLE`, the naming all 13 keys follow, so a re-admission dossier copies the server's own backend module only, keeping the rule of `kit_backends` that an agent never receives the lifecycle of a backend its server does not record. `nuisance_provisioners.py` stays as it is (its tests monkeypatch its module-level names): a parity test pins each lifecycle to its provisioner instead.
8. **What a re-admission dossier copies is the static import closure** of the modules it needs (the server's fix-check modules, its backend module, the probe, the kit modules), computed in the repository by walking the `evals.*` imports, so a sibling fix-check module, `responder_backend` or `closed_network` comes along without a hand-kept list. The writer refuses a closure that reaches a module importing `mcp_auditor`, and the isolation tests check it at run time in a fresh interpreter run from the dossier root (`holdout_kit_isolation.import_closure_offenders`, which runs `sys.executable -c` with the dossier as working directory, not `-I`: `-I` would drop the working directory from `sys.path` and `evals` would not import). The first-admission `--backend doris` path uses the same closure, since `doris_backend` now imports `nuisance_confinement` and `backend_lifecycle`.
9. **Layout of a re-admission dossier.** The committed fixture mirrors the repository under `evals/`: its Dockerfiles in `evals/docker/` (where the copied backend lifecycles and the neo4j fix check look them up, `docker_paths.DOCKER_DIRECTORY` resolving to the dossier's `evals/docker/`), its fix-check modules in `evals/nuisance_fix_checks/`. `docker/` stays the agents' workshop, where the first-admission README has them write and where they build under a prefixed tag. A holdout-calibration flaw's fixture module goes to `reference/holdout_fixtures/<module>.py.txt` with the source of its target's builder appended, text an interpreter does not import and the `*.py` isolation scan does not read, since the module imports `mcp_auditor.domain.ports` and `cve_environments`. The builder's source is added because the fixture module names its builder (`mysql_db_env`) without showing the launch.
10. **The probe's default calls** are every distinct benign call of the record, in record order (model equality, so kanban's repeated calls play once), not the vet's one-per-counted-tool selection, which needs `nuisance_counting`; an agent re-deciding what counts passes its own calls with `--calls`. The probe exits 0 when every call is listed, answers without error and holds its `expect` when one is set, 1 otherwise; a launch failure raises.
11. **The stand-ins go into both dossiers.** `copy_clean_sources` copies `evals/stand_ins/` whole (captures, `tls/` with the authority's key and `generate.sh`, all committed in the public repository, which an agent writing a new stand-in needs to issue a leaf) and `docker/Dockerfile.stand-in` beside the sentinel's, and both READMEs build the stand-in image in step 1. This covers the calibration kit (requirement item 4) and the nuisance dossier, whose clean modules load the same directory.
12. **The pin is stated as `mcp>=1.18.0,<2`**, the repository's own specifier, in both READMEs, and a test compares it with `pyproject.toml`.
13. **Logs.** The memory bound, the fingerprint coverage and the re-admission dossier are instrument changes of the nuisance suite: one entry in `docs/nuisance-log.md`. The stand-ins in the calibration kit, the stand-in image and the pin: one entry in `docs/holdout-log.md`, which also records that the shared Doris cluster runs under the nuisance memory bound and that the fixture fingerprint of CVE-2025-66335 moves once, since its `backend_sources` hash `evals/doris_backend.py`, which this plan edits. No rule version opens: the bound implements what version 3 already states.
14. **No Docker integration test for the benign probe** (maintainer decision): argv parity with the run's launch is covered by unit tests, and the probe is exercised on praisonai and mysql in the Verification.

## Approach

Three independent strands, in this order. First the clean foundations: `docker_paths`, `nuisance_confinement` (with the bound), `backend_lifecycle`, the backend modules rewired on them, the nuisance fingerprint part. That makes every backend and fix-check module clean and puts the bound in one place, used by the run launch and by every backend container. Then the kit side: `kit_backend_launch` and `benign_probe`, both clean and tested against the repository's own launch builders. Then the dossiers: the re-admission writer in two new modules (selection and writing, then the rendered docs), the CLI flag, the stand-ins and pin in `copy_clean_sources` and the READMEs. Logs and living docs close it, with the memory measurement and the fingerprint print in Verification.

### `evals/nuisance_confinement.py` (new, clean)

```python
MEMORY_BOUND = "4g"  # arcadedb's fixed 2 GiB ZGC heap plus an audit's load; the product's regime uses 2g (ADR 018)
MEMORY_BOUND_BYTES = 4 * 1024**3

def memory_bound_args() -> list[str]: ...
def nuisance_confinement_args() -> list[str]: ...
def carries_memory_bound(inspected_memory: str) -> bool: ...
def running_with_bound(container: str) -> bool: ...
def user_args(user: SymbolicUser) -> list[str]: ...
def single_container_run_args(image: str, host: PlantingHost, server_launch: Sequence[str]) -> list[str]: ...
```

Module docstring: the container options every nuisance server runs with (rule v3, Eligibility, The real software), the acceptance and holdout confinement plus the memory bound, which only the nuisance suite sets, on its server containers and on every backend container (the shared Doris cluster included). `memory_bound_args` returns `["--memory", MEMORY_BOUND, "--memory-swap", MEMORY_BOUND]`, with the comment the product carries: equal to `--memory`, so the bound bites, since Docker otherwise grants as much swap again. `nuisance_confinement_args` returns `[*confinement_args(), *memory_bound_args()]`. `carries_memory_bound` is pure: whether the `{{.HostConfig.Memory}}` value `docker inspect` prints equals `MEMORY_BOUND_BYTES` (a test pins that `MEMORY_BOUND_BYTES` is the byte value of `MEMORY_BOUND`). `running_with_bound(container)` runs `docker inspect -f '{{.State.Running}} {{.HostConfig.Memory}}' <container>` and returns whether it exists, runs and carries the bound, `False` for an absent container: each backend's `ensure` uses it in place of its running check, so a persistent container started without the bound is removed and started again (decision 3). `user_args` moves from `doris_backend` unchanged (a `match` on `SymbolicUser`, `host_user_args` or `unprivileged_user_args`). `single_container_run_args` returns `["run", "-i", "--rm", *nuisance_confinement_args(), *user_args(host.user), "-w", host.working_directory, *no_network_args(), image, *server_launch]`, the argv `_single_container_launch` builds today plus the bound. Imports `cve_planting_base` and `subprocess` only. About 65 lines.

```python
@dataclass(frozen=True)
class ProbeCall:
    tool: str
    arguments: dict[str, Any]

    before: tuple[tuple[str, dict[str, Any]], ...]

```

The record is the dossier's `admission_record.json`, read as plain JSON (`nuisance_admission` is not clean). `record_calls` returns the benign calls of every flaw, in record order, with exact duplicates dropped. `probe_calls` parses calls in the `BenignCall` JSON shape (`tool`, `arguments`, optional `expect`, optional `before` list of `{tool, arguments}`), raising `ValueError` naming the call on a missing `tool` or `arguments`. `record_host` builds the `PlantingHost` from `record["host"]` (`SymbolicUser(user)`, `working_directory`, `has_network`, and `public_names` as a `PublicNames` of tuples, which `model_dump_json` writes for every server even at its default). `single_container_launch` is `Launch("docker", single_container_run_args(image, record_host(record), record["launch"]))`. `probe_launch` returns `nullcontext(single_container_launch(...))` when `record["backend"]` is null, else `backend_launch(lifecycle_of(record["backend"]["provisioner"]), image, record_host(record), record["launch"])`. `probe` connects through `KitMCPClient.connect` (with `docker_client_env(os.environ)` and a temporary stderr file, as `fix_check._exercise` does) and delegates to `probe_client`, which lists the tools, then makes each call's `before` calls in order and the call, collecting a `ProbeReport` (`listed: frozenset[str]`, one `ProbeOutcome` per call: the call, the before responses, the response). `report_lines` is pure: a first line `tools/list: <n> tools`, then per call one line per before call, `  before <tool> [listed|NOT LISTED] -> ok|error <content!r>`, and one line `<tool> [listed|NOT LISTED] -> ok|error[, expect found|, expect MISSING] <content!r>`, the whole text on one line through `repr`. `main` parses `--record PATH`, `--image TAG`, `--calls PATH` (default: `record_calls(record)`), `--tool-call-timeout N` (default 30), runs the probe, prints the lines, returns 0 when every call and before call is listed and answers without error and every set `expect` is found, else 1. ## Edge cases

- A server that does not start or answer its benign calls under the bound: none on the committed fixtures at `4g` (decision 2). One that appears later is named by the vet, logged, not repaired by raising the bound silently, and handled by the campaign under The real software (`container_unrepairable`) or by a logged change of the bound.
- A server killed on memory during an audit: a lost connection in the run's health, not a counted alarm (decision 2).
- A backend container that does not start or answer under the bound (Doris the likeliest, a JVM pair at about 2.14 GiB at rest): the vet or `run_holdout calibrate --cve CVE-2025-66335` names it; logged as a finding with its measured use, not repaired by raising the bound silently.
- A persistent backend container started before this change (the maintainer's running Doris cluster, MySQL pair, Neo4j, responders): `running_with_bound` reads it as absent, so the first `ensure` removes it and starts it again with the bound, Doris re-provisioning its schema as every `ensure_doris` does.
- Host memory: the bound caps each container, not their sum. The worst case of a nuisance run, the Doris cluster plus three concurrent servers at the bound, is 16 GiB on a 31 GB host.
- `--readmission` for a server the admission does not hold, with no admission file, or with `--backend`: refused, exit 3, nothing written.
- A `holdout_calibration` flaw whose target is not in `HOLDOUT_TARGETS`, or whose identifier matches no fixture module or two: refused naming the flaw (none on the committed files, a test checks it).
- A server with both kinds of flaw (aws-api-mcp, doris, markdownify, desktop-commander): its fix-check modules and its references both ship.
- A fix-check module importing a sibling (`ghsa_8g7g_hmwm_6rv2_n8n`): the closure copies the sibling.
- A closure reaching a module that imports `mcp_auditor`: the writer raises before writing that module, naming the chain.
- A backend key whose module lacks `LIFECYCLE`: `lifecycle_of` raises naming the key; a unit test runs `lifecycle_of` on every `BACKENDS` key.
- The probe on a record with a backend while the backend is down: `ensure` brings it up (shared, persistent), as `vet` does; the probe never removes it.
- `--calls` with a call missing `tool` or `arguments`: `ValueError` naming the call before any launch.
- A response with an empty text and an `expect`: `expect MISSING` and exit 1. Without `expect`: `ok ''`.
- A tool absent from `tools/list`: the line says `NOT LISTED`, the call is still made (the agent reads the server's answer), and the exit is 1.
- The apify backend in a dossier: its stand-in capture, leaf and key load from the copied `evals/stand_ins/`, and its two images build from `evals/docker/` (`apify-responder`, `stand-in`).
- Two agents on one machine: their run and fix-check images carry their own prefixes, the backend images and containers are shared by name (`mcp-auditor-cve-*`), and a responder image is built once if absent.
