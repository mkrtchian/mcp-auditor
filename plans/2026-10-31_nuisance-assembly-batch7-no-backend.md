# Nuisance suite assembly, seventh batch, first plan: the fourteen backend-free servers and the ContextForge sandbox own-server

## Context

The nuisance suite admits forty-two servers after the second batch-6 plan (`evals/nuisance_admission.json`), with the fix-check mechanism (`evals/nuisance_fix_checks/`, `FIX_CHECK_TARGETS` in `evals/nuisance_fixtures.py`, `run_nuisance calibrate`, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` tests), the backend registry (`RegisteredBackend`, `BACKENDS` and `backend_problems` in `evals/nuisance_backends.py`, the provisioners in `evals/nuisance_provisioners.py` and the per-responder lifecycle modules), the kit builders (`command_injection_env`, `filesystem_env`, `ssrf_env` in `evals/holdout_kit/kit_launch.py`), and the forty-two existing entries. The seventh admission batch was adjudicated at sixteen admits and eight drops across positions 131 to 182 of the salted draw order, plus ContextForge's CVE-2026-53710 carried over from batch 5 as an own server. This first plan handles the fifteen additions that need no new backend code: the fourteen backend-free admits (nine command_execution, four read_outside_scope, and git-mcp-server with one counted flaw of each class) and the ContextForge sandbox own-server. The two servers that need a new TLS responder backend (facebook-ads at `graph.facebook.com:443`, figma at `api.figma.com:443`) are deferred to the second batch-7 plan, which carries the new repo backend code, exactly as batch 6 split its backend servers out. This plan extends the admission from forty-two to up to fifty-seven servers (fewer if a server drops at calibration).

Every one of the fourteen is from the "entered" queue (positions 131 to 182, non-drawn), so none is a holdout twin: each server derives from scratch, with its own vulnerable and run Dockerfiles and a fresh fix-check module, confirmed by a real Docker calibration (no `holdout_calibration` recopy). The ContextForge sandbox is the exception that is not from the batch-7 run: its analysis is from batch 5, it is a distinct stdio server (`python_sandbox_server`) shipped in the same package as the already-admitted ContextForge gateway, and it is assembled directly rather than from a run record.

Scope is fifteen servers, each one new admission entry merged after the existing forty-two, no edits to existing entries. No new backend provisioner, no new kit builder, no grammar change, no baseline recording.

## Approach

Same split as every assembly since batch 2: eval data (the admission entries and the Dockerfiles) is authored directly by the maintainer and committed by hand; repo logic (the fix-check modules, their imports into `evals/nuisance_fixtures.py`, the tests) goes through the implementation flow. The cyber work (each fix-check module's exploit and its vulnerable/patched Dockerfiles) runs in Opus 4.8 and is not delegated to a Sonnet implementer sub-agent (the classifier cuts Sonnet on exploit authoring, confirmed at batch 3); the Sonnet passes of this write-plan review the plan text only.

Each counted server is host unprivileged, `runs_over_stdio` true, `runs_under_docker` true. `server_patched_surfaces` is null when the counted flaw's patched version equals the server's and set otherwise. Run Dockerfiles are maintainer-authored (`Dockerfile.<service>` plus a `-vuln` arm, a nuisance `service` slug that is not an acceptance service), digest-pinned `FROM`, no `COPY`/`ADD` from the build context (`tests/unit/test_cve_compose_labels.py`); they are not compose services, so no `compose.yml` entry and no fingerprint label is added. A baked stub (adb-mcp's `adb` CLI) is inlined by `RUN`, never `COPY`ed, as siri's `shortcuts` stub and kanban's `gh` stub are.

The admission data each server contributes is one `AdmittedServer` entry merged after the existing forty-two (untouched), with its counted flaw(s), the settled counted tools, a benign call per counted tool, its dropped flaws kept with their real or null class, its `agents`/`agreement`/`settlements`, a `fix_check` block (`source` `fix_check`, with a `FixCheckTarget`), `backend_need` `none` for all except adb-mcp (`fixture`, the baked `adb` stub), and `backend` null for all fifteen (no provisioned backend). The top-level `rule_commit` stays `93de2d8` and `grammar_fingerprint` stays `cve_baseline.grammar_fingerprint()`.

## What this batch reuses, and therefore does not build

The earlier assemblies built, and this plan does not touch: the fix-check mechanism and its coverage/parity tests' logic, `run_nuisance calibrate`, the backend registry and every existing provisioner and responder module, the kit builders (`command_injection_env` and `filesystem_env` are reused unchanged; no builder is added or ported), `evals/cve_environments.py`, and the existing forty-two entries. The command_execution fix-checks (`cve_2025_53818_github_kanban.py`, `cve_2026_55157_token_optimizer.py`, `cve_2026_44717_calc.py`) are the precedent for the command_execution servers (nine, plus git-mcp's command_execution flaw): a planted witness file read through the injected shell argument of a counted tool, on `command_injection_env`. The read_outside_scope fix-checks (`ghsa_cc2g_gq8c_r332_grok_faf.py`, `ghsa_rr55_jp92_8wp2_claude_faf.py`, `cve_2025_67366_sylphxltd_filesystem.py`, `cve_2026_7728_mcp_rtfm.py`) are the precedent for the read_outside_scope servers (four, plus git-mcp's read flaw): a witness file at an out-of-scope absolute path reached through a counted tool, on `command_injection_env` (grok-faf, claude-faf, sylphxltd, mcp-rtfm and gemini-bridge all use it). `filesystem_env` is not the default for a read: it appends the in-scope checkout `/srv/app` as the final launch argument and plants `leakN` symlinks, which fits a server whose entrypoint takes a scope directory (mcpvault is the only nuisance fix-check on it), not the three read servers here whose records launch with no argument (python-notebook's `python /app/nb86_launch.py`, scrapling's `scrapling-fetch-mcp`, geekgod's `python /app/server.py`). faf-mcp is literally the same `fileHandler.js` family as the already-admitted claude-faf and grok-faf, so its module mirrors `ghsa_cc2g_gq8c_r332_grok_faf.py` closely. Each fix-check module imports only from `evals.holdout_kit` and the clean `evals.cve_*` modules, never `evals.cve_environments`; the import-closure scan enforces it.

### ContextForge sandbox own-server (CVE-2026-53710)

CVE-2026-53710 is a RestrictedPython sandbox escape in the sandbox's code-execution tool (command_execution); the witness is an OS escape (a shell command through `subprocess`, not a bare `print(1+1)`, which would also succeed on the patched version and be a false witness) that succeeds on the vulnerable version and fails on 1.0.2. This is a second admission entry whose `server_package` differs from the gateway entry's (the gateway uses `PyPI:mcp-contextforge-gateway` for CVE-2026-18905), and it counts as its own server in N.

## The adb-mcp structural gap

`evals/nuisance_counting.py` reads `declared_function_is_effect` at the flaw level (`flaw_counted_tools` returns an empty set when `flaw.declared_function_is_effect` is true), all-or-nothing across a flaw's tools. adb-mcp's CVE-2025-59834 is the first census flaw that reaches both a runner tool (`adb_shell`, dfie true) and bounded tools (dfie false) in one flaw. This plan resolves it in data, not code (Decision 1): `adb_shell` is left out of the flaw's `tools` list, the flaw's `declared_function_is_effect` stays false, and the bounded tools count (up to seven, narrowed at calibration). No change to `evals/nuisance_counting.py`, the grammar, or any baseline. The alternative of splitting the CVE into two `FlawRecord`s (one dfie-true `adb_shell`, one dfie-false bounded set) is rejected: it puts the same identifier on two records of one entry, which `_foreign_flaws` and the fix-check parity test were not written for, and it buys nothing the exclusion does not. A per-tool dfie in the counting code is a separate structural change, out of this assembly's scope, noted for a future rule/code pass if a second such flaw appears.

## Edge cases

A counted tool with no benign call fails `_benign_call_problems`, so every counted tool of every entry carries a benign call. The two-counted-flaw server (git-mcp) must satisfy `_patched_version_problems`: `server.patched_version` equals one counted flaw's `patched_version`, and every counted flaw sets `server_patched_surfaces` null iff its `patched_version` equals the server's. The server's version is the later one, CVE-2026-85626's (2.15.3 or 2.15.2), so CVE-2025-53107 (patched 2.1.5) records a non-null `server_patched_surfaces` from a fix-check replayed on the run image, and its `FixCheckTarget` sets `server_patched_service`. fast-filesystem has one counted flaw, so its server version is CVE-2026-5327's 3.5.2 and the rule is trivial; its uncounted CVE-2025-67364 (`patched_version` null) is outside `_patched_version_problems`, which reads counted flaws only. `test_each_target_mechanism_and_tools_match_the_admission_flaw` raises `KeyError` on a target whose flaw has no admission record, so each fix-check module and its `FIX_CHECK_TARGETS` row land in the same commit as its entry, never before, and a server authored speculatively (node-code-sandbox's shell-reach risk) commits its module, row and entry together or not at all. adb-mcp's `adb` stub is inlined by `RUN`, never `COPY`ed. A benign argument that enters the fixture fingerprint must be a stable string, not a per-launch uuid. The contextforge-sandbox entry shares no `service` slug with the existing contextforge gateway entry (`namespace_problems`), and its `server_package` census spelling differs from the gateway's on purpose. A server whose fix-check comes out red at calibration (node-code-sandbox if the shell is never reached, any server whose witness does not surface on the vulnerable arm or surfaces on the patched arm) is a logged drop, its speculative entry, module and row not committed.

## Test scenarios

Unit (existing tests gain rows once the entries land): `test_nuisance_admission_loads.py` loads the up-to-fifty-seven-server admission. `test_nuisance_fix_checks.py` coverage: every counted `(server, flaw)` has a `FixCheckTarget` (one per single-counted-flaw server, two for git-mcp, none for fast-filesystem's uncounted CVE-2025-67364). Each fix-check builder's pure part (the planted witness `Place`, the exploit's tool calls and arguments, the host and builder) is tested as a pure function, never the sequence of `docker` calls, in the kanban/grok-faf test shape. Pyright strict and ruff clean on changed files, each new module under 300 lines and each function about 20 lines.

Docker (calibration, no LLM), a maintainer action that never gates the unit checks: `run_nuisance calibrate --cve <id>` green on each counted flaw, the witness surfacing on the vulnerable version and on the patched (run-image) version not at all, the benign call clean on the patched version. ## Implementation steps

Seven steps in dependency order, grouped by fix-check shape so each step keeps the implementer's working set within the file budget (two to three servers) and a calibration drop isolates to one step. Each admitted server lands in its own commit (the repo's one-feat-commit-per-server pattern, as the batch-6 log shows), so a three-server step is three commits; the step bounds the working set, not the commit. Repo code (the fix-check modules, the `nuisance_fixtures.py` imports, the tests) goes through the implementation flow in Opus 4.8, not a Sonnet sub-agent. Eval data (every `evals/nuisance_admission.json` entry and every Dockerfile) is hand-authored by the maintainer and committed by hand, and each step says what must exist before the implementer starts. The calibration-held items stay the maintainer's, resolved at the step that cites them, before the entry depending on them is committed. Each server's entry, fix-check module and `FIX_CHECK_TARGETS` row land in the same commit (`test_each_target_mechanism_and_tools_match_the_admission_flaw` raises `KeyError` on a target whose flaw has no admission record, and the coverage test is red on an entry without a target). None edits an existing entry; each merges after the existing forty-two.

Test-first within every repo-code step (CLAUDE.md Workflow): the step's unit tests are written and run red before the code that makes them pass.

Verification common to every step: the short loop while working (`uv run pytest tests/unit -n auto --maxprocesses 4`, `uv run pyright <changed files>`), then the step-closing full checks with no file argument: `uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format .`, `uv run pyright`. Docker calibration is a maintainer action per server and never gates the unit checks. `tests/unit/test_cve_compose_labels.py` constrains every maintainer-authored Dockerfile: every `FROM` pinned by digest, no `COPY`/`ADD` from the build context (adb-mcp's stub inlined by `RUN`). The nuisance Dockerfiles are not compose services: no `compose.yml` entry, no fingerprint label.

A server held open at calibration (node-code-sandbox, auto-commit) sits in a step whose other servers do not depend on its outcome, so a drop does not block them. The common shape of every code step below: **Before the implementer starts (maintainer, committed with each server)** the two Dockerfiles (`Dockerfile.<service>-vuln` and `Dockerfile.<service>`, digest-pinned `FROM`, no `COPY`/`ADD`) and the `AdmittedServer` entry merged after the existing forty-two (the counted flaw, counted tool, benign call, `patched_version`/`patched_source`, `server_patched_surfaces` null unless a differing patched version, `agents`/`agreement`/`settlements`), which makes the coverage test red on the flaw. **Files**: `tests/unit/test_<slug>_fix_check_builder.py` (new, per server), `evals/nuisance_fix_checks/<cve>_<slug>.py` (new, per server), `evals/nuisance_fixtures.py` (modify, import and extend `FIX_CHECK_TARGETS`). **Do**: tests first, run red, then the module, importing only from `evals.holdout_kit` and the clean `evals.cve_*` modules; `FixCheckTarget` `vulnerable_service` `<slug>-vuln`, `patched_service` `<slug>`, `server_patched_service` `None` unless noted. **Test**: builder pure parts, coverage and parity green, import-closure green. **Verify**: the step-closing full checks plus the `load_admission` one-liner; maintainer under Docker `calibrate --cve <id>` green per server, recopying any settled tool or version into the entry before its commit.
