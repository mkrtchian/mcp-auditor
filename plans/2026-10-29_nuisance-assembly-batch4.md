# Nuisance assembly, batch 4 (entered servers)

## Context

The nuisance admission (`evals/nuisance_admission.json`) holds 23 servers. A fourth admission batch has been run and adjudicated: eleven servers reached by the holdout walk but never drawn (the "entered" tail, undrawn flaws of outcomes `given_up` / `excluded` / `skipped`). Unlike batches 2 and 3 these are not holdout twins, so there is no `holdout_calibration` to reuse: every fix-check is fresh and calibrated under Docker. The adjudication settled eleven servers into four plain admits, two backend-conditional admits, and five drops. This plan assembles the admits into the repo (fix-check modules, Dockerfiles, backend provisioners, admission entries, calibration) and logs the drops, following the batch 1-3 pattern and the established modules. The per-server findings and the dfie settlement are summarised here as the facts the implementation needs. No out-of-repo path or reference appears in any committed file or message.

## Verdicts to assemble

Plain admits, no backend (four): `knowns` (read_outside_scope, patched 0.30.0), `@bitbonsai/mcpvault` (read_outside_scope, patched 0.11.5), `vibe-trading-ai` (read_outside_scope, patched 0.1.10), `praisonai` (read_outside_scope, patched 4.6.40).

Backend-conditional admits (two, admitted only if calibration is green): `mcp-atlassian` (read_outside_scope access-control bypass, patched 0.22.0, needs a mock Jira/Confluence responder), `@apify/actors-mcp-server` (internal_fetch, patched 0.9.21, needs a TLS docs responder, admitted only if a feasibility probe passes).

The admission and the census name a server by `<ecosystem>:<name>`: `npm:knowns`, `npm:@bitbonsai/mcpvault`, `PyPI:vibe-trading-ai`, `PyPI:praisonai` (the census spells it `PyPI:PraisonAI` on two flaws, `normalized_package` lowercases it), `PyPI:mcp-atlassian`, `npm:@apify/actors-mcp-server`. `AdmittedServer.server_package` and `load_admission`'s census match use those spellings, not the bare names used below for brevity.

Drops to log, not assemble (five servers plus two flaws): `dynatrace-mcp-server`, `@cardano402/mcp-server`, `skill-ninja-mcp-server`, `mcp-memory-keeper`, `grafana/mcp-grafana`, plus the dropped flaws `CVE-2026-50143` (apify `call-actor`) and `CVE-2026-81093` (apify `get-html-skeleton`).

## Approach

Reuse the existing mechanism without duplication: fix-check modules under `evals/nuisance_fix_checks/`, discovered by `evals/nuisance_fixtures.py`; Dockerfiles under `evals/docker/`; backend provisioners in `evals/nuisance_backends.py` built on `evals/responder_backend.Responder`; the admission schema of `evals/nuisance_admission.py`; the counted-flaw predicate of `evals/nuisance_counting.py`; the calibration command `uv run python -m evals.run_nuisance calibrate`. The four plain admits follow the standalone template `evals/nuisance_fix_checks/cve_2026_65831_arcadedb.py` (no backend, `builder` one of the kit builders of `evals/holdout_kit/kit_launch.py`, see below). The two conditional admits follow the responder template `evals/nuisance_fix_checks/cve_2026_73844_ckan.py` plus a new backend module on the model of `evals/ckan_backend.py`. Each admitted flaw is proved by `run_nuisance calibrate` under Docker before its admission entry is trusted: the witness surfaces on the vulnerable service and on neither patched service, and the benign call returns without error on the patched server. Order the work so a failing conditional (apify probe, atlassian mock) never blocks the four plain admits: assemble and calibrate the plain admits first, land them as their own commits (on the maintainer's go), then each conditional on its own.

## What stays unchanged

`evals/cve_grammar.py` and every grammar fingerprint: this batch adds no class and touches no grammar, so the acceptance baseline and any holdout figure stay comparable. `evals/nuisance_counting.py`: the counted-flaw predicate is reused, never duplicated or altered. The 23 existing admission entries, their Dockerfiles, their backend wirings. The existing `BACKENDS` entries (`doris`, `mysql`, `ckan`, `contextforge`, `n8n`). `evals/holdout_census.json` and the draw: the nuisance walk reads them unchanged. The run-phase deferrals (compose services and fingerprint labels for the admitted servers, their run Dockerfiles) stay out of this plan, exactly as batches 1-3 deferred them: this plan admits and calibrates, it does not wire the run.

## Files and work

### The four plain admits (no backend)

For each of `knowns`, `mcpvault`, `vibe-trading`, `praisonai`: one fix-check module `evals/nuisance_fix_checks/<cve>_<slug>.py` exporting a `TARGETS` tuple of `FixCheckTarget` (one per counted flaw), registered in the aggregator `evals/nuisance_fixtures.py` (import and `*module.TARGETS` in `FIX_CHECK_TARGETS`, else `calibrate` never sees it), and the Dockerfiles under `evals/docker/`, named `Dockerfile.<service>` (the server's shipped patched version, the admission `service`), `Dockerfile.<service>-vuln` (pre-fix for every counted flaw, or one `-vuln-<version>` per distinct vulnerable version where one image cannot be pre-fix for all) and, where a counted flaw's first fix predates the server's patched version, `Dockerfile.<service>-flaw-<version>` (the `flyto-flaw-2.26.3` pattern: `patched_service` builds each flaw's own first-fixing version, `server_patched_service` the shipped one, `None` when equal). That makes a third image for `praisonai` (4.6.34 for CVE-2026-44336, which `rules.show` carries, shipped 4.6.40). `knowns` needs none unless calibration shows a counted flaw first fixed before 0.30.0 (both listed counted flaws are fixed at 0.30.0). `mcpvault` needs none: its one counted flaw CVE-2026-57442 is fixed at the shipped 0.11.5, with a 0.11.4 vulnerable image. The service names must not be acceptance service names (`namespace_problems`). The module follows `cve_2026_65831_arcadedb.py`: a `WITNESS` `Place` (`PlantKind.FILE`, `reachable_by={"arbitrary_read"}`) whose file the kit plants outside the server's scope, an `AIM` regex matched against the string values of the exploit's tool-call arguments (`cve_proofs.is_aimed`), never against the response: the nonce is random per run, so a static regex cannot match it, and the traversal marker (for example `\.\./`) is what aims the exploit while the benign call, an in-scope path, does not match it; the nonce surfacing in the response is checked separately (`proofs_in`, with the anti-echo rule: the nonce must not appear in the arguments sent). A `PlantingHost` (`SymbolicUser.UNPRIVILEGED`, the working directory the server's image uses, `has_network=False` since none needs the network), a `builder` taken from `kit_launch`: `command_injection_env` (read-only `/srv` mount, nothing appended after the image, what the flyto read-outside-scope check uses) for a server that takes no scope argument, or `filesystem_env` (it appends the in-scope checkout `/srv/app` as the final argument and plants the `leakN` symlinks, as the aws-api and desktop-commander holdout fixtures do) for a server that takes its root as a launch argument such as mcpvault's vault path. There is no "plain filesystem bridge". `exploits` must call every counted tool of the flaw with a traversal argument reaching the planted witness (`test_each_target_mechanism_and_tools_match_the_admission_flaw` asserts the exploits' tool set equals the flaw's counted tools), `benign_calls` one in-scope read per counted tool that returns clean (`_benign_call_problems` refuses a counted tool with no benign call in the admission), `vulnerable_service` and `patched_service` (and `server_patched_service`) naming the Docker services above. Counted tools and the exact traversal mechanism per server, from the adjudication and confirmed against real source:

`knowns`: tools `docs`, `memory` (reaching flaw CVE-2026-86439) and `get_doc` (CVE-2026-30633). The doc store joins `path.Join(ds.root, "docs")` and `Get(path)` normalises a path relative to that root, so a `../` argument escapes the docs root. Counted flaws: CVE-2026-86439 and CVE-2026-30633. Server patched version 0.30.0. GHSA-qjrq-cvv4-3g9w is not counted (settled): the census marks it withdrawn (2026-09-25) as a duplicate of CVE-2026-86439 (same package, same 0.30.0 fix), so counting it would score the same flaw twice; it is left out of the counted set, recorded as a settlement. Flaws not counted: CVE-2026-88938 and CVE-2026-88939 (no patched version removes the leak, `patched_surfaces` stays true), and CVE-2026-30632 / CVE-2026-86541 / CVE-2026-86544 (settled out of this batch: the two blind records disagreed on their reproduction, CVE-2026-30632 is on `create_doc`, a write with no surfacing witness, and knowns already admits on its two solid read flaws; they can be revisited in a later batch rather than chased here).

`mcpvault`: tools `read_note`, `read_multiple_notes`, declared "Read a note from the Obsidian vault", `path` argument "relative to vault root". There is no `../` vault escape: the advisory states vault-root `..` containment is not affected. The one counted flaw is CVE-2026-57442 (fixed 0.11.5): PathFilter's deny-list for `.git` / `.obsidian` / `node_modules` is root-anchored only (`src/pathfilter.ts`), so these restricted directories NESTED inside the vault pass `isAllowed()` / `isAllowedForListing()`, and `read_note` of a nested metadata file (for example `sub/.git/config`) returns its content. This reproduces on a case-sensitive Linux filesystem (it is a missing-nested-match, not a case bypass). The witness is a nested restricted-dir file planted inside the vault root carrying a nonce (an embedded token or URL), so the fixture plants it inside the mounted vault, not via the out-of-scope leak symlinks; `AIM` matches the nested restricted-dir segment in the call path (for example `\.git`), not a `../` marker. CVE-2026-57441 is NOT counted: its bypasses are case variants (case-insensitive macOS / Windows only) and Windows trailing dot or space, neither reproducible on the Linux run filesystem. Server patched version 0.11.5, vulnerable image 0.11.4. dfie=False (a bounded vault read whose deny-list misses nested metadata, a confinement gap, not reading a caller-named arbitrary file).

`vibe-trading`: counted tool `get_run_result` (CVE-2026-58171, CWE-22). `run_dir` (`agent/src/swarm/store.py`) joins the caller-supplied run identifier onto the runs base directory without validation, so a crafted identifier escapes the runs directory, and `load_run` reads `run_dir(run_id)/"run.json"` and returns the parsed `SwarmRun` content to the caller: the traversed file's content surfaces in the response (confirmed on source; the fix on 0.1.10 adds a "must be a bare run directory name" check in `run_dir`). The CVSS `VC:N` in the advisory is a scoring artifact, the content is returned. The witness is therefore a planted file named `run.json` that parses as a `SwarmRun`, with the nonce in a surfaced string field; `AIM` matches the traversal marker in the `run_id` argument. `get_swarm_status` and `retry_run` are not counted for this flaw (`retry_run` would also overwrite the planted file). Counted flaw: CVE-2026-58171, patched 0.1.10, vulnerable image 0.1.9. dfie=False (a bounded load-run-by-id whose traversal is the bypass).

`praisonai`: the counted tools are the file-READ tools whose response surfaces content, not the write or delete ones. CVE-2026-47394 (fixed 4.6.40): `workflow.show` "returns the contents of any file" from a caller-supplied absolute path with no containment, and `workflow.validate` and `deploy.validate` share the pattern (`mcp_server/adapters/cli_tools.py`); all three are counted, high-confidentiality arbitrary file read. CVE-2026-44336 (fixed 4.6.34, earlier commit `68cc9427`): of the `rules.*` handlers only `rules.show` is a read that returns content, so only `rules.show` is counted; `rules.create` and `rules.delete` are the write / delete side of the traversal (no surfacing witness, and delete would destroy a planted witness) and are NOT counted. Counted tools: `workflow.show`, `workflow.validate`, `deploy.validate` (CVE-2026-47394) and `rules.show` (CVE-2026-44336). Server patched version 4.6.40 (`rules.show`'s CVE-2026-44336 first fixes at 4.6.34, hence the `-flaw-4.6.34` image and a `server_patched_service` at 4.6.40). The read tools join the caller path onto `~/.praison/rules/` or take an absolute path; the witness is a file planted outside that directory with a nonce. dfie=False (the declared function is to show a workflow or rule, not to read an arbitrary file). The command_execution flaws CVE-2026-34935 / CVE-2026-41497 / CVE-2026-57124 are dfie=True and not counted.

Each flaw's `dfie` is False: the tool's declared contract is a bounded read (a doc under the docs root, a note under the vault, a run under the runs directory, a workflow or rule entry), and the flaw is a traversal, a nested-metadata deny-list gap, or an absolute-path read that bypasses that intended confinement. This is the `read_note` / ckan shape, not the `context_import` / `get-html-skeleton` shape (a tool whose declared function is to read the caller-named target).

### atlassian (backend-conditional)

A new backend module `evals/atlassian_backend.py` on the model of `evals/ckan_backend.py`, built on `evals/responder_backend.Responder`: a light HTTP responder image `Dockerfile.atlassian-responder` serving a mock Jira/Confluence Server/DC API. The mock holds two projects, `ALLOWED` and `SECRET`, with a witness nonce in a `SECRET` issue summary, and a Confluence space pair keyed `ALLOWED`/`SECRET` with the nonce in a `SECRET` page (both secrets keyed `SECRET` so one `AIM` covers both tools). It answers the search endpoints the client calls: Jira `GET rest/api/2/search` (the atlassian-python-api `jira.jql` path, Server/DC, selected because a local `JIRA_URL` makes `is_atlassian_cloud_url` false) and Confluence `GET rest/api/content/search` (the `confluence.cql` path). The mock evaluates only a tiny boolean grammar over `project = X`, `project IN (...)`, `AND`, `OR` and parentheses (spaces for CQL): it returns the issues whose project satisfies the JQL. It need not implement `/myself` or connection validation, which runs only under debug logging. Exact endpoint paths and response shapes are confirmed once against a catch-all logging stub and against `tests/fixtures/jira_mocks.py` and `confluence_mocks.py` in the audited server's own test suite, before the responder is finalised. The shared singleton responder cannot carry the fix-check witness: `check_fix` plants a fresh random nonce per exercise (`RANDOM_NONCES`), so the nonce has to reach the mock at launch. The responder therefore reads the witness nonce from an env var (`WITNESS_NONCE`, absent for the run-phase singleton, which then returns a fixed non-secret summary), and the fix-check builder starts its own per-launch container of the same image with `spec.nonces[WITNESS.id]` and the server pointed at it, reaped in the builder's `finally` (the per-launch stand-in pattern of `cve_2026_44694_n8n.py`; `ckan` and `contextforge` avoid the issue only because the kit sentinel serves the nonce). The module takes its own bridge and subnet, distinct from the CKAN `203.0.113.0/24`, ContextForge `198.51.100.0/24` and n8n `192.0.2.0/24` ones. Register `"atlassian"` in `BACKENDS` with an `atlassian_provisioner` following `ckan_provisioner` (stand the responder once under a launch lock, yield the server `Launch` wired to it, reap on exit). Fix-check module `evals/nuisance_fix_checks/cve_2026_77252_atlassian.py` on the ckan template: `builder` the atlassian responder env, `WITNESS` the nonce the responder returns for a `SECRET`-project query, `exploits` calling every counted tool, `jira_search` and `confluence_search`, with `projects_filter`/`spaces_filter` set to the out-of-allowlist project, `AIM` matching that argument (for example `SECRET`) in the call, not the nonce (see the aim rule above), and one benign call per counted tool (an allowed-project search) in `benign_calls`. Vulnerable service runs mcp-atlassian before 0.22.0 (the caller filter replaces the admin allowlist), patched service runs 0.22.0 (the caller filter only narrows, so the `SECRET` query returns empty and no nonce surfaces). Config as `-e` arguments of the server's `docker run` (the `extra_args` of `Responder.server_args`, shared by the builder and the provisioner, as `ckan_server_args` does for its TLS flag), not the auditor's `--env` flag: `JIRA_URL`/`CONFLUENCE_URL` at the responder, a dummy `*_PERSONAL_TOKEN`, `JIRA_PROJECTS_FILTER=ALLOWED` / `CONFLUENCE_SPACES_FILTER=ALLOWED`. Admission entry counts `jira_search` and `confluence_search` for CVE-2026-77252, `backend_need="fixture"`, the `BackendFixture` the registry defines for `"atlassian"`. CVE-2026-77251 (boards) stays out of this admission: its Agile endpoints are a larger mock surface and it is not confirmed to take a `projects_filter` argument. The `confluence_upload_attachment` traversal flaws (dfie=True) and the dependency advisories (out of grammar) are not counted. Calibrate on both the vulnerable and the patched version before trusting the entry, because the witness depends on how the emitted JQL parenthesises the caller clause: a false witness is possible if the mock's precedence differs from the server's.

### apify (backend-conditional, probe first)

First, a feasibility probe, because the only counted flaw needs a TLS responder reached by a hostname-suffix bypass and the confined image must both resolve the name and trust the cert. In the confined run image, with a self-signed responder, run `node -e "fetch('https://docs.apify.com.<name>:<port>/x')"` against the responder and confirm name resolution (via `--add-host`) and TLS trust both work. Trust comes from relaying `NODE_TLS_REJECT_UNAUTHORIZED=0` as the ckan backend does, not from `NODE_EXTRA_CA_CERTS`, which would need the responder's self-signed cert inside the server image (the responder image generates its own, so it would take a shared pinned cert). The relay is a `-e` argument of the server's `docker run`, not the auditor's `--env` flag. If the probe fails, drop apify as network-dependent and log it instead of assembling it. If the probe passes: a new backend module `evals/apify_backend.py` on the `ckan_backend.py` model, a TLS responder image `Dockerfile.apify-responder` whose cert SAN covers the suffix host `docs.apify.com.<name>`, `--add-host` entries for `docs.apify.com` and the suffix host, both pointing at the responder, so the benign call (`https://docs.apify.com/<path>.md`) and the witness (`https://docs.apify.com.<name>:<port>/`, which passes the vulnerable `startsWith` allowlist check and is rejected by the patched host-set check) both resolve locally, the responder telling them apart by Host/SNI; register `"apify"` in `BACKENDS`. As for atlassian, the fix-check witness nonce reaches the responder through a per-launch container started by the builder (`WITNESS_NONCE` env, the container's address read back for `--add-host`), with its own bridge and subnet distinct from the three TEST-NET ones, and the shared singleton serves only the run-phase benign call. Fix-check module `evals/nuisance_fix_checks/cve_2026_46341_apify.py` on the ckan template: counted tool `fetch-apify-docs`, the `url` argument carrying the suffix-bypass host, `WITNESS` the nonce the responder serves there, `AIM` matching the suffix host in the call arguments (for example `docs\.apify\.com\.`), one benign call (`https://docs.apify.com/<path>.md`). Vulnerable service runs 0.9.20 (allowlist is a raw `startsWith`), patched service runs 0.9.21 (hostname parsed and compared to a set). Admission entry counts `fetch-apify-docs` only, `backend_need="fixture"`. CVE-2026-50143 (`call-actor`) is not counted and is logged as dropped: its attacker vector is the Actor definition fetched from the hardcoded `api.apify.com`, not a tool-call argument, and reproducing it needs the hosted platform. CVE-2026-81093 (`get-html-skeleton`) is dfie=True and not counted.

## Edge cases

A conditional whose calibration or probe fails drops cleanly without blocking the rest: assemble and commit the four plain admits first, then atlassian, then apify, each able to fail alone. A plain-admit flaw whose witness does not surface vulnerable-only at calibration is dropped from its module, not forced. The atlassian mock can emit a false witness if its JQL precedence differs from the server's: calibrate on both versions and require the patched version to surface nothing. The witness nonce is random per run and is excluded from the fix-check comparison already (the `fix_check_mismatches` fix): do not reintroduce a nonce comparison. No exploit recipe is baked into a patched image that the run will audit. Responder and stub content is inlined by `RUN` in the Dockerfiles, never `COPY`, with no private path. Exploit builders run unprivileged.

## Implementation steps

Seven steps, one commit each, in dependency order: two for the four plain admits, two per conditional (backend, then fix-check and admission), one for the living docs and the drop log. The conditionals each stand alone: a failing apify probe or atlassian calibration drops that conditional (its two steps are replaced by its drop entry in Step 7) and blocks nothing else.

Verification common to every step: the short loop while working (`uv run pytest tests/unit -n auto --maxprocesses 4`, `uv run pyright <changed files>`, `uv run ruff check .`), then the step-closing full checks with no file argument: `uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format .`, `uv run pyright`. Docker steps (image builds, `uv run python -m evals.run_nuisance calibrate --cve ID`) are part of Do where a step says so, because the counted flaws are decided by them. If Docker or network is unavailable to the implementer, stop and report: the step is not closed on unit checks alone.

Constraints that apply to every Dockerfile written here, enforced by `tests/unit/test_cve_compose_labels.py`: every `FROM` pinned by digest (`image:tag@sha256:...`, read from the local image with `docker image inspect --format '{{index .RepoDigests 0}}'`, or `docker buildx imagetools inspect image:tag --format '{{json .Manifest}}'` for the index digest), no `COPY`/`ADD` (content inlined by `RUN`). The nuisance Dockerfiles are not compose services (the run phase is deferred), so no fingerprint label is added. Image names must not be acceptance service names. No private path or out-of-repo reference in any committed file.

Admission entries are maintainer data (the per-server agent records, the `agreement` rows, the `settlements`), not part of this plan. For each step that adds an entry, the maintainer merges it into `evals/nuisance_admission.json` before the implementer starts (after the existing entries, `rule_commit` and `grammar_fingerprint` unchanged), with the `fix_check` blocks at their expected values (vulnerable true, patched false, `server_patched_surfaces` per the Dockerfiles, benign not errored) and a placeholder `witness` (calibrate never compares the nonce). With the entry in place and no fix-check module yet, `test_every_counted_flaw_has_a_fix_check_target_unless_holdout_calibrated` is red: that is the red state the implementer starts from. The implementer reconciles any `fix_check` mismatch `calibrate` reports (counted flaws that do not surface vulnerable-only are removed from both the module and the entry's counted set, per the Edge cases section).
