# Nuisance suite assembly, sixth batch, first plan: the ten no-backend servers

## Context

The nuisance suite admits thirty-three servers after the first five batches (`evals/nuisance_admission.json`), with the fix-check mechanism (`evals/nuisance_fix_checks/`, `FIX_CHECK_TARGETS`, `run_nuisance calibrate`, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` tests), the backend registry (`evals/nuisance_backends.py` with the nine provisioners now moved to `evals/nuisance_provisioners.py`), and the kit builders those use. A sixth admission batch produced two independent blind records per server across positions 90 to 128 of the salted draw order (the first extension lot beyond the frozen first eighty-six positions), and a maintainer adjudication plus two adversarial contradictor passes settled each: thirteen servers are admitted, five dropped, one skipped as a settled duplicate.

The thirteen admits split across two assembly plans. This first plan turns the ten no-backend admits into committed artifacts, extending the admission from thirty-three servers to forty-three. The second plan (authored separately) handles the three servers that need a provisioned backend or a stub: ios-simulator (a fixture stub), gitlab (a mock-Jenkins-style responder), and googleapis/mcp-toolbox (three counted flaws, a new fake-gcs-server provisioner and a composite backend). Keeping the backend work out of this plan makes the first plan mechanically uniform: every server here is `backend_need` none, every counted flaw carries a fresh `FixCheckTarget`, and no provisioner, registry entry or compose service is added.

None of these ten servers is a holdout twin, so there is no `holdout_calibration` recopy: every counted flaw carries a fresh `FixCheckTarget` calibrated under Docker, with its own vulnerable and patched Dockerfiles. The scope mixes two mechanism classes: four command_execution servers (calc, siri-shortcuts, serverless, pi-llm-wiki) and six read_outside_scope servers (ciguard, mcp-rtfm, claude-faf, grok-faf, maa, mastra-docs). Five of the ten carried a dfie disagreement between the two blind records (pi-llm-wiki, mcp-rtfm, claude-faf) or a convergent over-marking (grok-faf, maa), all settled False on source under the unified dfie principle: a read_outside_scope traversal out of a declared scope is the flaw, not the declared function, and a command_execution tool whose fix removes the execution capability (an expression evaluator becoming a math parser, a shortcut runner taking a named shortcut, a wiki capture losing its shell) is bounded once patched, so a finding on the patched server is a false alarm.

Scope is ten servers, each one new admission entry, no edits to existing entries. The admitted count is forty-three only if all ten calibrate green: a server whose every counted tool is removed at calibration, or whose counted flaw fails `_counts` (for instance a command_execution flaw whose injected command's output never enters a tool response, the motive that dropped kubectl-mcp-server at batch 5), is not committed and is logged as a drop instead, so every "forty-three" below reads "forty-three, or fewer by each calibration drop".

## Approach

Same split as the earlier assemblies: eval data (the admission entries and the Dockerfiles) is authored directly by the maintainer and committed by hand; repo logic (the ten fix-check modules, their imports into `evals/nuisance_fixtures.py`, the tests) goes through the implementation flow. The repo-logic surface this plan is ten fresh fix-check modules and no backend code at all, which is the simplest assembly surface since the suite began: no new provisioner, no `evals/nuisance_backends.py` or `evals/nuisance_provisioners.py` change, no registry entry, no backend-module test.

Run Dockerfiles, as at every batch since 2, are maintainer-authored (`Dockerfile.<service>`, a nuisance `service` slug that is not an acceptance service). The nuisance Dockerfiles are not compose services (`calibrate` builds the fix-check images through `kit_launch.build_images`), so no `compose.yml` entry and no fingerprint label is added, and `tests/unit/test_cve_compose_labels.py`'s fingerprint-label test is untouched (it covers only `compose.yml` services). Its per-Dockerfile checks still apply to every file authored here: each `FROM` pinned by digest (`image:tag@sha256:...`), no `COPY`/`ADD` from the build context. The acceptance service names reserved by `namespace_problems` are `filesystem`, `git`, `kubernetes`, `fetch` and their patched variants; none of this batch's slugs may collide with them (none naturally does, the packages being unrelated).

Because no server here is a holdout twin, every counted flaw carries a `FixCheckTarget` (`source` `fix_check`), so every counted server's vulnerable and patched Dockerfiles are authored in this batch; the patched Dockerfile doubles as the run image. Each counted server is host unprivileged, `runs_over_stdio` true, `runs_under_docker` true. Every server here is single-counted-flaw with the patched version equal to the counted flaw's, so `server_patched_surfaces` is null throughout and no `server_patched_service` third arm exists (unlike the ContextForge edit of batch 5).

The admission data each new server contributes is one `AdmittedServer` entry merged after the existing thirty-three (untouched), with its counted flaw, the settled counted tools, a benign call per counted tool, any dropped sibling flaw kept with its real or null class, its `agents`/`agreement`/`settlements`, a `fix_check` block (`source` `fix_check`, with a `FixCheckTarget`), and `backend_need` none (no `backend`). The top-level `rule_commit` stays `93de2d8` (rule v2) and `grammar_fingerprint` stays `cve_baseline.grammar_fingerprint()`, unchanged from the existing file.

## What this batch reuses, and therefore does not build

The earlier assemblies built, and this batch does not touch: `evals/nuisance_fix_checks/` and its module convention (this batch adds ten modules and imports them into `evals/nuisance_fixtures.py`, extending `FIX_CHECK_TARGETS`), the `run_nuisance calibrate` command and its handling, the `ADMISSION_PATH` and `FIX_CHECK_TARGETS` coverage/parity tests' logic (new rows are picked up automatically), the backend registry and the nine provisioners (no server here needs one), the kit builders, and the existing thirty-three entries.

The command_execution fix-checks already in the tree (kanban `cve_2025_53818_github_kanban.py`, token-optimizer `cve_2026_55157_token_optimizer.py`) are the precedent for calc, siri-shortcuts, serverless and pi-llm-wiki: the injecting tool reflects the injected command's output, the exploit calls only the injection point, the nonce comes from a planted witness file (a `PlantKind.FILE` Place the injected command reads, the `command_injection_env` builder) and never from the exploit text, so the grammar's anti-echo rule credits the surfacing. The read_outside_scope fix-checks (gemini-bridge `cve_2026_54785_gemini_bridge.py`, sylphxltd `cve_2025_67366_sylphxltd_filesystem.py`) are the precedent for ciguard, mcp-rtfm, claude-faf, grok-faf, maa and mastra-docs: a file planted outside the bounded scope whose content surfaces in the tool's response or error. Each fix-check module imports only from `evals.holdout_kit` and the clean `evals.cve_*` modules (`cve_planting` exports `planted`, `DockerPlanting`, `confinement_args`, `unprivileged_user_args`, `SENTINEL_IMAGE`), never `evals.cve_environments`; the import-closure scan over `evals/nuisance_fix_checks/` enforces it.

## Per-server data

Each counted server is host unprivileged, `runs_over_stdio` true, `runs_under_docker` true, `backend_need` none, `server_patched_surfaces` null (single counted flaw, patched version equals the server's). The `server_package` values below are the exact census spellings (`census.classifications` of the first classifier, `PyPI:` names normalised lowercase with hyphens by `nuisance_walk.normalized_package`), and an entry that spells one differently fails `load_admission` on `_foreign_flaws`. The `service` slug of each entry is the Dockerfile suffix (`Dockerfile.<service>`, `Dockerfile.<service>-vuln`), must not be an acceptance service and must not match an existing `evals/docker/Dockerfile.*`: `calc`, `siri-shortcuts`, `serverless`, `pi-llm-wiki`, `ciguard`, `mcp-rtfm`, `claude-faf`, `grok-faf`, `maa` and `mastra-docs` are all free today. A fix-commit patched version is recorded in full or as a 12-character prefix (the jenkins `dcee5f1aa4b3` and markdownify `a31204de058b` precedent), with `patched_source` `fix_commit`, on both the flaw and the server's `patched_version` (the two must be equal, `_patched_version_problems`); a registry version uses `patched_source` `advisory`. The per-launch random nonce is excluded from the fix-check comparison (`fix_check_mismatches` excludes `witness`, commit `b1ab38b`); do not reintroduce a nonce comparison.

## Fix-check source policy

Every counted flaw this batch is `source` `fix_check` with its own `FixCheckTarget` (none is a holdout twin at the holdout's calibrated version, so no `holdout_calibration` recopy applies). `run_nuisance calibrate` visits each target, builds the vulnerable version, and confirms the witness surfaces there and on the patched version not at all, with the benign call clean. Every target spans two versions (vulnerable, patched); there is no three-arm target this plan (no counted flaw's patched version differs from its server's).

## Edge cases

A counted tool with no benign call fails `_benign_call_problems` (each counted tool needs one), so every counted tool of every entry carries a benign call. A dropped sibling flaw stays in the admission with its real or null class and is not deleted (mastra-docs's GHSA-wxp6-9hmr-928g, null class). `test_each_target_mechanism_and_tools_match_the_admission_flaw` indexes the admission by `target.flaw`, so a registered `FixCheckTarget` whose flaw has no admission record raises `KeyError` and fails the full run: each fix-check module and its row in `FIX_CHECK_TARGETS` land in the same commit as its admission entry, never before. The parity test also equates a target's exploit-called tool set with the flaw's counted tools, so a counted tool whose exploit the calibration cannot make surface the witness is removed from the flaw's `tools` at calibration (ciguard's `scan`, mcp-rtfm's divergent tool, the `faf_write` acknowledgement path if it does not surface). The four command_execution servers assume the injected command's output reaches the tool response (the kanban and token-optimizer precedent). That is a calibration fact, not a design choice: a server whose injection is fire-and-forget (siri's `shortcuts` call and serverless's `list-projects` are the likeliest) cannot make the witness surface, its `vulnerable_surfaces` reads false, `_counts` rejects the flaw and the server is logged as a drop, not admitted with a guessed witness. A benign argument that enters the fixture fingerprint must be a stable string, not a per-launch uuid. The patched version left divergent between records A and B (mastra-docs alone) and each divergent counted tool set (siri-shortcuts, ciguard, mcp-rtfm, claude-faf, maa) are resolved on source at calibration before the entry is committed, and the entry is authored only once that fact is settled. Every `FROM` in every maintainer-authored Dockerfile is digest-pinned and copies nothing from the build context (`test_cve_compose_labels.py`), including the stubbed CLIs some servers bake (siri's `shortcuts` stub), which are inlined by `RUN`, never `COPY`ed.

No backend-module or registry test is added or changed (no backend this plan). Pyright strict and ruff clean on changed files in the short loop (the step-closing run is the full one of Verification), each new module under 300 lines and each function about 20 lines (split a builder that would exceed it into a sibling helper under the same import-closure rule).

Docker (calibration, no LLM), a maintainer action that never gates the unit checks: `run_nuisance calibrate --cve <id>` green on each of the ten counted flaws, the witness surfacing on the vulnerable version and on the patched version not at all, the benign call clean. ## Implementation steps

Eleven steps, one commit each: one per server (ten) and a final docs step. The split is by server, not by context budget alone: a server's `AdmittedServer` entry and its `FixCheckTarget` must land in the same commit (`test_each_target_mechanism_and_tools_match_the_admission_flaw` raises `KeyError` on a target whose flaw has no admission record, and the coverage test is red on an entry whose flaw has no target), so `load_admission` and the full test run stay valid at each commit. Each step is small (one module of 50 to 110 lines, at most one builder test file of about 50 lines, the `evals/nuisance_fixtures.py` import and row), so grouping several servers in one step would fit the budget, but would break the per-server commit and the per-server calibration that settles each entry's open facts before it is committed. No step adds provisioner, registry or compose code.

Repo code (the ten modules, their tests, the `evals/nuisance_fixtures.py` rows, the living docs) goes through the implementation flow. Eval data (every `evals/nuisance_admission.json` entry and every Dockerfile) is hand-authored by the maintainer and committed by hand together with the step's code, and each step says what must exist in the working tree before the implementer starts. The calibration-held facts of the Decisions section are settled by the maintainer before the step they belong to, so the entry is authored once, in its final form.

Common to every server step (Steps 1 to 10):

- **Before the implementer starts (maintainer)**: `evals/docker/Dockerfile.<service>-vuln` and `evals/docker/Dockerfile.<service>` (the patched build, also the run image), every `FROM` pinned by digest, nothing `COPY`ed or `ADD`ed from the build context (a stubbed CLI is inlined by `RUN`), no `compose.yml` entry and no fingerprint label (the nuisance images are built by `calibrate` through `kit_launch.build_images`). The server's `AdmittedServer` entry merged at the end of `evals/nuisance_admission.json` after the existing entries (untouched), per the Per-server data section: exact census `server_package` spelling, counted flaw with `source` `fix_check` and a `FixCheckTarget`, settled counted tools with one benign call each, dropped sibling flaws kept, `agents`/`agreement`/`settlements`, `backend_need` none, `server_patched_surfaces` null, `rule_commit` and `grammar_fingerprint` unchanged. The `fix_check` block carries a provisional witness, reconciled by the step's Verify `calibrate` run, which can only run once the module is wired (the nonce is excluded from the comparison). With the entry in the tree and no target yet, the coverage test `test_every_counted_flaw_has_a_fix_check_target_unless_holdout_calibrated` is red on the new flaw. That is the red state the implementer starts from.
- **Module**: `evals/nuisance_fix_checks/<flaw_id>_<server>.py`, a module docstring stating the mechanism and the two arms, importing only from `evals.holdout_kit` and the clean `evals.cve_*` modules (never `evals.cve_environments`, never `mcp_auditor`, enforced by the import-closure scan), a `TARGETS` tuple with one `FixCheckTarget`: `flaw` the counted flaw id, `vulnerable_service` and `patched_service` the two Dockerfile slugs, `server_patched_service` `None`, `witness` a `PlantKind.FILE` Place, `aim` a regex matching the exploit text and never the benign calls, `builder` `command_injection_env` from `kit_launch` (the kanban, token-optimizer, gemini-bridge and sylphxltd shape), `exploits` calling the counted tool(s) only, `benign_calls` one per counted tool. The nonce comes from the planted witness file and never from the exploit text. The shape to copy is named per step.
- **Wiring**: import the module in `evals/nuisance_fixtures.py` (alphabetical import block, `uv run ruff check . --fix` orders it) and append `*<module>.TARGETS` to `FIX_CHECK_TARGETS`.
- **Test**: the coverage test and the parity test (`test_each_target_mechanism_and_tools_match_the_admission_flaw`: the target's mechanism and the set of tools its exploits call equal the flaw's counted tools) go green on the new flaw, and the import-closure scans stay green. The command_execution modules (Steps 1 to 4) only wire `command_injection_env` with their own exploit and benign calls, as the kanban and token-optimizer modules do, so they carry no builder test of their own. The read_outside_scope modules (Steps 5 to 10) each get `tests/unit/test_<server>_fix_check_builder.py` in the shape of `tests/unit/test_gemini_bridge_fix_check_builder.py` (a small `RecordingClient`, helpers inline, no mock, written first and run red against the missing module): the target pairs the vulnerable and patched services with `server_patched_service` `None`, the exploit calls the counted tool(s) and nothing else with an argument matching `AIM`, and the benign call reaches the same tool(s) with an argument that does not match it.
- **Verify**: the step-closing full checks with no file argument, `uv run pytest -n auto`, `uv run ruff check .`, `uv run ruff format .`, `uv run pyright`, plus the `load_admission` one-liner of the Verification section against the running count (thirty-four after Step 1, up to forty-three after Step 10, each lower by the drops so far). Maintainer under Docker, never a gate on the unit checks: `uv run python -m evals.run_nuisance calibrate --cve <flaw id>` green (witness on the vulnerable image and on the patched one not at all, benign call clean), any mismatch recopied into the entry before the commit.
- **Drop path**: if the maintainer's pre-work shows the server cannot be admitted (the injected output never reaches a response, no counted tool surfaces the witness, `_counts` rejects the flaw), the step produces no Dockerfile, entry, module or row. It becomes a log-only drop recorded in Step 11, the later steps are unaffected, and the final count is lower by one.
