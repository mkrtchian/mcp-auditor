# CVE holdout selection rule

This is the selection rule of the holdout layer of the CVE benchmark. The decisions behind it are in [ADR 015](adr/015-eval-instruments-and-claims.md), [ADR 028](adr/028-cve-holdout-selection.md), [ADR 029](adr/029-nonce-only-proof.md), [ADR 030](adr/030-credit-replayed-on-patched.md), [ADR 031](adr/031-deployment-layout.md), [ADR 032](adr/032-holdout-drawn-without-sides.md) and [ADR 033](adr/033-nuisance-suite.md). Its changes, the excluded servers, the dropped targets, the cutoffs, the classes of the grammar and every other act this rule says is logged are in [`holdout-log.md`](holdout-log.md).

## Census

The census and the calibrations are done by LLM agents. Every agent of one step of a census or a calibration runs on the same model, so that no flaw is read by a stronger or weaker model than the other flaws of that step. The steps of a census are its collection, with every run after a widening, its recall, with the `vulnerablemcp.info` check, its classification and its grouping by proof. The steps of a walk's calibration (the draw, an addition or a replacement) are the calibration of its candidates, second calibrations included, and the check of their cards. When a step is done by two readers that each read every flaw of the step independently of each other, each reader may instead run on its own model, with every agent of one reader on that model, since every flaw is then read by both models. The classification and the grouping by proof are such steps. The maintainer chooses the model of each step, or of each reader, before the step starts and does not change it while the step runs, and the census records the model ID of each agent. An extension of the census is a census of its own for this clause, so its steps may run on models other than those of the census it extends.

**What counts as an MCP server.** An MCP server is a program that serves the Model Context Protocol to a client and exposes tools, distributed as a package or a public repository. Clients, hosts, inspectors, registries and SDKs are not servers, and a flaw of an SDK is not a candidate. A server is one package, or one repository when it is published only as a repository. When one package of a repository is an excluded server, the other packages of that repository stay candidates.

**The unit of the census is one flaw.** It is identified by its CVE ID in upper case, or by its GHSA ID as GitHub writes it when it has none. When several IDs describe one flaw as it enters the census, the lowest CVE ID that is not rejected (by year, then by number) is kept. The identifier, once recorded, never changes, even when a CVE ID is assigned or found later, so its draw hash never changes. A flaw found again under another ID, in this census or in a later extension of it, is matched to its recorded entry and not added twice.

**Sources.**

1. The GitHub Advisory Database, reviewed advisories only, through its public repository `github/advisory-database`.
2. The NVD, through its JSON data feeds.
3. OSV, through its data export, for the advisories the first two do not carry.

**Collection.** One agent per source runs a broad pre-filter on it, then reads every flaw the pre-filter returns and keeps every flaw of software that implements MCP: servers, clients, hosts and SDKs. The pre-filter, as first written, matches without regard to case the strings `mcp` and `model context protocol` anywhere in the advisory text or in the names of affected packages (on the NVD, in CPE product names). Each agent also looks beyond the pre-filter in its source, for instance at other advisories of the organizations that publish MCP servers, and records each flaw it finds there as a gap of the pre-filter.

**Recall.** Three more agents search, one per angle set in their instructions: the MCP vulnerability aggregators and security blogs, the security advisories of MCP server repositories, and servers whose names do not contain `mcp`. A flaw they find enters the census only through an advisory in one of the three sources. Every MCP CVE that `vulnerablemcp.info` lists with a disclosure date within the census must be found, or recorded as absent from the three sources. For each flaw found outside the pre-filter, by any agent, the pre-filter gains a string or a package name that matches it, and the collection runs again. These widenings are recorded in the census and open no version of this rule. The census is complete when the pre-filter, as last widened, finds every flaw the agents found.

**Classification.** Two classifiers classify every flaw of the census, independently of each other. A classifier may run as several agents, each in its own context on its own share of the flaws. Each flaw is classified from its advisory and the pages it links to, without access to this repository or its prompts. Each classifier records, per flaw: the server package and its versions, whether a vulnerable version and its first patched version can both be pinned, the disclosure date, the transport, the MCP primitive, whether the effect shows in a tool response, whether the server appears able to run in a container (no third-party service, credential or proprietary binary needed), the effect class (one of the grammar's, or another class it names), and for an ineligible flaw the first of the criteria checkable from an advisory (see Eligibility) that it fails, in their listed order. Every field is filled for every flaw, even after a first failed criterion. The classifiers' agreement is recorded as the share of flaws on which they agree, field by field. Until a disagreement is settled, a flaw counts as meeting a criterion when either classifier finds that it does. A flaw counts outside the grammar only when both classifiers place it outside the grammar. For the candidates a walk reaches, the maintainer settles each disagreement criterion by criterion, never on a guess about what the auditor would detect, and records each settlement with its reason. The maintainer applies the exclusions to the classified flaws.

**Grouping by proof.** Two readers group by proof the flaws that have a census identifier (a CVE or GHSA ID), meet the criteria of the draw order, have a server that either classifier finds able to run in a container, and are placed outside the classes of the grammar by both classifiers. Each reader works in its own context, told to read only what it is given: the advisory records of each flaw and the pages they link to, the flaw's server package, the effect names the two classifiers gave it, offered as hints, and a description, as of the day of the grouping, of how the benchmark proves a detection. For each flaw, the reader states how the effect could be proven in a tool response and gives its reason. It groups the flaws by that proof, with one group for the flaws whose effect cannot be proven in a tool response. The flaws a reader places in that group are the known gap of the holdout as that reader finds it (ADR 029). The judgments of the two readers are never settled into one. Neither the grouping nor the judgment that a server appears able to run in a container takes a flaw out of the draw order: a flaw of the known gap, or of a server judged unable to run in a container, is drawn and calibrated like any other. The grouping is done once for the census, and each extension groups only the flaws it adds. The census records, for every flaw the readers group, each reader's group, proof and reason.

**The disclosure date** of a flaw is its earliest publication date across the three sources, compared as a UTC calendar day. The census covers every flaw disclosed on or before the committer date of the commit that introduces version 1 of this file. An extension of the census covers every flaw disclosed on or before the date its log entry sets, under the version of this file in force when its collection starts. The entry is committed before the collection of the extension starts, the date it sets is on or before the committer date of that commit, and no extension is committed, nor its collection started, while the flaws of a walk are being calibrated.

**Output.** The census is committed as `evals/holdout_census.json`, before and after each draw, each extension, each addition and each replacement. It refers to the large artifacts it read instead of holding them: the commit of `github/advisory-database`, the date and SHA-256 of each NVD and OSV export, and for each pinned version, the integrity hash npm or PyPI publishes, or its commit SHA when it is pinned as a commit. It records the grammar fingerprint at the draw, the grouping by proof, the calibration records and cards, the number of give-ups for each reason, and two coverage figures: the share of MCP server flaws the auditor can reach (stdio transport, Tools primitive, effect in a tool response), and, once for each reader, the share of the known gap among the flaws that have a census identifier, meet the criteria of the draw order and have a server that either classifier finds able to run in a container. A flaw that either classifier places in a class of the grammar counts outside the gap without being read, so that share is a lower bound. It also reports, over every MCP server flaw of the census, the shares by transport, by MCP primitive, by effect class, and of effects that do not show in a tool response, and the number of flaws disclosed each month.

## Proof

A detection is proven only by a nonce that surfaces in a tool response: a random value the auditor cannot write, planted where only the flaw reaches it. At each launch of a target, every place calibration keeps for it holds a nonce of its own, drawn for that launch, so the report tells which place each detection came from. The effect class of a target is a label, reported with the target. The calibration agent files each target under the class of the grammar its published mechanism produces, or under the union of its flaws' classes when they differ, or under no class when none fits, and records that choice in the card. The class sets which judge categories count in `fail_without_proof` (see the per-target report). Under no class, every category counts.

The places come from two sources, the catalogue below and the deployment layout. Calibration keeps, for each target, every place the target reaches, and keeps a layout place only when the auditor also has a route to it (see Deployment layout). A target is a flaw together with its siblings. Another flaw of the current census is a sibling when the pinned vulnerable version carries it and the target's first patched version does not, so the replay on that version cannot tell them apart (ADR 030). The siblings are filed under the drawn identifier, the target's aim is their union, and the card carries each one's mechanism, so a place a sibling reaches is the target's own. A place is left out when something other than the target reaches it, the server at launch (see Deployment layout) or a tool's own function the benign call surfaces (see Eligibility). A tool function the benign call does not exercise is caught instead by the replay, which refuses the credit (ADR 030). A flaw the patched version still carries is not a sibling and leaves no place out, since the replay refuses the credits it gives (ADR 030). The reach of each flaw of the target (read, exec or fetch) is judged from its published mechanism. The acceptance layer forms its targets the same way, under the identifier each already has, so a flaw another acceptance target absorbs as a sibling is no longer a target of its own. On a target whose flaw runs code the caller chooses, the account of the process is one of the catalogue places: the server runs under an account named after the nonce of that place, so `id`, `whoami` and the passwd file print it. A value the kernel or the runtime computes from nothing the fixture sets, such as the version a database reports, holds no nonce.

The list was written before any draw, from the pinned sources below. Its filter keeps the ATT&CK techniques that have a tactic among Credential Access, Discovery or Collection, and a platform among Linux, Containers or IaaS. The other pinned sources cover what ATT&CK does not name: ATLAS covers the process environment and the configuration of an agent or its tools, the Falco rules cover the container and cloud locations, and the MCP security best practices cover the internal network services. The technique ID of a place comes from the ATT&CK or ATLAS object, even when a Falco rule tags the place with an ID. Each place cites its technique ID at the pinned version and a text that names the place. That text is quoted from an ATT&CK or ATLAS object, a Falco rule or the MCP security best practices. When none of them names the place itself, it is quoted from the documentation or the source of the software that defines that place as its default. A place that cannot be cited this way does not enter.

## Deployment layout

The second source of places is a deployment layout, written before the first holdout draw ([ADR 031](adr/031-deployment-layout.md)). It reproduces a project deployed from git: a checkout, the bare repository it was cloned from, and the project files a deployment carries. Every acceptance and holdout target is launched as its documentation prescribes (the first stdio launch its documentation gives, when it gives several), with the layout mounted and the checkout as its working directory. Wherever the launch takes a scope (the directory the server is limited to, given as an argument or an environment variable), the checkout is that scope.

**A place enters the layout under 3 conditions, the same for every target.**

1. It carries the citation a catalogue place carries: a technique ID at its pinned version and a text that names the place, quoted from a pinned source, or, when none names it, from the documentation or the source code of the software that sets that place as its default.
2. It is present in every target and its patched version, with the same ownership and mount mode, and the launch arguments are the same whether a target keeps it or not, so the command the auditor is given does not tell a kept place from one that is not kept.
3. No path segment the layout invents names a security concept. A denylist, listed and frozen with the layout, is applied only to the segments the layout invents, and not to a segment that a cited default dictates.

The layout as a whole meets 2 more conditions: no place holds content that a runtime executes or sends away at launch (a credential is scoped to a host outside any public registry, a variable carries a name no common tool reads), and the paths of the layout stay out of the auditor's prompts, under the contamination test of [ADR 014](adr/014-proving-impact.md) widened to those paths. A place holds a nonce only for a target whose calibration keeps it. For any other target it holds a value that the layout fixes in the place's documented format and that does not read as a secret, so that the auditor has no reason to open the place.

**A place is kept for a target when 2 checks pass.** Calibration shows that the flaw reaches it, as for a catalogue place. And a mechanical check, the route check, finds a route to it in what the server shows a procedure, the route procedure, that is the same for every target: the launch command the auditor is given, the server's `tools/list`, and the response or error of each tool, called once in the order of `tools/list` with the minimal arguments its schema requires. The check runs on the vulnerable version, launched the way the target runs and under the target's tools filter when it has one, inside a throwaway container that has its own copy of the layout, because some calls may write files. A route is the launch command, a response or an error that names the place's path, or that names a location from which the default path in the place's citation, taken relative to that location, leads to the place. The launch command counts only for the scope the layout dictates and a documented default taken relative to it, not for an option the agent set for the flaw. A path the procedure itself fills into a call's arguments is not something the server shows, as the grammar does not credit a proof copied from the arguments (ADR 029). A file the layout plants is never an observation by itself, so a place that nothing shows has no route. The benign call is not among the observations, because the calibration agent writes it after reading the mechanism. The route check is code committed before the first holdout draw. It fixes how arguments are filled, how long a call may take and what counts as naming a path, and it decides the route once, at calibration. A place the server itself reads at launch, as its documentation or source says, is not kept for that target: something other than the flaw then reaches it. The route decides only which places are kept. The credit does not depend on it: a nonce earns it whichever way the auditor found the place, and the replay can still refuse it (ADR 030).

**A server the layout breaks falls back to a pre-registered launch.** At calibration, before the exploits, and again before each holdout run (see Run conditions), the layout check, a mechanical check without an LLM, launches each version once with a minimal valid empty node at each path of the layout, by the node's type (an empty directory, an empty initialised repository or an empty bare repository), and once with the layout, and runs the route procedure each time. The layout breaks a version when the launch or `tools/list` succeeds without it and fails with it, or when a call that returns no error without it returns one with it. The layout check sends no call the calibration agent writes, so it cannot be aimed at a flaw. When the layout breaks either version, both versions run in the fallback, so that the run and its replay share one launch: the layout stays mounted, but the scope is the default the documentation prescribes. A path the documentation gives only as an example is not a default. A server that requires a scope and documents no default is scoped to an empty directory outside the layout, the same for every such server. A server whose scope is optional is launched without one. When the fallback launch fails as well, the calibration gives up, with the reason that the container cannot run the server. Each fallback is recorded in the census with its reason, for a candidate the calibration gives up on as for one that passes. When calibration found no break and the layout check before a holdout run finds one, the target is reported as not run for that holdout run and left out of N, since it was calibrated under a launch it can no longer use. It comes back only through a calibration under the fallback, done as a repair. When calibration found a break and that check finds none, the target keeps its fallback.

**The layout is frozen before the first holdout draw and never changed to make a target pass.** Before the layout entered this rule, each of its places was planted and reached on a fixture used for nothing else, and the confirmation is logged. They are listed below, as the catalogue places are. The run conditions are set no earlier than the layout, since a scope full of files may need a larger budget: the version that froze the layout set the budget in the same commit, and the chain settings and the tool call timeout are logged after it. Once the layout is frozen, only a new version of this file, committed after the log entry of an extension of the census and before its collection starts, adds a place to the layout. A version removes a place only when the place no longer meets a condition of entry, and that condition is logged.

## Eligibility

A flaw is eligible when all of these hold:

- it is a flaw of an MCP server, as defined above.
- the server runs over stdio, and the flaw is reached through `tools/call`.
- its effect shows in a tool response.
- a vulnerable version and the first patched version can both be pinned, as a release or a commit of a public source.
- both versions run in Docker.
- the calibration passes as it does on the acceptance layer: it keeps at least 1 place, and on the vulnerable version the nonce of every place it keeps surfaces in the response to at least one of the exploits written from the published mechanism, each exploit reading as aimed under the target's aim predicate, while the benign call surfaces no nonce and does not read as aimed. On the patched version, the benign call returns no error and no exploit surfaces a nonce.

The first four criteria are checkable from an advisory. With the first two exclusions below, they are the criteria of the draw order.

A flaw is excluded when any of these holds:

- it is a target of the CVE benchmark, now or before, or a sibling of one (the current targets are in `evals/cve_targets.py`, the dropped ones in the log).
- its server is an excluded server, listed in the log, or a package built from a repository GitHub marks as a fork of an excluded server's repository.
- for a drawn candidate, the maintainer finds that its vulnerable code is taken from an excluded server, and records the evidence in the census.

**Calibration.** Candidates are calibrated in draw order by an LLM agent. From the advisory and the published mechanism, it writes the fixture of the candidate and of its patched version, the places it keeps from the catalogue and the layout, its aim predicate, the exploits and the benign call. It sets no tools filter and no chain setting, which are conditions of the run. The launch it writes is the one the server documents, with every option that the server does not need in order to start left at its documented default, unless the flaw needs it set otherwise. No path or name it seeds refers to the flaw. Nothing it seeds lies inside the layout unless the server cannot start without it. The layout check and then the route check, being code, run on the fixture before it settles the places it keeps, the route check on the launch the layout check retains, so it keeps a layout place only among those the route check leaves open. When the layout makes the benign call error, it writes another benign call, since any call not aimed at the flaw serves. It works from the fixture format, the grammar of the benchmark, the list of places, the deployment layout and the advisories of the other census flaws of the candidate's server, without access to the auditor's code, its prompts, its results or its traces. Its instructions are to make each candidate reproduce. It makes as many attempts as it needs, and gives up on a candidate only when it concludes that the calibration cannot pass in a container. The census records the number of attempts and, for a give-up, a sentence of detail and one reason from a closed set: the flaw reaches no place, every place it reaches is left out for one of the reasons a calibration card lists, the container cannot run the server or the fixture, or the exploit cannot be made to reproduce. The maintainer does not exclude a candidate at calibration. When the agent gives up on a candidate, a second calibration follows at once, in a fresh context that receives the record of the first. A second give-up excludes the candidate, and both reasons are recorded.

**Calibration card.** For each candidate that passes, the agent writes a card into the census with:

- the mechanism as the advisory states it, and the class it files the target under.
- each place kept, with the reason only the target reaches it.
- each catalogue place whose reach the target has (read, exec or fetch, from its published mechanism) but that is not kept, and every layout place the target did not keep, each with its reason.
- the result of the route check for each layout place.
- each launch option set to a value other than its default, and each file seeded inside the layout, each with its reason and the documentation quoted for it.
- the fallback scope, when the target runs in the fallback, with the line of the documentation that prescribes it.
- the exploit calls, the benign call, and the result on the patched version.

A place is left out because the target does not reach it, something other than the target reaches it (the server at launch, or a tool's own function), no route reaches a layout place, it cannot be planted in a container, or for another reason the card states in full. A second LLM agent, without access to the auditor either, checks each card against the advisory, the advisories of the other flaws of the same server, the fixture, the list of places and the layout, and reports to the maintainer any gap and every place the card leaves out for a reason outside the listed ones. The maintainer reads, on every card, the mechanism, the exploit calls, the result on the patched version and every gap the second agent reports, before the candidate enters the holdout. A gap the maintainer confirms, criterion by criterion and recorded with its reason, sends the candidate back to calibration. Reading a card spends nothing.

## Sides

Each run sets its own sides. The cutoff of a model is the latest knowledge cutoff its vendor declares, with its type (as the vendor words it, for instance training data or reliable knowledge), and with a note when the vendor only gives the cutoff of a base model. When the vendor declares none, the cutoff of the model is its release date, the date of its earliest public availability recorded on a page of its vendor or of a host serving the model. The cutoff's type is then release date, with that page as its source. The cutoff of every model a holdout run uses is recorded in the log. The cutoff of a run is the latest cutoff among its models (generator and judge). A target whose drawn flaw was disclosed on or before it sits on the pre-cutoff side of that run (see the split by side), a later one on the post-cutoff side, whatever the dates of its siblings.

## Draw

The flaws are sorted in ascending order of the lowercase hexadecimal SHA-256 digest of the UTF-8 string `"mcp-auditor-holdout:" + id`, where `id` is the census identifier and the prefix is the salt. The order covers the flaws that meet the criteria of the draw order. The walk takes the flaws in that order until the holdout holds 20 targets. Each flaw reached goes through these steps, in this order:

1. its disagreements are settled.
2. it is skipped, and the skip recorded, if its server already gives a target to the holdout or a census flaw to the acceptance layer, or if it is a sibling of a flaw a walk excluded at calibration.
3. the maintainer checks its vulnerable code against the excluded servers.
4. it is calibrated.

It enters only if it is still eligible, its calibration passes and the maintainer has read its calibration card as set out above. Classes and disclosure dates have no quota. If fewer than 20 flaws pass in all, the holdout takes every one that passes.

## Run conditions and statistic

Before each holdout run, every vulnerable and patched image is built again from its committed Dockerfile, with the build cache. Each target is then checked without an LLM, as at calibration, on both versions and for every place it keeps. A target that no longer passes, on either version, is reported as not run and left out of N, the number of targets the statistic counts, until its fixture is repaired. Repairing a fixture is calibration, done by the calibration agent, and spends nothing. The patched versions serve the check and the replay, and a holdout run does not audit them. The nuisance suite ([`nuisance-rule.md`](nuisance-rule.md)) audits a holdout server at the patched version its own rule sets, under the reading discipline below. That version need not be the one checked here.

A holdout run audits every target at one commit, under these conditions:

- 3 runs, budget 10, no tools filter, and the list of targets.
- the chain settings (chains per tool, steps per chain, and any chain setting the auditor gains later) and the tool call timeout, the same for every target, set in the log before the first run that uses them.
- the provider, models and reasoning levels of the run, default or not, and their cutoff. A run refuses to start when the cutoff of one of its models, or its type, is not in the log.
- the replay of every detecting run on the patched version of its target (ADR 030). The replay keeps or refuses each credit, the detection that the nonce of a unit gives the run, a unit being the case or chain the grammar grades as one.
- the grammar fingerprint, and the fixture fingerprint of each target, which covers its patched version, the layout and the launch the target runs under, fallback included.

The commit of this file, the commit of the census and the image ID of each target are recorded as provenance, not as conditions, as ADR 024 decides for image IDs.

If the cost of a holdout run has to come down, the runs go from 3 down to 1 before any target is cut, since only targets narrow the interval (ADR 015). The change is logged, and the new number of runs is a condition of the runs that follow. Lowering the chain settings is logged the same way.

**The primary number is the mean over the runs of k/N**, the share of targets detected in one run, averaged. A target counts as detected in a run when its status, after the replay, is in `DETECTION_RUNGS`. Its detection share is the fraction of the runs that detect it. The cited interval is the 95 % two-sided Wilson score interval, without continuity correction, over the N targets with the sum of the detection shares as the count, never over the N × runs verdicts. The number speaks about the eligible flaws under this rule, in the composition the draw gave, and not about MCP flaws at large.

Beside it, each holdout run reports the composition of each side of its split and the full ladder of statuses. Per target, after the replay, it reports the target's class, the detection share, the runs where a nonce surfaced and from which places, each a catalogue place or a layout place, the credits the replay refused, the credits it could not check, the runs where a unit aimed at the flaw, the runs where an aimed unit judged FAIL in a category its class admits surfaced no nonce (`fail_without_proof`), whether it ran in the layout fallback, and the number of tools. It also reports the cost of the run in dollars, at the vendors' list prices on the day of the run.

**The split by side.** Each holdout run reports the primary number of each side of its cutoff, and the type of that cutoff. No side triggers a new target, however few targets it holds.

**The contrast between two sides** is a difference of proportions, with each side's sum of detection shares as its count, and its 95 % two-sided Newcombe hybrid score interval, without continuity correction, computed only when each side holds at least 5 targets. Below that, both sides are reported next to each other, without a test.

**Every conclusion drawn from an interval is checked.** A conclusion is a statement that an interval lies above or below a value, zero for the contrast. For the primary number: the Jeffreys and Clopper-Pearson intervals on the same count, Clopper-Pearson in its Beta-quantile form for a non-integer count, and the hierarchical Beta-Binomial credible interval with the target as cluster and its detected runs binomial over the runs (θ ~ Beta(1, 1), and d, the concentration of the per-target rates around θ, ~ Gamma(shape 1, scale 1), then ~ Gamma(shape 2, scale 2)). For the contrast: the Agresti-Caffo interval, and the difference of the two hierarchical posteriors with one d shared by both sides. Only the Wilson and Newcombe intervals are cited. A conclusion that changes with the method, or that changes when the credits the replay could not check count as misses, is reported as inconclusive, with the intervals that disagree.

**Two primary numbers compare** only under the same run conditions, apart from the provider, models and reasoning levels and their cutoff, the list of targets, or both, as paired outcomes on the targets both ran: a target is gained when its detection share rises and lost when it falls. A difference in these is named beside the comparison. A target that either of the two did not run leaves the comparison, as does a target recalibrated between them, its composition changed. They never compare by the overlap of two intervals. Under any other difference in run conditions, they are reported side by side.

**An audit with a step refused by the model provider and no detection counts as not detected in that run**, and the number of such audits is reported, with the targets they touch. A detection stands whatever step was refused. A refused audit is not attempted again, unlike on the acceptance layer, since a retry until no step is refused would keep the best of several attempts. A failure to launch the fixture, or an audit that ends on any other error, is retried at most 2 times. A target that still fails in any run is reported as not run for the whole holdout run and left out of N, so N is the same in every run. A replay that fails to launch is retried the same way, and a credit still not replayed is kept and reported as unchecked.

## Reading

A holdout target is spent as ADR 015 defines it. So that running the holdout spends nothing, a holdout run writes and prints no proof text (`evidence`), no judge input and no verdict per case, only the statuses, the counts and the places above. The replay keeps the calls and the patched responses in memory only. The run exports no judged case, and refuses to start when `LANGSMITH_TRACING` or `LANGCHAIN_TRACING_V2` is set. Holdout targets stay out of every other instrument (the acceptance gate of ADR 024, the draw of the judge fixture and the probe corpus), except that their servers enter the nuisance suite as report-only servers, audited under the discipline of this section. The nuisance suite walks the same draw order, at least as far as the holdout walk has gone ([`nuisance-rule.md`](nuisance-rule.md)). Before the draw, the contamination test of ADR 014 is extended to the text the excluded servers produced in the CVE cases of the judge fixture (tool descriptions, responses and errors, the auditor's own payloads echoed back left out), and it passes on the code of that day. The auditor is then not fitted to the text of an excluded server, which a holdout server built on the same framework or the same conventions could also emit.

When the traces of a target feed a decision (a change to a prompt, a guard or the oracle, or a case of the judge fixture), its server is listed in the log as an excluded server the same day. Reading traces without such a decision spends the target read, not its server. When a nuisance trace feeds such a decision, the server the trace comes from is listed in the log as an excluded server the same day, whatever version of the server produced the trace. A server excluded after a draw, or a package built from a fork of its repository, takes its drawn target out of the holdout, and the target is replaced.

Holdout traces are never read: error analysis is done on the acceptance layer. Reading a trace anyway spends its target. The reading is logged with how it happened and the target's detection share in the runs before it. Its server is excluded only if the reading leads to a decision as defined above. A nuisance trace of a holdout server is never read either. Reading one anyway spends its holdout target, which is replaced as below. The reading is logged in the nuisance log as the nuisance rule prescribes, and in the holdout log with the spent target's detection share in the holdout runs before it.

The acceptance layer may take a census flaw only when its server gives no holdout target. It grows when its targets no longer suffice for understanding the auditor, never on a holdout number, and never aimed at reaching or skipping a flaw of the draw order. Each census flaw it takes is logged with its reason, and is a target of the CVE benchmark from then on.

No change to the auditor, to the list of places or to the deployment layout is made or reverted because of a holdout number, and no extension of the census or addition of targets is decided, sized or dated on one or on an alarm number of the nuisance suite, nor aimed at reaching or skipping a flaw of the draw order or a server of the nuisance suite. The census is extended and targets are added when the holdout's measure is not precise or relevant enough, never to change what the acceptance layer may take. A change made or reverted because of a holdout number is reversed, and the reversal is logged.

A spent target leaves the holdout and may move to the acceptance layer, with a tools filter. It is replaced by the first flaw, in draw order, that the walk has not yet reached, and the replacement is logged.

## Versioning

This is version 8. Any edit of this file, the list of places, the deployment layout and its denylist included, opens the next version. An edit to the code of the route check or the layout check opens a version only when it changes what the check decides, which a committed golden master of their decisions confirms. A new version keeps the salt and the draw order, and applies its criteria again: a target that stays eligible stays drawn, with its calibration. A change to the list of places sends the target back to calibration for the places it adds, removes or modifies. A change to the layout or to either check sends the target back for the places the change touches, and the route check runs again on every layout place, the layout check on every target. An extension of the census that adds a sibling of the target, as Proof defines it, sends the target back for the places that sibling reaches. A target that is no longer eligible leaves the holdout and is replaced as above. A flaw that becomes eligible enters only through the walk, either to fill such a vacancy or as part of an addition. Extending the census and adding targets open no version. Targets are added by resuming the walk on the census in force, from the first flaw in draw order that the walk has not reached, whether old or newly added. Each addition is logged with the number of targets it takes. The targets already drawn stay drawn.
