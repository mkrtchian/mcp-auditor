# Nuisance suite rule

This is the rule of the nuisance suite, the instrument that counts the alarms the auditor still raises on the patched version of a server whose known flaws are fixed. The decisions behind it are in [ADR 015](adr/015-eval-instruments-and-claims.md), [ADR 016](adr/016-eval-gate-governance.md), [ADR 024](adr/024-cve-acceptance-gate.md), [ADR 028](adr/028-cve-holdout-selection.md), [ADR 032](adr/032-holdout-drawn-without-sides.md), [ADR 033](adr/033-nuisance-suite.md) and [ADR 034](adr/034-closed-eval-networks.md). Every event this rule logs goes in [`nuisance-suite-log.md`](nuisance-suite-log.md): the rule's changes, the servers that leave, the traces read and the reversals.

## Eligibility

The flaws come from the census of the [detection suite rule](detection-suite-rule.md) (`evals/census.json`), its extensions included, under the flaw IDs the census records. A server is one package, or one repository when it is published only as a repository, as the detection suite rule defines it.

**The nuisance walk.** Servers enter in the draw order of the detection suite rule: the census flaws that meet the criteria of the draw order (the detection suite rule's Eligibility section), sorted by the salted hash its Draw section defines. The nuisance walk takes the flaws in that order. A flaw the detection walk has not reached has the disagreements of the census classifiers on it settled first, as the first step of the detection suite rule's Draw section requires, and the nuisance walk skips it if it then fails the criteria of the draw order. When the nuisance walk reaches a flaw whose server it has not reached yet, that server goes through the admission (see Admission) with every census flaw it carries. A server enters only through a flaw of the draw order, and its other census flaws then count as set out below. Each server the nuisance walk reaches is logged with the flaw ID of the flaw that reached it.

The nuisance walk reaches at least every flaw the detection walk has reached, so every detection holdout server, the server of a holdout target, is reached. It follows the detection walk each time that walk resumes. Past these flaws, it reaches a flaw only for an addition, which is logged with the number of servers it takes. The nuisance walk then stops once that many more servers have entered the nuisance holdout layer. A server enters the nuisance holdout layer, as a **nuisance holdout server**, once its admission is committed and no exit of the list below holds for it. A server that leaves the nuisance holdout layer later is not replaced, and the nuisance walk does not go on for it. Each time the nuisance walk resumes, it starts from the first flaw in draw order that it has not reached, old or newly added, as the detection walk does. An extension of the census alone does not resume it. No addition to this suite, no addition of holdout targets and no extension of the census is decided, sized or dated on an alarm number of this suite (the holdout nuisance rate, a side or the raw count), and none is aimed at reaching or skipping a server of this suite. The cost of a run may size an addition.

A **graded class** is a class of the grammar of the oracle (`evals/cve/grammar.py`), which fixes the judge categories valid for it. A flaw of any other class does not count.

**The counted flaws of a server** are its census flaws that are in a graded class, reached through `tools/call` (with at least one tool the admission records for it, whatever transport the census records), whose effect shows in a tool response, and whose vulnerable version can be pinned as a release or a public commit. The patched version of the server is the first release, in the ordering of the package's version scheme, on which every one of these flaws is fixed. A flaw is fixed on a release that is at or above its patched version and outside every affected range its advisory gives.

A **counted tool** is a tool of a counted flaw that exists in the patched version, that does not need a backend the fixture cannot provide, whose benign call (a call not aimed at the flaw, see Admission) can return without error, as The benign call defines it, on the real software it drives and under the confinement, and whose declared function is not the effect of its flaw's class. An alarm on any other tool of a counted flaw cannot be read as false, so it leaves the count. The tools of a flaw are the ones a `tools/call` request reaches it through, one or several. A tool the fix renamed is a counted tool under the name the admission records for the patched version. The benign call and the counter use that name.

**The real software.** A tool drives real software when it calls a program, a device or a service outside the server. The confinement is the set of container options every nuisance server runs with, the same for every server (its user, the dropped capabilities, the memory bound). That software is the one the server's documentation or tests name, at the version they name or else at the stable release that is current on the day of the admission, and it runs in a deployment where it works, set up as the server's documentation says and otherwise at its defaults. The admission records that release and that day, or those of the card of the holdout target whose calibration it reuses. The configuration the fixture models (a device, an operating system, a version) is never chosen according to which tools it lets succeed or fail. A tool is not a counted tool when its benign call returns an error on that software with every argument that its description allows and that is not aimed at the flaw. Nor is it one when no distribution channel that the software's documentation or the server names still distributes any version of the software. A tool in either case leaves the count because its benign call could pass only on a stand-in that returns what the software would not, so the benign call would prove nothing about it. For each such tool, the admission records the run of the benign call, the capture or the source line that shows the error or the missing channel, and a tool without such a record stays counted. A failure can also come from the container rather than from the software: a first start that still needs initialization, a missing daemon or device, a read-only directory or a host the run does not serve. Such a failure is repaired in the fixture. So is a container failure that the software reports as an empty result rather than as an error. A failure the fixture cannot repair under the confinement, such as a tool that needs a capability the confinement drops, takes the tool out of the count, and the admission records why.

**The declared function.** A tool's declared function is the effect of its flaw's class when its description declares the action of that class on what a tool argument carries or names, wherever that action happens (in the server, in a program it calls or on a remote host). The action of a class is running or evaluating a command, code or an expression for `command_execution`, fetching a URL for `internal_fetch`, and reading a path for `read_outside_scope`. It is not the effect when the argument only parameterizes a fixed operation, such as reading a path inside a root the server declares (reading outside that root being the flaw) or running a fixed program on a path or a name the argument gives. What reaches the tool other than through an argument (a transport header, the server's configuration, data held by a platform the server talks to) bears on whether the flaw is reached through `tools/call`. It does not change the declared function. When the fix commit removes the capability, so that the patched tool no longer does the action of the class on what an argument carries or names, the declared function is read from the description of the patched tool.

**The patched version of a flaw** is the first patched version the advisory gives. When the advisory gives one version per affected range, the lowest in the ordering of the package's version scheme is taken. A version the advisory gives that no release carries is read as absent. When the advisory gives no version, the patched version is the first release that contains the fix commit the advisory links. When neither source gives a version, or when no release passes the fix check, the flaw is never fixed. A release is a version published on the package's registry, or a tag of the public repository when the server is published only as a repository. When no registry release carries the fix, the earliest public tag or commit that does counts as a release too, recorded with the `fix_commit` source, even though a user of the registry does not install it by default. When the advisory's version and the release that contains the fix commit differ, the advisory's version stands. When the census sources (the GitHub Advisory Database, the NVD and OSV) give different versions for one flaw, the maintainer settles which version holds from the advisory records and the pages they link, and records the reason.

The server of a current or dropped acceptance target of the detection suite (the current targets are in `evals/cve/detection/targets.py`, the dropped ones in the detection suite log) has traces that may be read (see Reading), so it never enters the nuisance holdout layer, even when the nuisance walk reaches it. A nuisance run does not audit it. The server of a current acceptance target goes through the admission, outside the nuisance walk, and once admitted is a **nuisance acceptance server**, audited by the nuisance gate in a run of its own (see Run conditions and statistic).

A server leaves the nuisance holdout layer when any of these holds:

- it has no counted flaw.
- one of its counted flaws is never fixed.
- it has no counted tool left, because the fix removed them, because they need a backend the fixture cannot provide, because their benign call cannot return without error on the real software or under the confinement, because their software is no longer distributed, or because their declared function is the effect of their flaw's class.
- it does not run over stdio.
- its patched version does not run under Docker: the server needs a remote third-party service that the fixture cannot run and that no stand-in can replace under the rules of Stand-ins (Admission), a credential or an account the maintainer does not have, or a proprietary binary to start. A backend the fixture itself brings up, a database or a service in its own container, is not such a case. What the census recorded about the server only informs the admission.
- it is an excluded server of the detection suite log, or a package built from a repository GitHub marks as a fork of an excluded server's repository, unless it is the server of a current or dropped acceptance target, which has its own row below.
- it is the server of a current or dropped acceptance target.
- it is spent by a reading (see Reading).

Each exit is logged with its reason. A benign call that fails, or an error that outlasts its retries, takes the server out of N for one nuisance run only (see Run conditions and statistic), not out of the nuisance holdout layer.

## Admission

Two agents carry out the admission, independent of each other and each in its own context. For every flaw, each agent reads the advisory records of the census sources and the pages they link, the fix commit among them. It reads the registry page of the package, or the tags of its repository. It reads the source of the server at the version it decides on, the tool list and the tool descriptions included. The agents have no access to the auditor's code, prompts, results or traces. They have no access to the audits of this suite, except the result of the benign call.

For each flaw, each agent records:

- the tools of the flaw, by name in the vulnerable version and in the patched version, each marked unchanged, renamed or removed.
- its effect class, one of the grammar's or none.
- its patched version, and the source that gave it: the advisory's field, the first release that contains the linked fix commit, or none.
- whether the fix needs a launch option set, with the documentation quoted.
- for each tool of the flaw in the patched version, whether its benign call can return without error on the real software it drives and under the confinement, as Eligibility defines both, and, when it cannot, the run, the capture or the source line that shows the error, the missing distribution channel, or why the container failure cannot be repaired.
- a benign call for each tool of the flaw in the patched version whose call can return without error on the real software and under the confinement: the tool and its arguments, written from the tool's description so that it returns without error, and not aimed at the flaw.
- for the fix check, a witness planted where the flaw reaches, and an exploit whose tool calls surface it in a tool response on the vulnerable version.
- whether a tool of the flaw needs a backend to answer its benign call, and whether the fixture can run that backend (a database or a service in its own container) or cannot (a remote third-party service, a credential or an account the maintainer does not have).
- for each tool of the flaw, whether its declared function is the effect of the flaw's class, read from the tool's description alone, as Eligibility defines the declared function.

For each server, each agent records whether its patched version runs over stdio and under Docker, and writes its launch, the Dockerfile of its patched version, and the Dockerfile of a vulnerable version that the fix check uses. When the server needs a backend to start or to answer a benign call, the agent also writes the backend fixture: the backend as its own Dockerfile or service, and the network that joins it to the server, with no witness planted in it. It writes the stand-ins the server calls and what the fixture seeds, under the three paragraphs below (Stand-ins, Seeding, What no fixture serves). The launch is the one the server documents. Every option the server does not need in order to start stays at its documented default, unless a fix needs it set, or unless the server must trust the certificate of a stand-in served under the real name of the host it replaces (ADR 034), a setting the admission records. When the patched version of a detection holdout server is the one the calibration of its holdout target checks, the agents may start from that fixture, its backend included. The agents also write the repairs of a Dockerfile, a stand-in, a seed or a benign call, under the same access restrictions.

**Stand-ins.** The real software the server calls runs in the container whenever it can run under the confinement the suite launches the server with, or else as a backend within the memory bound of that confinement. A stand-in takes the place of the part that cannot run there, be it a program, a device, an HTTP backend or a public host served under its real name (ADR 034), and it answers what the real software, as Eligibility defines it, would answer. Its output for a request is taken from the first of these sources that holds one, in this order: a capture from the real software, then that software's documentation, fixtures, tests or published API examples, then the server's own tests. Within one source, it is the first output the source gives for that request. A copied output cites its source, and the only edits it admits replace an identifier (a name, an id, a host, a date) with a fixed value of the fixture, each replacement recorded. When no source holds an output for a request, the output is invented in the form of the closest output a source gives, and the admission records it as invented, with the source whose form it follows. An invented output contains no part of the request. A stand-in branches only on fixed words at fixed positions of the request, and for any other request it answers with the error that the real software gives for an input it does not recognize, as the same sources give it. It quotes the request only where its source quotes it, in the source's wording. It returns no success or failure the real software would not return, and it evaluates no code: code the server passes on is run by the real interpreter of its language or answered from the sources.

**Seeding.** When the software the fixture seeds data into publishes a sample (a demo dataset, a quick-start example, a sample project), or failing that when the server does, the fixture seeds that sample whole, cites it and pins it in the admission by a commit, a version or a digest. When the documentation names several samples, it seeds the first one. What the server needs to start and what the benign calls need come from that sample when it holds them, failing that from what the software or the server generates on its own at build time, and failing that from a document the project publishes. Only then are values written for the fixture, each recorded as written, including the names the benign calls use.

**What no fixture serves.** Whatever the source, nothing the fixture serves, seeds or passes to the server (its launch and environment included) carries a value taken from the machine that runs the suite (a hostname, a user name, a path), a value in the witness's format, or a word written for the fixture about the audit, the fixture or a flaw (benign, seed, stub, calibration, secret, in scope and the like). An output or a name the real software or the server produces on its own, at build time or as it runs, a captured or copied output, and a published sample taken whole are kept as they are, even where they contain a word of that list. No stand-in carries a flaw's effect to a tool response: a backend may hold content at the place the flaw reaches, but a stand-in never returns what reaches it through the flaw (content read outside the scope, the output of an injected command, a fetched body), even where the real software would. This limit binds the fix check too, so a witness that surfaces only because a stand-in relays it fails the positive control, and the calibration of a holdout target is not reused when its positive control rests on such a stand-in (see A fix verified by reproduction). Neither the limit on words nor the limit on the witness's format binds the witness, the exploits of the fix check or content that only the fix check reads, provided none of it remains in anything a run builds, seeds or serves. Nor does the limit on words bind the certificate authority the stand-ins' certificates chain to, or the names it gives in the certificates it issues.

**Agreement and settlement.** Whether the two agents agree is recorded for each of the following fields: the tools and their status, the class, the patched version, the backend, the real software and the confinement, the declared function, stdio and the container. The maintainer settles each disagreement on the advisory and the pages it links, never on a guess about what the auditor would flag, and records each settlement with its reason. A disagreement on the patched version is settled as Eligibility sets the patched version of a flaw. Of the two benign calls written for one tool, the maintainer keeps one or the other, since any call not aimed at the flaw will do. The fix check plays both exploits written for a flaw, and the witness counts as surfaced when either surfaces it. Of the two launches, Dockerfiles, backend fixtures, stand-ins or seeds written for one server, the maintainer also keeps either one. A server enters only once every disagreement on its flaws and on its own fields is settled. The class settled at the admission is the class of the flaw under this rule, whatever the census classifiers recorded. A record, a field or a repair written on instructions that misstate or leave out a clause of the rule in force that bears on a flaw, judged from their text and never from the result, is void, logged with the sentence at fault, and redone by two admission agents.

**Output.** The admission is committed in one file. It holds the record of each flaw and each server, the model ID of each agent, the agreement and the settlements. The patched Dockerfile, the backend fixture, the launch and the benign calls of each server, and the vulnerable Dockerfile and exploits the fix check uses, are committed beside it. The fixture fingerprint covers the patched Dockerfile with every file it copies in, the backend fixture with what it serves, the stand-ins and the seeded samples, the host, the launch, the counted tools with the class of each, and the benign calls. All of it is committed before the first nuisance run.

**A fix verified by reproduction.** Reading the advisory and the fix does not show whether the chosen version really fixes the flaw, so each counted flaw is checked by reproduction, without an LLM and outside any run, before the first nuisance run. A witness value is planted where the flaw reaches, and the exploits are played on both versions. When the server needs a backend, the fix check brings it up on both versions from the backend fixture the admission records, so the exploits and the benign call run against a server that has started. The check passes when the witness surfaces in a tool response on the vulnerable version, the positive control that proves an exploit sound and the flaw real, and surfaces neither on the flaw's patched version nor on the server's patched version, where every benign call the admission records returns without error. This is the calibration check of the detection holdout layer applied here, without its constraint that the witness sit at a place of the detection suite's list of places or deployment layout: the witness is planted at the flaw's own location, which is why a server whose flaw the detection walk took out for reaching none of those places can still enter. When an exploit still surfaces the witness on the advisory's patched version, that version does not fix the flaw, and the flaw's patched version is the first later release where the witness no longer surfaces. A flaw that no release clears is not a counted flaw, and neither is a flaw whose exploits surface no witness on the vulnerable version, the positive control having failed. Each case is logged. A detection holdout server whose patched version is the one the calibration of its holdout target already checks is not checked again for the drawn flaw and its siblings, as the detection suite rule's Proof section defines them, provided the admission records that its positive control does not rest on a stand-in that relays the flaw's effect. Otherwise the flaw goes through the fix check. The calibration reused is the holdout target's current one: when that target's fixture fingerprint changes, the admission copies it again and records its positive control again before the next run, and while the target is back in calibration or out of the detection holdout layer, the flaw goes through the fix check. The vulnerable version and the exploits serve this check only, never a run, and the auditor never sees them.

## Run conditions and statistic

Before each nuisance run, every image is built again from its committed Dockerfile, the backend's included when the fixture builds it, with the build cache. An image pins the server's patched version and the digest of its base image, as the Dockerfiles of the detection suite do. The transitive dependencies stay floating. A nuisance run plants nothing and draws no nonce, the fix check being the only place a witness is planted. When the server needs a backend, the run brings it up from the committed backend fixture, as the fix check does, and plants nothing in it. Every network the fixture uses reaches neither the machine that runs the suite, nor its local network, nor the Internet, and a public host that the server needs to start, that a benign call needs, or that a flaw's published mechanism goes through is served by a stand-in under its real name (ADR 034). The launch is the one the admission records. The fixture seeds what the Seeding paragraph of Admission sets out.

**The benign call.** Once the server runs, the benign call of every counted tool is made without an LLM, and it must return without error: no protocol error, no tool result marked as an error, and no result whose text reports that the call failed. A server whose benign call fails is reported as not run with that reason and leaves N, the number of servers the statistic counts, for the whole nuisance run. Its benign call or its fixture is repaired by the admission agents before a later run, which opens no version of this rule. Until the auditor first audits any nuisance fixture (in a nuisance run, a gate run or otherwise), the maintainer may also repair a fixture or a benign call, including the repairs that a new version of this rule requires, and logs each repair. The maintainer's repairs are limited to the launch, the seeded files, the stand-ins, the arguments of a benign call and the address of a backend, under the rules of Admission and never on a guess about what the auditor would flag. Taking a tool out of the count falls to the admission agents, as part of the admission. From that first audit on, only the admission agents make these repairs, since the maintainer has then seen the status of the servers.

A nuisance run audits every admitted server at one commit, under these run conditions:

- the budget of the holdout run the holdout nuisance rate is read beside, and no tools filter.
- the number of runs, which this suite sets in its log, since it changes the precision of the holdout nuisance rate and leaves the auditor it describes unchanged. If the cost of a nuisance run has to come down, the runs go down before any server is cut, since the interval is over the N servers and only servers narrow it.
- the list of admitted servers.
- the chain settings and the tool call timeout, as `evals/holdout_conditions.json` records them.
- the provider, models and reasoning levels of the run, and the cutoff of each model with its type, which `evals/holdout_conditions.json` records. A run refuses to start when the cutoff of one of its models, or its type, is not recorded there.
- the grammar fingerprint, the fingerprint of the counter, and the fixture fingerprint of each server, which covers what the Output paragraph of Admission lists.

The commit of this file, the commit of the admission and the image ID of each server are recorded as provenance, not as conditions, as ADR 024 decides for image IDs. Each run records its date, since a model can change behind one identifier.

**A server is flagged in a run** when a test case or a chain of its audit calls a counted tool and is judged FAIL in a category valid for the class of a counted flaw that tool carried. A chain counts when any of its steps calls such a tool. A tool that carried counted flaws of several classes takes the union of their valid categories.

**The holdout nuisance rate is the mean over the runs of f/N**, where f is the number of servers flagged in a run and N the number of servers the run audits. A server's flagged share is the fraction of the runs that flag it. The cited interval is the 95 % two-sided Wilson score interval, without continuity correction, over the N servers with the sum of the flagged shares as the count, never over the N × runs verdicts. It is published as "at most" with its interval. Every conclusion drawn from an interval is checked as the detection suite rule checks its own, with the server as the unit, and a conclusion that changes with the method is reported as inconclusive. The number describes the admitted servers, in the composition the nuisance walk gave.

**The split by side.** Each run reports the holdout nuisance rate of each side of its cutoff, and names the type of that cutoff. The cutoff of a run is the one the Sides section of the detection suite rule defines: the latest cutoff among its models, a model's cutoff being its release date when its vendor declares none. For the split, each server counts through one flaw only, its first flaw of the draw order that still has a counted tool, so that the number of flaws a server carries moves neither its side nor its chance of being flagged on that side. The server is on the pre-cutoff side when that flaw was disclosed on or before the cutoff, the disclosure date being the one the census records, and on the post-cutoff side otherwise. It is flagged for the split when it is flagged, as defined above, through a counted tool of that flaw. A server with no such flaw leaves the split.

**The contrast between the two sides** is computed, cited and checked as the detection suite rule does for its own, with the server as the unit, and only when each side holds at least 5 servers. Below that, both sides are reported next to each other, without a test. Two biases pull the gap between the sides toward zero: a server on the post-cutoff side can carry another flaw disclosed before the cutoff, and when the cutoff is a release date, the pre-cutoff side can hold servers whose flaw the model never read. The published holdout nuisance rate stays the one over all the servers of the run, and the two sides do not add up to it.

**The raw count.** For reference, each run also reports the total number of test cases and chains judged FAIL per nuisance holdout server and per run, on every tool and in every category. It reports separately the part of that count that falls, in a category valid for the class of a counted flaw, on the tools of that flaw left out because their declared function is the effect of that class. It computes this count in memory, without writing any verdict per case. It counts FAIL verdicts nobody read, true and false mixed, so it is neither a false-positive rate nor a number of false alarms. It stays in the run report, never goes to the README, and is never compared between two nuisance runs.

**The exits.** Each run publishes two tables, one row per reason with its count. The servers outside the nuisance holdout layer: no counted flaw, a counted flaw never fixed, no counted tool left, a server that does not run over stdio, a patched version that does not run under Docker, an excluded server, a server of a current or dropped acceptance target, and a server spent by a reading (see Reading). And the servers left out of N for this nuisance run only: a benign call that failed, and a server not run after its retries.

Per server, after the runs, the report gives the status in each run (flagged or not flagged), the flagged share, the number of counted tools and the number of tools. It also reports the cost of the run in dollars, at the vendors' list prices on the day of the run.

**An audit that raises no counted FAIL, in which the model provider refused a model call or a model call came back unreadable, counts as not flagged in that run.** The holdout nuisance rate describes what an audit shows, and a user whose audit meets the same refusal sees no alarm either. Such an audit is not attempted again. The number of such audits is reported, with the servers they touch. A conclusion that changes when these audits count as flagged is reported as inconclusive. An alarm stands whatever model call was refused. A failure to launch the server, or an audit that ends in any other error, is retried at most twice. A server that still fails in any run is reported as not run for the whole nuisance run and leaves N, so N is the same in every run.

**Two holdout nuisance rates are compared** only when their run conditions are the same, except for the provider, models and reasoning levels with their cutoff, the list of servers or the fixture fingerprint of a server. They are compared as paired outcomes on the servers both nuisance runs audited: a server counts as improved when its flagged share falls and as worsened when it rises. A server that either nuisance run did not run leaves the comparison. So does a server whose fixture fingerprint changed between the two nuisance runs. They are never compared by the overlap of two intervals. Under any other difference in run conditions, they are reported side by side.

The holdout nuisance rate is published beside the holdout detection rate from a holdout run at the same commit, under the same provider, models, reasoning levels, budget, chain settings and tool call timeout. The holdout nuisance rate of a nuisance run with no such holdout run stays in its run report and is not published in the README.

**Only the nuisance acceptance servers are gated.** The gate audits them in a run of its own, under the run conditions its baseline records, as the detection gate does (ADR 024). A nuisance run does not audit them, and a gate run audits no other server. The baseline is recorded under `evals/baselines/`. It is recorded from a green gate and never under a red one (ADR 016). A nuisance acceptance server not flagged in any run of the baseline is gated. When a candidate raises an alarm on it, the alarm is retested under the retest rule of ADR 016, with the numbers the baseline file records. The gate fires when the alarm reproduces. A server with an alarm in some runs of the baseline is unstable, and a new alarm on it is reported as inconclusive. The other rules of ADR 024 apply, with the server in place of the target and an alarm in place of a miss.

## Reading

A server is **spent** by being read, as ADR 015 defines reading: by opening its per-case traces, its judge inputs or its judge verdicts, by hand or through an agent that reports back what it read. The status per run, the result of the benign call and the harness log spend nothing.

The traces of the nuisance acceptance servers may be opened and their alarms analyzed, and a gate run writes their per-case report as a graded run of the detection acceptance layer writes it. Every nuisance holdout server is audited under the reading discipline of the detection suite rule (its Reading section). A nuisance run writes and prints no proof text (`evidence`), no judge input and no verdict per case. It prints the status flagged or not flagged per server and per run, the counts above and the raw count. It exports no judged test case. It refuses to start when `LANGSMITH_TRACING` or `LANGCHAIN_TRACING_V2` is set.

A nuisance holdout server whose trace is read anyway is spent. It leaves the nuisance holdout layer from the next run, with its row in the exits. The reading is logged with how it happened and the server's flagged share in the runs before it. When the spent server is the server of a holdout target, the reading spends that target too, and the target is replaced under the detection suite rule as if a trace of a holdout run had been read. When a nuisance trace feeds a decision as the detection suite rule defines one (a change to a prompt, a guard or the oracle, or a judge case), the server is excluded the same day in the detection suite log, whatever version of the server produced the trace.

No change to the auditor, to the admission or to the counter is made or reverted because of a number of this suite on the nuisance holdout servers. A change made or reverted because of one is reversed, and the reversal is logged. Changes to the auditor are decided on the honeypot suite, the judge eval, the detection acceptance layer and the gate of this suite on the nuisance acceptance servers. Using the nuisance holdout servers to choose a model needs a decision of its own.

## Versioning

This is version 5. Any edit of this file opens the next version, pinned by its commit in the log. A new version applies its criteria again to the servers the nuisance walk has reached. A server that stays eligible stays admitted, with its admission record. A server that is no longer eligible leaves the nuisance holdout layer, logged with its reason. The fields a new version adds are recorded for every admitted server by two admission agents and settled as the admission settles them. A fixture that breaks a limit the new version sets is rewritten under Admission before the next run. A change to the code of the counter opens no version. It changes the counter's fingerprint, which resets the baseline of this suite's gate and keeps the holdout nuisance rates before and after it from being compared. A change to the grammar opens no version of this rule either, but it applies the eligibility again, resets the gate's baseline and keeps holdout nuisance rates across it from being compared.

An extension of the census opens no version by itself. A reached server to which the extension adds a census flaw is admitted again, since its patched version and its counted tools can move. A census flaw the detection acceptance layer takes makes its server the server of a current acceptance target from the next run, and opens no version. The detection acceptance layer never takes a flaw because of a number of this suite, nor to reach or skip a server of this suite.
