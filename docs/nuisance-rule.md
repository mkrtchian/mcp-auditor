# Nuisance suite rule

This is the rule of the nuisance suite, the instrument that counts the alarms the auditor still raises on the patched version of a server whose known flaws are fixed. The decisions behind it are in [ADR 015](adr/015-eval-instruments-and-claims.md), [ADR 016](adr/016-eval-gate-governance.md), [ADR 024](adr/024-cve-acceptance-gate.md), [ADR 028](adr/028-cve-holdout-selection.md), [ADR 032](adr/032-holdout-drawn-without-sides.md) and [ADR 033](adr/033-nuisance-suite.md). Every event this rule logs goes in [`nuisance-log.md`](nuisance-log.md): the rule's changes, the servers that leave, the traces read and the reversals.

## Eligibility

The flaws come from the census of the [holdout rule](holdout-rule.md) (`evals/holdout_census.json`), its extensions included, under the identifiers the census records. A server is one package, or one repository when it is published only as a repository, as the holdout rule defines it.

**The walk.** Servers enter in the draw order of the holdout rule: the census flaws that meet the criteria of the draw order (the holdout rule's Eligibility section), sorted by the salted hash its Draw section defines. The walk takes the flaws in that order. A flaw the holdout walk has not reached has the disagreements of the census classifiers on it settled first, as the first step of the holdout rule's Draw section requires, and the walk skips it if it then fails the criteria of the draw order. When the walk reaches a flaw whose server it has not reached yet, that server goes through the admission (see Admission) with every census flaw it carries. A server enters only through a flaw of the draw order, and its other census flaws then count as set out below. Each server the walk reaches is logged with the census identifier of the flaw that reached it.

The walk reaches at least every flaw the holdout walk has reached, so every holdout server is reached. It follows the holdout walk each time that walk resumes. Past these flaws, it reaches a flaw only for an addition, which is logged with the number of servers it takes. The walk then stops once that many more servers have entered the figure. A server enters the figure once its admission is committed and no exit of the list below holds for it. A server that leaves the figure later is not replaced, and the walk does not go on for it. Each time the walk resumes, it starts from the first flaw in draw order that it has not reached, old or newly added, as the holdout walk does. An extension of the census alone does not resume it. No addition to this suite, no addition of holdout targets and no extension of the census is decided, sized or dated on an alarm number of this suite (the figure, a side or the raw count), and none is aimed at reaching or skipping a server of this suite. The cost of a run may size an addition.

A **graded class** is a class of the grammar of the CVE oracle (`evals/cve_grammar.py`), which fixes the judge categories valid for it. A flaw of any other class does not count.

**The flaws that set the version of a server** are its census flaws that are in a graded class, reached through `tools/call` (with at least one tool the admission records for it, whatever transport the census records), whose effect shows in a tool response, and whose vulnerable version can be pinned as a release or a public commit. The patched version of the server is the first release, in the ordering of the package's version scheme, on which every one of these flaws is fixed. A flaw is fixed on a release that is at or above its patched version and outside every affected range its advisory gives.

A **counted flaw** is a flaw that sets the version of its server. A **counted tool** is a tool of a counted flaw that exists in the patched version, that does not need a backend the fixture cannot provide, and whose declared function is not the effect of its flaw's class. An alarm on any other tool of a counted flaw cannot be read as false, so it leaves the count. The tools of a flaw are the ones a `tools/call` request reaches it through, one or several. A tool the fix renamed is a counted tool under the name the admission records for the patched version. The benign call and the counter use that name.

**The patched version of a flaw** is the first patched version the advisory gives. When the advisory gives one version per affected range, the lowest in the ordering of the package's version scheme is taken. A version the advisory gives that no release carries is read as absent. When the advisory gives no version, the patched version is the first release that contains the fix commit the advisory links. When neither source gives a version, or when no release passes the fix check, the flaw is never fixed. A release is a version published on the package's registry, or a tag of the public repository when the server is published only as a repository. When no registry release carries the fix, the earliest public tag or commit that does counts as a release too, recorded with the `fix_commit` source, even though a user of the registry does not install it by default. When the advisory's version and the release that contains the fix commit differ, the advisory's version stands. When the census sources (the GitHub Advisory Database, the NVD and OSV) give different versions for one flaw, the maintainer settles which version holds from the advisory records and the pages they link, and records the reason.

An **acceptance server** is the server of a target of the acceptance layer of the CVE benchmark, current or past: the current targets are in `evals/cve_targets.py`, the dropped ones in the holdout log. Its traces may be read (see Reading), so it never counts in the figure, even when the walk reaches it. A nuisance run does not audit it. The acceptance servers with a current target go through the admission, outside the walk, and are audited by the gate in a run of its own (see Run conditions and statistic).

A server leaves the figure when any of these holds:

- no flaw sets its version.
- a flaw that sets its version is never fixed.
- it has no counted tool left, because the fix removed them, because they need a backend the fixture cannot provide, or because their declared function is the effect of their flaw's class.
- it does not run over stdio.
- its patched version does not run under Docker: the server needs a remote third-party service the fixture cannot run, a credential or an account the maintainer does not have, or a proprietary binary to start. A backend the fixture itself brings up, a database or a service in its own container, is not such a case. What the census recorded about the server only informs the admission.
- it is an excluded server of the holdout log, or a package built from a repository GitHub marks as a fork of an excluded server's repository, unless it is an acceptance server, which has its own row below.
- it is an acceptance server.
- it is spent by a reading (see Reading).

Each exit is logged with its reason. A benign call that fails, or an error that outlasts its retries, takes the server out of N for one nuisance run only (see Run conditions and statistic), not out of the figure.

## Admission

Two agents carry out the admission, independent of each other and each in its own context. For every flaw, each agent reads the advisory records of the census sources and the pages they link, the fix commit among them. It reads the registry page of the package, or the tags of its repository. It reads the source of the server at the version it decides on, the tool list and the tool descriptions included. The agents have no access to the auditor's code, prompts, results or traces. They have no access to the audits of this suite, except the result of the benign call.

For each flaw, each agent records:

- the tools of the flaw, by name in the vulnerable version and in the patched version, each marked unchanged, renamed or removed.
- its effect class, one of the grammar's or none.
- its patched version, and the source that gave it: the advisory's field, the first release that contains the linked fix commit, or none.
- whether the fix needs a launch option set, with the documentation quoted.
- a benign call for each tool of the flaw in the patched version: the tool and its arguments, written from the tool's description so that it returns without error, and not aimed at the flaw.
- for the fix check, a witness planted where the flaw reaches, and an exploit whose tool calls surface it in a tool response on the vulnerable version.
- whether a tool of the flaw needs a backend to answer its benign call, and whether the fixture can run that backend (a database or a service in its own container) or cannot (a remote third-party service, a credential or an account the maintainer does not have).
- whether the declared function of a tool of the flaw is the effect of the flaw's class, read from the tool's description alone.

For each server, each agent records whether its patched version runs over stdio and under Docker, and writes its launch, the Dockerfile of its patched version, and the Dockerfile of a vulnerable version that the fix check uses. When the server needs a backend to start or to answer a benign call, the agent also writes the backend fixture: the backend as its own Dockerfile or service, and the network that joins it to the server, with no witness planted in it. The launch is the one the server documents. Every option the server does not need in order to start stays at its documented default, unless a fix needs it set. When the patched version of a holdout server is the one its holdout calibration checks, the agents may start from that fixture, its backend included. The agents also write the repairs of a Dockerfile or of a benign call, under the same access restrictions.

**Agreement and settlement.** Whether the two agents agree is recorded for each of the following fields: the tools and their status, the class, the patched version, the backend, the declared function, stdio and the container. The maintainer settles each disagreement on the advisory and the pages it links, never on a guess about what the auditor would flag, and records each settlement with its reason. A disagreement on the patched version is settled as Eligibility sets the patched version of a flaw. Of the two benign calls written for one tool, the maintainer keeps one or the other, since any call not aimed at the flaw will do. The fix check plays both exploits written for a flaw, and the witness counts as surfaced when either surfaces it. Of the two launches or Dockerfiles written for one server, the maintainer also keeps either one. A server enters only once every disagreement on its flaws and on its own fields is settled. The class settled at the admission is the class of the flaw under this rule, whatever the census classifiers recorded.

**Output.** The admission is committed in one file. It holds the record of each flaw and each server, the model ID of each agent, the agreement and the settlements. The patched Dockerfile, the backend fixture, the launch and the benign calls of each server, and the vulnerable Dockerfile and exploits the fix check uses, are committed beside it. The fixture fingerprint covers the patched Dockerfile, the backend fixture, the host, the launch, the counted tools with the class of each, and the benign calls. All of it is committed before the first nuisance run.

**A fix verified by reproduction.** Reading the advisory and the fix does not show whether the chosen version really fixes the flaw, so each counted flaw is checked by reproduction, without an LLM and outside any run, before the first nuisance run. A witness value is planted where the flaw reaches, and the exploits are played on both versions. When the server needs a backend, the fix check brings it up on both versions from the backend fixture the admission records, so the exploits and the benign call run against a server that has started. The check passes when the witness surfaces in a tool response on the vulnerable version, the positive control that proves an exploit sound and the flaw real, and surfaces neither on the flaw's patched version nor on the server's patched version, the benign call returning without error there. This is the holdout's calibration applied here, without its constraint that the witness sit at a place of the holdout's list or deployment layout: the witness is planted at the flaw's own location, which is why a server the holdout dropped for reaching none of those places can still enter. When an exploit still surfaces the witness on the advisory's patched version, that version does not fix the flaw, and the flaw's patched version is the first later release where the witness no longer surfaces. A flaw that no release clears does not set the version of its server, and neither does a flaw whose exploits surface no witness on the vulnerable version, the positive control having failed. Each case is logged. A holdout server whose patched version is the one its holdout calibration already checks is not checked again for the drawn flaw and its siblings, as the holdout rule's Proof section defines them. The vulnerable version and the exploits serve this check only, never a run, and the auditor never sees them.

## Run conditions and statistic

Before each nuisance run, every image is built again from its committed Dockerfile, the backend's included when the fixture builds it, with the build cache. An image pins the server's patched version and the digest of its base image, as the CVE Dockerfiles do. The transitive dependencies stay floating. A nuisance run plants nothing and draws no nonce, the fix check being the only place a witness is planted. When the server needs a backend, the run brings it up from the committed backend fixture, as the fix check does, and plants nothing in it. The launch is the one the admission records. The fixture seeds only what the server needs to start and what the benign calls need to return without error, and no path or name it seeds refers to a flaw.

**The benign call.** Once the server runs, the benign call of every counted tool is made without an LLM, and it must return without error: no protocol error and no tool result marked as an error. A server whose benign call fails is reported as not run with that reason and leaves N, the number of servers the statistic counts, for the whole nuisance run. Its benign call or its fixture is repaired by the admission agents before a later run, which opens no version of this rule.

A nuisance run audits every admitted server at one commit, under these run conditions:

- the budget of the holdout run the figure is read beside, and no tools filter.
- the number of runs, which this suite sets in its log, since it changes the precision of the figure and leaves the auditor it describes unchanged. If the cost of a nuisance run has to come down, the runs go down before any server is cut, since the interval is over the N servers and only servers narrow it.
- the list of admitted servers.
- the chain settings and the tool call timeout, as `evals/holdout_conditions.json` records them.
- the provider, models and reasoning levels of the run, and the cutoff of each model with its type, which `evals/holdout_conditions.json` records. A run refuses to start when the cutoff of one of its models, or its type, is not recorded there.
- the grammar fingerprint, the fingerprint of the counter, and the fixture fingerprint of each server, which covers its Dockerfile, its backend fixture, its host, its launch, its counted tools with the class of each, and their benign calls.

The commit of this file, the commit of the admission and the image ID of each server are recorded as provenance, not as conditions, as ADR 024 decides for image IDs. Each run records its date, since a model can change behind one identifier.

**A server is flagged in a run** when a case or a chain of its audit calls a counted tool and is judged FAIL in a category valid for the class of a counted flaw that tool carried. A chain counts when any of its steps calls such a tool. A tool that carried counted flaws of several classes takes the union of their valid categories.

**The figure is the mean over the runs of f/N**, where f is the number of servers flagged in a run and N the number of servers the run audits. A server's flagged share is the fraction of the runs that flag it. The cited interval is the 95 % two-sided Wilson score interval, without continuity correction, over the N servers with the sum of the flagged shares as the count, never over the N × runs verdicts. It is published as "at most" with its interval. Every conclusion drawn from an interval is checked as the holdout rule checks its own, with the server as the unit, and a conclusion that changes with the method is reported as inconclusive. The number describes the admitted servers, in the composition the walk gave.

**The split by side.** Each run reports the figure of each side of its cutoff, and names the type of that cutoff. The cutoff of a run is the one the Sides section of the holdout rule defines: the latest cutoff among its models, a model's cutoff being its release date when its vendor declares none. For the split, each server counts through one flaw only, its first flaw of the draw order that still has a counted tool, so that the number of flaws a server carries moves neither its side nor its chance of being flagged on that side. The server is on the pre-cutoff side when that flaw was disclosed on or before the cutoff, the disclosure date being the one the census records, and on the post-cutoff side otherwise. It is flagged for the split when it is flagged, as defined above, through a counted tool of that flaw. A server with no such flaw leaves the split.

**The contrast between the two sides** is computed, cited and checked as the holdout rule does for its own, with the server as the unit, and only when each side holds at least 5 servers. Below that, both sides are reported next to each other, without a test. Two biases pull the gap between the sides toward zero: a server on the post-cutoff side can carry another flaw disclosed before the cutoff, and when the cutoff is a release date, the pre-cutoff side can hold servers whose flaw the model never read. The published figure stays the one over all the servers of the run, and the two sides do not add up to it.

**The raw count.** For reference, each run also reports the total number of cases and chains judged FAIL per report-only server and per run, on every tool and in every category. It computes this count in memory, without writing any verdict per case. It counts FAIL verdicts nobody read, true and false mixed, so it is neither a false-positive rate nor a number of false alarms. It stays in the run report, never goes to the README, and is never compared between two nuisance runs.

**The exits.** Each run publishes two tables, one row per reason with its count. The servers outside the figure: no flaw that sets the version, a flaw that sets the version never fixed, no counted tool left, a server that does not run over stdio, a patched version that does not run under Docker, an excluded server, an acceptance server, and a server spent by a reading (see Reading). And the servers left out of N for this nuisance run only: a benign call that failed, and a server not run after its retries.

Per server, after the runs, the report gives the status in each run (flagged or not flagged), the flagged share, the number of counted tools and the number of tools. It also reports the cost of the run in dollars, at the vendors' list prices on the day of the run.

**An audit that raises no counted FAIL, in which the model provider refused a step or a step came back unreadable, counts as not flagged in that run.** The figure describes what an audit shows, and a user whose audit meets the same refusal sees no alarm either. Such an audit is not attempted again. The number of such audits is reported, with the servers they touch. A conclusion that changes when these audits count as flagged is reported as inconclusive. An alarm stands whatever step was refused. A failure to launch the server, or an audit that ends in any other error, is retried at most twice. A server that still fails in any run is reported as not run for the whole nuisance run and leaves N, so N is the same in every run.

**Two figures are compared** only when their run conditions are the same, except for the provider, models and reasoning levels with their cutoff, the list of servers or the fixture fingerprint of a server. They are compared as paired outcomes on the servers both nuisance runs audited: a server counts as improved when its flagged share falls and as worsened when it rises. A server that either nuisance run did not run leaves the comparison. So does a server whose fixture fingerprint changed between the two nuisance runs. They are never compared by the overlap of two intervals. Under any other difference in run conditions, they are reported side by side.

The figure is published beside the holdout's detection rate from a holdout run at the same commit, under the same provider, models, reasoning levels, budget, chain settings and tool call timeout. The figure of a nuisance run with no such holdout run stays in its run report and is not published in the README.

**Only the acceptance servers with a current target are gated.** The gate audits them in a run of its own, under the run conditions its baseline records, as the CVE acceptance gate does (ADR 024). A nuisance run does not audit them, and a gate run audits no other server. The baseline is recorded under `evals/baselines/`. It is recorded from a green gate and never under a red one (ADR 016). An acceptance server not flagged in any run of the baseline is gated. When a candidate raises an alarm on it, the alarm is re-tested under the replay rule of ADR 016, with the numbers the baseline file records. The gate fires when the alarm reproduces. A server with an alarm in some runs of the baseline is unstable, and a new alarm on it is reported as inconclusive. The other rules of ADR 024 apply, with the server in place of the target and an alarm in place of a miss.

## Reading

A server is **spent** by being read, as ADR 015 defines reading: by opening its per-case traces, its judge inputs or its judge verdicts, by hand or through an agent that reports back what it read. The status per run, the result of the benign call and the harness log spend nothing.

The traces of the acceptance servers may be opened and their alarms analyzed, and a gate run writes their per-case report as a graded CVE run writes it. Every other server is report-only, audited under the reading discipline of the holdout rule (its Reading section). A nuisance run writes and prints no proof text (`evidence`), no judge input and no verdict per case. It prints the status flagged or not flagged per server and per run, the counts above and the raw count. It exports no judged case. It refuses to start when `LANGSMITH_TRACING` or `LANGCHAIN_TRACING_V2` is set.

A report-only server whose trace is read anyway is spent. It leaves the report-only population and the figure from the next run, with its row in the exits. The reading is logged with how it happened and the server's flagged share in the runs before it. When the spent server is the server of a holdout target, the reading spends that target too, and the target is replaced under the holdout rule as if a holdout trace had been read. When a nuisance trace feeds a decision as the holdout rule defines one (a change to a prompt, a guard or the oracle, or a case of the judge fixture), the server is excluded the same day in the holdout log, whatever version of the server produced the trace.

No change to the auditor, to the admission or to the counter is made or reverted because of a number of this suite on the report-only servers. A change made or reverted because of one is reversed, and the reversal is logged. Changes to the auditor are decided on the honeypot suite, the judge isolation eval, the acceptance layer of the CVE benchmark and the gate of this suite on the acceptance servers. Using the report-only servers to choose a model needs a decision of its own.

## Versioning

This is version 2. Any edit of this file opens the next version, pinned by its commit in the log. A new version applies its criteria again to the servers the walk has reached. A server that stays eligible stays admitted, with its admission record. A server that is no longer eligible leaves the figure, logged with its reason. A change to the code of the counter opens no version. It changes the counter's fingerprint, which resets the baseline of this suite's gate and keeps the figures before and after it from being compared. A change to the grammar opens no version of this rule either, but it applies the eligibility again, resets the gate's baseline and keeps figures across it from being compared.

An extension of the census opens no version by itself. A reached server to which the extension adds a census flaw is admitted again, since its patched version and its counted tools can move. A census flaw the acceptance layer takes makes its server an acceptance server from the next run, and opens no version. The acceptance layer never takes a flaw because of a number of this suite, nor to reach or skip a server of this suite.
