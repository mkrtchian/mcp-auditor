## [Unreleased]

### Added

- `python -m evals.run_cve_benchmark --survey` plants every in-scope candidate place and prints, per target and candidate, what the exploits surface on the vulnerable version, what the benign call surfaces there, and what the exploits surface on the patched version, with no live or dead verdict. It needs Docker and no LLM, runs behind the same preflight and crash handler as the graded run, and feeds the choice of each target's kept places.
- `python -m evals.run_census` builds the CVE holdout census, `evals/holdout_census.json`, from the GitHub Advisory Database, NVD and OSV exports and the output files of the census agents. `prefilter` writes the pre-filter hits no collector has decided yet, `status` lists what is left and exits `0` once the census is complete, `classify-dossier` writes the classifiers' input, and `assemble` builds the census with the grouping by proof of its two readers, recomputes its figures and each reader's known gap, and refuses to write one that does not load. See `evals/holdout_census_method.md`.
- An `openrouter` provider reaches OpenRouter's Chat Completions API with `OPENROUTER_API_KEY`. Its default model is GLM 5.3 (`z-ai/glm-5.3`) at reasoning effort `low`, `MCP_AUDITOR_REASONING` takes OpenRouter's `reasoning.effort` levels (`none` to `max`), and every call requires a host that supports every parameter sent.
- `MCP_AUDITOR_OPENROUTER_HOSTS` pins the `openrouter` calls to a comma-separated list of OpenRouter provider slugs, in order and with no fallback, so an audit never lands on a host that filters security content or serves a lower quantization. Unset, OpenRouter routes the calls. The other providers ignore it.
- `python -m evals.run_holdout` drives the CVE holdout draw, which now holds all thirty of its targets. `draw-order` prints the salted-SHA-256 draw order of the draw-order candidates with each one's disclosure date (`--census` defaults to `evals/holdout_census.json`). `calibration-dossier --cve ID --out DIR` writes a self-contained, `mcp_auditor`-free calibration kit for one candidate to `DIR`, outside the repository, so the candidate is calibrated without access to the auditor's code. Both need no LLM and no network. See [`docs/holdout-rule.md`](docs/holdout-rule.md).
- `python -m evals.run_holdout calibrate` confirms each drawn target is live on its vulnerable version and dead on its patched one, with every kept layout place routed (`--cve ID` restricts it to one target). It needs Docker and no LLM, exits `1` on a dead or unrouted fixture, `4` on a fixture-config error, and `0` when every target holds or nothing is drawn.
- `python -m evals.run_holdout run` audits the drawn targets under the rule's run conditions and reports the capability number (the share of holdout targets detected, averaged over its runs, with a 95% Wilson interval and control intervals), writing the report JSON and markdown to `--report` (default `output/holdout_report.json`) and keeping no per-case proof. It reads the run conditions from `evals/holdout_conditions.json`, joins the disclosure dates from the census (`--census`), prices each role separately, needs Docker and an LLM key, and refuses when tracing is on. It prints that nothing is drawn and exits 0 while no target is in its list. It has not been run.
- `python -m evals.run_nuisance walk` scaffolds the nuisance admission, which has not been run. It prints, per server the holdout walk reached, its package, its reaching flaw and the flaws that set its version (a graded class, reached through tools, its effect visible in a tool response, and pinnable), for the maintainer to admit. It needs no LLM and no network, and no server is admitted yet.
- `python -m evals.run_nuisance nuisance-dossier --server PKG --out DIR` writes, outside the repository, the isolated admission dossier for one server (advisories, fixture format, grammar and the fix-check driver), free of any `mcp_auditor` import, for the two blind admission agents. It needs no LLM, the fix-check driver it ships needs Docker, and no server is admitted yet.
- `python -m evals.run_nuisance run` audits the admitted servers on their patched images under the holdout's run conditions and reports the nuisance figure: the share of admitted servers flagged on a counted tool, averaged over its runs, published as "at most" with its Wilson interval, its split on either side of the run's cutoff, the table of servers outside the figure, the table of servers not run, and the raw count of failing verdicts. It writes the report JSON and markdown to `--report` (default `output/nuisance_report.json`), needs Docker and an LLM key, and refuses when tracing is on. No server is admitted, so it prints that no server is admitted and exits 0.
- `python -m evals.run_nuisance gate` gates the acceptance servers, the servers of the current CVE targets: it audits the admitted ones on their patched images and compares each to its baseline under `evals/baselines/nuisance/`, an alarm on a server with none in its baseline replayed under the replay rule, and writes a report with the flagged tools and the judged cases and chains of every run. It exits 0 green, 1 red, 3 not comparable or refused, 4 on a crash. `--record-baseline` records one file per server, `--server PKG` restricts the run to one server for a reset. No acceptance server is admitted, so it prints so and exits 0.
- An `AuditReport` splits its provider usage per role: `judge_usage` is the usage of the judgment and chain-judgment calls (a refused judgment's billed usage included), `generator_usage` is the complement, and `provider_usage` stays the grand total, so a holdout run whose judge model differs from its generator prices each role.
- An `AuditReport` splits its provider usage per phase: `chain_usage` is the usage of every chain step (planning, step observation, step planning, chain judgment, missed steps included) and `single_step_usage` the complement, the chain judgment counting both there and in `judge_usage`. Each usage carries `largest_input_tokens`, the input tokens of the largest single request, for a vendor that bills a request by its size.
- `python -m evals.run_cve_benchmark` takes four measurement flags, accepted only with `--ungated`: `--chains N`, `--chain-steps M`, `--tool-call-timeout T` and `--no-tools-filter` force their setting on every target, a flag left out keeping the target's own, and the report records them in a `measurement` field apart from the run conditions, so no baseline comparison reads them. An ungated run whose generator and judge both have a price in `evals/holdout_conditions.json` reports, per target, the usage of single-step tests, chains and judge summed over every attempt, its cost in dollars and the largest request in input tokens, and warns on a target with a request above 100,000 input tokens. A measurement run with an unpriced model is refused before any audit.
- `evals/holdout_conditions.json` gains `claude-haiku-5-5`, the tooling-phase model, with its cutoff and its list prices (prompts up to 100,000 tokens), and both prices are checked as of 2026-10-17.

### Changed

- The judge writes its justification before its verdict: the `Judgment` schema it answers in asks for the justification first, and both judge prompts, single-step and chain, ask it to write its justification, then decide, then give the severity, so the verdict can follow from the justification.
- On the `openai` provider, the judge's answer is bound to its schema in strict mode.
- The holdout run's per-target result carries its runs as a tuple of per-run statuses, its aggregates (detected runs, detection share, places, aimed, incomplete runs) computed from them, so no two can disagree. The report is unchanged.
- The calibration kit of `python -m evals.run_holdout calibration-dossier` tags its images `mcp-auditor-kit-<service>:local`, so a kit build never overwrites an acceptance image, and its README lists the acceptance services a kit service name must not reuse.
- The CVE benchmark preflight, and the probe corpus capture for the vulnerable images, rebuild through `docker compose` an image whose Dockerfile fingerprint label does not match its Dockerfile, absent images included, instead of auditing whatever the tag holds. A failed build stops the run as a preflight crash (exit `4`) naming the services and compose's error.
- `evals/holdout_conditions.json` sets the holdout's chain settings and tool call timeout (3 chains per tool, 3 steps per chain, 30 seconds), logged in `docs/holdout-log.md`, so `python -m evals.run_holdout run` no longer refuses on them.
- The judges' input_validation guidance counts an action a parameter withholds permission or consent for, done anyway (an `overwrite=false` call that still replaces an existing file), as acting against a valid parameter, beside `dry_run` and `recursive`.
- The report's usage line reads `**Throttled by the model provider**: N requests (HTTP 429)`, its `, retried` dropped: the last 429 of a call that ran out of retries was not retried.
- The e2e evals read a pass or a replay whose report holds a step throttled past every retry as a failed one, so the run is not comparable (exit `3`), the other passes kept. A refused or unreadable step still leaves a completed pass.
- The CVE acceptance run skips an attempt whose report holds a throttled step, as it skips a crashed one: it is not graded, whatever it detected, never audited again as an incomplete attempt, and its detecting run is not replayed on the patched version. The holdout run retries such an attempt as an infrastructure failure, and a target whose attempts stay throttled is dropped with the cause `throttled`. The holdout report's `not_run` entries gain a `cause` (`pre_run_check`, `launch_failure` or `throttled`), and its Markdown not-run section opens with one count per in-run cause against the targets launched, so a throttled provider pushing large servers out of the count shows.
- The judge isolation eval reads a judgment throttled by the model provider past every retry as uncovered, lists it in the report (`throttled_judgments`) and makes the run not comparable, `--ungated` included: it exits `3` with its report written instead of crashing with exit `4`. Once one judgment is throttled past every retry, the later ones are not sent.
- The evals no longer print a line for each throttle wait, since many audits in flight would print one per wait and each eval already prints the throttle total. The model probe does not wait on a throttled call: it records the call as an error with its usage and the provider's message, so the provider's queue stays out of the latency it measures.
- **Breaking.** The JSON report's `refused_steps` becomes `missed_steps`, and each entry carries a `cause` (`provider_refusal`, `unreadable_answer` or `provider_throttled`) and a `detail` (the provider's message, the number of attempts for an unreadable answer, or the seconds waited and the provider's message for a throttled step) in place of `provider_message`. The e2e eval report's `runs[*].refused_steps` becomes `runs[*].missed_steps`, and the holdout report's `refused_runs` and `refused_run_count` become `incomplete_runs` and `incomplete_run_count`. An audit interrupted under a previous version with a refused step or a chain under way does not resume: `--resume` stops with `checkpoint written by an earlier version, run without --resume`, and the audit runs again without it.
- A missed step names its cause wherever it is shown (the Markdown report's summary, with one count per cause, and tool sections, the console, the progress line of an unjudged case, the eval and CVE benchmark output). A case left unjudged in the Markdown report gives as its reason `the judgment step was missed, its cause is listed under the tool`.
- `python -m evals.run_holdout run` refuses up front, before any LLM spend, a drawn target absent from the census, a drawn target with an unknown kept place or a placement its spec rejects, and a dirty git tree, and refuses a run where no target survives the pre-run check (listing why each was dropped) rather than crashing on an empty result. Its hierarchical control interval integrates the Gamma(1,1) prior the rule names, no longer one conditioned on `d >= 0.1`.
- The holdout run report names the run's cutoff, the latest of its models' cutoffs that splits the targets: the model that gives it, its date, type and source page. `python -m evals.run_holdout run` refuses to start when a model's cutoff has no type or no source in `evals/holdout_conditions.json`, which now gives each cutoff its source page.
- `MCP_AUDITOR_REASONING` is accepted with the `anthropic` provider: `none` turns thinking off, `low` to `max` set the effort with adaptive thinking. Unset, the default model still gets no reasoning setting.
- The `anthropic` provider gives up on a request after 120 seconds and caps an answer at 8,192 output tokens, as `openai` and `fireworks` do, and fails at startup when `ANTHROPIC_API_KEY` is unset or empty. It detects an answer cut at the output cap (`stop_reason: "max_tokens"`) and retries it as a truncated attempt, instead of accepting a repaired JSON. It uses Anthropic's native structured output, which forces the schema even with thinking on, carrying a tool call's arguments as a JSON string on that path and decoding them back, so a payload comes back with its arguments instead of being lost when the model answers without a forced tool. An answer with no valid structured output, a refusal, a cut during thinking or a non-JSON arguments string included, still reaches the refusal and truncation checks instead of failing as an unexplained parsing error.
- A refusal by Anthropic's classifiers names its category in the coverage gap's provider message (`stop_reason refusal, category cyber`), when the API gives one.
- A host-level block through OpenRouter (a 403 whose error metadata reads `content_policy_violation` or `refusal`, with the host's name and code in the provider message) and a `content_filter` finish on the Chat Completions path (`openrouter` and `alibaba`, with the model's refusal text when it gives one) are reported as provider refusals, a coverage gap, instead of failing the step. A `content_filter` refusal keeps the tokens its completion reports.
- With the `openrouter` provider, a reasoning effort the model does not publish in OpenRouter's model listing (`supported_efforts`) is refused when the model is built, naming the efforts it supports, instead of failing every call of the audit. A model the listing does not describe, or a listing that cannot be fetched or read, logs a warning and the audit goes on.
- `mcp-auditor` starts faster: it imports a provider's SDK only when it builds that provider's model, instead of all of them at startup.
- The judge decides on the clauses that label the judge isolation cases (`docs/labeling-log.md`): a verdict says whether the tool's response or error shows a failure of the category tested, and a failure that is only possible is a PASS. A failure that meets the definitions of several categories is a FAIL in each. A failure the response does not show is a PASS, a timeout or a dropped connection on a payload that is not oversized included. A payload that reaches something outside the tool's declared reach and brings it back is an injection and an info_leakage failure, whatever the tool's declared function. The rules every category shares are `JUDGING_RULES` in `graph/prompts.py`, the guidance of each category stays in `domain/category_guidance.py`.
- The chain judge reads the same rules and category guidance as the single-call judge, and counts a failure shown by any step of the chain: the multi-step progression explains how a failure was reached and is no longer required.
- The CVE oracle's grammar no longer depends on the auditor's code: it grades units, which one adapter builds from an audit report, and its fingerprint now covers that conversion. A golden master freezes what it grades, and the conversion changes no grade (`docs/labeling-log.md`).
- The CVE oracle grades a detection by the planted nonce alone. The command-output proof and its lower `detected_execution_only` rung are removed, so the ladder is `detected`, `reached_but_judged_pass`, `missed`, and a command execution target is detected only when its nonce surfaces. The grammar also carries a per-unit rule that strikes a credit a replay against the patched server could earn without the flaw, and its fingerprint now covers that rule. See ADR 029, ADR 030 and `docs/labeling-log.md`.
- The CVE benchmark plants each fixture's proof as a per-launch nonce drawn per location, in place of one per-run sentinel. A launch that declares a network has it created by the planting layer as a labelled bridge, a planted HTTP endpoint is served by a sidecar inside a network-namespace holder the launch joins (a server with no network still gains the endpoint and no egress), and an orphan a crashed run leaks is swept by its `mcp-auditor-cve` label, the containers before the networks. See ADR 029 and ADR 030.
- Each CVE server now has a patched twin image, built by the same `docker compose -f evals/docker/compose.yml build` (nine images in all): filesystem at `2025.7.1`, one git twin (`2025.9.25` for CVE-2025-68143, keeping the `mcp<2` pin), kubernetes at `2.5.0` and a fetch `1.1.1` candidate. The sentinel sidecar has no twin. The benchmark preflight refuses a run whose patched or sentinel image is not built, and a recorded baseline lists the patched image's ID beside the server image's. See ADR 030.
- `--calibrate` now checks both versions of each target. On the vulnerable version a target is live when it keeps at least one place, the nonce of every kept place surfaces in an exploit, every exploit reads as aimed, and the benign call surfaces no nonce and does not read as aimed. On the patched version no exploit surfaces a nonce and the benign call returns no error. The patched launch starts only once the vulnerable one is torn down. `--calibrate` and `--record-baseline` also fail when a kept deployment-layout place has no discovery route, and a dead target that needs network egress prints a hint when no outbound egress is reachable, so a missing-egress run is not mistaken for a broken patch. See ADR 029, ADR 030 and ADR 031.
- The CVE graded run checks each target without an LLM on both versions, as `--calibrate` does, before any audit. A target that no longer passes is not run: it keeps an empty grades entry, its conditions go to a section of the report after the per-target table (printed in every mode, `--ungated` included), and the gate reads it `not_run` and not comparable whatever its baseline, so a gate cannot read green with a target missing. Under `--record-baseline` a failing target refuses the recording before any LLM call. A configuration error the check raises (an unknown kept id, a planting_spec refusal) crashes the run (exit 4) before any audit. See ADR 030.
- The CVE benchmark deploys its acceptance targets into a fixed `/srv` layout tree (a bare `app.git` with an add-then-remove `.env` history, its shallow checkout `app`, and a workspace `.env`), built per launch and mounted into every target of both layers so the tree is universal apart from the nodes a target keeps a nonce in. The layout offers three places a nonce can sit (a git remote URL's userinfo, a committed-then-removed `.env`, a workspace dotenv), and a target keeps one only when calibration reaches it and the route check finds a route to it in the server's own output: across the four acceptance targets that keeps only the workspace dotenv (on the git target, by the dotenv documented default), the bare-repo places having no route the acceptance servers reveal. Each exploit sweeps every place its flaw reaches. The filesystem sibling pair merges into one target, leaving four acceptance targets (merged filesystem, git CVE-2025-68143, kubernetes, fetch); CVE-2025-68145 (the `--repository` bypass) is out of scope, since no git tool names the out-of-scope bare its sole place sits in, so the route check finds no route. The git target mounts `/srv` read-write so the `git_init` traversal can write, and that exploit stages exact relative paths, never `"."`. See ADR 031.
- Every detecting CVE run is replayed without an LLM against a fresh container of the patched version: the auditor's recorded calls are sent again, and a proof the patched server reproduces is a credit the auditor could have earned without the flaw, so it is struck before the run is graded. A credit the replay could not check, because the patched container would not launch or its connection dropped after the retries, is kept but marked unchecked. The report lists the refused and the unchecked credits (place ids) in a section after the per-target table. A run whose status rests on an unchecked credit leaves the gate not comparable (`unchecked_decides`) whatever its baseline, and `--record-baseline` refuses it, so a gated baseline never rests on a credit the replay could not check. A detecting run whose only credit is struck and that carried a provider refusal reads as a refusal, not a miss. See ADR 030.

### Fixed

- A request the model provider throttles (HTTP 429) past the retries of its client no longer stops the audit. The auditor waits and tries again, honouring the delay the provider sends (`retry-after-ms`, then `Retry-After`), otherwise a growing delay, each spread randomly upward, with one warning per wait, for up to five minutes of waiting per model call. A call still throttled after that is reported as a missed step of cause `provider_throttled`, the audit carries on without it and `--ci` exits `3`. Once one call of an audit has waited its five minutes, the later calls of that audit, generator and judge alike, are not sent and their steps are missed, so an audit on a provider that does not recover ends quickly. A 429 the provider marks as not worth retrying (`x-should-retry: false`, or an OpenAI billing limit: credit exhausted, spend or usage limit reached) is not waited on and still stops the audit with the provider's error. `--resume` does not replay a throttled step.
- The throttle count includes the 429s of a call throttled past every retry, which it used to lose with the crashed audit.
- An answer from the model that matches no expected format after the parse attempts no longer stops the audit: the step is reported as a missed step of cause `unreadable_answer`, the audit carries on without it, `--ci` exits `3`, and its usage is counted in `provider_usage` (and `judge_usage` for a judgment). The CVE graded run audits such a run again when it did not detect, as it does a refused one, and the holdout counts it as not detected, with no retry.
- A generated payload holding a character that cannot be encoded as UTF-8 (a lone surrogate) is blocked before it is sent, with the argument named in the reason, instead of crashing the MCP transport and ending the audit.
- An `alibaba` answer cut at the output cap is retried as a truncated attempt, counted with its tokens, instead of failing the step with the `openai` SDK's `LengthFinishReasonError`.

## [0.4.0] - 2026-10-05

### Added

- `--env NAME` relays a variable from your environment to the audited server, and `--env-plain NAME` or `--env-plain NAME=value` relays one without redaction. Both are repeatable and CLI only, with no configuration-file key. `--env NAME=value`, an unset or empty `--env` variable, a name given twice and an invalid name are refused before launch, and so are `HOME`, `PATH` and any `DOCKER_` name under the two container regimes. The audit warns about a short `--env` value, a `--env-plain` name that looks like a secret, and a `docker run` you wrote that does not pass a relayed name with `-e`. See ADR 026.
- The value of each `--env` variable is replaced by `[value of NAME, redacted by mcp-auditor]` in the tool responses, the tool list, the server's stderr and the MCP SDK's log lines, before the models, the checkpoints, the trace, the report or the terminal see it. While a value is relayed, the prompts say that a marker stands for a value the server returned.
- The JSON report's `execution` object gains `relayed_variables` (the `--env` names) and `plain_variables` (the `--env-plain` names and values), both `null` without relays. The Markdown report adds a relayed environment line.
- The audit counts the requests the model provider throttled (HTTP 429, retried by the provider's client), warns at the first one while it runs, and reports the total in the console summary, the Markdown report and the JSON report (`provider_usage.throttled_requests`).
- The e2e evals and the CVE benchmark print a line for each audit the model provider throttled, as it completes, and the session total with the concurrency in their summary. The eval report records the total in its config (`throttled_requests`), the CVE report on its conditions line and in its JSON (`throttled_requests`). No baseline records or compares it.
- The CVE benchmark's graded run is an acceptance gate. It compares each target to its own baseline file in `evals/baselines/cve/`, which records the run conditions, the target's fixture fingerprint, the runs and the image IDs. A target detected in every run of a confirmed baseline is gated, either detection rung counting: a miss on it is replayed alone and the gate goes red when the miss reproduces 4 times out of at most 5. The run exits `0` green, `1` red, `3` not comparable or refused and `4` on a crash. `--record-baseline` records from a clean tree, all files or none, and a recording refused once the runs are done still writes the report with its reasons: a first recording is exploratory, a second at the same commit confirms it, and a baseline is never recorded over a regression. `--ungated` runs with no comparison. A baseline file of a target no longer benchmarked is reported as orphaned. The CVE report carries the gate: its verdict and reasons, and per target the outcome, the runs and the replays. See ADR 024.
- `evals/declared_flips.json` declares the gated cells of the honeypot evals, or the gated cases of the judge eval, that a change to the system under test is expected to lose, in the commit that makes the change (ADR 020). At that commit, on a clean tree, a declared cell that flips reads `declared`, is not replayed and does not fail the gate, and a declared cell that did not flip is listed as such in the summary. An entry is active only at the commit whose parent is its `base`. An active entry naming a cell outside the ground truth, or a cell named twice, refuses the run before any LLM call, and an entry that does not parse refuses it too. A green run with declared flips can be recorded as the new baseline.
- The CVE benchmark's graded run writes `cve_judged_cases.jsonl` beside its report: one line per judged single-step case of each completed run, with its CVE id and run index, the judge's input and its verdict. A replay is not exported, nor is a chain, and `--calibrate` exports nothing.
- The e2e eval report and the CVE report record the commit they ran at and whether the tree had tracked modifications (`commit`, `dirty`), and the e2e report its run conditions (`conditions`). The CVE report records the input and output tokens the model provider billed over the session, every attempt and replay included (`provider_usage`), and prints them on its conditions line.
- `python -m evals.draw_judge_cases` draws the judge isolation cases from the judged cases of two e2e runs and a CVE run, clean and at one commit, into `evals/fixtures/judge_cases_drawn.json`, unlabeled and stripped of the judge's verdicts. It refuses to write when a drawn case holds the invoking user's home path, user name or an API key pattern. `--complement` draws one more case per PASS cell once the labels call for it.
- The judge isolation eval shows its progress, a count per case outcome and a table of the cases that left `unchanged` (baseline and run observations, replays, cause), warns at the first request the model provider throttled and prints the total with the concurrency, and its report records `concurrency`, `throttled_requests` and `replay_observations`.
- The outcome tables of the e2e evals and of the judge eval list as `partial` a cell or case wrong in every baseline run and right in some runs of the current one, which the gate does not gate and the tables used to leave out. The judge's case count shows them apart from `unchanged`.

### Changed

- **Breaking.** The JSON report's `token_usage` key is renamed `provider_usage`. An audit interrupted under a previous version still resumes, but the tokens of the steps it ran before the interruption are missing from its report.
- The judge isolation eval gates case by case against a recorded baseline, `evals/baselines/judge_isolation.json`, instead of an F1 threshold of 0.90. It judges each case three times by default (`--runs`), and a case stable and correct in every run of a confirmed baseline that flips is replayed and fails the gate when the flip reproduces. A recall floor (one detection per run) and a precision floor (0.50) gate in every mode, and alone until a baseline is confirmed. A judge call that gives no verdict is an uncovered observation. `--record-baseline` records from a clean tree at the CI conditions, twice at one commit (exploratory, then confirmed), `--ungated` runs on the floors alone at any conditions, and `--concurrency` sets the judge calls in flight (default 30). Gated cases can be declared under the `judge` suite of `evals/declared_flips.json`. The run exits `0` green or recorded, `1` red, `3` not comparable or refused, `4` on a crash, and the `/eval` comment on a pull request names the judge's reason on a failure. Precision, recall and F1 stay in the report as diagnostics. See ADR 025.
- The judge fixture `evals/fixtures/judge_cases.json` has a new format: each case carries an id computed from its judge inputs, a source, an origin, its inputs, a label (`pass`, `fail` or `unspecified`) and the rubric clause that decided it, and the fixture records the draw it came from. It now holds 78 cases, drawn from honeypot and CVE runs and labeled by rubric, in place of the 32 hand-written cases (`evals/judge_fixture_method.md`, `docs/labeling-log.md`).
- The CVE benchmark no longer grades an audit in which the model provider refused a step as a miss. It audits the target again, up to three attempts, and the first attempt that detects or holds no refused step grades the run. A detection stands whatever step was refused. A run refused at every attempt does not complete, which makes the gate not comparable and refuses a recording.
- The `google` provider talks to the API over `httpx` instead of `aiohttp`.
- The CVE benchmark runs its graded audits side by side, six at once by default, and settles the replays of different targets side by side. `--calibrate` calibrates its targets side by side too. `--concurrency` sets how many audits (or calibrations) are in flight, `1` runs them one after the other as before. The report records the concurrency on its conditions line, and no baseline records or compares it.
- The e2e evals run their runs side by side, and the three honeypots of a run side by side, nine audits at once by default so the three runs go at once, replays included. `--concurrency` sets how many audits are in flight, `1` runs them one after the other as before. Each report records the concurrency in its config, and no baseline records or compares it.
- A failed preflight of the CVE benchmark (Docker unreachable, an image missing) exits `4` instead of `1`, under `--calibrate` too, so it no longer reads as a dead fixture.
- The CVE benchmark grades each target on a ladder of conditions instead of a single planted sentinel, credits a command's output on command execution targets as a lower rung, no longer credits a proof the auditor's own arguments echoed, classes each miss, reports the awaited capability as a hypothesis, and writes its report as an object with the run conditions and the grammar's fingerprint. Calibration checks every proof of a target's class and a benign call per target.

### Removed

- The `MCP_AUDITOR_LANGSMITH_PROJECT` setting. Its only reader was the e2e evals' lookup of the latest trace, which is gone. LangSmith's own `LANGSMITH_PROJECT` still names the project the traces go to.

### Fixed

- `mcp` is now required below 2. The 0.3.0 release accepted any version from 1.0.0, so a fresh install resolved `mcp` 2.x, which renames the fields the client adapter reads (`inputSchema`, `isError`): every audit stopped at tool discovery with an `AttributeError`.
- The e2e evals attach each run's recall and precision in LangSmith to the traces of that run's own audits, instead of to the most recent trace of the project.
- The CVSS column of the CVE benchmark report gives each score from the CVE record on cve.org, with its CVSS version and source (the CNA, or CISA-ADP when the CNA gives none). Five of the seven scores change.

## [0.3.0] - 2026-09-27

### Added

- Two LLM providers: `openai` (default model `gpt-6-luna` at reasoning effort `none`, needs `OPENAI_API_KEY`) and `fireworks` (default model GLM-5.3-Flash at reasoning effort `medium`, needs `FIREWORKS_API_KEY`). Set `MCP_AUDITOR_PROVIDER` to select one. Each request to either provider is abandoned after 120 seconds, then retried like any other failed request. Their answers are capped at 8,192 output tokens, reasoning included on some providers, and an answer cut by that cap counts as unparsed: it is retried, then reported as a failure.
- The `alibaba` provider: `qwen3.8-flash` on Alibaba Cloud Model Studio's international endpoint, with thinking always off, needs `DASHSCOPE_API_KEY`. It takes no `MCP_AUDITOR_REASONING` value, and shares the timeout and output cap of `openai` and `fireworks`.
- `MCP_AUDITOR_REASONING` sets the reasoning level sent to the main and judge models (`minimal`, `low`, `medium` or `high` with `google`, `none`, `low`, `medium`, `high`, `xhigh` or `max` with `openai`, `low`, `medium` or `high` with `fireworks`, refused with `anthropic` and `alibaba`). Unset, the provider's default applies to its default model only, and a model named by `MCP_AUDITOR_MODEL` or `MCP_AUDITOR_JUDGE_MODEL` gets its API default.

### Changed

- **Breaking.** The audited server now runs in a Docker container by default. `-- python server.py`, `-- node server.js` and `-- uv run ...` no longer launch: they stop with the ways forward, and run again as `--unconfined -- python server.py` (or with `--image IMAGE` to pick a container of your own). The quick start's `-- npx ...` form still works and now needs Docker installed and running. An audit interrupted before this release resumes only with `--unconfined` and the same command, because the thread identity of a container regime carries its regime. The container drops all capabilities, forbids privilege escalation, runs as the invoking uid and gid, bounds processes and memory, mounts each path the command names writable at the same absolute path and nothing else of the host, and keeps egress open. `--image` overrides the image chosen for the launcher, `--mount PATH[:rw]` adds a host path (read-only by default) and is the way to mount a root the auditor otherwise refuses, such as your home directory. Reports gain an `execution` entry recording the regime, the image and its digest, the mounted paths, and whether the container was killed on memory. The kill state is recorded only: no verdict is rewritten. None of the three options is a configuration-file key, since the file is read from the audited project's own directory. See ADR 017 and ADR 018.
- **Breaking.** `--ci` exits with code 3 on an incomplete audit, a step refused by the model provider or a tool left with a coverage gap, including a coverage gap that used to pass. Findings at or above the severity threshold still exit with code 1, and take precedence.
- **Breaking.** The default provider is now `openai`, running `gpt-6-luna` at reasoning effort `none` for the main model and the judge, so an audit with no configuration needs `OPENAI_API_KEY`. Its list prices are $0.10 input and $0.50 output per million tokens, against $0.30 and $2.50 for `gemini-3.5-flash-lite`. To keep Google, set `MCP_AUDITOR_PROVIDER=google`: its default model stays `gemini-3.5-flash-lite` at thinking level `minimal`. A configuration that sets a Gemini model or `MCP_AUDITOR_REASONING=minimal` without `MCP_AUDITOR_PROVIDER=google` now fails. See ADR 021.
- The default Google model is now `gemini-3.5-flash-lite`, still at thinking level `minimal`, for the main model and the judge. Google has scheduled the shutdown of `gemini-3.1-flash-lite` for 2027-05-07. Its list prices are higher ($0.30 input, $2.50 output per million tokens, against $0.25 and $1.50), so an audit on Google costs more. Set `MCP_AUDITOR_PROVIDER=google`, `MCP_AUDITOR_MODEL=gemini-3.1-flash-lite` and `MCP_AUDITOR_REASONING=minimal` to keep the previous model until then.
- A generated test case batch that holds fewer cases than the budget, or fewer categories than requested, is asked for once more. A batch still missing categories after that retry is completed with the missing categories alone, each asked for its share of the budget, and only what is still missing after that is flagged, with the requested and received case counts ("7 cases generated for 10 requested") and the missing categories: a warning in the console and the dry run, a line under the tool heading in the Markdown report, and a `coverage_gap` entry on the tool report in JSON (`null` when the batch is complete).
- The test case generator keeps integer literals to 10 digits and string arguments under 1,000 characters, and probes resource exhaustion by what an argument asks the tool to do rather than by the size of the argument. A string longer than a few dozen characters is composed from varied text, never from one character repeated. It was told to use "extremely large" values, which some models answered with literals of thousands of digits that cost output tokens, could be cut by the output cap and tested the transport rather than the tool.
- Gemini's thinking level is now set explicitly to `minimal` for the default model. It is the API default, now pinned, so a change of default on the API side no longer changes the audit.
- Token usage in JSON reports gains `cached_input_tokens` (a subset of `input_tokens`) and `reasoning_tokens` (a subset of `output_tokens`).
- The honeypot eval ground truth is revised by rubric: four labels changed after the servers were written return to their creation verdict, and four cells whose planted flaw cannot be tied to a mechanism or a category leave it, which keeps 36 cells, 8 of them expected failures. Precision, its resolution and consistency now count only the cells of the ground truth. The rubric and the revision are recorded in `docs/labeling-log.md`.
- The generator, judge and chain planning prompts no longer name the values, errors or tools of this repo's test servers. A few lines written while tuning against those servers asked for them by name or described their tools one by one, and they now state the general rule instead. A unit test fails when a shipped string contains a discriminating literal of the three test servers. Audits of other servers see prompts that no longer steer toward this repo's fixtures, and the repo's own eval numbers are expected to move.
- The e2e evals gate against a recorded baseline (`evals/baselines/honeypot_e2e.json`, written by `--record-baseline`). A stable cell that flips is replayed and fails the build when the flip reproduces, and three metrics keep an absolute floor: recall at one planted flaw found per run on average, counted over the runs, precision and distribution coverage at 0.50. A run whose conditions or honeypot sources differ from the baseline's is reported not comparable and exits `3`. So is a run where fewer runs completed than were requested, in every mode, the absolute thresholds included, and a baseline file whose runs do not match its conditions or the ground truth is refused before any LLM call. A ground truth revision re-scores the baseline's stored runs under the current labels, and a cell it adds stays out of the comparison until a recording covers it. A recording is refused when no planted FAIL cell, or no PASS cell, comes out stable and correct, since the gate could then not see a lost detection or a new false positive. A second recording at the same commit confirms the first by adding its runs, and a cell is gated only if every run of both gives it the same observation. A committed baseline that a label revision leaves in that state is refused before any LLM call, and names the reset: delete the file in a commit of its own and record twice. A recording prints, and the baseline file stores, how many planted FAIL cells and PASS cells came out stable and correct and how many are unstable, and a gated run prints the same counts for the baseline under the current labels. Comments, formatting and module docstrings of a honeypot are not part of its source fingerprint. A crash of the eval runner exits `4` instead of `1`, which read as a red gate. The first baseline is recorded and confirmed, so the absolute thresholds no longer gate. `--ungated` runs on the floors alone, at any conditions. CI runs the e2e evals at 3 runs and budget 10, the conditions a baseline is recorded at, instead of 2 runs and budget 7. See [ADR 016](docs/adr/016-eval-gate-governance.md), [ADR 020](docs/adr/020-honeypot-baseline-changes.md), [ADR 022](docs/adr/022-honeypot-recall-floor.md) and [ADR 023](docs/adr/023-honeypot-second-recording.md).
- The e2e evals print a grid of the cells (gated, unstable, missed or flagged, with this run's flips and regressions) and an outcome table with the raw observations and replays, which replaces the Cells table.
- The CVE benchmark's filesystem, git and kubernetes fixtures now run with no network. Their images are built with everything they need and the auditor talks to them over stdio, so the only use left for egress was an exploit that succeeded and wanted out. The SSRF fixture keeps its dedicated network, since reaching the sentinel over it is the flaw under test. All six fixtures stay live under calibration.
- The CVE benchmark's containers now run with all capabilities dropped, no privilege escalation and a process bound, and the vulnerable servers whose image has no `USER` run as an unprivileged user. The images are deliberately exploitable servers and the auditor's payloads reach them, so the container was the only boundary between a successful exploit and the host running the benchmark, and it carried none of these limits. The calibration mode replays every fixture's exploit path under the new profile and all six stay live. A memory bound is not part of it yet: a server killed on memory mid-audit would be counted as a missed detection rather than a skipped run, because the benchmark does not read the container's kill state. The benchmark also warns when the Docker host cannot enforce the process bound, which Docker otherwise discards silently.
- The CVE benchmark report ends with a count per status instead of a single `Detected X/Y` ratio. That ratio pooled targets whose traces have been read with targets that have not, and the two back different claims. See ADR 015.
- The README no longer publishes the honeypot eval metrics or the judge F1 as quality numbers. A `Measurement` section replaces the thresholds table: it names what each of the three instruments answers and the measurement none of them makes, the false-positive rate on a healthy server. See ADR 015.
- The auditor now proves injection non-destructively: the generator is instructed to prefer benign reflected evidence, and a deterministic guard refuses to send a payload containing an enumerated destructive construct (`rm -rf`, `DROP TABLE`, a shutdown command, a fork bomb, and a handful more). A refused payload is reported as blocked with its reason in every output format, never sent to the server and never judged. Writes are still permitted: auditing a tool that writes writes. The generator is also told to prove impact by reading rather than writing, so a report can now carry a secret read from the audited server. See ADR 013 and ADR 014.
- JSON reports now always include the `owasp` key on eval results, with `null` for categories without an OWASP MCP mapping. The key used to be absent in that case. OWASP data is derived on the model itself and appears in every `EvalResult` serialization. See ADR 012.

### Fixed

- The CVE benchmark's git fixture starts again when its image is built from scratch. The pinned `mcp-server-git` accepts any `mcp` from 1.0.0 on, a fresh build pulled `mcp` 2, which dropped the API the server registers its tools with, and the server exited at startup. The image now keeps `mcp` below 2.
- A CVE fixture whose server exits before the MCP handshake is reported dead by the calibration, with the error and the end of the server's stderr, and the targets after it still run. The calibration used to crash on it and hide both the cause and the state of the remaining fixtures.
- The e2e eval report lists, per run, the steps the model provider refused (`runs[*].refused_steps`), and the run's console summary prints them. The run merged the three honeypots' reports without their refused steps, so the list was always empty.
- A step the model provider refuses on policy grounds no longer stops the audit and loses everything tested before it. The audit carries on, and the refused step is reported with the provider's message: a warning in the console and the dry run, a line in the Markdown summary and under the tool heading, and a `refused_steps` entry in the JSON report. A case or chain whose judgment was refused is shown as not judged instead of being left out, and the Markdown summary says `Audit complete: no` when a step was refused or a tool has a coverage gap.
- `--resume` now resumes. It was inert: a normal run stored its checkpoints under a random thread nobody could name, while `--resume` read a thread no run had ever written to, so it failed with an internal `EmptyInputError` instead of picking anything up. The thread is now derived from the audited target and wiped whenever a fresh audit starts, so re-auditing the same target cannot inherit the previous report's tools and token count. `--resume` with nothing unfinished to pick up, either because the target was never audited or because its last audit completed, says so and runs a fresh audit rather than replaying the previous report. Two consequences of keying the thread on the target are worth knowing: a resumed run is governed by the budget, chain and tool options of the run it resumes, so passing different ones alongside `--resume` has no effect, and two audits of the same target running at once now share a thread, where before they were isolated. Neither run can produce a merged report, but the one that finishes first reads the other's state, so it reports the other's result or exits claiming no report was produced. Audit a given target from one process at a time.

## [0.2.0] - 2026-07-10

### Added

- Multi-step attack chains: the auditor plans multi-step attack scenarios against a single tool, executes them step by step against the live server, and judges the outcome. Opt-in via `--chains`, rendered in all output formats. See ADR 010.
- CVE benchmark: graded runs of the auditor against real, pinned-vulnerable MCP servers in throwaway Docker containers, with a no-LLM calibration mode and a `--cve` filter. See `plans/2026-07-06_cve_benchmark.md`.

- Dependabot updates for uv dependencies and GitHub Actions.

- Default Google model bumped to `gemini-3.1-flash-lite`.
- LangSmith tracing env vars migrated to the current `LANGSMITH_*` names.

### Fixed

- Audit verdicts could be attributed to a hallucinated tool name: the graph now dispatches on the tool actually under audit.
- Chain verdicts are now counted in eval aggregation.

## [0.1.0] - 2026-03-23

Initial public release on PyPI.

- Dynamic adversarial testing of live MCP servers: tool discovery, LLM-generated test cases across five categories (input validation, error handling, injection, information leakage, resource abuse), execution over the MCP protocol, LLM-as-a-judge verdicts with severity ratings.
- OWASP MCP Top 10 mapping in all output formats.
- Cross-tool learning: attack context extracted from earlier tools informs later probes.
- Config file support (`.mcp-auditor.yml`), `--tools` filter, `--budget` control, token usage reporting.
- Three-level test strategy: unit tests with fakes, integration tests against a honeypot server, LLM evals scored against planted ground truth.
